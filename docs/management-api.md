# Management API

The checked-in [OpenAPI 3.1 management skeleton](openapi/management.openapi.json) is drift-checked against the compiled route inventory. **Request/response schemas are incomplete**: this is not yet a complete client-generation or body-validation contract. It includes anonymous management routes and the authorized installation-policy tombstones, but excludes inference, SCIM, health and metrics. See [contract maintenance](openapi/management/README.md) for fragments, validation and explicit regeneration.

All paths below are under `/api/v1`. Two credential families authenticate management requests — a browser session (`omg_session` cookie) or an admin API token (`Authorization: Bearer omg_admin_…`, #37) — never both, with no fallback in either direction: a duplicate `Authorization` header, or any request carrying both an `Authorization` header and an `omg_session` cookie (even a malformed one), is refused before either credential is examined. Browser-session mutations require exact configured Origin and `X-CSRF-Token`; a successfully authenticated admin token is exempt from CSRF (its Bearer secret is never attached automatically the way a cookie is), but an unauthenticated or invalid token gets no such exemption. Inference keys never authorize management, in either credential family. UUIDs identify resources; timestamps are UTC. Free-text list filters (`q`, the file list `search`) never accept control characters (`400`); routes that trim treat whitespace-only input as no filter. Handler errors use `{error:{code,message,reason?}}`, where `code` is the HTTP status as a string and the optional `reason` is a stable machine code for selected cases (`personal_workspace_name_fixed`, `personal_limits_platform_controlled`, `stacked_budgets_require_budgets_field`, `key_revoked`, `key_disabled`, `workspace_wide_visibility_required`, the [settings](#installation-settings) reasons (`key_lifetime_exceeds_maximum`, `setting_locked_by_environment`, `credential_reference_not_allowed`, `plaintext_requires_loopback`, `email_not_configured`, `email_test_rate_limited`, `file_storage_not_configured`, `file_storage_unhealthy`, `storage_test_rate_limited`, `logo_unsupported_type`, `logo_too_large`, `logo_invalid_image`, `logo_dimensions`), and the policy reasons listed in [governance API](governance-api.md#policy-rejection-reasons), which add a `period` or `limit` field). `route_unsupported_capability` and `price_meters_incomplete` (which adds `missing_meters`) use the same envelope: the HTTP status in `code` and the machine code in `reason`. Framework extraction errors may differ.

Every route's declared access level is in `apps/gateway/src/route_policy.rs`, enforced before body extraction by the management preflight and checked by both the exact middleware matrix and real-handler matrix; handlers retain their own authorization checks and were not reordered.

Refusals callers may notice: on every `/workspaces/{ws}` route (including mutations), another owner's personal workspace is indistinguishable from an unknown workspace: the same `404` and `{error:{code:"404",message:"Resource not found"}}` body, without a distinguishing reason, even for Platform Admins/Auditors. Platform staff's visibility into personal usage/cost totals remains in platform reporting; it does not grant foreign-personal workspace access. The role-first platform-write refusal below is unchanged: non-admins receive the same `403` for both foreign-personal and unknown workspaces. Personal owners' access and Team/Project authorization are unchanged. **An admin token (#37) gets the identical byte-for-byte answer, for the same reason, not a separate fix (#282/#320 follow-up, #337):** every `TokenPolicy::Scope` workspace route reaches this exact same authorization check, keyed on the token's owner, so the foreign-personal and unknown answers were already indistinguishable; every `TokenPolicy::Denied` workspace route (`/keys`, `/requests` and the rest of the workspace-member/key/admin surface) is refused before `ws` is even read from the path, so that `403` cannot depend on whether the id is a real foreign workspace or a random one either. `apps/gateway/src/management/authz_admin_token_tests.rs`'s `admin_token_principals_hide_foreign_personal_like_unknown` proves this across every scope that reaches a workspace route. A foreign human-key rotation is hidden as `404` in every state (revoked/expired keys stay `404`; workspace admins no longer receive another human key's `key_disabled` reason). A non-member auditor's key-policy request is `403` before key lookup, for existing and missing keys alike (previously `404`). Service-account key operations require a workspace admin; plain members receive `403`. Workspace-scoped platform writes refuse non-admins with `403` before looking up the workspace, even for a missing workspace. Malformed workspace/key identifiers consumed by the preflight are `404`. The removed `/platform/installation/policy` endpoint requires Platform Read for GET and Platform Write for PUT; authorized callers still receive `410`.

Most lists return `{data:[...]}`, default `limit=100`, range 1–200, `offset=0..100000`. Financial lists additionally expose `has_more`; see [governance API](governance-api.md). No list returns credential values/references or plaintext tokens. Organization routes have been removed, not retained as compatibility aliases.

<a id="your-sessions"></a>**Your sessions (#79).** For the caller's own dashboard sessions:

- `GET /me/sessions` returns `{data:[{id,client,created_at,last_seen_at,expires_at,current}]}`: live sessions only (not signed out, not expired), the current one first. `id` is a public handle, never the token; `client` is a browser/OS family or `null`.
- `DELETE /me/sessions/{id}` signs one out (`{revoked:1}`), including the current one. Another user's, an unknown or an ended session is `404`.
- `POST /me/sessions/revoke-others` signs out every other live session (`{revoked:n}`); `400` when the request's own session is unknown.
- `POST /platform/users/{user}/sessions/revoke` (Platform Admin) signs out all of a person's sessions (`{revoked:n}`); `404` for an unknown or cleaned user. `GET /platform/users/{user}` includes `active_sessions` (a count).

## Admin API tokens (#37)

Long-lived, high-risk management credentials for scripts and out-of-band tooling, distinct from both inference keys and browser sessions. Format `omg_admin_<32-hex uuid>.<64-hex secret>`; the whole token's SHA-256 is stored, never the plaintext or anything recoverable from it.

- **CRUD is browser-only** (`TokenPolicy::BrowserAdminOnly`): a token can never create, list or revoke another token, regardless of any scope it holds. `GET/POST /platform/admin-tokens`, `DELETE /platform/admin-tokens/{token}`; Admin only (Auditor is refused). `POST` returns `{id,token,scopes,created_at,expires_at}` **once**, with an explicit `Cache-Control: no-store` on that response (not only the management router's global default), and is always for the caller themselves — the body cannot name another user as owner. `expires_in_days` is 1–90 (no renewal, no enabling, no ownership transfer). `GET` lists every token installation-wide, metadata only (never a digest or the plaintext). `DELETE` is idempotent and any currently effective Admin may revoke any token, not only its owner.
- **Scopes**: `platform:read`, `catalog:write`, `access:write`, `governance:write`, `settings:write`. No wildcard, no duplicates, 1–5 scopes per token. A write scope does not imply the matching read scope. Every management route carries an explicit, individually assigned `TokenPolicy` in `apps/gateway/src/route_policy.rs`: `Denied` (workspace-member/key/admin, inference and SCIM routes — a token can never reach these, whatever scope it holds), `BrowserAdminOnly` (token CRUD itself, and other browser-only routes) or `Scope(…)` (one of the five above). An undeclared route denies by default; there is no prefix matching or class-wide inheritance. The handler-readiness inventory is checked against the scope declarations. `HEAD` follows its declared `GET` policy unless it has an explicit declaration. Scope checks never replace workspace membership, object visibility or personal-workspace privacy checks.
- **IP allowlist**: optional, immutable once created, 1–32 canonical IPv4/IPv6 CIDRs (no `0.0.0.0/0`/`::/0`, no duplicates, no IPv4-mapped IPv6 network). Omitted means unrestricted. Enforced per request against the resolved client address — the socket peer, or `GATEWAY_TRUSTED_PROXIES`' right-to-left `X-Forwarded-For` traversal when the peer is a trusted proxy, the same resolution sign-in throttling uses. Untrusted peers cannot select their address with forwarding headers. A malformed forwarding chain falls back to the socket peer; only configure proxies you control and avoid allowlisting their addresses as if they were clients. A restricted token with no resolved address fails closed.
- **No cookie, no positive cache.** A token's authority is only its own (owner id, scopes, optional allowlist) — it is never treated as a browser session, and every authorization check re-reads the primary database (unrevoked, unexpired, owner active and currently effective role exactly `admin`); there is no positive authorization cache. A successful request records last-use time/address at most once per 5 minutes.
- **Transactions and revocation.** Protected write transactions recheck the token and its owner's live authority under ordered locks. An explicit revocation or owner demotion either follows an already-authorized mutation's commit, or makes that mutation fail. Reconciliation carries the token identity into its separate accounting transaction and each deadlock retry. Previously authorized snapshot reads may finish.
- **Admission bounds.** Each replica uses token buckets with capacity 1,000 per client address and 1,000 per authenticated token, refilling at 1,000 per minute, plus an aggregate capacity of 10,000 refilling at 10,000 per minute. The aggregate gate runs before credential lookup; the token gate runs after authentication but before audit or dispatch. Address/token maps are capped and use shared overflow buckets. Excess requests return `429`; unauthenticated and over-limit attempts are counted in fixed-label metrics, not individually written to the audit tables.
- **Audit.** Every admitted token attempt gets an immutable start row before dispatch and a completion row before the response returns, including refusals, validation failures and handler errors. `admin_token_attempts` records token/owner IDs, the server request ID, method/template, required scope, admission outcome and completion status — never raw URLs, bodies, names, credentials or hashes. A failed start prevents dispatch. Business-action audit is transactional with the mutation and carries `admin_token_id`, including for reconciliation and SIEM export (`omg.audit.v1`; see [operations](operations.md#audit-export)); personal events remain excluded. A failed completion returns `503`. If the handler was dispatched, the action may already have committed: inspect the resource before retrying. A request refused before dispatch was not processed. Exporting the separate attempt table to the SIEM is not implemented.

## Session inventory and directories

`GET /me` returns:

```json
{
  "installation": {"id": "<uuid>", "name": "Enterprise", "support_url": null, "logo_url": null, "logo": {"url": "/api/v1/branding/logo?v=3f2a9c1b7d4e", "updated_at": "2026-10-09T12:00:00Z"}, "key_max_lifetime_days": 365},
  "user": {"id": "<uuid>", "email": "user@example.org", "platform_role": "user"},
  "workspaces": [],
  "capabilities": {"platform_read": false, "platform_write": false, "create_workspace": false}
}
```

`installation.logo` is the uploaded installation logo (`{url, updated_at}`, a same-origin URL that changes with every upload), or null when none is set or the file store is off. `logo_url` is deprecated: still returned and accepted, never shown by the UI.

Workspace entries include `id,name,kind,owner_user_id,role,membership_source,capabilities`. The list is the caller's personal workspace (first) plus shared workspaces where they hold an effective membership; platform roles never add entries, and `role` is the real membership role. Kind is `personal|team|project`. Sources are `manual|group|mixed|null`. Capabilities are `issue_own_key`, `manage_members`, `manage_service_accounts`, `manage_policy`, `delegate_models`, `view_all_activity`, `rename` and `manage_keys` (disable/revoke other people's keys). For personal workspaces `manage_policy` and `rename` are false (the name is always "Personal" and workspace limits are platform-set; per-key caps remain). Capabilities are presentation snapshots, not durable authorization.

**Workspace authority comes only from membership.** Workspace-scoped routes (`/workspaces/{ws}/…`) give a Platform Admin or Auditor who is not a member read-only metadata access to shared workspaces (`GET /workspaces/{ws}`, `GET …/policy` without usage, `GET …/members`, `GET …/models`, `GET …/catalog`, `GET …/access`) and nothing else: no keys, request rows, workspace-wide usage or mutations. Platform staff manage Teams/Projects through `/platform/workspaces/{ws}/…` routes. Personal workspaces stay owner-only on these routes; Admin/Auditor see a personal workspace's identity, totals and platform-managed configuration only through the platform reports and `/platform/workspaces/{ws}/policy` and `/catalogs`.

### Home (own scope)

- `GET /me/summary`: the caller's own human-key activity for the current and previous UTC calendar month, in total and per workspace (`known_cost_microusd`, `held_microusd`, `requests`, `attempts`, `unresolved_attempts`, `input_tokens`, `output_tokens`, `tokens`, `unknown_token_attempts`, all decimal strings; token sums are observed values and a lower bound when `unknown_token_attempts` is nonzero), plus `active_keys` per workspace. `budgets` lists workspace-wide budget windows (see [governance API](governance-api.md#policy-payloads)) only where the caller is owner/admin (personal: owner); otherwise null. Another member's activity never contributes to these numbers. `?totals_only=true` returns only `totals` (`workspaces` is empty); Home uses it, because the per-workspace breakdown grows with membership count.
- `GET /me/models?limit=6`: the models added in the caller's own workspaces (their personal workspace and shared memberships), aggregated in one request for Home. `models` (at most `limit`, 1–50) lists models with a serving route, most widely available first: `model_id`, `public_name`, `display_name`, `workspace_count` and at most two `workspaces` (`id`, `name`, Personal first). `usable_count` counts them all. `not_serving` (at most 20) and `not_serving_count` cover added models without an enabled route. `workspaces_without_models` lists the ids of the caller's workspaces with no model added.
- `GET /me/keys?status=active|disabled|revoked|expired|all&limit&offset`: the caller's own human keys across their workspaces with `workspace{id,name,kind}`, `status`, `created_at`, `expires_at`, `revoked_at`, `disabled_at`, `last_used_at`, `model_ids` and `usage` (below); `{data,has_more}`. Never secrets.

## Self-service membership requests (#83, slice A)

These routes are **browser-session only** (`TokenPolicy::Denied`), including platform reads. Every POST/PUT requires the configured Origin and `X-CSRF-Token`. Model-selection requests and in-app notifications are not implemented in this slice. The dashboard covers the membership workflow: see [dashboard](dashboard.md#access-requests-83-slice-a).

| Method/path | Authority and behavior |
| --- | --- |
| `GET /access-request-targets` | Active entitled user; `{data:[{id,name,kind}]}` for active, opted-in Teams/Projects where the caller has no live grant. No personal workspaces, hidden targets or membership lists. |
| `PUT /platform/workspaces/{ws}/discoverable` | Platform Admin; `{discoverable:true|false}`. Defaults off; personal workspaces are refused. Returns `{ok:true}`. |
| `POST /me/access-requests` | `{workspace_id,idempotency_key,reason?}`. Requests only the fixed `member` role; no entitlement, owner/admin role or policy changes. |
| `GET /me/access-requests` | Only the caller's history. |
| `GET /me/access-requests/{id}` | Only the caller's request; unknown/foreign request is `404`. |
| `POST /me/access-requests/{id}/withdraw` | Requester only; repeated withdrawal returns the recorded outcome. No JSON body required. |
| `GET /workspaces/{ws}/access-requests` | Live owner/admin membership; platform status alone is insufficient. |
| `POST /workspaces/{ws}/access-requests/{id}/approve` | Live owner/admin membership, never the requester. |
| `POST /workspaces/{ws}/access-requests/{id}/deny` | Same authority and separation rule. |
| `GET /platform/access-requests` | Platform Admin/Auditor; shared-request history. |
| `POST /platform/access-requests/{id}/approve` | Platform Admin, including a non-member, never the requester. |
| `POST /platform/access-requests/{id}/deny` | Same authority and separation rule. |

Lists use the standard bounded `limit`/`offset`. Creation, detail and decisions return a request object: `id,requester,target_kind,workspace_id,workspace_name_at_request,requested_role,status,reason,created_at,expires_at,decided_by,decided_at,membership_grant_id`, plus `requester_display_name`/`requester_email` on the two approver-scoped queues only (`GET /workspaces/{ws}/access-requests` and `GET /platform/access-requests`; absent elsewhere). References remain the submitted IDs; history never adds newly visible **live** workspace names or membership data. Decision routes need no JSON body. Unknown, hidden and personal submission targets all return the same `404`.

`workspace_name_at_request` is the target's name captured once, server-side, at submission (a column populated by the INSERT-time trigger in `0066_access_requests.sql`, never by the runtime role, and never updated afterward). It is present on every read, including the requester's own `mine`/detail history, so "My requests" can show a name instead of a raw workspace ID without disclosing a later rename or the workspace becoming non-discoverable: it is a frozen reference, not the live name.

`requester_display_name`/`requester_email` are shown **only** to the two approver-scoped queues, never to the requester's own `mine`/detail reads and never to another workspace's approvers. This discloses nothing new: a workspace owner/admin already sees the same pair for any entitled user through the Members "Add member" picker (`GET /workspaces/{ws}/member-candidates`), and a Platform Admin/Auditor already sees it through `GET /platform/users`; both are scoped the same way (live owner/admin membership, or platform read) as the matching access-request queue. A user without display name set simply has `requester_display_name:null`.

That picker excludes a disabled, cleaned or currently unentitled user, so both fields are server-redacted to `null` the moment the requester stops being picker-eligible, even for a request submitted earlier while they were eligible — a queue never discloses more about a requester's *current* state than the matching picker would. `requester_display_name`/`requester_email` both `null` on an otherwise normal row means exactly this; the dashboard then shows a fixed "Retained identity" label instead of looking anything else up.

`idempotency_key` is a requester-scoped, 1–128-byte visible ASCII string. The server stores its SHA-256, not the key. Reusing it with the same workspace/reason returns the current recorded request without another submission; a different payload is `409`. There can be only one pending request per requester/target (`409` for another key). `reason` is optional plain text, at most 1,000 characters, without control characters; render it as text, never HTML. Unknown JSON fields are rejected.

PostgreSQL enforces at most **20 unexpired pending requests**, **five submissions in a rolling minute**, and **50 in a rolling 24 hours** per requester across replicas. Excess returns `429`, `reason:"access_request_rate_limited"`, `retry_after_seconds` and `Retry-After` (pending-cap retry: 60 seconds; withdrawal/expiry may free capacity sooner).

Pending requests expire seven days after database-owned creation time. Reads/decisions check expiry synchronously; the fenced lifecycle worker also expires at most 100 requests per minute. States move only `pending → approved|denied|withdrawn|expired`; terminal requests never reopen. Expiry does not revoke an approved membership.

Approval and application are one transaction: under ordered type → workspace → user locks, recheck the approver's live authority, requester entitlement/activity, active shared workspace, discoverability and absence of **any** existing membership grant. Any membership grant or revocation after submission permanently makes that pending request stale, even if membership was subsequently removed. A trigger-owned database wall clock records these changes, independently of when the changing transaction began. Stale requests conflict without changing pending state or replacing a stronger/group role; withdraw and submit a new request to seek a fresh decision. A successful application creates a manual `member` grant with immutable request linkage. Repeated approval returns that recorded outcome without granting again, even after later revocation. Revocation either precedes and blocks approval, or follows its authorized commit. Self-approval is always refused, including for Platform Admins.

The transactional `access_request.created|approved|denied|withdrawn|expired|applied` audit events contain request/workspace IDs and typed outcomes, never reason text. Reasons and `workspace_name_at_request` appear in subject exports; reasons are scrubbed at account cleanup unless a user/workspace legal hold preserves them (`workspace_name_at_request` is not personal data about the requester and is never scrubbed). After a hold ends, the fenced lifecycle pass also clears up to 100 retained reasons per tick for already-cleaned users, rechecking both hold scopes; runtime still cannot arbitrarily update reasons. See [identity](identity.md#self-service-membership-requests).

Migration **0066_access_requests.sql** and the updated runtime grants must be applied explicitly to the selected enterprise database. This branch reserves 0066 behind migrations 0059–0065; do not deploy it until the ordered migration prefix is complete. Serving never migrates or resets a database.

## Infrastructure and catalogs

- `GET/POST /platform/providers`, `GET/PATCH/DELETE /platform/providers/{id}`. Create `{name,provider,credential_ref,endpoint?,region?,enabled,aws_external_id?,aws_session_name?}`; patch `{enabled,credential_ref?,aws_external_id?,aws_session_name?,endpoint?}`. GET returns redacted `auth_mode:"none"|"credential"`, never the reference, plus `model_count` (distinct models with any deployment on the connection) and, for Bedrock, `aws_auth:"default"|"profile"|"role"` (otherwise null). Bedrock `credential_ref` is `aws:default`, `aws:profile:<name>` (name on `GATEWAY_AWS_PROFILE_ALLOWLIST`) or `aws:role:<role-arn>`; `aws_external_id`/`aws_session_name` are accepted only with `aws:role:` and are stored inside the hidden reference, so a patch restates the role to change them. Bedrock `region` is a region code; `endpoint` is null (regional endpoint) or an exact HTTPS origin on `GATEWAY_BEDROCK_ENDPOINT_ALLOWLIST`. Patch `endpoint` is Bedrock-only (omitted keeps it, `null` clears it). See [Bedrock](bedrock.md#connection-configuration). Cloud vendor bases are fixed (`openai`, `anthropic`, and `openrouter` at `https://openrouter.ai/api/v1`, env key reference only); local profiles require exact server approval. The `openrouter` adapter serves Chat, embeddings, images, speech to text, text to speech, rerank and System One (see [provider adapters](provider-adapters.md#openrouter)); its public catalog drafts prices (see [governance API](governance-api.md#openrouter-price-suggestion)). Deletes are soft disablement, not history deletion.
- `GET/POST /platform/models`, `GET/PATCH/DELETE /platform/models/{id}`. Create `{public_name,display_name,description?,supported_protocols?,enabled}`; omitted protocols default to `["chat_completions"]`. Allowed protocols: `chat_completions,responses,messages,embeddings,images,audio_transcriptions,audio_speech,rerank,systemone`. A model's protocols must belong to one workload: Chat/Responses/Messages may combine; `embeddings` and each multimodal kind stand alone (database `valid_model_protocols` enforces the same rule; mixed generation+embeddings models must be split before migration `0002`). Every kind is served: `images` at `/v1/images/generations`, `audio_transcriptions` at `/v1/audio/transcriptions`, `audio_speech` at `/v1/audio/speech`, `rerank` at `/v1/rerank` and `systemone` at `/v1/systemone` (see [protocol matrix](protocol-matrix.md)). The public alias is global. PATCH accepts optional `public_name,display_name,description,enabled,supported_protocols` (`description:null` clears it); DELETE disables.
- `GET/POST /platform/deployments`, `GET/PATCH/DELETE /platform/deployments/{id}`. Create `{model_id,provider_connection_id,upstream_model,enabled}`; PATCH `{enabled}`; DELETE disables. On a Bedrock connection `upstream_model` must be a model ID, an inference profile ID (for example `us.anthropic.…`) or a Bedrock ARN in the connection's region; anything else is `400`.
- **Routes must be servable.** A route's connection profile must serve at least one of its model's protocols, by the same capability table the inference path uses for `unsupported_capability` ([protocol matrix](protocol-matrix.md)); a text model's other protocols may be served by other routes. Creating such a route (here or through model setup), enabling one with PATCH, and a model PATCH that changes `supported_protocols` away from what an enabled route serves return `400` with `error.reason:"route_unsupported_capability"` (`error.code` is `"400"`) and a message naming the profile, the workload and protocols, and what the profile serves (for example `The vllm connection profile can't serve System One (systemone); it serves chat_completions, embeddings, rerank.`). Disabling is always allowed. Routes created before this check are not migrated: readiness reports them (below) and workspace catalogs count only servable routes.

**Deployment configuration preview (#85).**

`POST /platform/deployments/{id}/configuration/preview` accepts exactly `{"enabled":true|false}`. Browser-session **Platform Admin only**; Auditor/User are refused, and all admin tokens are denied regardless of scope. Like other browser POSTs it requires the configured Origin and CSRF token. Unknown JSON fields return `422`, a missing deployment `404`, and enabling an unsupported connection/model protocol combination `400 route_unsupported_capability` (in `error.reason`), matching PATCH. Disabling an unsupported legacy route remains allowed.

The response contains:

- `target:{kind:"deployment",id}`, `expected_revision` (opaque string), and `diff:[{field:"enabled",before,after}]` (empty for unchanged state).
- `serving_routes_gained` / `serving_routes_lost` (deployment IDs) and `models_losing_last_serving_route:[{id,public_name}]`. Serving here requires an enabled model, deployment and connection, with a compatible connection profile. Other serving routes prevent a last-route warning; unrelated models are unaffected.
- `affected_workspaces:{data:[{id,name,kind}],total,limit:100,truncated}`: active Teams/Projects with a current model selection whose route choices change. Current catalog eligibility, inherited defaults, replacement catalogs and independent direct assignments apply before counts and the first 100 rows (ordered by name/ID). Multiple catalogs do not duplicate a workspace; catalog availability without selection is not counted. **Personal effects are omitted**, including from counts; no personal IDs, owners, keys or requests are read into the response.
- `observed_at`, `dependency_versions` (`catalog` and `access` configuration topic versions as decimal strings) and `warnings`.

This is a configuration estimate, not a reservation or an admission simulation. It reads one REPEATABLE READ, READ ONLY snapshot on the **primary**, without management advisory/row locks, provider calls, audit, notifications or configuration/cache writes. Normal credential/session bookkeeping is separate. Prices, passive health, circuit state, quotas and key-specific restrictions are not simulated; admitted work may finish.

**Deployment revision (#86):** `expected_revision` is now the deployment's monotonic enablement revision as a decimal string, replacing the earlier `catalog:<version>` observation. Existing deployments start at `0`, new deployments at `1`; each actual enablement transition increments it, including change-away/change-back. No-ops do not increment it or emit a change audit. Model/connection/catalog changes remain represented by `dependency_versions`, not this counter. PATCH/DELETE **do not enforce revision preconditions** yet; refresh the preview before confirmation. Rollback/preconditioned apply (#87) and bulk (#88) remain deferred.

**Deployment configuration history (#86).** Browser-session Platform Admin/Auditor only; User, inference keys and all admin tokens are refused. GET does not require CSRF. Current role authorization is checked in a read-only primary snapshot on every page/detail request.

- `GET /platform/deployments/{id}/configuration/history?limit=25&cursor=...` returns `{data,next_cursor}`. `limit` is 1–100; cursor is the last returned timestamp-in-microseconds/UUID pair. Descending `(created_at,id)` ordering supports stable keyset pagination; invalid limit/cursor returns `400`.
- `GET /platform/deployments/{id}/configuration/history/{change}` returns one matching entry, or `404` (including a change belonging to another target).
- Each entry contains immutable `id` (also the audit event ID), `created_at` (the audit timestamp), `target:{kind:"deployment",id}`, `action`, `actor:{id,label,admin_token_id}`, `schema_version`, decimal-string `revision`, `values_available`, and allowlisted `before`/`after` enabled objects. Creation has `before:null`. Snapshot schema 1 contains no secrets or other configuration fields. Actor display labels are sanitized; immutable IDs distinguish renamed people and targets.
- Legacy creation/enablement audit events remain readable with `values_available:false`, `before:null`, `after:null`, and no revision/schema. The UI says **Values unavailable**; it never consults current configuration to invent past values. Personal-workspace events are excluded before pagination. Targets need not have a live row or name to retain their identity.

Migration **0067_configuration_history** adds the append-only table and deployment revision. Database triggers capture every deployment INSERT and actual `enabled` change (including setup, PATCH, DELETE-as-disable and non-management SQL) with exactly one audit-linked snapshot in the writer's transaction. Management writes retain current user/admin-token attribution; bootstrap/demo/unattributed SQL use System. Failure to record either audit or snapshot rolls back the state change. No snapshots are backfilled. History has SELECT/INSERT-only runtime ACLs plus UPDATE/DELETE/TRUNCATE guards. The audit link uses `(id,created_at)` with insert-time validation rather than a foreign key that would prevent partition archival: retained snapshots still show values and immutable IDs after audit archival, but their actor label becomes unavailable. Apply migration and runtime grants explicitly on an approved database; serving never migrates.

These collections support literal case-insensitive `q` (max 200 characters, surrounding whitespace trimmed, no control characters: `400`) and `enabled`; deployments also accept `model_id,provider_connection_id`, and models accept `provider_connection_id` (models with any deployment on that connection). Direct GET returns one object.

`GET /platform/models` also accepts `not_in_catalog=<catalog uuid>` and `not_direct_in=<workspace uuid>`, which leave out models already in that catalog or directly assigned to that workspace (for "Add models" and "Assign models" pickers), and `type=generation|embeddings|images|audio_transcriptions|audio_speech|rerank|systemone` (the model's workload), `max_input_price` (integer micro-USD per million input tokens; models without a known base rate are excluded), `data_policy=allow|deny|unknown` (any enabled route with that policy, see below), `include_deprecated=true|false` (default true; no separate deprecation state exists, so `false` hides disabled models) and `sort=name|price|newest`. Rows add `workload`, `created_at` and `min_input_microusd_per_million` (cheapest untiered input rate across enabled routes' latest prices, exact decimal string, or null). The response adds `counts` per workload, computed with every filter except `type`. `q` matches the API or display name. This list and `GET /workspaces/{ws}/catalog` choose a page's rows before building them, so a deep page costs about as much as the first (#68).

`GET /platform/deployments/{id}` adds `provider`, `connection_enabled`, `region`, `residency`, `protocols`, `workload`, `price` (latest version with `display_lines`/`display_summary`, or null), `features` (configuration-derived only: `cache_pricing`, `prompt_size_tiers`, `openrouter_free_variant`) and `data_policy:{data_collection,basis}`. For OpenRouter connections `data_collection` is the current effective policy (`allow|deny`, `basis:"current_configuration"`: the `GATEWAY_OPENROUTER_DATA_COLLECTION` override, else the [Data & privacy setting](settings.md#data--privacy)); every other connection reports `unknown` (`basis:"not_configured"`). It is current configuration, not a per-request snapshot.

`GET /workspaces/{ws}/catalog` (members, and platform readers for shared workspaces) lists enabled models eligible for the workspace or assigned to it: `model_id,public_name,display_name,description,protocols,workload,eligibility:"selected"|"direct"|"available_from_catalog",reason,min_input_microusd_per_million,min_output_microusd_per_million,routes` (enabled routes whose connection can serve the model)`,priced_routes` (those with a price; `0` means the model is unpriced, whatever its workload)`,created_at`. Supports `q`, `type`, `limit`, `offset` and `sort=name|newest|price` (default `name`; `price` orders by the cheapest untiered input rate, unknown last). Model list and detail objects (`GET /platform/models`, `GET /platform/models/{id}`) include `created_at`.

Model list/detail objects include aggregate `readiness`:

```json
{"routes":2,"enabled_routes":1,"priced_enabled_routes":1,"serving_routes":1,"unsupported_routes":0,
 "unsupported_profiles":[],"type_tokens_per_minute":100000,
 "routes_over_token_limit":0,"openrouter_free_routes":0,"catalogs":1,"direct_workspaces":0,
 "connections":[{"id":"uuid","name":"Local"}]}
```

`routes` counts deployments; `enabled_routes` counts enabled deployments whose connection is also enabled; `priced_enabled_routes` counts those with at least one price version. `serving_routes` counts enabled routes whose connection profile serves one of the model's protocols; `unsupported_routes` counts the enabled ones that cannot (accepted before route validation), and `unsupported_profiles` lists their profiles. An enabled model whose enabled routes are all unsupported reads *Not serving: <profile> connection can't serve <workload>*; one with some unsupported routes needs attention. `catalogs` counts catalogs containing the model; `direct_workspaces` counts active workspaces with a direct assignment. `connections` lists distinct connections of the model's deployments by name (max 20; id/name only). The UI derives *Ready* as `enabled && serving_routes>0 && (catalogs>0 || direct_workspaces>0)` (`enabled_routes` from older gateways); this is display guidance, not proof of upstream health.

Two best-effort **configuration checks** turn a ready model into *Needs attention*:

- `type_tokens_per_minute` is the smallest tokens-per-minute limit among the workspace-type defaults whose default catalogs offer the model (every type when none does; null when none is set). `routes_over_token_limit` counts enabled routes whose latest price's `input_token_limit + output_token_limit` exceeds it. Each attempt reserves the input ceiling plus its output reservation against tokens-per-minute limits, so such a route can be refused with `token_reservation_exceeds_limit` in those workspaces. Platform overrides, local and key limits are not considered.
- `openrouter_free_routes` counts enabled routes on OpenRouter connections whose upstream model ends in `:free`. When `GET /platform/server-policy` (Admin/Auditor) reports `{"openrouter":{"data_collection":"deny","free_models_available":false}}`, those routes cannot be served: free endpoints may train on prompts, so OpenRouter rejects them under the server's deny policy. The endpoint returns configuration values only, never credentials.

`POST /platform/model-setup` (Platform Admin) creates a model, its first deployment, an optional price and catalog memberships in one transaction:

```json
{"model":{"public_name":"...","display_name":"...","description":null,"supported_protocols":["chat_completions"],"enabled":false},
 "route":{"provider_connection_id":"uuid","upstream_model":"...","enabled":false},
 "price":null,
 "catalog_ids":[]}
```

`model` is the model create body; `route` is the deployment create body without `model_id`; `price` is `null` or the [price publish body](governance-api.md); `catalog_ids` follows the model-catalog rules below. Validation, lock order, status codes (`400` invalid, including `route_unsupported_capability` and `price_meters_incomplete`; `409` duplicate alias or unknown connection) and audit events (`model.created`, `deployment.created`, `price.created`, `catalog.models_replaced` per catalog) match the individual endpoints. Returns `201 {model_id,deployment_id,price_id}` (`price_id` null when unpriced). Any failure creates nothing.

`GET /platform/overview` (Admin/Auditor) returns aggregate counts only:

```json
{"setup":{"connections":0,"enabled_connections":0,"models":0,"ready_models":0,"enabled_routes":0,"priced_enabled_routes":0,
           "catalogs":0,"type_defaults":{"personal":0,"team":0,"project":0},"entitled_users":0,"oidc_mappings":0},

The response no longer has `installation_budgets` (removed with installation-wide limits in 0026; watch total spend with an [installation spend alert](alerts.md)). `entitled_users` counts active users with a platform role; `oidc_mappings` counts enabled group mappings; `type_defaults` counts default catalogs per kind; teams/projects are active shared workspaces. `attempts_7d` counts every upstream attempt started in the trailing seven days and `known_cost_7d_microusd` sums their settled configured-rate cost, both as decimal strings; unresolved attempts add nothing, so this is a known floor, not an invoice. Record existence/configuration does not prove upstream readiness. Prices/routing are in [governance API](governance-api.md).

## Membership, invitations and credentials

- `GET/POST /workspaces/{ws}/members`, `DELETE /workspaces/{ws}/members/{user}`: POST `{user_id,role:"owner"|"admin"|"member"}` sets the manual grant; DELETE removes only manual source. Target requires active entitlement. Owner changes require being an actual owner and cannot strand the last owner. Group grants remain independent.
- `GET /workspaces/{ws}/member-candidates?q=` (shared owner/admin; `400` for personal): member picker. `q` is 1–200 characters matched case-insensitively anywhere in the email (prefix matches first). Returns at most 20 `{user_id,email}` for active, entitled users with no non-revoked grant in the workspace; no other personal data. Add the chosen person with the POST above. `GET /platform/workspaces/{ws}/member-candidates?q=` is the same search for Platform Admins/Auditors on an active Team or Project (`404` otherwise).
- Member lists (`GET /workspaces/{ws}/members`, `GET /platform/workspaces/{ws}/members`) take an optional `q` (at most 200 characters) matched case-insensitively against email and display name, with `limit`/`offset`; the dashboard pages and searches them on the server.
- `GET/POST /platform/workspaces/{ws}/members`, `DELETE /platform/workspaces/{ws}/members/{user}`: the same rows and manual-grant rules for Admin › Teams/Projects (read: Admin/Auditor; write: Admin, including owner changes, with the last-owner guard). Shared workspaces only (personal: `404`).
- `GET/POST /workspaces/{ws}/invitations`, `DELETE /workspaces/{ws}/invitations/{id}`: POST `{email,role:"admin"|"member"}` returns `{id,token,email_delivery}` once; 72-hour expiry. Shared only. With [email delivery](settings.md#email) configured the code is also emailed after commit (`email_delivery:"sent"|"failed"`); otherwise `"not_configured"` and it is delivered out of band. The code is never put in a URL.
- `POST /invitations/accept` `{token}` returns `{workspace_id}`. Requires the entitled session's verified matching email and current inviter authority. It does not grant platform entitlement or reactivate a suspended account.
- `GET /workspaces/{ws}/key-issuance`: how much of the rolling 24-hour [key issuance budget](governance.md#key-issuance) the caller has used: `{window_seconds:86400, holder:{used, limit, next_available_at}}`, and `workspace:{…}` (everyone's use) for workspace admins only. `next_available_at` is null while there is room. Non-members `403`, unknown or disabled workspaces `404`. Admin API tokens are refused.
- `GET/POST /workspaces/{ws}/keys`: POST `{name,expires_in_days:1..365,service_account_id?,model_ids?,requests_per_minute?,tokens_per_minute?,concurrent_requests?,concurrent_jobs?,budgets?}` returns `{id,token,model_ids,policy}` once. A human key's `expires_in_days` (also on rotate) may not exceed the installation's `key_max_lifetime_days` ([settings](settings.md#general)), else `400 reason:"key_lifetime_exceeds_maximum"`. Omitted/null restrictions inherit current workspace grants; `[]` denies all; selected UUIDs narrow, never grant access. The optional rate caps and `budgets` (`[{period,amount_microusd}]`, at most one per period) set the new key lineage's policy in the same transaction as the key, validated exactly like the key policy PUT (tighten-only under the workspace's platform and local layers, same `error.reason` codes); any rejection creates nothing. Without them no key-layer policy is stored and `policy` is null.
- Key list and key rows add `issued_to_name` (the holder's display name, else email) for those who can see the key. `GET /workspaces/{ws}/keys` takes an optional `q` (at most 200 characters) matched case-insensitively against key names, within the caller's usual visibility.
- `GET /workspaces/{ws}/keys/{key}`: one key row (the same object as a list row, including `usage`), with the list's visibility: members their own human keys (others `404`), shared administrators and the personal owner any key in the workspace, non-members and non-member platform staff `403`. Never returns the token.
- `POST /workspaces/{ws}/keys/{key}/rotate` `{expires_in_days}` returns `{id,token}`; old credential is revoked, governance/model lineage retained. Rotate only own human keys or administered service keys, never another human's key.
- `DELETE /workspaces/{ws}/keys/{key}` revokes permanently. Members list/revoke their own keys; shared admins can revoke others. Human shared keys require actual membership even for platform administrators.
- `PATCH /workspaces/{ws}/keys/{key}` `{disabled:true|false}`: reversible disablement (`disabled_at`), distinct from permanent revocation. The key's holder (own human key) or a shared owner/admin (any key) may toggle it; the personal owner toggles own keys. Disabled keys fail authentication and admission like revoked ones. A revoked key returns `409` `reason:"key_revoked"` and never re-enables; rotating a disabled key returns `409` `reason:"key_disabled"`.
- Key list rows add `status` (`revoked` > `expired` > `disabled` > `active`), `disabled_at`, `last_used_at` (latest admitted attempt of this credential), `lineage_id` and `usage:{period,used_microusd,limit_microusd,window_start,window_end,unresolved_usage}` — the lineage's smallest key-layer budget (`month` with `limit_microusd:null` when none) and its current-window use.
- `GET /workspaces/{ws}/keys/{key}/stats` (whoever may list the key): `daily` (30 UTC days through today: `spend_microusd`, `held_microusd`, `requests`, `unresolved_attempts`), `totals.today|week|month` (ISO week, calendar month), every applicable budget window (`budgets`, platform/local usage only with workspace-wide visibility) and `last_used_at`. Series and totals cover the whole key lineage, so rotation continues them.
- `GET/POST /workspaces/{ws}/service-accounts` (`{name}`); `PATCH /workspaces/{ws}/service-accounts/{id}` (`{disabled}`). Shared administration only. Disablement revokes keys; re-enabling does not restore them.
- `GET /workspaces/{ws}/key-safety[?key_id=&unused_days=&rotation_days=]` returns findings for the active keys the caller may list. `GET /platform/key-safety[?workspace_id=]` (Admin and Auditor) returns Team/Project keys without names or holders, and counts personal keys only. See [key safety](key-safety.md).

Catalog/model authorization retirement deletes affected key selections but retains restriction headers. Regranting cannot turn an emptied restricted key into inheritance or resurrect retired selections. Restrictions cannot be edited during rotation; create/revoke separate credentials to change them.

## Activity and allocation

`GET /workspaces/{ws}/executions`, `/usage`, `/audit` expose bounded metadata, not prompts/outputs.

<a id="logs"></a>**Logs (requests, generations, sessions).** Metadata only, never prompts or bodies. Visibility is the same in every view: members see their own human-key activity, shared administrators the whole workspace, personal workspaces only their owner; platform staff without membership get `403` on workspace routes.

*Common filters* (all optional, strict: unknown or repeated parameters and invalid values are `400`): `start_date,end_date` (YYYY-MM-DD, UTC `[start,end)`, 1–93 days, default the last 30 days; requests and sessions are selected by the first attempt's start, generations by their own start), `model` (public name), `key_id`, `status` (comma list of `succeeded|failed|cancelled|indeterminate|in_progress`; requests: the last attempt; generations: the attempt), `finish_reason` (comma list of `stop|length|tool_calls|content_filter|error|cancelled|unknown`; requests: the last attempt), `streamed` (`true|false`), `session_id` (exact client session id, 1–128 characters), `q` (request or execution id, full UUID or hex prefix of at least 4 characters). Lists take `limit` 1–100 (default 50) and an opaque `cursor` from `next_cursor`; detail and metrics endpoints reject `limit`/`cursor`.

*Telemetry* (migration 0009, written per attempt): `finish_reason` (normalized provider reason; `error` for failed and `cancelled` for cancelled attempts; null while running and for successful non-generation workloads), `time_to_first_token_ms` (streams: upstream dispatch to the first delta), `generation_ms` (upstream dispatch to the end of the upstream response, excluding admission/accounting), `reasoning_tokens` (provider-reported subset of output tokens; null = not reported), `cached_input_tokens` (`billing_usage.cache_read_input_tokens`), `upstream_model` (the route's configured upstream model id snapshotted at admission; older rows fall back to the route's current value), `reported_upstream_model` (migration 0013: the model the provider reported serving the attempt, 1–256 printable non-space ASCII characters; null = not reported, so show `upstream_model` marked as configured; see [provider adapters](provider-adapters.md#logs-telemetry-served-model-and-reasoning-tokens)), and per root request the optional client `session_id` and `app` ([client labels](protocol-matrix.md#client-labels-logs-sessions-and-apps)). `tokens_per_second` (decimal string, 2 dp) = output tokens × 1000 ÷ (`generation_ms` − `time_to_first_token_ms`) for successful generation attempts; null otherwise. Unknown values are null, never zero.

- `GET /workspaces/{ws}/requests` lists root requests newest first: `root_request_id,workspace{id,name,kind},started_at,completed_at,model,upstream_model,reported_upstream_model,provider,key{id,name},status,finish_reason,attempts,input_tokens,output_tokens,cached_input_tokens,reasoning_tokens,cost_microusd,held_microusd,latency_ms,time_to_first_token_ms,generation_ms,tokens_per_second,cost_center,workload_kind,streamed,session_id,app`. Token/cost sums are null when any attempt is unknown; `held_microusd` sums active holds; status, finish reason, timings, upstream models and provider come from the last attempt.
- `GET /workspaces/{ws}/requests/{root_request_id}` (same filters) returns the summary plus `workspace_id`, `attempt_count`, `attempts` (number, execution id, state, `error_code`, `finish_reason`, timestamps, `latency_ms`, `time_to_first_token_ms`, `generation_ms`, deployment `{id,upstream_model}`, `reported_upstream_model`, connection `{id,name,provider}`, tokens incl. `cached_input_tokens`/`reasoning_tokens`, `billing_usage`, `meter_usage`, `cost_microusd`, `held_microusd`, `accounting_state`, `unresolved_reason`, pinned price id/version, `failover_reason` (the previous attempt's error code or state) and `data_policy`) and `prev_id`/`next_id` (newer/older neighbours within the filters). A malformed id is `404`.
- `GET /workspaces/{ws}/generations`: one row per upstream attempt, newest first: `execution_id,root_request_id,attempt_number,workspace,started_at,completed_at,model,upstream_model,reported_upstream_model,connection{id,name,provider},key,status,error_code,finish_reason,streamed,workload_kind,input_tokens,output_tokens,cached_input_tokens,reasoning_tokens,cost_microusd,held_microusd,latency_ms,time_to_first_token_ms,generation_ms,tokens_per_second,session_id,app`.
- `GET /workspaces/{ws}/sessions`: root requests with a session id grouped by `(workspace, session_id)`, most recent activity first: `session_id,workspace,requests,attempts,failed_requests,in_progress_requests,input_tokens,output_tokens` (null when any is unknown), `cost_microusd` (null when any request's cost is unknown), `known_cost_microusd`, `held_microusd`, `unresolved_requests`, `first_at,last_at`, `models` (up to 10, sorted), `model_count`, `last_model`, `app`, `keys` (distinct key count). The filters apply to the requests before grouping. `GET /workspaces/{ws}/sessions/{session_id}` (URL-encoded; same filters) returns one such row or `404`; list its requests with `/requests?session_id=`.
- `GET /workspaces/{ws}/logs/metrics` (same filters) summarizes the filtered root requests: `requests`, `completed`, `failed`, `error_rate` (failed ÷ completed, 4 dp, null when none completed), `latency_p50_ms`/`latency_p95_ms` (completed requests), `avg_time_to_first_token_ms` (+ `ttft_requests`), `tokens_per_second` (aggregate over requests with a rate), `input_tokens`/`output_tokens` (observed sums; lower bounds when `unknown_token_requests` > 0), `known_cost_microusd`, `held_microusd`, `unresolved_requests`.
- **Platform** (Admin/Auditor; Team/Project workspaces only — personal workspaces never appear as rows, their totals stay in Usage & costs): `GET /platform/logs/requests`, `/platform/logs/requests/{root_request_id}`, `/platform/logs/generations`, `/platform/logs/sessions`, `/platform/logs/sessions/{ws}/{session_id}` and `/platform/logs/metrics`, with the same shapes and filters plus `workspace_id` (a personal or unknown id matches nothing; a personal request's detail is `404`). Ordinary users get `403`. Rows carry `workspace{id,name,kind}` for the Workspace column.

<a id="model-compare"></a>**Model compare.** `GET /workspaces/{ws}/models/compare?ids=a,b[,c,d]` and `GET /platform/models/compare?ids=…` take 2–4 distinct model UUIDs. Malformed, repeated or too few/many ids return `400`. The workspace route needs actual membership (as Logs do), and every id must be in the workspace catalog (enabled, and selected, assigned or available from its catalogs), otherwise the whole request returns `404`. The platform route is Admin/Auditor and accepts any model. `data` follows the order of `ids`. Each entry has `id,public_name,display_name,enabled,protocols,workload,routes,enabled_routes,priced_enabled_routes`, plus:

- `price`: the latest price of the model's **first enabled route** in routing-priority order, as `{pricing_version,lines,display_lines,input_token_limit,output_token_limit,created_at}`, or `null` when that route has no price (or there is no enabled route). A missing price is unknown, never zero. `lines` is v3-shaped for every version (exact integer `microusd_per_batch` strings). v1/v2 token rates become `input_tokens`/`output_tokens` lines, and v2 cache rates become cache lines when priced or not applicable. Unknown cache rates are left out.
- `metrics`: root requests whose first attempt started in the last 30 UTC days (`period:{start,end}`): `requests,completed,failed,error_rate` (4 dp, null when none finished), `latency_p50_ms`, `ttft_p50_ms` (+ `ttft_requests`), `tokens_per_second` (null when not measured). Visibility follows Logs and is reported as `activity`: `own` (members: their own human keys), `workspace` (shared administrators, personal owner) or `shared_workspaces` (platform: Team/Project activity aggregated; personal workspaces never contribute).

The dashboard opens it from the checkboxes on Workspace › Models and Admin › Models (`/workspaces/{ws}/models/compare?ids=`, `/admin/models/compare?ids=`) and marks the best known value per row only when the values differ.

**Effective access.** `GET /workspaces/{ws}/access` and `GET /workspaces/{ws}/keys/{key}/access?model_id=` (read-only, same visibility as the policy GET) return `layers` in order `type_default`, `workspace_override` (`applies`, `catalogs_apply`, catalogs), `workspace` (local limits/budgets, `selections`), `key` (`restriction`), each with cumulative `models:{available,partial,unavailable}`; a `summary`; and `models` (catalog-eligible or assigned models, plus `model_id` when given; at most 200, `truncated`) with `status` and `reasons:[{code,layer,period?}]`. Platform Admins/Auditors may also read a disabled Team/Project's workspace access (`workspace_disabled:true`, every model blocked by the `workspace_disabled` reason), selected models (`GET /workspaces/{ws}/models`, its remaining assignments), platform policy, catalogs and members, read-only; everyone else, key access and every mutation still get `404`. Codes: `workspace_disabled`, `model_disabled`, `no_enabled_route`, `not_in_catalog`, `not_selected`, `key_restriction`, `budget_exhausted` (a workspace or key budget's current window is used up), `unresolved_usage_blocking` and the non-blocking `some_routes_unavailable` (partial). `no_enabled_route` and `some_routes_unavailable` count only enabled routes whose connection can serve the model. Reasons with layer `platform` are model-level facts (a model or its routes turned off); there is no installation layer row or installation limit (removed in 0026). `protocol_unsupported` is reserved: the management API has no provider-registry view, so it is not emitted yet. Members see own human-key activity; shared administrators see whole workspace. Personal details remain owner-only. Platform Auditors without membership have configuration/reporting authority, not workspace keys/private requests. `GET /platform/audit` (Admin/Auditor, `limit` 1–200, `offset`, `{data,has_more}`) excludes every personal-workspace event, whoever the actor or owner. Optional filters, validated strictly (`400` otherwise; unknown or repeated parameters are rejected): `actor_user_id=<uuid>` keeps events that user performed; `hide_sign_ins=true|false` excludes events recorded as a side effect of signing in (`identity.groups_synchronized`, `identity.rebound`); `exclude_actions` is a comma-separated list of up to 20 exact action codes (`[a-z0-9_.]`, at most 64 characters each). Filters only narrow what the caller can already read; the user page's Activity tab uses them. Its rows add display-only names so the dashboard needn't load every user or workspace: `actor_name` (display name, else email), `workspace_name` and `workspace_kind` for Team/Project events, and `target_name`: the name of a user, Team/Project (with `target_kind`), cost center, group mapping (its group value), model, catalog or connection, `"<upstream_model> on <connection>"` for routes (`deployment`) and `"Price vN for <upstream_model> on <connection>"` for prices, where N is the price's position in that route's append-only history. Other targets (keys, service accounts), and targets that no longer exist, get `null`. `GET /workspaces/{ws}/audit` rows likewise add `actor_name` (for workspace admins, or the caller's own events) and `target_name` (keys the caller can list, models, the workspace, and for admins service accounts and people). `model.granted`/`model.grant_revoked` metadata `source` is `catalog` for a workspace's own catalog selection and `direct` for a Platform Admin's direct assignment.

<a id="files"></a>**Files (Workspace › Files).** The same files as the [Files API](files-api.md) (`GET /v1/files`) for one workspace. Members (or the personal owner) only. Workspace admins and personal owners see every file; other members see files they uploaded themselves. Platform staff without membership get `403`. Contents are never in audit or logs.

- `GET /workspaces/{ws}/files?purpose=&search=&limit=1..200&after=file-…`: `{data:[{id,filename,purpose,bytes,content_type,created_at,expires_at,status,mine,via_key}], has_more, scope:"workspace"|"own", storage:{quota_bytes, used_bytes (null without workspace-wide visibility)}, store:{configured, batch, user_files}, max_bytes}`.
- `GET /workspaces/{ws}/files/{file_id}/content`: the decrypted file as an `application/octet-stream` attachment (`nosniff`, `no-store`).
- `DELETE /workspaces/{ws}/files/{file_id}`: admins delete any workspace file; members delete only their own (others are `404`). Audited as `file.deleted` with `{kind: <purpose>}`.

<a id="batches"></a>**Batches (Logs › Batches).** The same batches as `GET /v1/batches` ([batches](batches.md#monitoring)). Members only: workspace admins and personal owners see every batch, other members the batches they created; platform staff without membership get `403`. Money is integer micro-USD strings; `cost_unknown` means part of the cost is unresolved (never zero); `cost_unknown_attempts` counts those attempts. A failed line on a priced route keeps an unknown cost (the gateway never assumes the provider charged nothing), so the dashboard shows the settled amount as a lower bound ("At least $X") with the count in its tooltip, not "Unknown". `waiting_reason` reports the binding limit: `concurrency` when the route's batch limit is reached (all batches), `workers` only when the gateway's own batch workers are the constraint.

- `GET /workspaces/{ws}/batches?status=active|finished&limit=1..200&offset=`: `{data:[{id,state,upstream_status,mode,endpoint,model,provider,price_tier,batch_price,total,completed,failed,error_code,created_at,in_progress_at,finalizing_at,completed_at,cancel_requested_at,last_progress_at,input_file_id,output_file_id,error_file_id,settled_microusd,held_microusd,cost_unknown,cost_unknown_attempts,key_name,mine,workspace_id,workspace_name,workspace_kind,running_lines,waiting_reason}], has_more, scope}`. `batch_price` is true/false for native batches (batch list applied or not) and null for gateway-run ones. `waiting_reason` (gateway-run, unfinished) is why lines are held back (`outside_window`, `live_traffic`, `server_busy`, `metrics_unavailable`, `concurrency`, `fair_share`, `workers`, `rate_limited`) or null; with `running_lines` 0 the dashboard shows "Queued — waiting for capacity".
- `GET /workspaces/{ws}/batches/{batch_id}`: `{batch, outcomes:[{state,code,lines}], scheduling:[{model,reason,waiting_lines,running_lines,position,queue,since}]}` (line counts by state and error code; gateway-run batches). `scheduling` lists the batch's waits per model route with its place in that route's fair-share queue.
- `POST /workspaces/{ws}/batches/{batch_id}/cancel`: admins cancel any batch, members only their own. `409` when already finished. Audited as `batch.cancelled` with `{mode}`.
- `GET /platform/batches?status=&limit=&offset=` (Platform Admin/Auditor): Team/Project rows (no key names) plus `personal:{active,finished,failed,lines}` totals.

<a id="batch-scheduling"></a>**Batch scheduling (Admin › route).** When gateway-run batch lines may start on a route ([batches](batches.md#scheduling-on-self-hosted-models)).

- `GET /platform/deployments/{id}/batch-scheduling` (Platform Admin/Auditor): `{settings, defaults, priority_supported, status:{queued_lines,waiting_batches,running_lines,paused_reason,checked_at,live_in_flight,metrics:{checked_at,ok,waiting,running,kv_cache_permille,error}|null}}`. Settings are the defaults when none are stored.
- `PUT /platform/deployments/{id}/batch-scheduling` (Platform Admin): `{max_concurrency (1–256), yield_live_threshold?, metrics?:{url,max_waiting?,max_running?,max_kv_cache_percent?}, priority?, window?:{timezone,days:["mon"…"sun"],start:"HH:MM",end:"HH:MM"}}` replaces the settings; omit a field (or send null) to turn it off. `400` with a fixed message when the metrics URL is not `/metrics` on an approved local origin, a limit is out of range, no metrics limit is set, `priority` is set on a route that is not `vllm`/`openai_compatible` or is not 1–1000000, or the window's zone, days or times are invalid. Unknown fields are refused. Audited as `batch_scheduling.updated` (numbers and on/off flags only).
- `POST /workspaces/{ws}/files/upload`: multipart `purpose` + `file` (any order), the same pipeline and limits as `POST /v1/files` (body cap `GATEWAY_FILES_MAX_BYTES` + 64 KiB). Returns the file row. Refusals use the management error envelope with `reason` `file_storage_not_configured` (503), `file_purpose_disabled` (403), `storage_quota_exceeded` / `file_too_large` (413), `invalid_request_error` / `unsupported_capability` (400) or `file_storage_unavailable` (503). Audited as `file.uploaded` with `{kind: <purpose>}`.

<a id="storage-usage"></a>**Storage usage (not charged).** `GET /workspaces/{ws}/usage/storage?start_date&end_date` (UTC days, 1–366, workspace-wide visibility: admins and personal owners) and `GET /platform/usage/storage?start_date&end_date` (Admin/Auditor). They return `{period, unit:"gb_day", gb_bytes:"1073741824", cost_state:"not_charged", recorded_through, total:{byte_seconds, gb_days}, by_purpose:[{purpose, byte_seconds, gb_days}]}`:

- Byte-seconds are exact integer strings; GB-days are rounded to 6 decimals.
- The workspace route adds `daily:[{date, byte_seconds, gb_days}]` and `current:{used_bytes, quota_bytes}`.
- The platform route adds `workspaces:[{workspace_id, name, kind, byte_seconds, gb_days, current_bytes, quota_bytes, by_purpose}]` (at most 500; `by_purpose` is `null` for personal workspaces: totals only).
- Storage is never shown as a cost: `cost_state` is always `not_charged`. See [Files API](files-api.md#storage-usage-not-charged).

**Storage limit.** Policy GET/PUT bodies of the workspace-type default, platform override and workspace local layers carry `storage_bytes` (bytes, 1 to 2^50, or null). On PUT, absent keeps the stored value and null clears it (the local layer is tighten-only, with the `exceeds_parent_rate` / `stored_rate_loosen_not_allowed` reasons and `limit:"storage_bytes"`). Key policy PUTs refuse a non-null `storage_bytes` with `400`. Workspace and platform workspace policy responses add `storage:{quota_bytes, used_bytes, usage_visible}`; `used_bytes` is null without workspace-wide visibility. See [governance](governance.md#storage).

**Key issuance limits.** The same three layers carry `key_issuances_per_holder` and `key_issuances_per_workspace` (1 to 10,000 or null; type defaults 50 and 500). On a platform override, a field that is set replaces the type default and one that is null inherits it (unlike other limits, where a null override field means no limit); `policy` shows the override's own fields (null stays null) while `provenance.platform` and `effective` show what applies. With no type default either, the ceiling is 10,000, never unlimited. The fields have the same absent-keeps and null-clears PUT rules and the same rejection reasons (`limit:"key_issuances_per_holder"` or `"key_issuances_per_workspace"`). Key policy PUTs refuse a non-null value with `400`. `POST /workspaces/{ws}/keys` and `POST /workspaces/{ws}/keys/{key}/rotate` answer `429` `reason:"key_issuance_limit_exceeded"` with a `Retry-After` header and `scope`, `operation`, `window_seconds` and `retry_after_seconds` when a budget is spent, after every `401`/`403`/`404`/`400`/`409` check. See [governance](governance.md#key-issuance).

`GET/POST /platform/cost-centers` and `GET/PATCH/DELETE /platform/cost-centers/{id}` manage `{name,code}`. DELETE archives. Only Admins assign nullable `cost_center_id` through platform workspace PATCH. This affects future admission snapshots, not existing financial labels or access. Reports, details, policies and reconciliation are covered by [governance API](governance-api.md).

## Alerts

<a id="alerts"></a>Rules, history and notifications ([alerts](alerts.md)). Rule bodies are flat and strict (unknown fields `422`, invalid values `400`): `name`, `kind` (`budget_threshold`, `spend_threshold`, `spend_spike`, `error_rate`, `provider_failing`, `batch_failed`, `batch_stalled`, `admission_ceiling`), `enabled` (default `true`), the kind's own fields only (`budget_layers` + `thresholds`; `spend_period` + `spend_amount_microusd` (integer micro-USD string) + `thresholds`; `spike_factor_percent` + `min_spend_microusd` as an integer micro-USD string; `window_minutes` + `error_rate_percent` + `min_requests`; for connections also `consecutive_failures` and an optional `provider_connection_id`; `admission_ceiling`: `window_minutes` 5–10 plus `ceiling_requests_per_second` 1–100000 and/or `ceiling_lock_wait_ms` one of 10, 25, 50, 100, 250, 500, 1000, 2500, installation only and without `notify_emails`), and recipients `notify_workspace_admins` (workspace rules only), `notify_platform_admins`, `notify_emails` (up to 10). PUT replaces the rule; its `kind` is fixed (`409 reason:"alert_rule_kind_fixed"`). DELETE soft-deletes (history stays). At most 50 rules per scope (`409 reason:"alert_rule_limit"`). Responses add `firing` (open incidents), `last_fired_at` and `provider_connection`. Changes are audited (`alert_rule.created|updated|deleted`).

- `GET/POST /platform/alerts/rules`, `GET/PUT/DELETE /platform/alerts/rules/{id}`: Admin writes, Auditor reads. Every kind; budget layers `type`, `override`, `local`, `key`. `budget_layers` containing `installation` is `400 reason:"installation_limits_removed"` (there is no installation budget; use `spend_threshold`).
- `GET/POST /workspaces/{ws}/alerts/rules`, `GET/PUT/DELETE /workspaces/{ws}/alerts/rules/{id}`: Team/Project owners and admins write (actual membership); platform readers may read; members get `403`. No `provider_failing`, `spend_threshold` or `admission_ceiling`. The list adds `writable`. Personal workspaces: the owner's GET returns `data:[]` and `builtin:{thresholds:[80,100],budget_layers}`; POST returns `403 reason:"personal_alerts_built_in"`; nobody else may read.
- `GET /platform/alerts/events` (installation rules) and `GET /workspaces/{ws}/alerts/events` (that workspace's rules, or the personal owner's built-in alerts), with `status=firing|resolved`, `kind`, `rule_id`, `limit` 1–200, `offset`; `{data,has_more}`. Each incident: `id,rule:{id,name,scope,deleted}|null,builtin,kind,state,severity,level,summary,details,workspace:{id,name,kind}|null,connection|null,fired_at,resolved_at,resolution,email:{status,recipients,sent,failed,error}|null`. Money in `details` is integer micro-USD strings; `unknown_cost_requests` counts reservations left out of spend. No key, owner or request details. `admission_ceiling` incidents name a Team/Project (`workspace`, `details.workspace_name`) for Platform Admins only; for Auditors (here and in notifications) both are omitted, and personal workspaces are never named (`details.personal:true`).
- `GET /me/notifications[?status=unread&limit&offset]` (the caller's incidents by live authority, last 90 days, each with `read`), `GET /me/notifications/summary` (`{unread,firing}`; no installation lock, safe to poll) and `POST /me/notifications/read` with `{ids:[…]}` (1–200) or `{all:true}`. Ids the caller can't see are ignored, not disclosed; the response is `{marked}`.

### Saved alert webhooks

#45 exposes saved platform destinations, signed delivery, fixed test-send and redacted delivery status. The dashboard is **Admin › Settings › Alerts › Webhooks** ([administration](alerts.md#dashboard-administration-slice-3)).

- `GET /platform/alerts/webhooks` returns `{data:[…]}`; `GET /platform/alerts/webhooks/{id}` returns an item. Platform Admin/Auditor; admin tokens need `platform:read`. Status includes `id,label,enabled,created_at,updated_at,signing_configured,overlap_active,previous_secret_until,waiting,exhausted,last_success_at,last_error`. Only browser-session Platform Admins and admin tokens holding both `platform:read` and `settings:write` also receive `url,current_secret_ref,previous_secret_ref`; Auditors and read-only tokens receive none of those fields.
- `POST /platform/alerts/webhooks`: Platform Admin; token `settings:write`. Required `{label,url,current_secret_ref}` only. The destination always starts disabled. Labels are trimmed, 1–120 characters, without controls. URL must match the operator's canonical URL allowlist; references must be allowlisted `env:NAME`. Save never resolves signing bytes or contacts the receiver. Ten nondeleted destinations maximum (`409` when full).
- `PATCH /platform/alerts/webhooks/{id}`: same write authority. Optional `label,enabled,current_secret_ref,previous_secret_ref,previous_secret_until`; `url` is not writable. Previous reference and RFC3339 timestamp must be present together in the resulting configuration, different from the current reference, with a newly configured overlap ending within the next 24 hours. Clear both with `null` to end overlap. Other fields cannot be `null`. Enablement rechecks current operator approval.
- `DELETE /platform/alerts/webhooks/{id}`: same write authority; empty body or `{}` only. Soft-deletes, disables and scrubs the URL and signing references; later item reads/edits return `404`. Disable and delete terminate committed waiting rows as `ineligible`, and so does re-enabling for rows of an older enable generation (a label edit changes nothing); terminal rows never reopen, so re-enabling does not replay. Each change of `enabled` increments the destination's trigger-owned enable generation, which every queued row records. A concurrent enqueue can commit later; the delivery worker rechecks eligibility before every claim, refusing deleted destinations and NULL (scrubbed) URLs, and requiring the row's generation to equal the destination's, with the destination locked (destination before outbox row). PATCH locks the destination `FOR NO KEY UPDATE`, which does not block alert enqueue's foreign-key `FOR KEY SHARE`.

- `POST /platform/alerts/webhooks/{id}/test`: Platform Admin; token `settings:write`. No body or `{}` only. Queues one fixed `test:true,event:null` delivery to the enabled saved receiver; returns `{id,state:"waiting"}`. `409` if no enabled saved destination exists. Replica-safe audited limits are 2/user/minute, 2/destination/minute and 20/installation/hour (`429`), counting failed deliveries too. No caller-selected URL, headers, payload or event.
- `GET /platform/alerts/webhooks/{id}/deliveries`: same read authority/redaction as item GET. Returns `{destination,counts,data}`: counts for `waiting,leased,sent,failed,exhausted,ineligible`, at most 50 newest rows with `id,state,test,attempt_count,created_at,completed_at,next_attempt_at,last_error`. No payloads, event ids, signatures or secret material. Waiting rows/counts exclude stale enable generations. There is no replay endpoint.

Malformed/unknown fields and invalid values are `400`. Browser writes retain Origin/CSRF checks. Writes revalidate tokens/owners inside their transaction and append `alert_webhook.created`, `.updated`, `.disabled` or `.deleted` audit events containing the destination id and changed-field names only. See [alerts](alerts.md#saved-platform-webhooks-45-slice-1) and [operator configuration](operations.md#credential-allowlists).

### Public installation logo

`GET /api/v1/branding/logo` needs no session (the sign-in page shows the logo before login) and is served same-origin, so browsers never contact a third party. It returns the current logo's bytes with its image `Content-Type`, `ETag` (the SHA-256), `Cache-Control: public, max-age=300`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'` and `Cross-Origin-Resource-Policy: same-origin`; `If-None-Match` gives `304`. `404` when no logo is set or the file store is off. A `v` query parameter is ignored (it only busts caches). The public `GET /api/v1/auth/config` adds `logo` (same shape as in `/me`) and `installation_name` (only when a logo is set; its alt text).
