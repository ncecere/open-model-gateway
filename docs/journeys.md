# Journeys: real-path checks against a running gateway

Needs **Python 3.12 or newer** (standard library only; `python3 -I scripts/journeys …` refuses an older Python with one line and exit 2).

`scripts/journeys` runs user-facing flows against a forwarded demo environment: an environment on the Spark test platform (`scripts/spark-env.py`, AGENTS.md) or the local demo ([local demo](local-demo.md)). Both are the same passwordless demo, so the suite signs in as the five demo personas through the real OIDC redirect flow. It complements the unit, integration and browser suites with the one thing they cannot show: the changed build, deployed, answering real requests, including the refusals.

```sh
python3 -I scripts/spark-env.py up my-name --ref <tag or candidate commit>
python3 -I scripts/spark-env.py forward my-name &       # gateway on 127.0.0.1:3000, demo issuer on 127.0.0.1:18084
mkdir -p .local/journeys                                # .local/ is git-ignored; summaries stay out of commits
python3 -I scripts/journeys run --base http://127.0.0.1:3000 --label rc1 --summary .local/journeys/summary.json
python3 -I scripts/journeys run --base http://127.0.0.1:3000 --only keys signin   # chosen journeys, in this order
python3 -I scripts/journeys list
```

`--base` must be the gateway's public origin, which for the demo is `http://127.0.0.1:3000`: another spelling of the same address (`localhost`) is refused with the origin to use, because the Origin check on every mutation would fail. `--shuffle [--seed N]` runs every journey in a random order (without `--seed` a seed is generated, printed and recorded; `--seed` alone is an error). `--label` names the run in the summary, `--request-timeout` bounds one request and `--deadline` the whole run (journeys that have not started by then are reported as not run). The exit code is 0 when every check passed, 1 when a check failed or a journey errored (also when the run stopped early or the summary could not be written), 2 when the command was refused (below).

## What the suite promises

- **Safe to point at.** It refuses a `--base` that is not loopback (127.0.0.1, `::1`, `localhost`) unless `--allow-remote` is given, refuses a base with credentials, a path or a query (and never echoes it), and prints which environment it is about to modify. Before anything else it checks that the gateway is ready, that its sign-in redirect names the same origin as `--base` (its `redirect_uri`) and an issuer on loopback, and that the issuer is **the passwordless demo issuer**: its account chooser must list `operator@demo.invalid`. `--allow-remote` relaxes only the loopback rule; a gateway whose sign-in is a real identity provider is always refused. Never aim it at production: it creates throwaway workspaces, keys, invitations, requests, access reviews, cost centres, catalogues, schedules and admin tokens.
- **Refusal checks are harmless if the refusal regresses.** A "must be refused" request carries a body that does nothing if it is accepted (a body no create accepts, the current value written back, a throwaway object), and when a refusal does turn out to succeed the check fails and an undo for what it created runs. Seeded state (the personas, Product, Research, installation settings, the type defaults) is only ever read, or written back unchanged and restored if that changed anything.
- **Re-runnable and order independent.** Every journey creates what it needs under a unique name (`journeys-<run>-<journey>-<thing>`), undoes it afterwards, also when a check fails or the journey errors, and the other journeys still run. Every undo is a check: one that gets a refusal, or a status other than success or an explicit "already gone", is a failed check, so a cleanup that does not clean cannot pass. A journey that records no check fails.
- **One run per environment at a time, with a gap between runs.** The persona sessions are shared within a run and `me-summary` revokes a persona's other sessions, so two suites against one environment would sign each other out. The gateway also limits, per person or address: sign-ins (`GATEWAY_LOGIN_RATE_PER_MINUTE`, docs/identity.md; a throttled step is retried after `Retry-After`, a bounded number of times), access-request submissions (a few a minute and 50 a day per requester, docs/management-api.md) and the personal data export (3 an hour). The suite spreads access requests over four requesters (Blair, the Auditor, the Admin and Alex use one each), so a second run may start as soon as the first has finished; about fifty runs fit in a day before a requester's daily allowance is used, and `export.own-data` accepts the documented 429. Do not start runs back to back in a loop.
- **No secret in the output.** Keys, admin tokens, invitation codes, cookies, CSRF values and response bodies never reach the summary or the terminal, by construction rather than by scrubbing: the recorder takes only a check name, an expected and an actual HTTP status and a note from a fixed list, and is never handed a response. A check name is a string literal or a loop over literals (tested on the source), so response data cannot become one. Credentials are held in a `Secret` that prints as `<secret>`; an exception is reported by an allow-listed type name only, with the last check recorded before it and the source line; an id taken from a response is validated as a UUID before it goes into a path; the summary names no URL, query, e-mail address or identifier. It is written with mode 0600 and a symlink at its path is refused. Keep it under `.local/journeys/` (git-ignored) until it is attached to a release PR.
- **Honest about the demo.** The demo has no model server or provider and its example connections and deployments start disabled, so no generation completes here, and a request is sent for a catalogue model only after the platform views show it has no enabled route. The demo's file store is off (platform storage backend `off`), so an upload is refused with the documented `file_storage_not_configured` (503) and file contents cannot be exercised. The inference journeys cover authentication, validation and the documented `model_not_found` refusal per protocol, not a completed response (see "Not covered").
- **Run identity.** The summary records the label, the UTC start time, the run id, the journey order and the seed. No endpoint of the gateway exposes its version (health, `/me`, the platform overview and the settings were checked), so the summary cannot record one: put the tag or commit in `--label`.

## What each journey leaves behind

Nothing the API can delete is left. These objects have no delete route, so they stay until `spark-env.py down` (the local demo keeps them; they are named `journeys-<run>-…` and are harmless):

| `workspaces`, `keys`, `inference-auth`, `credential-boundaries`, `csrf-origin`, `members-invitations`, `platform-admin`, `auditor-readonly`, `access-requests`, `access-reviews`, `reports-usage`, `catalogs-models`, `schedules-alerts-holds` | Disabled throwaway Teams and Projects (several per journey; disabled workspaces drop out of every list and every person's access), revoked keys, a disabled service account, accepted or revoked invitations |
| every journey | Audit entries for what it did, including the no-op writes of seeded settings and type defaults, and one sign-in and sign-out record per session it opened (`signin` opens ten, `me-summary` three more, the rest share one session per persona per run, signed out at the end) |

| `catalogs-models` | One removed catalogue is gone; the workspace and catalogue assignments were on throwaway objects |
| `schedules-alerts-holds` | One released legal hold (a record) |
| `access-requests` | Decided or withdrawn requests; notifications this run caused are marked read |
| `access-reviews` | One closed campaign |
