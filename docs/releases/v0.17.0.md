# Open Model Gateway v0.17.0

A minor release after [v0.16.0](v0.16.0.md): fixes to how the gateway ends and accounts for a few failures, a wider set of accounting-failure stages, a measurement of lost upstream connections, a large round of verification work in CI and the tests, and more internal restructuring.

- **Fixes.** `serve` releases its job leases when start-up fails after taking them (#527). A realtime client that breaks the WebSocket protocol or drops the connection no longer ends as a clean stop (#410). Accounting and storage failures that had no cause are counted in `gateway_accounting_failures_total` under six new stages (#497). A Bedrock stream that ends in an exception frame is classified by the exception type, and a rejection inside a returned stream no longer settles as a known zero on a free price (#486).
- **Measured and narrowed.** Pooled outbound HTTP clients drop an unused connection after a pool idle timeout below their upstream's, and the new counter `gateway_upstream_connection_lost_total{client}` counts the requests that still lose their connection (#483).
- **Security and verification** work in CI and the tests: the egress client rule is enforced by the compiler (#509, #569), the shipped build is linted (#502), committed secrets are scanned for (#596), image-building jobs are pinned whole (#488, #493) and several test guards read source more completely (#498, #506, #511, #576). None changes how the gateway runs.
- **Spark test platform.** Branches and release candidates are tested on the owner's dedicated arm64 k3s cluster, and branch images now include linux/arm64 (#599).
- **Internal restructuring.** Thirty-four long functions and five more large files are split into named steps and child modules (#537 to #561, #607, #617, #618). Two log events have a different target because their code moved ([below](#behaviour-changes)).

No migration and no runtime-grant change: the schema stays at **0080**, so a v0.16.0 or v0.15.x database is served as it is. The Helm chart changes only in its version and default image tag. The OpenAPI inference document gains two realtime close codes (1002 and 1007); the management document changes only in `info.version`.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## Fixes

- **`serve` releases its job leases when start-up fails after taking them** (#527). A start-up failure after the background-job leases were taken (a busy public or metrics port, or the audit export state check) used to exit with every lease still held, so another replica could not run those jobs until the terms expired (up to 30 seconds). Every such failure now stops renewing and releases the leases this process holds, as graceful shutdown does, then returns the original error. `GATEWAY_PARTITIONS_AHEAD_MONTHS` is now checked before any lease is taken, so a refused value never holds one. Each release is bounded to 2 seconds, on both paths; a release that fails or times out is logged (`work lease not released; it ends at expiry`, field `lease`) and its term still ends at its expiry.
- **A realtime client that breaks the WebSocket protocol or drops the connection no longer ends as a clean stop** (#410). Every browser socket error other than a size refusal was treated as the client leaving, so with no response in flight an invalid UTF-8 text frame, a stray continuation frame or a connection lost without a close frame finished the session as `succeeded` with finish reason `stop`. Now a text frame or close reason that is not UTF-8 gets an `invalid_payload` error event and close 1007, and any other protocol violation reported by the WebSocket parser a `protocol_error` error event and close 1002. Both fail the session with `invalid_request_error`, idle or mid-response (a response in flight keeps its hold as unknown cost, as before; it used to be recorded as `cancelled`). A connection lost without a close frame (a reset, an I/O error), or a client the gateway can no longer write to, is `cancelled`, like a dropped HTTP request; as with those, an idle drop no longer updates routing health (it used to record a healthy, non-provider result). Only a close frame with no response in flight is still `succeeded`/`stop`. Close frames and error events are best effort: if the client still has unread data in flight, the connection can be reset and lose them; accounting does not depend on them. The OpenAPI document lists the two new close codes.
- **Accounting and storage failures that had no cause are counted** (#497). v0.16.0's `gateway_accounting_failures_total{stage,cause}` and its `accounting unavailable` `WARN` line (fields `stage` and `cause` only) did not cover four places ([known limitation](v0.16.0.md#known-limitations)). They now have their own stages:
  - `realtime_admission`: a realtime window reservation whose 5 s deadline elapsed; it rolls back and holds nothing.
  - `realtime_settlement`: a realtime response open, response settlement, session finish or detached finish of a dropped session whose 3 s deadline elapsed, leaving money held until reconciliation.
  - `job_storage`: database failures of the job module (batch runner, job poller, batch scheduler and the job API's own job-table work), all retried.
  - `job_settlement`: the job record written after admission or after the provider accepted a video, and a native batch's upstream id; a failure leaves the reservation to reconciliation.
  - `maintenance`: database failures of the maintenance loop's settings refresh, lock-wait flush and leased runs (a fenced run is not counted).
  - `key_authentication`: a failed API key lookup, which still answers `503 api_error`; it now writes the new `WARN` line as well as the existing `ERROR` line `authentication database lookup failed`.

  The four deadline stages (`explicit_settlement`, `cancellation_settlement`, `realtime_admission` and `realtime_settlement`) report the `deadline_*` cause of what they waited on when the deadline elapsed; the other stages report the database cause (for `job_settlement`, the database error). The label set stays fixed: 11 stages and 16 causes, at most 176 combinations, at most 103 produced (was 5, 16, 80 and 45); the metric's help text lists the new stages. Each failed operation is counted once; the background loops retry on their own schedule, so a database outage keeps the counter rising at a bounded rate ([volume](../operations.md#accounting-failures)). No response, retry or existing log line changed; an `accounting_unavailable` from an internal consistency check still has no database cause and is not counted.
- **Lost connections to upstreams are measured, and the window narrowed** (#483). A request written to a pooled connection the upstream is closing on its own idle timeout is lost, and the caller sees a failed request (found while fixing #417; for the demo issuer 2 to 37 of 3000 requests). Every pooled outbound HTTP client (OpenAI, OpenRouter and its catalog, Anthropic, Bedrock, S3, local endpoints and their metrics poll, and the OTLP/audit/webhook export client; not OIDC) now drops an unused connection after a fixed pool idle timeout below its upstream's ([values](#behaviour-changes)); reqwest's default was 90 s. The values are constants, not settings, with their evidence and what is unverified in [Lost connections](../operations.md#lost-connections-483). The new `gateway_upstream_connection_lost_total{client}` (OTLP System class) counts requests that failed before a complete response head arrived because the connection was lost. It does not prove the connection was reused (neither reqwest nor hyper says), and a counted request may have been processed by the upstream or never written; it also counts a fresh connection reset, an upstream restart mid-request, a middlebox cut and a partial response head, but not a failure of the gateway's own request body. The gateway and reqwest resend nothing and the error a caller sees is the same; the connection pool beneath reqwest can still re-dispatch a request it had not written, as it did before. A loopback server that closes idle connections lost 6 of 12 requests spaced past its timeout before the change and none with the pool idle timeout below it. `HttpClientBuilder` gains a `pool_idle_timeout` passthrough (it changes no redirect, retry, proxy or resolver safeguard), added deliberately to the client-module list in `egress_source_scan_tests.rs`; a source-scan test pins each call site's client.
- **A Bedrock stream that ends in an exception frame is classified by the exception type** (#486). AWS sends an exception frame's type in the `:exception-type` header and `{"message": ...}` as the payload, with no code. The gateway read the class from a payload code that is never there, so every exception frame ended the stream as `upstream_unavailable`: a throttled stream was not `rate_limit_error`, and a `validationException`, which is the client's input, counted as a provider failure in routing health, so repeated invalid requests could open a deployment's circuit breaker. The class now comes from the header alone (never the payload or the message text), and only the documented names are classified; see [Behaviour changes](#behaviour-changes) for the table and what else changes with it. See [Bedrock](../bedrock.md#exception-frames). New tests feed the wire shape through the SDK decoder and run both client protocols against a mock endpoint on PostgreSQL, on a v1 and an all-free v3 price.

## Behaviour changes

- **New metric.** `gateway_upstream_connection_lost_total{client}` with `client` one of `openai`, `openrouter`, `anthropic`, `bedrock`, `local`, `s3`, `export` (`export` is the shared client of OTLP telemetry, the audit export and alert webhooks). OTLP System class, so it is exported wherever the OTLP metrics export is enabled. No series exists until the first loss: an alert on it must treat a missing series as zero. Nothing is logged for a lost connection; the counter is the record.
- **New stages on `gateway_accounting_failures_total`.** `realtime_admission`, `realtime_settlement`, `job_storage`, `job_settlement`, `maintenance` and `key_authentication` (11 stages in all, 16 causes). A dashboard or alert that selects stages by an explicit list needs the new names; the example rules place them: `realtime_settlement` and `job_settlement` join the critical `GatewaySettlementAccountingFailures` (a failure there leaves money held until reconciliation, which `GatewaySettlementHeld` does not see), the others the `GatewayAccountingFailures` warning (#528, [below](#operations-and-documentation)). `key_authentication` writes the new `WARN` line in addition to the existing `ERROR` line, so a failing key lookup now logs two lines per failed lookup that reaches the database.
- **Pool idle timeouts** (constants, not settings), per client: `openai`, `openrouter`, `anthropic`, `bedrock` 20 s; `s3` 3 s; `local` 4 s (uvicorn, vLLM and llama.cpp default to a 5 s keep-alive); `export` 10 s. OIDC is unchanged. The previous value was reqwest's 90 s for all of them. A call made more than the timeout after the previous one on a client now opens a new connection.
- **New log event:** `work lease not released; it ends at expiry` (`WARN`, field `lease`, target `open_model_gateway::leases`), written when a lease release fails or exceeds 2 seconds at shutdown or after a failed start-up.
- **Log events with a new target**, because the code that writes them moved. The messages and fields are unchanged and a prefix filter such as `RUST_LOG=open_model_gateway=info` still matches them; only a filter or query on an exact target needs updating:
  - `management storage error` is now `open_model_gateway::management::errors` (was `open_model_gateway::management`, #607);
  - `adapter request validation returned an error outside its contract` is now `open_model_gateway::inference::attempt` (was `open_model_gateway::inference`, #539).

  The other splits (#537 to #561, #617, #618, and the remaining files of #607) moved no log event; each was checked by comparing the log macro calls of the source tree at v0.16.0 and now.
- **Bedrock stream exception frames** are classified from the `:exception-type` header only:
  - `throttlingException`: `rate_limit_error`.
  - `validationException`: `upstream_rejected`; it no longer touches routing health.
  - `modelTimeoutException`: `timeout_error`.
  - `serviceUnavailableException`: `overloaded_error` on Messages, `upstream_unavailable` elsewhere, as for the same exception in an HTTP response.
  - `internalServerException`, `modelStreamErrorException`, any other name (in any casing, including HTTP-path names such as `AccessDeniedException`) and an empty name: `upstream_unavailable`, a provider failure that counts against health and is not a client or configuration fault.
  - A frame with no string `:exception-type`, a `:message-type: error` frame, a corrupt frame and a modeled exception whose JSON payload has the wrong shape fail closed as `invalid_upstream_response`.

  Visible: the recorded execution carries the new code; span `error.type` and the telemetry error buckets (`request_telemetry::error_kind_of`) change for throttling (busy), Messages `serviceUnavailableException` (busy) and `modelTimeoutException` (timeout); a mid-stream `validationException` now renders as `invalid_request_error` for Messages clients (it was `overloaded_error`) and `upstream_rejected` for chat clients. Not changed: when the response is returned (a stream that fails before any content is still a `200` that ends in an error), failover (none after a stream is returned, with a test at `max_attempts=2` and `allow_ambiguous_failover`) and the settlement of every other failure. Mid-stream transport failures and the other streaming adapters' in-stream classification are unchanged ([known limitations](#known-limitations)).
- **Settlement of an in-stream rejection on a free price (all adapters).** A rejection that arrives inside a returned stream (before or after content, `upstream_rejected` or context length) no longer settles as a known zero on an all-free pricing-v3 price: usage stays unknown (NULL, not 0) and the reservation stays `unknown` with its hold, like the other in-stream failures. Such reservations raise `gateway_reservations_held{state="unknown"}` and nothing resolves them automatically. Only a rejection returned as an error before any stream keeps the known-zero rule (`governance::free_rejection`, now told whether a stream had been returned). OpenRouter's in-stream numeric 4xx codes could already settle as a zero on a free price; they no longer do.
- **Realtime sessions that now end differently** (#410): a client protocol violation or invalid UTF-8 now fails the session (`failed`, `invalid_request_error`, close 1002 or 1007) where it was `succeeded`/`stop` (idle) or `cancelled` (response in flight); a connection lost without a close frame is `cancelled` (idle: it was `succeeded`/`stop`) and no longer updates routing health. Reports and log views that count realtime sessions by outcome will see the shift.

## Security and verification

These change CI, the tests and the build rules, not the gateway's behaviour.

- **The distroless runtime base is refreshed** (from Dependabot #533, landed in #589). The `gcr.io/distroless/cc-debian13:nonroot` index digest moves from `sha256:cc66d222…` to `sha256:cb87acc5…` in both Dockerfiles, `APPROVED_RUNTIME` (`tests/supply-chain/lib.mjs`, `ci.yml`) and the regenerated job pin. The Rust 1.100 build image from the same Dependabot PR is held for its own change (#587).
- **CI's PostgreSQL service containers are pinned by digest** (#493): the `gateway-tests`, `gateway-special` and `browser` jobs ran `mirror.gcr.io/library/postgres:17-alpine` by tag; they now run it by the digest of the multi-architecture index the tag named on 2026-11-14. The supply-chain test requires a digest on every job `container:` and every `services.<name>` image, and refuses an expression there unless it is allowlisted with a reason (none is).
- **The supply-chain test pins what the image builds build** (#488). Every job that builds, publishes, signs, imports or tests an image (all of `image.yml`, `branch-images.yml`, `loadtest-image.yml`, `oci-import.yml` and `prune-dev-images.yml`, and `ci.yml`'s `staging-image` and `image`) is pinned whole in `tests/supply-chain/pinned-jobs.yaml`, with the local actions they use, so any change to such a job shows in review. Any other job that can write packages, id-token, attestations or contents must be pinned too, and other jobs may not log in, push, sign or create releases. The staging rehearsal's gateway image must stay the candidate under test, build steps may name only the two known Dockerfiles with a literal context, every action must be on an approved list, Compose `build:` sections are restricted, and `scripts/staging.py` refuses a key set twice or hidden control characters. The suite makes changes to builds visible and catches drift; it is not a boundary against a malicious pull request, and scripts that CI calls are outside it. Dependabot updates `docker/build-push-action` and `docker/setup-buildx-action` in a group of their own.
- **The egress client rule is enforced by the compiler** (#509, #569). Every outbound reqwest client starts from one constructor, `egress::client_builder` (redirects, implicit retries and ambient proxies off, egress resolver on), or `egress::pinned_client_builder` for approved local endpoints. Clippy's `disallowed-methods` and `disallowed-types` reject every other reqwest constructor and builder method that changes destination, proxy, redirect, retry, DNS or TLS trust, through aliases and re-exports, and `reqwest::Client`/`ClientBuilder` by name outside `egress_http.rs`. Production code holds clients only as `egress::HttpClient`, which has no `Default` and no conversion to or from a reqwest value, so a client from `Default`, `mem::take` or `unwrap_or_default()` (which passed Clippy and would have followed redirects and used ambient proxies; none was in use) is now a compile error. A source test (`syn`-based) keeps the lints switched on and holds `egress_http.rs` to an exact list of its contents. Limits: code not compiled in a Clippy run, other workspace crates, `build.rs`, `hyper`'s own client and the AWS credential chain's HTTP client are outside the rule ([verification](../verification.md#egress-client-rule); #606). The nine client call sites keep their timeouts and settings.
- **CI lints the build that ships** (#502). Clippy ran only with `--all-features`, so code compiled only without the `integration-tests` feature was never linted. `gateway-lint` now also runs `cargo clippy -p open-model-gateway --bins --lib --locked -- -D warnings`, and `tests/ci.test.mjs` requires the step. The one error it found, `ApprovedEndpoints::parse` being unused in the shipped build, is fixed by compiling it only for its test callers (production loads approvals through `from_env`). Test code built without the feature is not linted yet.
- **Randomness drawn without a generator's name is refused by Clippy** (#511). Library calls that draw randomness under other names (tungstenite's `generate_key`, rustls's `SecureRandom::fill`, `aead::Generate`, oauth2's and openidconnect's `new_random*`, tower's `HasherRng`) are `disallowed-methods` in `apps/gateway/clippy.toml`, each naming `crate::entropy` as the alternative; tests keep the list in step and pin the crates those paths name to their reviewed versions in `Cargo.lock`. The upstream realtime handshake is the one sanctioned call (its `Sec-WebSocket-Key` is a protocol nonce). Nothing else was drawing secrets this way. The whole-file entropy scan from v0.16.0 (#506) is unchanged.
- **CI scans for committed secrets, and `<name>.env` files are ignored** (#596). `ci.yml` has a new read-only job, `secret-scan`, that runs gitleaks 8.30.1 (a pinned release fetched against its published SHA-256, no third-party action) over every commit of a pull request or push and the checked-out tree, with canaries that must be detected first so a broken scanner fails the job. The log shows rule, file, line and commit for a finding, never the matched text. `.gitleaks.toml` extends the default rules with four of the gateway's own and allowlists known fixtures one by one. `scripts/secret-scan.py` runs the same scan locally as an optional pre-commit hook or over the history of `HEAD`. `.gitignore` and `.dockerignore` now ignore `*.env`, `*.env.*`, `.envrc`, `.netrc`, `.pgpass`, `.git-credentials` and `.local/` at any depth. Limits are listed in [Secret scanning](../verification.md#secret-scanning): pattern scanners miss unusual formats, the scan runs after the push (rotation is the remedy for a finding), and the config and tests come from the same pull request. **Owner action:** `secret-scan` is a new check and is not required by branch protection until added; `image` does not depend on it. GitHub's own secret scanning and push protection are repository settings.
- **The shell tests read source the way JavaScript does** (#576, #498). `tests/bash-preflight.test.mjs` now joins line continuations and decodes escapes before matching, reads every `.js`/`.mjs`/`.cjs`/`.jsx`/`.ts`/`.mts`/`.cts`/`.tsx` file git would commit under `tests/`, and fails on a file under a `node_modules` path there (the suite therefore needs `git` and a git work tree). An allowed shell line is excused only as often as it is listed. The patterns themselves are unchanged; the spellings they still miss are #597. Test-only.
- **The threat model describes today's management authentication** (#514). `docs/threat-model.md` named `require_session`, a function that no longer exists. It now describes `identity::authenticate_management` (one credential family per request, refusal of both together and of inference keys) and cites the test that sends a real inference key to every management route.

## Operations and documentation

- **Branches and release candidates are tested on the Spark k3s platform, with arm64 branch images** (#599). The owner's dedicated test cluster (single node, arm64, namespace-scoped credentials and a shared quota) replaces the homelab's `dev-omg` for branch and candidate runs. `branch-images.yml` builds each commit on a native runner per architecture and tags `dev-<sha12>` (linux/amd64, unchanged) and `dev-<sha12>-arm64` (linux/arm64); `dev-<sha12>` is now only published together with the arm64 tag, and `prune-dev-images.yml` prunes the `-arm64` tags too. Release images were already multi-architecture. `scripts/spark-env.py up|status|forward|creds|down` runs a branch, commit or release tag there in the order the invariants require (role Secrets, a CloudNativePG PostgreSQL 17 Cluster and the chart's migrate Job with the runtime grants, `bootstrap-demo`, then the gateway), pinned to the image digest after checking that it has linux/arm64 and was built from the ref's commit. It passes the Spark kubeconfig to every `kubectl` and `helm` call, refuses to run unless that file names the Spark server, and touches only namespaces named `<base>-omg-<name>`. The demo is passwordless and reached only through a loopback `kubectl port-forward`; it proves the chart's CloudNativePG Cluster and migrate Job, migrations, grants and demo flows, not multi-replica behaviour ([known limitations](#known-limitations)). Files are in `deploy/spark`; `npm run test:demo`, `npm run test:supply-chain` and `npm run test:helm` cover the script, the manifests and the chart path. No gateway behaviour changes.
- **The example monitoring files cover accounting failures** (#528). `deploy/monitoring/prometheus-rules.yml` now has `GatewayAccountingFailures` (warning) and `GatewaySettlementAccountingFailures` (critical: the settlement stages, whose reservations stay held), linking to [Accounting failures](../operations.md#accounting-failures). Each counts the 10-minute `increase()` per stage and cause plus any series new within 10 minutes, so the first failure on an instance is seen; missing data cannot fire them. `grafana-dashboard.json` gains an "Accounting failures by stage and cause" panel. A new `npm run test:monitoring` (run in CI) checks that the rules and dashboard name only exported metric families and labels. `docs/operations.md` no longer says the example rules are validated with `promtool`; nothing runs it (#584).

## Known limitations

Carried forward or found this cycle and not fixed here:

- **An `accounting_unavailable` from an internal consistency check has no database cause** and is still not counted in `gateway_accounting_failures_total`.
- **A request on a connection the upstream closes at that instant is still lost** (#483, #611): the gateway resends nothing, so the caller sees a failed request. The pool idle timeouts are conservative constants, and the cloud values (20 s, S3 3 s, export 10 s) are unverified guesses to tune from the counter; a local server whose keep-alive is shorter than 4 s (gunicorn defaults to 2 s) still loses requests, and there is no per-endpoint setting yet. `s3` and `export` have no request count, so a loss rate cannot be computed for them (#611).
- **In-stream provider errors outside Bedrock are classified as invalid upstream output** (#614): in the Anthropic, OpenAI (chat, Responses and local profiles) and OpenRouter adapters an error that arrives inside a stream is classified differently from the same error as an HTTP response, so a route that keeps failing in-stream never trips its circuit breaker for chat and Responses clients. A transport failure in the middle of a Bedrock stream (reset, truncated or corrupt frame) is also `invalid_upstream_response` and does not count against health. Both wait on an operator decision.
- **A job the provider accepted and then failed settles as a known zero on an all-free price** (#616): video and batch jobs map the provider's failed state to `upstream_rejected` with default usage, and an OpenRouter non-stream response with an embedded 4xx error does the same. The amount is zero either way; usage is recorded as 0 tokens rather than unknown.
- **Spark test platform scope** (#601): it runs the one-pod passwordless demo, so nothing on a cluster exercises the chart's real multi-replica Deployment (Pooler, NetworkPolicy, rolling update, lease takeover across pods). Those are covered by the PostgreSQL integration tests and the Compose multi-replica harness only.
- **Assurance gaps in the checks themselves** (no effect on a running gateway):
  - #597: the no-direct-shell test's line patterns miss many literal spellings of a shell start; the suggested fix is an import rule.
  - #603: secret scanning has no scheduled full-history scan, does not open archives, reads its config from the pull request under test, and skips commit messages and some paths.
  - #606: the egress client rule does not cover other workspace crates, `build.rs` or `hyper`'s own client.
- **Live provider, SSO and production acceptance have not been repeated for this release.** Live SCIM acceptance passed once, on v0.9.1 (#60).

## Upgrade

From v0.16.0 (or v0.15.x) there is no migration and no grant change: deploy v0.17.0 by verified image digest, as a normal rolling update. Update any log filter or query that matches the two [moved targets](#behaviour-changes) exactly, and any dashboard or alert that lists accounting-failure stages explicitly. Expect new connections to cloud providers when requests are more than 20 s apart (3 s for S3, 4 s for local endpoints).

From an earlier release, follow the upgrade steps of each release in between, in order; the last migration is 0080 in [v0.15.0](v0.15.0.md#upgrade). v0.17.0 can be the image you finish on: it serves the same schema as v0.15.0, v0.15.1 and v0.16.0.

Rollback to v0.16.0 is a redeploy of its image; nothing in the database changes. The realtime close codes 1002 and 1007 and the new stages and metric disappear with it.
