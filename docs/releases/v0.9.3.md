# Open Model Gateway v0.9.3

A maintenance patch after [v0.9.2](v0.9.2.md), covering an opt-in Kubernetes database durability policy and test-only accounting fault signatures.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## Kubernetes

- Add explicit `cnpg.cluster.synchronous` values rendering CNPG's native
  `spec.postgresql.synchronous`, including `failoverQuorum`, with schema and
  incompatible-policy validation. Existing default rendering remains two instances and
  legacy min/max sync `1/1`; no installation changes policy automatically. Production
  guidance now recommends three instances, `any`/`1`, `dataDurability: required` and
  `failoverQuorum: true`, explicitly trading write availability for durability. With two
  instances, required writes cannot resume after promotion until a standby returns.
  See [upgrade guidance](../kubernetes.md#production-durability-policy-391),
  [#149](https://github.com/ncecere/open-model-gateway/issues/149) and
  [#391](https://github.com/ncecere/open-model-gateway/issues/391). Cluster failover
  acceptance and production rollout remain separate operator-controlled work.

## Verification

- The #391 proof-run comparison reports **16 lost acknowledged accounting writes** out of 10,674 successful requests on primary failover with the legacy two-instance setup. With three instances, `dataDurability: required` and `failoverQuorum: true`, the measured run lost **0** out of 11,416, with an approximately **34-second write outage** and a later approximately **5-second blip** as the old primary rejoined. The three-instance run used reduced data/WAL volumes (2 Gi / 1.5 Gi, `max_wal_size` 1 GB); these are bounded measurements, not a universal durability or availability guarantee.
- Test-only fault-signature tests from PR #388 pin distinct diagnostics behind `accounting_unavailable` for pool exhaustion, lock/statement timeouts, backend termination and finalization deadlines. Production behavior is unchanged; the historical #370 cause remains unresolved.

## Upgrade

From **v0.9.2**, replace the image and chart, using the normal drain procedure only after qualification and deployment approval. The schema is unchanged: the latest migration remains **0067**, with **66 migration records**. There are **no new migrations or runtime-grant changes**. Adopting the durability policy is an explicit, operator-controlled values change; follow [the production durability policy guidance](../kubernetes.md#production-durability-policy-391), including the transition window and applied-state verification. Do not reset or recreate an existing database, run a down migration or bootstrap implicitly.

From an older release, also follow the [v0.9.2 upgrade instructions](v0.9.2.md#upgrade) and their linked requirements. Publication verification and readiness remain separate from production activation and authenticated/provider acceptance.
