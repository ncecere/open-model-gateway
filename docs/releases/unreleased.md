# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.16.0](v0.16.0.md). They become the next release's notes.

## Fixes

- **`serve` releases its job leases when start-up fails after taking them** (#527). A start-up failure after the background-job leases were taken (a busy public or metrics port, or the audit export state check) used to exit with every lease still held, so another replica could not run those jobs until the terms expired (up to 30 seconds). Every such failure now stops renewing and releases the leases this process holds, as graceful shutdown does, then returns the original error. `GATEWAY_PARTITIONS_AHEAD_MONTHS` is now checked before any lease is taken, so a refused value never holds one. Each release is bounded to 2 seconds, on both paths; a release that fails or times out is logged and its term still ends at its expiry.
- **A realtime client that breaks the WebSocket protocol or drops the connection no longer ends as a clean stop** (#410). Every browser socket error other than a size refusal was treated as the client leaving, so with no response in flight an invalid UTF-8 text frame, a stray continuation frame or a connection lost without a close frame finished the session as `succeeded` with finish reason `stop`. Now a text frame or close reason that is not UTF-8 gets an `invalid_payload` error event and close 1007, and any other protocol violation reported by the WebSocket parser a `protocol_error` error event and close 1002. Both fail the session with `invalid_request_error`, idle or mid-response (a response in flight keeps its hold as unknown cost, as before; it used to be recorded as `cancelled`). A connection lost without a close frame (a reset, an I/O error), or a client the gateway can no longer write to, is `cancelled`, like a dropped HTTP request; as with those, an idle drop no longer updates routing health (it used to record a healthy, non-provider result). Only a close frame with no response in flight is still `succeeded`/`stop`. The OpenAPI document lists the two new close codes.

## Security and verification

- **CI's PostgreSQL service containers are pinned by digest** (#493): the `gateway-tests`, `gateway-special` and `browser` jobs in `ci.yml` ran `mirror.gcr.io/library/postgres:17-alpine` by tag; they now run `postgres:17-alpine@sha256:d3244e8c…`, the multi-architecture index the tag named on 2026-11-14 (the same digest as on Docker Hub). The supply-chain test now requires a digest on every job `container:` (string or `image:` mapping) and every `services.<name>` image, and refuses an expression there unless it is allowlisted with a reason (none is).
- **The supply-chain test pins what the image builds build** (#488). It read the repository's Dockerfiles but did not tie them to what the workflows and Compose files build. Every job that builds, publishes, signs, imports or tests an image (all of `image.yml`, `branch-images.yml`, `loadtest-image.yml`, `oci-import.yml` and `prune-dev-images.yml`, and `ci.yml`'s `staging-image` and `image`) is now pinned whole in `tests/supply-chain/pinned-jobs.yaml`, with the local actions they use, so any change to such a job, a step added before the build or after the scan included, shows there in review; the repository files those jobs run are a listed set (`PINNED_JOB_INPUTS`), changes to which are reviewed as changes to the image jobs. Any other job that can write packages, id-token, attestations or contents (by its own, the workflow's or the default permissions) must be pinned, and other jobs may not log in, push, sign or create releases. The staging rehearsal's gateway image must stay the candidate under test, in `deploy/staging/compose.yaml`, its overlays and `staging.env.example` (where `scripts/staging.py` now refuses a key set twice); the pinned jobs start Python with `-I`, and the npm scripts they run are pinned with their exact text, with no pre/post or install script or `.npmrc` around them. `staging.env.example` may set only its listed keys and no file the rehearsal reads may hide a line behind a control character or Unicode line separator; `staging.py` refuses both a key set twice and those characters. A build step must name one of the two known Dockerfiles through a literal context of the checkout, with no `target`, `build-contexts` or `BUILDKIT_*` build argument, and its inputs may use only the job's matrix and the runner's temporary directory (`image.yml` now takes its cache scope from the matrix, not from env an earlier step could rewrite). `setup-buildx-action` takes only the pinned BuildKit image. Every action must be on an approved list; Docker container actions, local actions outside `.github/actions` and container options that reach the host are refused. Compose `build:` sections take only `context` and `dockerfile`, with no `include`, `extends` or tracked `.env`. Other jobs' run steps are read for builds, builder or endpoint switches and unchecked Compose files. The Dockerfile walker also finds `Dockerfile.*`, `*.dockerfile` and `Containerfile*` in any case, and the Rust build image is pinned to its whole approved reference. The suite makes changes to builds visible and catches drift; it is not a boundary against a malicious pull request, and scripts that CI calls are outside it. The new checks live in `tests/supply-chain/`; Dependabot updates `docker/build-push-action` and `docker/setup-buildx-action` in a group of their own.
- **The egress client rule is enforced by the compiler** (#509). Every outbound reqwest client now starts from one constructor, `egress::client_builder` (redirects, implicit retries and ambient proxies off, egress resolver on), or `egress::pinned_client_builder` for approved local endpoints; the nine production sites keep their own timeouts and settings. Clippy's `disallowed-methods` rejects every other reqwest constructor, `reqwest::get`, and every builder method that changes destination, proxy, redirect, retry, DNS or TLS trust outside `egress.rs`, through aliases, renamed imports and re-exports such as `openidconnect::reqwest::Client`, which the old text scans missed. Those scans are removed. A source test keeps the rule switched on: it parses every source file with `syn` (so comments inside an attribute, raw identifiers and nested `cfg_attr` do not hide a lint switch), allows the lint's switch-off only at the sanctioned sites, ties each sanctioned switch-off to its own function, fails closed on attributes and macro calls it cannot read (macro metavariables, unparsable attributes), refuses `#[path]` outside `src/` or not a literal and `include!` in any spelling, and refuses Cargo lints tables, `.cargo/config`, a second Clippy configuration and `CLIPPY_CONF_DIR`, `rustflags`, `--cap-lints` or `-A warnings` in CI and the local gate scripts, in any case. Only the local-endpoint approval can create the destinations a pinned client connects to. New tests check both constructors over real HTTP. Limits: `Client::default()` is not caught (Clippy cannot name a trait impl's method); code not compiled in a Clippy run (#502), code from external macros or derives, lint levels produced by a procedural macro, Cargo or Clippy configuration outside the repository, clients built inside dependencies and non-reqwest transports are outside the rule. No gateway behaviour changes.
- **An allowed shell line in a test file is excused only as often as it is listed** (#498). `tests/bash-preflight.test.mjs` lists, per file, the exact lines that name a shell without starting one; a listed line used to be excused any number of times in its file, so a second copy could feed a real spawn. The list is now a multiset: each listing excuses one occurrence, and a line that appears more often than it is listed, or fewer times (but at least once), fails, naming the file, the line and both counts; a listed line that no longer appears fails as gone. No file needed a duplicate entry. A shell name put together at run time is still not seen.
- **CI lints the build that ships** (#502). Clippy ran only with `--all-features`, so code compiled only without the `integration-tests` feature was never linted. The `gateway-lint` job now also runs `cargo clippy -p open-model-gateway --bins --lib --locked -- -D warnings` on the default-feature library and binary, and `tests/ci.test.mjs` requires the step. The one error it found, the local-endpoint approval parser `ApprovedEndpoints::parse` being unused in the shipped build, is fixed by compiling it only for its test and integration-test callers (production loads approvals through `from_env`, which needs the detailed refusal). Test code built without the feature is not linted yet. No gateway behaviour changes.
- **Randomness drawn without a generator's name is refused by Clippy** (#511). The entropy source scan finds generators by name (`rand`, `OsRng`, ...), so library calls that draw randomness under other names passed it: tungstenite's `generate_key` and `IntoClientRequest` (which fills `Sec-WebSocket-Key`), rustls's `SecureRandom::fill`, key exchange and session ticketers, `aead::Generate` (`Key::<Aes256Gcm>::generate()`), oauth2's `CsrfToken::new_random*` and `PkceCodeChallenge::new_random*` (re-exported by openidconnect), openidconnect's `Nonce::new_random*`, tower's `HasherRng` and `RandomState`. They are now `disallowed-methods` in `apps/gateway/clippy.toml`, resolved by path (aliases and re-exports included), each naming `crate::entropy` as the alternative. A test keeps `clippy.toml` and the test's list in step, and another pins the crates those paths name to their reviewed versions in `Cargo.lock`, so a bump forces a review. What Clippy cannot name joins the name scan: the `secure_random` field, `RandomState` and `HasherRng` through `Default`, pgcrypto's `gen_random_bytes` in SQL, and `/dev/urandom`, `/dev/random` and `/proc/sys/kernel/random`, with paths normalised and `concat!` literals joined. The upstream realtime handshake (`handshake_request`) is the one sanctioned call: its `Sec-WebSocket-Key` is a protocol nonce. Nothing else was used: sign-in already draws OAuth state, the nonce and the PKCE verifier from `entropy` and passes them to the `new` constructors. `Uuid::new_v4()`/`now_v7()`/`new_v7()` and SQL `gen_random_uuid()` stay allowed for identifiers and fencing values, never secrets (threat model KEY-10, by policy). Limits: std `RandomState` through a generic `Default`, map iteration order, paths built at run time, randomness inside dependencies (tungstenite's handshake keys and masks, rustls's key exchange), UUIDs or weak values used as secrets, and code Clippy does not compile. No gateway behaviour changes.

## Documentation

- **The threat model describes today's management authentication** (#514). `docs/threat-model.md` named `require_session`, a function that no longer exists, and said management reads only the session cookie. It now describes `identity::authenticate_management`: one credential family per request (a browser session with Origin and CSRF checks, or an admin token as a bearer credential), refusal of both together, and refusal of inference keys. It also cites the test that sends a real inference key to every management route.

## Operations and documentation

- **The example monitoring files cover accounting failures** (#528). `deploy/monitoring/prometheus-rules.yml` did not use `gateway_accounting_failures_total{stage,cause}` (added in v0.16.0, #389). It now has `GatewayAccountingFailures` (warning: route lookup, pool acquire and storage stages) and `GatewaySettlementAccountingFailures` (critical: the two settlement stages, whose reservations stay held), linking to [Accounting failures](../operations.md#accounting-failures). Each counts the 10-minute `increase()` per stage and cause plus any series new within 10 minutes, so the first failure on an instance is seen; the critical one fires on it, the warning after 5 minutes pending. Missing data cannot fire them. `docs/operations.md` no longer says the example rules are validated with `promtool`; nothing runs it (#584). `grafana-dashboard.json` gains an "Accounting failures by stage and cause" panel in the accounting row. A new `npm run test:monitoring` (run in CI) checks that the rules and dashboard name only exported metric families and labels, that panel ids are unique and panels do not overlap, and that the alerts and panel stay in place. No gateway behaviour changes.
