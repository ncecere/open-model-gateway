# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.8.0](v0.8.0.md). They become the next release's notes.

## Development HTTP telemetry exports are loopback-only after DNS (#313)

**Behavior change for development installations.** Plain-HTTP OTLP traces, audit OTLP logs and audit webhooks (allowed only with `GATEWAY_ENV=development`) now connect only to canonical loopback addresses after name resolution, including IPv4-mapped loopback. If any resolved address is not loopback, the whole answer is refused, even when other answers are loopback or the address is covered by `GATEWAY_EGRESS_PRIVATE_ALLOW`. Literal non-loopback HTTP endpoints are refused before any connection. HTTPS exports keep the general egress policy, and production (non-development) installations are unaffected: they never allowed plain HTTP. To export to another host, use HTTPS. See [operations](../operations.md#outbound-connections).

## Alert webhook dashboard (#45, slice 3)

**Admin › Settings › Alerts › Webhooks** now manages saved signed receivers: create disabled, enable/disable, edit names and signing references with optional bounded previous-key overlap, confirm deletion, send fixed single-attempt tests, and inspect bounded delivery status/history. URLs remain immutable; signing secrets are never displayed. Auditors see redacted read-only status without mutating controls, URLs or references. Test throttling explains the limits without a countdown or automatic retry. Receiver guidance covers HMAC-SHA256, timestamp verification and durable delivery-ID deduplication. All webhook audit codes already have dashboard labels.

Adds Vitest contract/component coverage and a real-gateway Playwright journey with a disposable signed loopback receiver and 1440/390-width screenshots. No backend, migration, privilege or dependency changes. See [dashboard administration](../alerts.md#dashboard-administration-slice-3).

## Deployment configuration impact previews (#85)

Platform Admins can review deployment enable/disable changes before confirming: the allowlisted state diff, serving routes gained/lost, last-serving-route warnings and bounded affected Team/Project metadata. The new browser-only `POST /api/v1/platform/deployments/{id}/configuration/preview` requires Origin/CSRF and denies all admin tokens. It shares the typed deployment operation with existing PATCH/DELETE, reads one read-only primary snapshot and writes no configuration, audit, notifications or cache state. Personal effects are omitted, including from counts; no foreign personal IDs, owners, keys or request details are exposed.

No migration or new runtime privilege is required. `expected_revision` is the existing monotonic **catalog configuration version**, not a new deployment revision. It is an observation token only: existing apply behavior, statuses and audit remain unchanged and do not enforce preview preconditions. History/per-target revisions, rollback and bulk actions remain later slices. See [management API](../management-api.md) and [platform administration](../platform-administration.md).

## Claude Code Messages frontend and Anthropic fidelity (#70, deliveries 1–2)

`/v1/messages`, including `?beta=true`, parses Claude Code's field grammar through the ordinary workspace/key, admission and per-attempt accounting path. **Claude Code now works on native Anthropic routes within the [documented subset](../protocol-matrix.md#claude-code-field-rules).** Native routes preserve block-form system prompts and cache controls (including 1-hour TTL), thinking controls, effort, signed/redacted assistant history, context management, deferred tools, task budgets and `tool_result.is_error` (#341 Anthropic part). Beta values form an open list and are forwarded verbatim; none are added. Bounds are 16 header values of 1024 header-safe ASCII bytes and 32 nonempty tokens total. A reviewed denylist blocks only `context-1m-`, `code-execution-`, `web-search-`, `web-fetch-`, `files-api-`, `mcp-client-` and `computer-use-` prefixes (case-insensitive) for unmodeled pricing or unsupported capabilities. Refusals use Anthropic's exact `Unexpected value(s)` message so Claude Code can retry without rejected betas. `extended-cache-ttl-*` passes through, with the 1-hour body TTL still checked by the cache pricing gate. Operators can use `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` to disable experimental features. The beta-refusal message is a documented exception to the ordinary 1 KiB error cap: it echoes only already-bounded client beta names (at most 17 KiB of text), never upstream diagnostics or inference telemetry. Validated native response block order and thinking/signature deltas are preserved in JSON and streams.

Native Anthropic also accepts bounded base64 PNG/JPEG/GIF/WebP images in messages and tool results (5 MiB decoded per image, 20 images, still subject to the 2 MiB HTTP body cap). Remote URL sources are refused before dispatch. Translated providers retain their previous rules, including image refusals and 501 for error-marked tool results. Structured output and strict tools remain refused; OpenAI-style reasoning/structured-output mapping follows in delivery 3. Server tools remain refused because their extra charges are unpriced. `metadata.user_id` remains a gateway-only client label; caller credentials and arbitrary transport headers are never forwarded.

**Cache pricing compatibility:** native cache-enabled requests now require a pinned v2/v3 price explicitly pricing cache reads and every requested write TTL (absent TTL means 5 minutes). Repeated prompts can produce cache hits regardless of write TTL. Missing prices, v1 aggregate-only pricing and unknown/not-applicable required categories refuse with 400 naming `cache_control` before any reservation or upstream call. Operators must publish compatible immutable prices, including the applicable 5-minute/1-hour premiums (normally 1.25×/2× base input). A finite conservative hold is required even without a workspace budget. Existing bounds cover the full input ceiling in each priced cache category plus output; settlement still charges disjoint observed counts without charging write aggregates twice. Cache-enabled batch lines use gateway-run per-line admission instead of native Message Batches until native plans carry TTL requirements. No historical prices, reservations or usage are rewritten.

Messages error mapping now returns `prompt is too long` on context overflow (400), overload as 529 and rate limits as 429, without returning upstream diagnostics. The Messages output cap rises to 16 MiB; `max_tokens` remains the unchanged output reservation, including thinking. No migration, privilege change, prompt logging or client-credential forwarding is introduced. [Setup](../claude-code.md) explains configuring public model names explicitly; discovery only lists ids containing `claude`. Token counting and real Claude Code/provider acceptance remain separate deliveries; this note does not claim live-client acceptance.

## OIDC group-mapping preview (#89)

Platform Admins can now review a group-mapping change before saving it. `POST /platform/oidc/group-mappings/preview` (a new or edited proposal) and `POST /platform/oidc/group-mappings/{id}/preview` (edit or delete; an omitted body or `{"delete":true}` previews the delete) are a bounded, read-only dry-run, Platform Admin and browser session only, that never writes, audits or bumps a config version. It reuses the same matching predicates the real reconciliation runs (`lifecycle::group_match_predicate`/`group_enabled_for`/`group_target_predicate`), so the preview and the write path it previews can never disagree. Validation matches create/update exactly, including the `422` unknown-field refusal, and roster matching is exact (never case-folded). Covers platform roles and shared (Team/Project) membership only; never personal-workspace data.

Two things are reported separately, after review feedback: `immediate` is what the real PATCH/DELETE revokes synchronously the moment it commits -- every grant the existing mapping currently produces, unconditionally, even a same-role rename, plus consequent suspensions and (permanent, never-reactivating) key revocations, and whether the write would be refused for stranding the last admin. `diff` (`platform_role_gained/lost`, `workspace_membership_gained/lost`, 200 rows per list, `counts`/`truncated`) is the net *effective* role change by precedence across every active grant once a later sign-in/SCIM reconciliation catches up, including downgrades (a manual `member` grant outliving a deleted group `admin` mapping) and in-grace reactivations; a user already entitled through another source never appears to gain anything. Beyond a separate roster-evaluation cap the whole response is `complete:false` with a warning. `digest` (an existing mapping only) replaces `expected_revision` (there is no per-mapping configuration version): the new optional `If-Match` header on the PATCH/DELETE routes (additive) refuses a mapping changed since review with `412 reason:"precondition_failed"`.

The SSO groups page's Create/Edit/Delete mapping flows show a "Review changes" dialog (the immediate/diff sections, membership basis, warnings) before the existing save path runs, sending the reviewed digest as `If-Match` and reopening a fresh review on a `412`. See [identity](../identity.md#authentication-is-not-entitlement) and [management API](../management-api.md#session-inventory-and-directories).

## Signed alert webhook delivery (#45, slice 2)

Saved enabled receivers now receive `omg.alert.v1` envelopes signed with HMAC-SHA256 over timestamp plus exact queued bytes, with optional dual signatures during the saved overlap (at most 24 hours). Signing variables are resolved only by the dedicated allowlist and require 32–4096 bytes. Short destination-before-outbox claims use generation checks and 90-second owner/token leases; fenced completion preserves terminal outcomes. Dispatch is bounded to 25 steps, a 60-second claiming budget and a 70-second hard timeout, with 1m/5m/30m/2h backoff and at most five attempts in 24 hours. Only connection failures, timeouts, 408/429 and 5xx retry. TLS, credentials, redirects and policy refusals are terminal. Waiting counts exclude stale generations. Fixed-label attempt/delivery metrics and oldest-waiting age expose failures without destination identifiers. Receiver guidance requires constant-time signatures, ±300-second timestamp checks, header/body delivery-id equality and durable deduplication. Crash-after-acceptance duplicates remain possible; there is no replay endpoint. No new migration or privilege is needed beyond 0057. The dashboard and browser acceptance journey are described in slice 3 above.

## Runtime TEMP privilege revoked (#295)

**Upgrade:** this change adds no schema migration or runtime privilege. The owner/migrator's privileges and all unrelated databases are unchanged. `serve` never migrates or applies grants automatically. ## Webhook metrics independent of retained terminal history (#310)

The webhook collector now counts waiting, leased and recent terminal rows in separate branches of one statement, using one statement-start database clock for the strict 24-hour completion cutoff. Waiting counts and oldest age still exclude stale enable generations; leased counts do not. All six state series, the metrics lease-holder rule, OTLP **Traffic** classification, the two-second deadline and visible collection failures are unchanged. No hot-path counter or new lock is introduced. Work follows the active queue and recent completions plus index traversal, rather than scanning retained terminal history; a large active/recent set can still exceed the deadline.

**Upgrade:** explicitly run **0062_alert_webhook_metrics_index** with migrator credentials before starting the new binary. It builds the terminal-only `(completed_at) INCLUDE (state)` index `alert_webhook_outbox_completed` with `CREATE INDEX CONCURRENTLY`, outside a transaction. There is no data backfill, rewrite or replay, and no runtime grant/verifier change is needed for an index. If interrupted, rerun `migrate`: it drops an invalid leftover with standalone `DROP INDEX CONCURRENTLY`, then rebuilds it, as for 0054/0056. Concurrent build/recovery can wait for older transactions; `serve` never migrates. Readiness still requires the exact embedded versions/checksums, now including 0062; version gaps are allowed, not treated as missing embedded migrations.

The opt-in real-PostgreSQL harness seeds 200k then 1M old terminal rows, prints the exact collector SQL and `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` at both sizes, and asserts buffer/tuple bounds and exact counts. ## Local-upstream approvals in special-use ranges are now refused (#203)

**Breaking change for affected installations.** `GATEWAY_LOCAL_UPSTREAMS` approvals that pin an address in one of the ranges below are refused at startup. v0.8.0 only warned. An installation whose approvals are all public or RFC 1918 (private) addresses is not affected and needs no action.

| Range | Category |
|---|---|
| `198.18.0.0/15`, `2001:2::/48` | benchmarking |
| `192.0.0.0/24` | IETF protocol assignments |
| `192.88.99.0/24` | deprecated 6to4 relay |
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`, `3fff::/20` | documentation |
| `fd00:ec2::/32` (all of it, including what was accepted besides `fd00:ec2::254`) | AWS IPv6 metadata range |

These are the ranges the outbound egress policy already refused for every other client; approvals now follow the same table (`special_use.rs`), so the two cannot drift. The rules are over both schemes: the `fd00:ec2::/32` range was also accepted over plain HTTP like a private address, and is refused there too. An address that carries an IPv4 address (IPv4-mapped `::ffff:a.b.c.d`, compatible `::a.b.c.d`, 6to4, Teredo) is judged by the IPv4 address it carries, so `2002:c612:1::1` (6to4 of `198.18.0.1`) is refused as well. NAT64 (`64:ff9b::/96`) stays refused, as before. Every other address keeps its exact decision: public over HTTPS, RFC 1918 and unique-local over HTTP or HTTPS, loopback only with `GATEWAY_ENV=development`, and the same unconditional refusals as before (unspecified, link-local, multicast, broadcast, carrier-grade NAT, cloud metadata).

**How `serve` fails.** `open-model-gateway serve` stops before it connects to the database and exits with status 1, naming every affected approval (host, pinned address and category) and the setting, for example:

```
Error: GATEWAY_LOCAL_UPSTREAMS: refused approval(s), each pins an address in a range the gateway never connects to: host models.internal pins 198.18.0.1 (category: benchmarking). Change each approval's address to a public or RFC 1918 (private) address, or remove the approval (#203; see the release notes).
```

No credential can appear in it: the message contains only the URL's host, the pinned address and a category label (an approval URL cannot carry credentials; one that does is rejected as invalid). Only `serve` loads approvals; `migrate`, `grants` and the other commands are unaffected. A replica that fails this way never answers `/health/ready`, so a rolling deployment keeps the old replicas until you fix the setting.

**Check before you upgrade:**

1. Read `GATEWAY_LOCAL_UPSTREAMS` (every approval's `addresses`) against the table above.
2. If you run v0.8.0, look for the startup `WARN` it logs per affected approval (host and category), or `GET /health/ready`: `checks.local_upstream_approvals` is `"warning"` when any approval is affected. Stay on v0.8.0 until that is `"ok"`.

**What to change:** replace the approval's address with the real address of the model server, an ordinary public address or an RFC 1918 one (for example the `10.x` address of the host), or remove the approval. If you remove an approval, provider connections that use its endpoint can no longer be saved or used until they point at an approved endpoint; re-point or disable them first. Change `GATEWAY_LOCAL_UPSTREAMS` in the deployment's configuration before rolling out the new release.

**`/health/ready` is unchanged in shape.** `checks.local_upstream_approvals` stays in the response and is now always `"ok"`: the warning phase has ended, because an affected approval stops startup instead of being reported. It is kept so dashboards and alerts that read it keep working; do not rely on it for anything beyond "this replica started". It never affected the `ready`/`not_ready` decision and still carries no endpoint names.

Removed: the v0.8.0 startup warning (it can no longer apply). See [provider adapters](../provider-adapters.md#approve-local-endpoints-out-of-band), [operations](../operations.md#health-endpoints) and the threat model (EGR-3).

## Bounded API-key issuance (#253, slice A)

Creating or rotating an API key now counts in a rolling 24 hours against two budgets: the holder's (a member, or a service account) and the workspace's. Defaults are **50 per holder and 500 per workspace**; both are editable on the workspace-type default, platform per-workspace override and (tighten-only) workspace limits, from 1 to 10,000. If neither the override nor the type default sets a value, the 10,000 ceiling applies; nothing is unlimited. Personal workspaces use the type default and any platform override. A spent budget refuses the request with `429`, `reason:"key_issuance_limit_exceeded"`, a `Retry-After` header and `scope`, `operation` and `retry_after_seconds`. Authorization and validation errors still come first, the body carries no amounts, and nothing is audited for a refusal (it is counted in `gateway_key_issuance_refused_total{scope,operation}`). Raising a limit admits at once, and lowering one never revokes keys.

New `GET /workspaces/{ws}/key-issuance` returns the caller's budget (and, for workspace admins, the workspace's). The limits editor gains two rows, and the API keys page shows "X of Y issued in the last 24 h" and explains a spent budget instead of failing at Create. Counting uses the existing workspace lock and the append-only `api_keys` table: no counter rows and no new lock.

**Override semantics:** on a platform override these two limits behave differently from the others: a field that is set replaces the type default, and an empty one **inherits** it (it is not "no limit"). So an override written by a replica that predates this release, during a rolling upgrade, never loosens a workspace; set an explicit value (up to 10,000) for more.

**Upgrade:** migration **0053_key_issuance_limits** adds the six policy columns (type defaults 50/500) and makes `api_keys.created_at` default to `clock_timestamp()`; its brief ALTER locks are the only locks it holds. **0054_key_issuance_index** builds `api_keys_workspace_created` with `CREATE INDEX CONCURRENTLY` outside a transaction, so neither key authentication nor key writes are blocked while it builds. If that build is interrupted, rerun `migrate`: before running migrations it drops the invalid leftover index with `DROP INDEX CONCURRENTLY` (a standalone statement, so nothing is blocked), and 0054 builds it again. `grants apply` now grants the runtime role `INSERT` on explicit `api_keys` columns that exclude `created_at`, so a key cannot be backdated out of the window. Run `migrate` and `grants apply` with migrator credentials first; `serve` never does either. Replicas still on the previous binary ignore the columns, so issuance is unenforced only during the rolling-upgrade overlap. Fair alert dispatch (slice B) is described below.

**Operating `migrate`:** `migrate` and `grants apply` now take their session lock by polling `pg_try_advisory_lock` (about every 100 ms) instead of blocking in `pg_advisory_lock`, so a second migrator (or a retried Job) waits without holding a transaction open; a blocked lock call would have deadlocked against the concurrent index build. `CREATE INDEX CONCURRENTLY` (and the recovery's `DROP INDEX CONCURRENTLY`) wait for every transaction older than themselves and there is no `lock_timeout`, so a session left idle in transaction stalls `migrate` until it ends. Find it with `SELECT pid, usename, state, xact_start, left(query, 80) FROM pg_stat_activity WHERE state IN ('idle in transaction', 'idle in transaction (aborted)') ORDER BY xact_start;` and end it with `SELECT pg_terminate_backend(<pid>);` (or fix the client); `migrate` then continues. `migrate` is safe to cancel and rerun.

See [governance](../governance.md#key-issuance), [governance API](../governance-api.md) and [management API](../management-api.md).

## Fair alert dispatch (#253, slice B)

Alert email slots are now shared fairly across workspace buckets, plus one bucket for installation-scope events. Each tick prefers the due bucket served least so far, then the least recently served across ticks (never-served first), then the oldest due head. The evaluator process keeps a capped 4,096-bucket last-served map, evicting the oldest; it may reset on restart or lease failover. A quiet workspace no longer waits behind another workspace's entire backlog; a lone workspace can still use all 25 slots. Multi-replica fairness is approximate. Live recipient authorization, fenced leases, retry backoff, the send budget and 24-hour interrupted cutoff are unchanged.

**Upgrade:** explicitly run **0055_alert_delivery_buckets** (column, insert trigger and pending-only backfill; its `ALTER TABLE` ACCESS EXCLUSIVE lock is held through the backfill until commit, so the locked interval grows with the pending backlog and event-join work—plan a maintenance window for large queues) and **0056_alert_delivery_bucket_index** (partial pending index built concurrently). 0055 resets its 60-second lock-acquisition timeout before the concurrent build; 0056 has no lock timeout. `migrate` recovers interrupted index builds as for 0054; `serve` never migrates. Older outbox-aware replicas continue FIFO during overlap, but their inserts receive the correct bucket from the trigger. Runtime grants need no new privilege; `bucket_id` cannot be updated by the runtime role. Terminal deliveries are not rewritten or replayed.

Claims use one captured database timestamp as an index range bound to skip expired backlog. A claim statement timeout logs a warning and ends dispatch for the tick; cleanup still runs. Label-free gauges `gateway_alert_delivery_pending_buckets` and `gateway_alert_delivery_oldest_pending_age_seconds` expose pending bucket count and oldest age, including overdue work awaiting cleanup. See [alerts](../alerts.md#recipient-outbox-46).

## Workspace alert email generation bound (#277)

Email generation is now capped at **100 deliveries per workspace bucket per rolling 24 hours**, counting firing and clearing across all rules/built-ins. Incidents without a workspace share the nil installation bucket; other workspaces never touch that counter. Each admission reserves 50 recipient slots conservatively (at most 5,000 slots per bucket/window), with no refunds, even without recipients or SMTP. **Critical alerts and urgent 1-day key-expiry reminders have no priority exemption.** Existing key-expiry and aged-hold incident caps remain earlier, independent bounds. In-app incidents/history and eligible webhook enqueue are unaffected; fair dispatch, retries and fenced leases are unchanged.

Over-limit email rows are immediately terminal `suppressed`, with no recipient snapshot or attempts. History shows **“Not emailed — workspace notification limit”** independently for firing (`email`) and clearing (`cleared_email`). Existing authorization predicates remain unchanged. `gateway_alert_email_deliveries{state="suppressed"}` reports the last 24 hours without identifiers. A database guard also refuses a 51st snapshot recipient.

**Upgrade:** **stop every older gateway replica and any scheduled `alerts evaluate --once` job before running 0059** (scale to zero, as for 0050; mixed-version replicas are unsupported). Older evaluators do not prelock delivery buckets in canonical order; under 0059 an inverted acquisition fails with `40001` instead of waiting, which rolls back that evaluation and can permanently miss a transient incident. Then run explicit `migrate`, `grants apply` and `grants verify` before starting the new binary. **0059_alert_generation_limit** adds immutable `quota_charged`/`suppression_reason` metadata and enforces admission in the existing BEFORE INSERT bucket trigger, including old INSERT shapes. **0058_aged_unknown_hold_alerts** precedes 0059; this change does not replace it. 0059 has a 60-second ALTER lock-acquisition timeout, no historical backfill, and checks that avoid scanning retained history under the ALTER lock. It resets the timeout before **0060_alert_generation_window_index**, which builds the partial charged `(bucket_id, created_at)` index **CONCURRENTLY**, outside a transaction, because delivery history can be large. An interrupted invalid index is dropped concurrently and rebuilt on the next `migrate`, as for 0054/0056. Admission is enforced from 0059 even while 0060 builds, but lookups may be slower until the index is ready. The latest embedded schema version is **0060**. Existing rows, including pending deliveries, remain uncharged and are never replayed. Runtime grants permit the admission helpers, never UPDATE on quota/suppression/bucket/time metadata; executable refusal probes cover them.

**Rolling overlap:** old outbox-aware workers select only pending rows, so cannot send suppressed ones; their ordinary final UPDATE still works. Old UIs may omit the new label/clearing outcome. Exact schema-lineage readiness is still required; SQL compatibility does not promise healthy mixed-version readiness. Multi-bucket reconciliation (including personal budgets), key-expiry and aged-hold evaluation prelock their full candidate bucket union in signed advisory-key order before incident writes; single-bucket SCIM/partition/history producers prelock nil, while rule CRUD only retires incidents silently. Aged-hold fired delivery rows already count against the quota although recipient resolution follows in #101 slice D; the anonymous personal aggregate has NULL event workspace and uses the nil installation bucket. Excess deliveries are suppressed without losing incidents or eligible webhooks; aged-hold retirement stays silent. For old/direct SQL, an inverted bucket acquisition never waits: if unavailable it aborts with `40001`, rolling back incidents and quota together; a later normal evaluation can try again. Elevated isolation is refused (`25001`); admission requires READ COMMITTED and takes database time only after the bucket lock. See [alerts](../alerts.md#workspace-email-generation-limit-277).

## Fixed

Telemetry/OTLP export (traces today, metrics once #324 ships) logs a fixed, destination-free warning only when that purpose's connectivity actually changes - into refusal, or back to allowed - never on every export attempt, matching the exporters' own transition-only, fixed-enum diagnostics. A follow-up adversarial review found three LOW gaps, now closed: a dual-stack partial-drop DEBUG diagnostic still named the destination for these quiet purposes (now destination-free too); the audit exporter's OTLP collector destination (a new, distinct `Purpose::AuditOtlp`) gets the same transition-only, host-free treatment for both its DNS refusals and its own delivery-failure/recovery log, without quieting the webhook/syslog destination's diagnostics; and [operations](../operations.md#outbound-connections) now documents that reqwest/hyper's own dependency debug logs name destinations and bypass this policy entirely, confirming the production default `RUST_LOG` can never enable them. Address enforcement and `gateway_egress_denied_total{purpose}` are unchanged for every purpose. See [operations](../operations.md#outbound-connections).

- **Bounded dashboard access refresh (#291).** A refused management GET now triggers at most one automatic session refresh per navigation. A repeated refusal retires private cached data and one-time credentials and shows a stable permission notice instead of remounting and retrying indefinitely. Navigating rearms automatic refresh; an explicit access refresh can recover the denied view, and a 401 still ends the session.
