# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.16.0](v0.16.0.md). They become the next release's notes.

## Fixes

- **`serve` releases its job leases when start-up fails after taking them** (#527). A start-up failure after the background-job leases were taken (a busy public or metrics port, or the audit export state check) used to exit with every lease still held, so another replica could not run those jobs until the terms expired (up to 30 seconds). Every such failure now stops renewing and releases the leases this process holds, as graceful shutdown does, then returns the original error. `GATEWAY_PARTITIONS_AHEAD_MONTHS` is now checked before any lease is taken, so a refused value never holds one. Each release is bounded to 2 seconds, on both paths; a release that fails or times out is logged and its term still ends at its expiry.

## Security and verification

- **CI's PostgreSQL service containers are pinned by digest** (#493): the `gateway-tests`, `gateway-special` and `browser` jobs in `ci.yml` ran `mirror.gcr.io/library/postgres:17-alpine` by tag; they now run `postgres:17-alpine@sha256:d3244e8c…`, the multi-architecture index the tag named on 2026-11-14 (the same digest as on Docker Hub). The supply-chain test now requires a digest on every job `container:` (string or `image:` mapping) and every `services.<name>` image, and refuses an expression there unless it is allowlisted with a reason (none is).
- **The supply-chain test pins what the image builds build** (#488). It read the repository's Dockerfiles but did not tie them to what the workflows and Compose files build. Every job that builds, publishes, signs, imports or tests an image (all of `image.yml`, `branch-images.yml`, `loadtest-image.yml`, `oci-import.yml` and `prune-dev-images.yml`, and `ci.yml`'s `staging-image` and `image`) is now pinned whole in `tests/supply-chain/pinned-jobs.yaml`, with the local actions they use, so any change to such a job, a step added before the build or after the scan included, shows there in review; the repository files those jobs run are a listed set (`PINNED_JOB_INPUTS`), changes to which are reviewed as changes to the image jobs. Any other job that can write packages, id-token, attestations or contents (by its own, the workflow's or the default permissions) must be pinned, and other jobs may not log in, push, sign or create releases. The staging rehearsal's gateway image must stay the candidate under test, in `deploy/staging/compose.yaml`, its overlays and `staging.env.example` (where `scripts/staging.py` now refuses a key set twice); the pinned jobs start Python with `-I`, and no npm pre/post or install script or `.npmrc` may run around their npm commands. A build step must name one of the two known Dockerfiles through a literal context of the checkout, with no `target`, `build-contexts` or `BUILDKIT_*` build argument, and its inputs may use only the job's matrix and the runner's temporary directory (`image.yml` now takes its cache scope from the matrix, not from env an earlier step could rewrite). `setup-buildx-action` takes only the pinned BuildKit image. Every action must be on an approved list; Docker container actions, local actions outside `.github/actions` and container options that reach the host are refused. Compose `build:` sections take only `context` and `dockerfile`, with no `include`, `extends` or tracked `.env`. Other jobs' run steps are read for builds, builder or endpoint switches and unchecked Compose files. The Dockerfile walker also finds `Dockerfile.*`, `*.dockerfile` and `Containerfile*` in any case, and the Rust build image is pinned to its whole approved reference. The suite makes changes to builds visible and catches drift; it is not a boundary against a malicious pull request, and scripts that CI calls are outside it. The new checks live in `tests/supply-chain/`; Dependabot updates `docker/build-push-action` and `docker/setup-buildx-action` in a group of their own.
