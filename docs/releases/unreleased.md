# Open Model Gateway: unreleased

Notes for changes on `main` after [v0.18.0](v0.18.0.md). They become the next release's notes.

## Distribution

The gateway repository is now [bitop-dev/open-model-gateway](https://github.com/bitop-dev/open-model-gateway) (#623). New gateway and loadtest builds publish to `ghcr.io/bitop-dev/open-model-gateway` and `ghcr.io/bitop-dev/open-model-gateway-loadtest`. The next release will be the first published under the organization. This change does not add a migration, runtime grant or API change.

## Upgrade

For the next release, change the image repository to **`ghcr.io/bitop-dev/open-model-gateway`** and pin the verified release digest. For Helm, set `image.repository` and `image.digest` together (a digest takes precedence over `image.tag`). Do the same for explicit migration jobs and any separate gateway workloads; changing only the version tag on an old repository override will not pull the new release. Verify the signature with the exact `bitop-dev/open-model-gateway/.github/workflows/image.yml@refs/tags/<tag>` certificate identity and GitHub Actions OIDC issuer shown in the generated GitHub Release. See [image paths and signature identities](../staging.md#image-paths-and-signature-identities).

Published releases through **v0.18.0** stay pullable at `ghcr.io/ncecere/open-model-gateway`, with the `ncecere/open-model-gateway` signature identity. Their tags, digests and release notes are unchanged; they were not copied or re-signed. Keep the original repository plus digest for rollback, along with the database backup required by that release. Spark automatically selects the original repository for these release tags and the organization repository for newer releases and development images; it never retries a failed lookup against the other account.

Release preparation must update the chart's default repository to `ghcr.io/bitop-dev/open-model-gateway` **together with** its next `tag`, `appVersion` and chart version. Until then, the chart defaults still describe v0.18.0 and use its original repository, so they remain pullable. The release-metadata test enforces this boundary. Confirm both native architecture builds, package visibility/Actions access under organization policy, the exact release signature identity, and a Spark candidate journey run from the new path before tagging. Historical release notes and changelog entries remain as written; repository compare links now use `bitop-dev`.

## Security and verification

- **A fast test tier for the edit loop** (#722). `python3 -I scripts/test-fast.py` runs the gateway lib tests of the modules a change touches, the source rules and the matching npm scripts, typically in one to two minutes after the build; `--all` runs everything but the OpenAPI contract fixtures and `--contract` adds them. GitHub CI still runs the whole suite on every pull request (AGENTS.md, Checks).
- **Database tests clone a pre-migrated template** (#722). The 1,112 `#[sqlx::test(migrations = "./enterprise_migrations")]` library tests became `#[dbtest::test]`: each still gets its own database, but it is a `CREATE DATABASE ... TEMPLATE` copy of one the real migrator built once (named after the migrations and the server's UTC hour, built under an advisory lock, collected when unused) instead of an empty database plus 82 migrations. Test names and counts are unchanged; a test that checks a clone against a freshly migrated database is added. See `docs/verification.md` ("Database tests"). Test code only; no gateway, migration, grant or API change.
- **The OpenAPI contract-fixture tests are far cheaper and run in parallel** (#722). Internal verification change: no gateway code, route, schema, migration or grant changed, and no vector, response check or refusal expectation was removed. Measured alone on the 4-core build machine (user CPU seconds of the test process, before to after):

  | `management_openapi_slice4_money_fixtures` | 540 CPU s, 2.7 GB | 5 shards of 80 CPU s, 107 s wall |
  | `management_openapi_slice5_fixtures` | 147 CPU s, 2.5 GB | 2 shards of 50 CPU s, 65 s wall |
  | `management_openapi_slice2_fixtures` | 131 CPU s, 3.4 GB | 68 CPU s, 87 s wall |
  | `management_openapi_slice6_fixtures` | 72 CPU s, 2.4 GB | 40 CPU s, 56 s wall |
  | `inference_openapi_generation_real_handler_fixtures` | 173 CPU s | 3 shards of 57 CPU s, 86 s wall |
  | `management_openapi_review_every_completed_operation_rejects_response_mutations` | 445 CPU s | 5.6 CPU s |
  | `management_openapi_artifact_matches_regeneration`, `_metaschema_and_schema_controls`, `_rejects_response_links`, `_rejects_unresolved_and_external_references` | 111, 107, 113, 104 CPU s | 11, 10, 10, 10 CPU s |

  Three changes: (1) a schema now compiles as a fragment of the contract document registered once (`validation::compile_in_document`) instead of inside a fresh 2.8 MB copy of it for every schema, the vendored metaschemas are verified once per process, pattern validators and the operation-template index are memoised, and the mutation sweep keeps its validators for the one copy of the document it validates against (`responses::with_document_cache`, never shared with the artifact's cache or another copy); the validator cache no longer holds a document copy per entry, so the peak resident set of the fixtures fell from between 2.4 and 3.7 GB to about 0.2 GB. (2) The vector planner no longer serialises the valid body at every location, borrows schema nodes instead of cloning them, and skips the byte-limit walk where no limit can apply. (3) The long journeys are divided into parallel shards: every shard replays the whole journey and plans every vector run, but sends only its share of the planned vectors (plus each run's valid request), so each vector is judged by exactly one shard and each shard's coverage gate still covers the complete area group. The six divided fixtures sent 90,572, 38,670, 18,240, 11,234, 6,108 and 34,082 vectors in one test (slices 3, 4, 5, 2, 6 and generation); across their shards they now send each of those vectors exactly once, plus each run's valid request in every shard; `management_openapi_http_vectors_shards_divide_the_planned_vectors` pins this for any shard count and `management_openapi_hardening_every_shard_of_a_divided_fixture_has_a_runner` fails if a shard has no runner. The first shard keeps the old test name; the others add `_shard_<n>`. The journeys gained three requests that make the coverage gate independent of which shard sends a vector (a catalog without a description, a second listing of platform workspaces after the cost-center allocations, and a restore of the vector workspace after the `disabled` flips). See `docs/openapi/management/README.md` ("Sharded fixture runs").

- **Test databases run with JIT off, and the contract fixtures use fewer shards** (#722). Internal verification change again: no gateway code, route, schema, migration or grant changed, and no vector, response check or refusal expectation was removed. (1) The pool of every `#[dbtest::test]` database sets `jit=off`: PostgreSQL compiled any query whose planner estimate passed `jit_above_cost`, which took 1.2 to 1.4 s for the six-row model list of `GET /api/v1/workspaces/{ws}/keys/{key}/access` on every call (13 calls were a third of a slice 6 run) and cost the whole library suite about a quarter of its PostgreSQL CPU. (2) The vector planner and the validator cache build their keys with `responses::value_key`, a self-delimiting text that is equal exactly when two JSON values are, instead of `serde_json::to_string`, which was about half of planning time in the unoptimised test profile; run against the old keys on every candidate and every cache key of one shard per fixture, the two never disagreed. (3) The global log subscriber of the capture tests formats a span or an event only while a capture can read it (`log_capture_test::Capture`, or `keep_spans` for the one family of tests whose request starts before its capture); installed for the rest of the process, it cost every request-sending test about a tenth of its CPU for output nobody read. (4) A shard repeats the journey and the planning (10 to 35 CPU s) whatever its share of the vectors, and the machine has as many cores as the suite has test threads, so the shard counts fell to 6, 5, 3, 2, 1 and 1 (`SLICE3_SHARDS`, `SLICE4_SHARDS`, `GENERATION_SHARDS`, `SLICE5_SHARDS`, `SLICE2_SHARDS`, `SLICE6_SHARDS`). Across the shards of each fixture the vectors sent are the same as before the division (90,572, 38,670, 18,240 plus the raw upload vectors that every slice 5 shard repeats, 11,234, 6,108 and 34,082) plus each run's valid request in every shard. Whole library suite on the 4-core build machine (4 test threads, before to after): 1,810 s to 1,496 s wall, 3,235 to 2,899 CPU s in the test process, 2,133 to 1,571 CPU s in PostgreSQL.
- **CI builds the gateway tests once per shard** (#722). CI script and workflow change only. Each `gateway-tests` shard used to compile the gateway library tests twice: once in a `--workspace` build and again for the per-package runs, because Cargo unifies features over the selected packages: `--workspace --all-features` turns on every member's features (the datetime crate's `postgres-tests`), which the gateway alone does not ask for, so the two builds differed. `.github/scripts/rust-shards.mjs` now builds and runs doctests per package, the same selection as its test runs. The test jobs' builds carry no debug information (`CARGO_PROFILE_DEV_DEBUG=0`), and the test shards' PostgreSQL data directory is memory. The tests selected, their counts and the required checks are unchanged.

- **The Rust and web suites run as jobs on the Spark test platform** (#653). `python3 -I scripts/spark-test.py run <name> --ref <pushed ref> --suite lib|integration|web|checks|all` fetches the exact pushed commit and runs it on arm64 against disposable PostgreSQL 17. Two runs can coexist with one demo environment, providing extra capacity without queueing behind the local build slot. The tool reports test counts, failures and coverage limits in a compact JSON summary. Exit 0 means every selected suite passed in full; zero-test and incomplete runs fail, narrowed passes exit 3, setup or platform errors exit 2, and `--detach` exits 4 with the outcome unknown. Failed runs save a sanitised log before cleanup.

  Slot reservation and launch use one suspended Job with generation-fenced cleanup; purge reserves the idle slot before deleting its namespace. Interrupted cleanup/purge is resumable. Before upgrading from the ConfigMap-lease runner, stop prior clients and finish/down active runs with that version; idle slots/caches can be reused. See [runner safety and upgrade](../verification.md#tests-on-the-spark-platform).

  The tool uses only the Spark kubeconfig and its two labelled slot namespaces, pinned Rust and Node images, and a per-run progress nonce. Each slot keeps a 20 GiB cache: configuration, toolchains, unpacked sources and git metadata are reset between runs, while `target/` is reused unless `--fresh` is set. This is a trusted-code test runner: only run refs you would execute locally, and purge after other refs. The database password is mounted as a file and injected into `DATABASE_URL` only for database steps. A coverage test checks the suite commands against CI. Docker-dependent tests, browser tests, image jobs and CI's other npm checks still require CI; green GitHub CI remains the merge gate.

  Measured on `main` at `2538235091`, with the default 1.8 CPU limit: library 2,482 passed and 9 ignored of 2,491 listed (matching CI), integration 170 passed and 10 ignored, web 1,903 passed, and formatting/Clippy checks passed. `--fast` can raise the CPU limit within the available quota; its 6 CPU trial was stopped before completion, so no timing or speed-up is claimed. See `docs/verification.md` ("Tests on the Spark platform") for measurements, trust boundaries and coverage limits, and AGENTS.md for usage. No gateway code changed.
