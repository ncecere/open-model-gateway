# Open Model Gateway: unreleased

Notes for changes on `main` since v0.5.0. They become the next release's notes.

## Security

- **Remove personal data now** (#76): Platform Admins can run the departed-user cleanup at once for a suspended person (refused on legal hold). Cleanup now also clears the person's address on old invitations and alert recipients and the names of files they uploaded; history keeps the user id as its pseudonymous reference. [Identity](../identity.md#what-cleanup-removes-and-keeps-76) lists what is removed and kept. The runtime role gets `UPDATE(email)` on `workspace_invitations`.
- **Legal holds** (#75): Platform Admins place a hold on a person or a team/project (from its page, with a reference code) and release it in Admin › Records › Legal holds. While held, nothing of that scope is removed: departed-user cleanup, request-log compaction, file expiry and `archive partition` wait or refuse. Holds grant no access, are audited, and are released, never deleted. Migration 0045; the runtime role gets `SELECT`, `INSERT` and `UPDATE(released_at, released_by_user_id)` on `legal_holds`.

- **Audit export to a SIEM** (#106): set `GATEWAY_AUDIT_WEBHOOK_URL` and `GATEWAY_AUDIT_WEBHOOK_SECRET_ENV` to stream the platform audit log (never personal-workspace events) as signed HTTPS deliveries, at least once, in order, with nothing dropped during outages. Operator-controlled: only `GATEWAY_AUDIT_WEBHOOK_URL=off` turns it off (a replica without the setting changes nothing), and the on/off transitions are exported events. The secret's variable may not be on a provider or SMTP allowlist. Admin › Settings › Audit export shows status and sends a test. Format `omg.audit.v1` ([operations](../operations.md#audit-export)). Migration 0044 adds the export queue and its trigger on `audit_events`; the runtime role gets the queue and status grants (audit stays append-only). New metrics `gateway_audit_export_*`.
- Helm: `networkPolicy.egress.httpsCidrs` narrows outbound 443 to chosen networks, or `httpsExceptCidrs` keeps it off chosen ranges such as the private ones (#169). The default is unchanged (443 to any address). SMTP has never been opened by the chart: add an `extraEgress` rule for your relay's port. [Kubernetes › Outbound traffic](../kubernetes.md#outbound-traffic) explains aligning the NetworkPolicy with `GATEWAY_EGRESS_PRIVATE_ALLOW`.
- **Breaking: SMTP relay hosts need operator approval** (#168). The relay set in Admin › Settings › Email must be listed in the new `GATEWAY_SMTP_HOST_ALLOWLIST` (Helm `gateway.smtpHostAllowlist`), or email stops: status shows `host_not_allowed` and sends, including the test email, fail with that reason before the password is read. List your relay before upgrading. The relay and the OpenAI realtime WebSocket now also go through the outbound address policy (#167); a listed loopback relay stays allowed.
- **Outbound address policy** (#167, part of #33). Every outbound HTTP connection (providers, OIDC, S3, catalog) is checked at DNS resolution and connects only to an address that passed: never metadata, link-local or reserved ranges; loopback only with `GATEWAY_ENV=development`; private networks (RFC 1918, `100.64.0.0/10` including Tailscale, IPv6 ULA) only when listed in the new `GATEWAY_EGRESS_PRIVATE_ALLOW`. **Behaviour change:** an installation that reaches a private IdP, S3-compatible store or Bedrock/S3 private endpoint must list its network, or startup (OIDC) or those requests (S3, Bedrock) fail with a message naming the setting. Also affected: loopback sidecars (a local MinIO or proxy) outside `GATEWAY_ENV=development`; IP-literal S3 or Bedrock endpoints now stop startup instead of failing per request; IPv6-only clusters keep working through NAT64. List only your tailnet addresses, not all of `100.64.0.0/10`. Configured IP-literal endpoints are checked at startup. New metric `gateway_egress_denied_total{purpose}`, counted only when no allowed address remains. AWS credential lookups (instance metadata, ECS/EKS, STS) are not covered.

- **Behaviour change: dashboard sessions now end after 2 hours without activity** (#80), as well as 12 hours after sign-in. Set `GATEWAY_SESSION_IDLE_TIMEOUT` (`off`, or `15m` up to the lifetime) and `GATEWAY_SESSION_LIFETIME` (`15m` to `7d`) to change them (Helm `gateway.sessionIdleTimeout`, `gateway.sessionLifetime`). Existing sessions keep their expiry and get the idle limit from their next recorded activity (recorded at most every 5 minutes, so a session can end up to 5 minutes before the idle timeout); a longer setting never revives an ended session, and a shorter one doesn't shorten existing sessions (sign people out instead). Without SCIM, a longer lifetime also delays when a removed IdP group takes effect. Maintenance now deletes expired sign-in attempts (every minute) and sessions that ended more than 30 days ago (hourly). Migration 0042 adds `browser_sessions.idle_expires_at` and `users.first_signed_in_at`/`last_signed_in_at` (metadata only, with a 10-second lock timeout so admissions never queue behind it; retry the migration if it times out), and 0043 backfills the sign-in times from existing sessions (row locks on `users` until it commits: admission of affected users' keys waits that long), so "First signed in" and "Last sign-in" survive cleanup. The first hourly cleanup clears a large pre-existing sessions table at 10,000 rows an hour; the runtime role gets `DELETE` on `browser_sessions` and `UPDATE` on the new columns.
- Your sessions (#79): Your profile › Sessions lists where you're signed in (browser and OS family, sign-in and last-active times; no IP address or raw user agent) and signs one or all other sessions out. Platform Admins see a person's session count and can sign them out everywhere without suspending them. New API: `GET /me/sessions`, `DELETE /me/sessions/{id}`, `POST /me/sessions/revoke-others`, `POST /platform/users/{user}/sessions/revoke`. Migration 0041 adds `id`, `last_seen_at` and `client_label` to `browser_sessions`. The `id` default rewrites the table and builds a unique index under a full table lock: every dashboard request and sign-in waits until it finishes (inference is unaffected). Session rows have never been deleted (#80), so check `SELECT count(*) FROM browser_sessions` first and plan a short window for a large table. The runtime role gets `UPDATE(last_seen_at)`.
- Sign-in abuse controls (#78): per-address limits on sign-in starts and callbacks (`GATEWAY_LOGIN_RATE_PER_MINUTE`, default 60 a minute, per replica), and at most 10,000 pending sign-in attempts installation-wide (503 beyond). Refusals return 429 or 503 with `Retry-After` and store nothing. Behind a reverse proxy, set `GATEWAY_TRUSTED_PROXIES` (Helm `gateway.trustedProxies`) to its addresses, or every user shares the proxy's budget. New metric `gateway_auth_throttled_total`. Migration 0040 adds an index on `oidc_login_attempts(expires_at)`; it is a plain `CREATE INDEX`, so sign-in waits while it builds (the table holds only sign-in attempts, but they have never been deleted).
- An admin suspension is audited as `user.suspended` (with the reason) and a reactivation as `user.reactivated`, instead of `user.updated` without detail. `user.updated` now flags `email_changed` or `oidc_link_changed`, never the values, and is written only when something changed (#158).
- After a restore, `scripts/backup.py reapply-revocations` copies every revocation (keys, grants, sessions, invitations) and suspension (users, keys, service accounts, workspaces) from the old database onto the restored one, so access removed after the backup stays removed (#146). It's a dry run without `--yes`, applies in one transaction and refuses a different installation. The restore runbook in docs/operations.md now covers revocations, sessions and lost spend.

- Revocations are final in the database: migration 0039 adds triggers that refuse clearing or changing `revoked_at` once set on API keys, membership and platform role grants, browser sessions and invitations, for every role (#145). Hand-written SQL that "un-revokes" a key or grant now fails; issue a new one instead.

- The OIDC client (discovery, token exchange, JWKS) no longer uses ambient `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` or implicit retries, like every provider client (#144). If sign-in only worked through such a proxy, allow the gateway to reach the issuer directly.

- CI pins every GitHub Action by commit SHA and the `Dockerfile` build images by digest, and `npm run test:supply-chain` fails CI on any unpinned one (#143).

- Every response now carries a Content-Security-Policy, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` (#142). The dashboard's policy allows only its own scripts, styles, fonts and API (no inline script or `eval`) and can't be framed; API and file responses get `default-src 'none'`. If you embed the dashboard in a frame or load it through a proxy that injects scripts, that no longer works.

- **Breaking (#141):** Teams and Projects have a new setting, **who sees files, batches and videos** (Workspace › Settings › General; `object_visibility` on `GET/PATCH /api/v1/workspaces/{ws}`, migration 0038). **Per user**, the default for new and existing shared workspaces: a regular member's API keys and dashboard see only objects created with that member's keys; service-account keys and workspace owners/admins see everything. **Workspace-wide:** every key sees everything. In both modes only the creator, an owner/admin or a service-account key may delete or cancel (`403`); an object the caller can't see returns `404`, also as a batch's `input_file_id`. Before, any key of a shared workspace could read, delete or cancel every member's objects through `/v1/files`, `/v1/batches` and `/v1/videos`.

  **Upgrade:** run the migration and reapply the runtime grants (`object_visibility` is added to the runtime role's `UPDATE` on `workspaces`). Clients that read other members' objects with a member key get `404` until a workspace admin sets the workspace to Workspace-wide; use a service-account key for workspace-wide automation.

- rustls 0.23.45 → 0.23.46 for RUSTSEC-2026-0346 (session `Debug` output exposed TLS secrets), -0347 (data sent to the outer server after an ECH rejection), -0348 (unbounded Brotli certificate decompression) and -0349 (an unauthenticated ServerHello could downgrade later connections to classical key exchange).

- **Breaking (#140):** the SMTP password reference now resolves only from the new `GATEWAY_SMTP_SECRET_ENV_ALLOWLIST` (Helm: `gateway.smtpSecretEnvAllowlist`), never from the provider list `GATEWAY_SECRET_ENV_ALLOWLIST`. Before, a Platform Admin, who chooses the SMTP host, could set the SMTP password to a provider key reference and send that key to a mail server they control. The gateway refuses to start if a name is on both lists, or if the SMTP list names one of its own credentials (`DATABASE_URL`, `GATEWAY_*`, `AWS_*`, `GATEWAY_OIDC_CLIENT_SECRET`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`).

  **Upgrade:** move your SMTP password variable's name from `GATEWAY_SECRET_ENV_ALLOWLIST` to `GATEWAY_SMTP_SECRET_ENV_ALLOWLIST`. Until you do, invitations and alerts are not emailed (Settings › Email shows the reference as not allowed). If a provider key was ever used as an SMTP password, rotate it.

- New [threat model](../threat-model.md) (#32): STRIDE threats by area with the code and tests that mitigate each, residual risk, and a gaps table mapped to follow-up issues, for code reviews and the independent security review (#61).

Accounting stayed exact through every fault. A second write outage after a 2-instance failover is tracked in #149, and the remaining steady-load stalls in #132.
