# Open Model Gateway v0.18.0

A minor release after [v0.17.0](v0.17.0.md), focused on batch ownership, settlement accuracy and returned-stream failures. It adds two explicit, audited operator actions for eligible unknown costs and replaces the unmaintained Chrono dependency graph with maintained date/time types.

**This is a drained schema upgrade, not a rolling image replacement.** The latest migration advances from **0080 to 0083** (82 migration records). Apply migrations **0081–0083** and the matching runtime grants before starting v0.18.0. Existing unknown history is retained; the upgrade does not resolve it automatically.

## Upgrade

From **v0.17.0**, use the following procedure after qualification and deployment approval. Older installations must also follow their intervening release instructions.

1. **Back up and verify.** Take and verify a pre-upgrade backup using the [operations procedure](../operations.md#upgrade-and-migration-procedure). Rollback depends on this backup. Select the existing installation database explicitly; never reset, reseed or recreate it as part of an upgrade.
2. **Drain every gateway replica and worker.** Stop ingress, drain in-flight work, scale the gateway to zero and suspend any autoscaler. Old runners do not know the new epoch fence. Once a migration commits, the old gateway no longer matches the schema and reports not ready; never leave old workers running against it.
3. **Migrate and apply runtime grants with v0.18.0 migrator credentials.** Run `open-model-gateway migrate`, then `open-model-gateway grants apply`. With the chart, scale the previous Deployment to zero first and use the explicit migrate hook (`migrations.run=true`); the hook applies grants after migration. Migration does not run from `serve` or the normal container entrypoint.
4. **Start the matching gateway and verify.** Deploy the verified v0.18.0 image digest and matching chart. Restore the intended replica count and autoscaler, wait for `/health/ready` to report the schema ready, and run `open-model-gateway grants verify`. Run `budget verify` and check metrics, sign-in, a gateway-run batch and an explicitly authorized bounded inference request before restoring traffic. Retain the backup until acceptance is complete.
5. **Handle failures without image rollback.** If migration committed but a later migration, grants or startup step failed, fix the cause and rerun the explicit migration/grant steps with v0.18.0 while drained. There are no down migrations. Redeploying v0.17.0 is safe only if no migration committed; otherwise restore the pre-upgrade backup into a **new database**, verify it with the matching old gateway/grants and cut over. Preserve configuration, file-store objects and encryption keys separately. A restore loses post-backup writes and can restore revoked access; reapply revocations/suspensions and account for missing spend before serving. Do not run `helm rollback` against an upgraded database.

| Migration | Change and lock implications from the SQL |
|---|---|
| 0081 `batch_runner_epoch` | Adds a constant-default epoch to `async_jobs` without a table rewrite. `ALTER TABLE` still takes `ACCESS EXCLUSIVE`; the new epoch trigger also blocks writers while installed. |
| 0082 `free_price_resolution` | Adds a reservation marker and replaces/validates settled-usage constraints on the reservation parent and retained partitions. Exclusive locks and validation scans can take time. |
| 0083 `batch_envelope_resolution` | Adds the distinct envelope marker, replaces/validates the narrowed NULL-usage constraints and installs its eligibility guard across retained reservation partitions. It also takes exclusive locks and scans retained history. |

These are source-derived lock implications, not a migration-duration estimate. The migrator supplies no lock timeout; drain other writers before starting so locks do not queue behind them. The runtime role gains column UPDATE permission for `async_jobs.runner_epoch`, `governance_reservations.free_price_resolved` and `governance_reservations.batch_envelope_resolved`; it receives no owner or schema privilege. Use the matching [runtime grant allowlist](../../deploy/staging/runtime-grants.sql). Connect directly to PostgreSQL rather than through a transaction pooler for migration and grant operations.

Management clients gain the two explicit resolution routes and their aggregate request/response schemas. Inference protocols and settings remain the same, but returned-stream error classes and passive-health effects change as described below. Publication, release qualification and production activation are separate; these notes do not authorize deployment or v1.0.0.

## Behaviour changes

- **Provider errors inside returned generation streams use the adapter's HTTP error classes** (#614, #622): documented rate-limit/quota, server/overload, client-fault and configuration names (and numeric statuses) now drive sanitized terminal errors, execution error codes, existing metrics and passive routing health consistently. Anthropic, OpenAI Chat/Responses, OpenRouter and local profiles share a documented name/status table; Bedrock keeps its exception-header table. Messages clients retain their HTTP overload/context refinements. Unknown names are `upstream_unavailable`; complete malformed SSE lines, including invalid UTF-8, remain `invalid_upstream_response`. [Full mappings and limits](../provider-adapters.md#failures-inside-a-returned-stream).
- **Truncated streams now count against routing health.** SSE body resets already surfaced as `upstream_unavailable` before this change; the new SSE behavior is EOF before the protocol's terminal frame, with or without a partial frame. Local OpenAI-compatible servers that omit `[DONE]` already failed, but those failures now count and three consecutive failures open the default breaker. This resolves the stream-error health limitation recorded in [v0.17.0](v0.17.0.md). Bedrock body resets, incomplete terminal sequences and corrupt binary framing (length, CRC, headers or SDK decode) now surface as `upstream_unavailable`; complete decodable protocol violations remain invalid responses. Bedrock body/SDK timeouts surface as `timeout_error`.
- **Operational effects:** in-stream server errors count even when a local server's 500 was triggered by model output (such as a malformed tool call). Gateway-side network blips that reset streams also count (already true for SSE). Error-type reports/alerts can shift between existing classes. A returned stream still ends in an error without a success marker, retry or failover; unknown usage retains its hold, including free-price in-stream rejections. Client disconnects and engine deadline cancellation leave health unchanged. Non-stream behavior is unchanged ([#665](https://github.com/ncecere/open-model-gateway/issues/665)). SSE stream requests answered with a 200 JSON body instead of SSE still fail as invalid responses before stream return. The Bedrock timeout alignment landed in #669/#666: stream lifetime follows the engine watchdog, active reads reset on wire progress and accept queued bytes after backpressure, and the fixed 300 s total cap and whole-event receive timer no longer govern returned streams. Non-stream limits remain intact.

## Fixes

- **Deployment-preview focus returns to a connected control** (#588, #667). Route actions and the narrow header preserve control identity when navigation or route tiers arrive after dialog dismissal, so the Actions trigger or fallback remains focused through the refresh.

- **Maintained datetime dependency graph** (#674): replace Chrono with Time 0.3.55 and bounded UTC/calendar carriers, preserving existing timestamp precision, leap observations, cursor bounds, SQL microseconds, accounting periods and OIDC expiry comparisons. SQL date/timestamp decoding safely refuses infinities and values outside the former carrier range. Locally maintained OAuth2 5.0.0/OpenID Connect 4.1.0 source ports retain upstream identities and normal/upstream-base advisory coverage; [maintenance procedure](../datetime-maintenance.md). Jiff remains for timezone/DST scheduling. This dependency change adds no migration or runtime grant; the release-wide migrations above are required.

- **Explicit resolution of terminal gateway batch envelopes** (#661). Browser-session Platform Admins can preview and apply `/api/v1/platform/reservations/resolve-batch-envelopes` with bounded aggregate-only pages and an expected count/reason. Native, nonterminal and ambiguous jobs refuse eligibility. Only the unused UNKNOWN envelope hold settles at zero: line charges are retained and recorded as evidence, and unknown/pending lines keep their own holds. No usage zeros, history rewrites or automatic resolution. This is separate from #657 free-price eligibility. Migration `0083_batch_envelope_resolution` adds a distinct marker and validates narrowed NULL-usage settlement checks across retained reservation partitions, taking exclusive table locks and scanning while drained. Back up/verify, stop ingress and gateway, explicitly `migrate`, `grants apply`, restart the matching gateway and `grants verify`; runtime gains only the marker column update grant. Rollback restores the pre-upgrade backup into a new database. Each page covers at most 10,000 envelopes and 150,000 line attempts without splitting a job; statement/lock/action limits remain 10 s/2 s/60 s. Failures before COMMIT roll back the page; a failed COMMIT acknowledgement is uncertain. Preview again before replay: an expected count is not an idempotency key, and repeating an apply can resolve another same-sized page. See [operations](../operations.md#explicit-resolution-of-terminal-gateway-batch-envelopes).

- **Explicit bulk resolution of free-price unknowns** (#657). Browser-session Platform Admins can preview a count and explicitly apply zero-cost settlement with a reason for terminal unknown reservations whose hold is exactly zero and pinned price/tier is entirely free/not applicable. Existing observations survive and missing usage stays NULL; reconciliation ledger and private workspace-scoped audit events name the operator. Optional month/workspace/deployment filters, count guards and canonical locks prevent duplicate settlement of a reservation. Bounded pages evaluate at most 10,000 preliminary candidates; numeric `offset` and nullable `next_offset` let operators process larger buckets and skip ineligible prices. Apply returns its continuation after removing resolved rows. Named variants require a free default rate, so a listed free variant cannot establish a missing price for another variant. Forward migration 0082 and reapplied runtime grants are required. This action performs no automatic resolution and does not resolve gateway batch envelopes; use the separate #661 action for those. See [operations](../operations.md#explicit-resolution-of-free-price-unknown-reservations).
- **Accepted video and batch failures keep unknown usage on free prices** (#616). A provider job id now carries acceptance into settlement, so a later failed video, native batch or legacy passthrough batch cannot use the pre-processing free-rejection exemption. Missing token/meter observations remain NULL and the original/grown hold stays, including a zero hold. A native submission's accepted id is retained even if the concurrent encoder fails. Explicit pre-processing rejections and OpenRouter non-stream HTTP 200 error-only 4xx responses retain the existing free-zero rule. No schema or runtime-grant change, no history rewrite. Free unknowns still prevent archival until eligible history is explicitly resolved through #657 or #661; broader non-stream classification remains separate (#665).

- **Batch creation commits its final lease atomically; accepted-video recording and lease extension commit together** (#640). Creating a gateway batch admitted its reservation (the envelope) with a 10 minute lease, wrote the job row, and only then extended the lease to the job's deadline in a separate step; a native batch and a video did the same. If the process died, or the extension failed (it only logged `job lease extension failed; reconciliation will keep the hold as unknown`), between those steps, reconciliation turned the reservation `unknown` ten minutes later while the job stayed queued. **What you could have seen:** a gateway-run batch whose every line failed with `503 provider_configuration_error` ("Provider configuration is unavailable") and ended `completed` with `request_counts.completed` 0; an `unknown` reservation of a batch or video whose job was still queued or running; a native batch or video that finished but whose cost stayed `unknown` instead of settling. Money was never at risk: an `unknown` reservation keeps its hold, and no line ran. **Now:** a batch's envelope, execution, ledger entry and job row are written in one transaction, with the envelope's lease running to the job's poll deadline plus ten minutes from the start (a create that rolls back leaves no job or hold and removes its private input copy; batch statement failures are counted at `governance_storage` instead of `job_settlement`. If the COMMIT acknowledgement is lost, the create returns an accounting error but keeps the private work file, so a job the server committed can still run; an unreferenced copy is removed at retention expiry). A video's lease extension and job row are one transaction after the provider accepts it; if that transaction fails the create returns an error, the job row may be absent (or committed if only its acknowledgement was lost), and the reservation keeps its hold until reconciliation marks it unknown (the provider may be running the video; the hold is never released). **A gateway-run batch an earlier release already left with a non-pending envelope** is no longer run line by line into 503s: when a runner claims it, it attempts no line and ends it `failed` with `error_code` `hold_unavailable`, preserved counts and results for any finished lines (0 completed and 0 failed if none ran; unstarted lines are not counted), and an error file listing unstarted lines as `batch_hold_unavailable` ("Create the batch again"); the Batch failed alert rule, when configured, opens an incident. Nothing is charged for lines that did not run. **What to do:** the affected users create the batch again. The old envelope stays `unknown` with its hold (the gateway never releases or values it automatically), so it keeps counting against budgets until an operator resolves it. The evidence-based usage reconciliation (`POST /api/v1/workspaces/{ws}/costs/{execution}/reconcile`) cannot value a gateway-run envelope, because it pins no price (it refuses with a configuration error), so use the separate terminal-envelope preview/apply action added in #661 to resolve eligible gateway-run envelopes; it preserves line charges and holds. An accepted video whose job record could not be written also needs follow-up #662. Find them with `SELECT j.id, r.execution_id, r.held_microusd FROM governance_reservations r JOIN async_jobs j ON j.execution_id=r.execution_id WHERE j.kind='batch' AND j.batch_mode='gateway' AND r.state='unknown'`. Native batches and videos with an unknown reservation continue polling and record their terminal job state, but leave the unknown hold for evidence-based reconciliation. **No migration in this individual fix; the release requires 0081–0083** and the [drained upgrade procedure](#upgrade). This code change reads batches from older replicas safely (an older replica still creating a batch uses the old two-step flow, which the new code reads correctly). New error-file code `batch_hold_unavailable`, new batch `error_code` `hold_unavailable`, and a WARN carrying the job id. Accepted-video transaction failures (begin, global lock prefix, lease update, insert and commit) retain the `job_settlement` critical alert stage. SCIM/lifecycle user row locks and file rekey claims allow the creator/input foreign-key checks without a row/advisory deadlock or a wait across object-store rewrap.

- **A client that disconnects as its request is being settled no longer leaves a fully reported success `unknown`** (#639). The settlement write of a finished attempt (the upstream's complete response, or a stream that delivered its final usage and `Done`) ran inside the client's request, so a client that hung up in that moment (a timeout on its side, a closed browser tab, a dropped connection right at the end) abandoned the write, and nothing retried it. The attempt then stayed `pending` until its lease expired, and the expired-lease reconciler marked it `unknown` and kept its hold, although the provider had reported complete usage. What you could see: `unknown` reservations with retained holds, an execution recorded `cancelled` with no tokens or cost, and spend overstated by the hold in budgets and alerts, until a Platform Admin resolved each one with evidence. It was an accuracy gap, not a money leak: nothing was lost or charged twice. Now, once the outcome and usage are final, the settlement runs to completion whether or not the client is still there (a request dropped while the write is in flight hands it to a spawned task, which finishes it): the reservation settles at the reported cost, the execution records `succeeded` and the ledger gets its one settlement entry. The write keeps the 3 s settlement deadline and holds the request's concurrency slot until it ends (unless the request's own deadline already gave it back), so a stuck database cannot accumulate detached writes beyond `max_concurrent` plus the writes of requests that timed out, each ended by the 3 s deadline, and closing the pool at a graceful shutdown waits only for writes that already hold a connection (one still queued or waiting for a connection gets `PoolClosed` and is left to reconciliation). The same applies to a failure recorded with the usage seen so far, and to the non-generation workloads (embeddings, images, audio, rerank) that settle through the same path. Unchanged: a client that drops before the outcome is final (mid-stream, or while the upstream call is running) still cancels the upstream work and leaves the hold as unknown cost, because usage is not known; a write that fails or exceeds the deadline is still not retried, is counted and logged once (`gateway_settlements_total{outcome="held"}`, and `gateway_accounting_failures_total{stage="explicit_settlement"}` for a deadline) and is left to reconciliation. Realtime sessions settle through their own path and are not changed (#659). Two limits are accepted: a client that disconnects after the stream's final usage event but before its terminal event is processed still takes the cancellation path (usage `unknown`, hold kept), and for a write handed off after the request was dropped, the exported request telemetry labels the request `cancelled` while the ledger records the attempt as succeeded, and the routing-health update is skipped (it was lost on a disconnect before as well). Reservations that already ended `unknown` for this reason are not corrected by the upgrade; resolve them with evidence as before. No migration, setting or API change.
- **A gateway-run batch's runner can no longer write to a batch another runner has taken over** (#638). A runner holds a batch with a 60 s lease it renews every 15 s. If it stalled for the lease term (a frozen VM, a stopped process, starvation) or its renewals kept failing, another runner claimed the batch and marked the first runner's in-flight lines `interrupted`; the first runner then still wrote, because only a local flag, set later by its renewal task, told it. After such a stall you could see: the result of a billed line dropped, a segment-number collision that made the *new* owner lose every later result flush (its remaining billed lines reported `result_unavailable`), progress counters above the batch total for a while, the first runner finishing the batch and closing its budget envelope while the new owner still had lines running (the owner's later lines then failed to admit), and duplicate output files. Money stayed consistent and no line was sent to a provider twice. Now each claim bumps a **claim epoch** and every runner write checks `(runner id, epoch)` inside its own transaction while holding the batch's job row (`FOR KEY SHARE`, or `FOR NO KEY UPDATE` when it also writes the row). A claim is `FOR UPDATE SKIP LOCKED`, so it skips a batch with a write in flight and takes it on a later tick, and a runner that lost the batch is refused at its next write: it admits and starts no further line, records no result, counter, segment or demand row, finishes nothing and closes no envelope (a result segment or output file it had already stored is deleted when its record is refused). Each of those transactions ends its session after 30 s without a statement, so a frozen runner cannot hold a batch against a claim. Segment numbers are taken by the database inside that transaction, so one lost or failed flush never makes later flushes collide. Counters move in the same transaction as the line's state and only when that write moved the line out of `running`, so a line is counted once; at the end of a batch a line recorded `succeeded` with no stored result is counted failed, to agree with the error file that lists it. A refused lease renewal ends the run's work. Failed renewals (a renewal that has not answered after 10 s counts as failed) end it only once 45 s have passed since the last success (`lease - renewal interval`): the run then starts no further line and finishes the ones it has, but keeps renewing and does not resume dispatch if the database recovers, then gives the batch up, still open, so the next claim finishes it without waiting out the lease. A run that only doubts its lease never ends a batch. The first failed renewal also makes the run store the results it holds. A process no longer re-claims a batch it is still running.

  **Two accepted limits, in plain words.** A line whose provider call completes *after* the takeover is charged (its attempt settles at the real cost, so the batch's cost and the usage reports include it) but its result is not recorded: the new owner has already counted it failed and the error file lists it as `result_unavailable`; a warning with the execution id and line number is logged. And a result that was still in the old run's buffer (at most 10 s or 256 lines) when the batch was taken over is lost the same way, because the line is recorded `succeeded` before its result is stored; the run stores its buffer at the first failed renewal, which covers a database outage but not a frozen process. Reordering the two (store, then mark succeeded) is a larger change and is not part of this fix (#654). Two related gaps are tracked separately: after a takeover the new owner can exceed a route's concurrency limit by the old run's in-flight lines until their provider calls end (#655), and result files a crash or an unknown-outcome failure leaves unreferenced stay until a sweep removes them at retention expiry (#656).

  **Upgrade:** follow the [drained upgrade procedure](#upgrade); migration 0081 adds the runner epoch, and 0082–0083 add the two explicit resolution markers.

  New log lines: `batch runner no longer holds its batch; it stops working on it` (once per run), `batch lease renewal failed`, and `batch line outcome not recorded: the runner no longer holds the batch` (execution id and line number). Failed renewals are counted at the existing `job_storage` stage; no metric or label is added. Native (provider-run) batches, video jobs and the poller are not changed; their claim is a soft `next_poll_at` push and is tracked in #651.
- **A malformed `top_provider` in the OpenRouter catalog no longer fails the price suggestion** (#634). When the public catalog returned a model whose `top_provider` was a string, number, boolean or array (not an object) and the chosen endpoint listed `max_completion_tokens`, the gateway panicked while building the suggestion, so a Platform Admin's request for `GET /api/v1/platform/deployments/{id}/price-suggestion` got no response: the connection was closed (a proxy in front may show a 502), the dashboard's price suggestion failed, and for an admin-token caller the audit trail kept an attempt that started and never completed. The process and other requests were not affected, and nothing stayed locked. The mapper now reads such a `top_provider` as absent, which is how it already treated every other malformed catalog field, and the chosen endpoint's own `max_completion_tokens` is the output ceiling; the draft is otherwise unchanged and no warning is added, because the ceiling comes from the endpoint, not from the malformed field. The price-tier copy from the catalog entry is likewise guarded against a non-object endpoint `pricing` (an endpoint without a readable prompt price was never chosen, so this was not reachable). The generated endpoint test now draws hostile `top_provider` values.

## Security and verification

- **Vendored OAuth2 examples avoid logging credentials** (#674). Authorization codes, callback state, device codes and tokens are no longer printed to captured output. Required human authorization prompts use the controlling terminal and reject control characters in provider values. Gateway cryptographic verification and egress policies remain unchanged.

- **Source comments no longer record review history, and a check keeps it that way** (#595). Comments such as "#98 PR 2 review item 5: ...", "found in the review of #37" or "(review rule 12)" go stale and give the next change a justification to copy instead of a rule to follow; git history and the PR record why. 125 such comments (comment blocks as the check reads them: 93 in `apps/gateway/src`, which show as 106 diff hunks because a few blocks changed in two places, and 32 in `apps/web/src`), plus three web comments that kept a bare review-rule number are restated as the invariant they carried, or dropped where the code already said it; no code changed. `cargo test -p open-model-gateway --all-features --lib source_rules::review_history` and `apps/web/src/lib/review-history.test.ts` (`npm run test:web`) now refuse such comments in production sources, reading real comments (not strings) from a Rust lexer and the TypeScript parser, from one shared pattern file with planted refused and allowed comments; product vocabulary (access-review reviewers, `needs_review`, "security review" as a requirement) passes without an allowlist. A `docs/verification.md` row and one sentence in AGENTS.md state the rule. `proc-macro2`'s `span-locations` feature is enabled for the crate's tests only.
- **Property tests for the parsers the hard pass verified by hand** (#593). The OpenRouter price mapper (`microusd`, `map`, `map_with_endpoints`), the Bedrock Converse request encoder and the OpenAI Responses, Anthropic Messages and Bedrock ConverseStream parsers now have permanent `proptest` properties in place of the throwaway differential tests of the hard pass, each in a `*_property_tests.rs` module next to its target with bounded case counts and no regression file written to the tree. They assert invariants, not old outputs: no panic for any input (valid, mutated by dropping, duplicating, swapping and truncating events, wrong types, huge or negative numbers, oversized strings and unknown fields, or arbitrary JSON); every error is the documented class (each adapter's documented stream-error classes; `InvalidRequest`, `Unsupported` or `InvalidField` for the encoder, each of 34 faults refused with its own class); a stream is never completed by truncation, a driver that stops at the first `Done` sees at most one terminal (by construction of the driver; the Anthropic parser also refuses every frame after `Done`), and usage is exactly as the terminal frames reported it, read independently (absent stays unknown, never `0`) unknown fields in guarded objects refused at any depth, deterministic sweeps of every single mutation of a rich stream, endpoint selection checked against an oracle, and the block, tool and byte limits refusing rather than truncating (a failing generated case must be pasted into a named regression test, as seeds are not persisted); an accepted request is carried whole; and every price is a canonical integer micro-USD amount equal to an independent decimal reference, rounded up and flagged when inexact, with no missing, malformed, negative, over-range or non-string rate ever mapped to a free price. They found three real defects. The first is fixed (see Fixes, #634): `map_with_endpoints` panicked when a catalog entry's `top_provider` was a string, number, boolean or array and the chosen endpoint listed `max_completion_tokens`. The other two are kept as ignored regression tests (#635, #636): a prompt-size tier priced for a meter whose base rate is unusable leaves the price draft without the explicit `unknown` base line (fail-closed downstream and flagged `needs_review`); and the OpenAI Responses `State` has no terminated flag, so a second terminal frame would re-emit `Finish`, `Usage` and `Done` (unreachable through `execute`, which returns at the first `Done`). No gateway behaviour changes.
- **An experimental TLA+ model of the money path** (#594). `spec/formal/` holds a small model of admission, settlement, cancellation, expired-lease reconciliation, operator evidence, failover, crashes, message loss and lease fencing, checked with TLC by `spec/formal/check.sh` (a pinned JRE image run with no network, and `tla2tools.jar` pinned by SHA-256). TLC found no violation of the reservation invariants in the model (the comparison with the code was by reading), deliberate bugs show that several independent guards together keep a settled reservation final, and the comparison exposed the old gateway-run batch runner's missing fencing token, subsequently fixed by #638 in this release. It is documentation and a design-review aid, not a gate: nothing in CI or `package.json` runs it. No gateway code changed.

- **A maintained journey suite for Spark and local-demo environments** (#592). `scripts/journeys` replaces the ad hoc release-candidate scripts: `python3 -I scripts/journeys run --base http://127.0.0.1:3000 --label <tag> --summary .local/journeys/summary.json` (Python 3.12+) signs in as the five demo personas through the real OIDC redirect flow and runs 16 journeys (about 990 checks) against a forwarded environment: sign-in and sign-out, `/me`, workspaces of both shared kinds, keys including rotation, revocation and key policy, inference authentication and the documented `model_not_found` refusal for Chat Completions, Responses and Messages, members and invitations, platform administration and policy composition, model selection, catalogues and the live type defaults (written back unchanged only), the auditor's read-only boundary, access requests and reviews, report schedules, workspace alert rules and legal holds, reports and usage with their documented shape, health, the SPA fallback, CSRF and Origin refusals and the credential boundaries (an inference key or an admin token is not another family's credential, and a scope-gated route accepts a token only with the scope). Every journey has refusal cases, and every refusal check is harmless if the refusal regresses. Each journey creates its data under a unique `journeys-<run>-…` name and undoes it also when it fails (an undo that is refused is a failed check), so journeys run in any order and can be re-run, one run per environment at a time. The suite refuses a non-loopback base, a base with credentials, a gateway whose public origin differs from `--base`, and any gateway whose sign-in is not the passwordless demo issuer. The summary (mode 0600, no symlink) names the label, UTC time, run id, order and seed, and per journey the checks passed and failed with the expected and actual HTTP status and the duration, and never a response body, cookie, key, token or e-mail address, by construction (the recorder accepts only a name, statuses and a note from a fixed list, and check names must be literals). `docs/journeys.md` is the feature map, derived against the route table (`tests/journeys.test.py` fails when a route group of `route_policy.rs` has no row), with every flow that is not covered and why (no model server, provider or file store in the demo). `tests/journeys.test.py` runs in `npm run test:demo`. `docs/verification.md` has the release-candidate steps. No gateway code changed.

- **Five AGENTS.md rules are now checks, and every rule has a row in `docs/verification.md`** (#591). A new table, "AGENTS.md rules and their checks", lists each rule in AGENTS.md's Invariants and Deployment lists with the check that enforces it, or "review only" with the reason, and AGENTS.md points to it. The new checks, each with planted-violation tests that fail first: no `f32`/`f64`, float literal or SQL float cast in money code (the governance, billing, pricing, rates, metering, cost, spend, budget, ledger and rollup files, and any item that names `micro`, `usd`, `cost`, `price`, `spend` or `budget`), with two reviewed exceptions listed by file and item; `serve` never reaches `migrate`, `grants apply`, `bootstrap-*` or `provision-user` (a call graph over the gateway, plus both Dockerfiles running exactly `serve` and the Helm chart's gateway containers, which run `["serve"]` and wait with `wait-for-database --schema`); no provider id, adapter type or provider module named in `inference/`, so providers are reached only through `ProviderAdapter` and `ProviderRegistry`; every value a `tracing` call, `#[instrument]` or `print!` can log in the request path (`inference/`, `providers/`, `protocols/`, `jobs/`, `http.rs`, `auth`) is pinned to a reviewed snapshot, with credential and body words refused and `#[instrument]` without `skip_all` refused; and browser requests stay same-origin and relative, with every absolute URL literal and every `VITE_*` name pinned (none exist) and none allowed to look like a secret. No gateway behaviour changes. The provider-switch check found real switches outside the engine, in admission and batch planning (Anthropic cache-control pricing in three places and `PRIORITY_PROFILES`, the profiles that accept vLLM's `priority` request field); they are listed in the allowlist and left for a follow-up.

## Known limitations and qualification boundaries

- A line finishing after batch takeover can be charged while its result is `result_unavailable`; buffered results can be lost too (#654). Old in-flight calls can temporarily exceed route concurrency (#655), unreferenced files remain until retention cleanup (#656), and native/video poll claims remain soft (#651).
- Accepted-video persistence can fail after provider acceptance (#662). Realtime settlement is outside #639 (#659). A disconnect before the final stream event still retains unknown usage; detached settlement can record successful accounting while request telemetry says cancelled.
- The new resolution actions process eligible retained history only, with no automatic resolution. Pending/unknown lines keep their holds, other unknowns can still prevent archival, and a held floor is not a proven upper cost bound.
- Non-stream error classification remains provider-dependent (#665); an SSE request answered with JSON still fails validation before stream return. Returned streams never retry or fail over. #409 HTTP range changes and held dependency upgrades are not part of this release.
- Spark journeys cover the demo's one gateway pod, OIDC, management and refusal flows. They do not complete provider inference, successful file/batch flows, either resolution action, or multi-replica/Pooler/NetworkPolicy acceptance. Separate PostgreSQL, running-gateway, provider-mock and browser checks remain required. Formal modelling is a design aid, not a proof of the implementation.
