# Open Model Gateway v0.13.0

A minor release after [v0.12.0](v0.12.0.md). It adds reviewed onboarding templates for Teams and Projects (#84). A Platform Admin writes a template, a different Platform Admin reviews it, and once published it creates a Team or Project in one step: the owner and members, catalogs, catalog models and tighten-only local limits. It is a minor release because it adds two migrations (**0074**, **0075**), runtime-grant changes, eight management operations and a new optional field in the shared error envelope.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## New features

- **Onboarding templates** (#84). Platform Admins write templates under `/api/v1/platform/workspace-templates`, from a browser session only (admin tokens are refused). Platform Auditors read them.
  - **Content:** references only, never secrets, emails, platform roles or group mappings. A template sets:
    - the workspace kind (Team or Project);
    - its catalogs: inherit the type's defaults, or a replacement list;
    - catalog models to select;
    - optional local limits, in the object policy form with a `budgets` list;
    - member slots: one owner slot, plus up to 9 admin or member slots, each required or optional, for one person or several.
  - **Versions:**
    - A version is immutable. The database computes its SHA-256 content hash and checks it against the content.
    - A Platform Admin **other than its author** reviews it, and the database checks that too.
    - A reviewed version can be published. Publishing retires the template's previously published version, and any version can be retired.
    - Nothing is deleted.
    - An installation with a single Platform Admin cannot publish templates.
  - **Caps and names:** at most 100 versions per template and 500 templates. Names are unique ignoring case and surrounding spaces.
- **Create a Team or Project from a template** (#84). `POST /platform/workspace-templates/{id}/apply` takes the published `version`, the workspace `name`, a person (or people) per slot and an `idempotency_key`.
  - **What it writes:** one transaction writes only what the applying Platform Admin could already write:
    - the workspace and its owner;
    - the catalog replacement;
    - each catalog model selection, which must be eligible under the resulting catalogs;
    - the local limits, checked tighten-only against the live platform layers exactly as `PUT /workspaces/{ws}/policy` does;
    - a manual grant for each person, who must be live and entitled. It never grants a platform role or a group grant.
  - **All or nothing:** anything that no longer fits refuses the whole application with `409` and changes nothing:
    - `template_version_stale`: not the published version, or retired;
    - `template_reference_unavailable`;
    - `template_model_unavailable`;
    - `template_limits_exceed_platform`;
    - `template_assignment_ineligible`, which names the `slot`.
  - **Body checks:** a missing, unknown or repeated slot, a person in two slots, more than 100 people or more than 10 slots is `400` before any lock is taken.
  - **Records and retries:** each application is recorded with the version and content hash it used. A retry with the same key and body returns the same workspace (`replayed: true`); the same key with a different body is `409`.
- **Workspace templates in the dashboard** (#84). Admin › **Workspace templates** (under People) lists templates and creates them.
  - A template's page lists its versions, with state, author ("You" or "Another admin") and content hash. Each version offers only the step the viewer can take: **Approve** (never the author's own version), **Publish**, **Create workspace** (the published version) and **Retire**. **Add version** starts from the latest content.
  - **Create workspace** asks for the name and a person for each slot, searched by email. It refuses one person in two slots, then opens the new Team or Project.
  - Auditors read without actions.

## Fixes

- A workspace's **Models** page offers **Request** only to members of the workspace, not to a Platform reader viewing it without membership. Submitting would have returned `404` (#453).

## Behaviour changes

- **Management API:** eight new operations under `/platform/workspace-templates` (above), for **263 operations** in total. Each write needs a browser session, Origin and CSRF, and every admin token is refused.
- **Error envelope:** the shared management error envelope gains an optional `slot` detail, set with `template_assignment_ineligible`. Clients with closed schemas need the new contract.
- **New error reasons** (all `409`): `template_version_stale`, `template_reference_unavailable`, `template_model_unavailable`, `template_limits_exceed_platform`, `template_assignment_ineligible`.
- **Audit:**
  - **New actions:** `workspace_template.created`, `workspace_template.version_created`, `workspace_template.reviewed`, `workspace_template.published`, `workspace_template.retired` and `workspace_template.applied`, on resource type `workspace_template`.
  - **On apply:** the workspace, membership, catalog, model and policy events are recorded too, exactly as for the same changes made directly.
  - **Implicit retirement:** publishing a version that replaces a published one also records the implicit `workspace_template.retired`.
- **Personal data:** template and slot names are operator labels; do not put personal data in them. Templates record their authors, reviewers and appliers by user id.

## Contracts and documentation

- **Management OpenAPI:** **263 operations** (was 255), still with no incomplete schema slots.
  - **Templates:** `AccessTemplate`, `AccessTemplateCreated`, `AccessTemplateVersion`, `AccessTemplatePendingVersion`, `AccessTemplateContent` and `AccessTemplateStoredContent`, plus the apply request and response.
  - **Envelope:** the error envelope gains `slot`.
  - **Fixtures:** the contract fixtures walk the template journey and the apply bodies (object and positional forms).
- **Docs:** the management API guide documents templates and applying them, with the migrations, caps and refusals. The dashboard guide documents Admin › Workspace templates. The roadmap marks #84 implemented.

## Migrations and runtime grants

- **0074_workspace_templates:**
  - Adds the insert-only `workspace_templates` (with the unique `lower(btrim(name))` index) and `workspace_template_versions`.
  - **Versions:** created pending on the server clock, with the database computing and CHECKing their content hash. The reviewer is a current Platform Admin other than the author.
  - **Transitions:** review, publication (at most one published version per template) and retirement each happen once, in order. Content, hash and authorship never change.
  - **No deletes:** `DELETE` and `TRUNCATE` are refused.
- **0075_workspace_template_applications:** adds the insert-only `workspace_template_applications`: the version and hash, the workspace (one application per workspace), the applier, and digests of the idempotency key and payload. A trigger binds each row to:
  - a published version with its own stored hash;
  - an applier who is a current Platform Admin;
  - a shared workspace of the template's kind, created in the same transaction.
- **Runtime grants** (`deploy/staging/runtime-grants.sql`, applied by the chart's migrate Job):
  - `SELECT` on the three tables;
  - column `INSERT` of their creation columns;
  - `UPDATE(reviewed_by, reviewed_at, published_at, retired_at)` on `workspace_template_versions`.

  The schema preflight (startup and `/health/ready`) inventories the new tables.

## Tests and CI

- Real-PostgreSQL tests for authoring cover review by a second admin, publication and retirement, the database hash and guards, the caps and near-duplicate names, the content and limits rules, races, demotion and the single-admin case, and the refusals for Auditors, owners, members and outsiders.
- Real-PostgreSQL tests for apply cover:
  - the whole workspace written;
  - every `409` rolling back completely;
  - stale and retired versions;
  - ineligible, disabled and unknown people, reported with the slot;
  - limits above the platform layer;
  - idempotent replay (reordered input, after retirement), and two concurrent applications with one key creating one workspace;
  - the database binding of application rows;
  - Auditor, owner, member and outsider refusals.
- `verify-privileges.sql` probes the new grants and guards under `gateway_runtime`. The contract fixtures cover the new operations.
- Web unit tests cover the templates pages and the #453 fix. A new browser spec walks create, the author unable to approve, a second admin's approval, publish, and creating a Team with an owner and a member.
- The slice 2 management contract fixture now runs on its own 16 MiB thread, because its debug-build stack frame outgrew the 2 MiB test-thread stack.

## Dependencies

No dependency, Rust crate or base-image change. `deny.toml` ignores RUSTSEC-2026-0441 (`pin-utils` unmaintained, reached through `aws-smithy-http`); #456 tracks the AWS SDK update that removes it.

## Known limitations

- An installation with a single Platform Admin cannot publish templates, because a version needs a second admin's review.
- Template content is written as JSON in the dashboard. The server validates it, but there is no structured editor or diff between versions.
- Applying creates a new workspace only. It does not change an existing workspace or re-apply a newer version.

## Upgrade

From **v0.12.0**, replace the image and chart, using the normal drain procedure only after qualification and deployment approval.

1. **Back up.** Take a backup and `verify` it before migrating (`docs/operations.md`, "Upgrade and migration procedure"); the rollback below depends on it.
2. **Drain, then migrate.** A gateway serves only a database whose migrations match its own. v0.13.0 does not start on a v0.12.0 schema. Once 0074 has committed, v0.12.0 does not start and its running replicas report not ready. Drain first.
   - **With the chart:** scale the v0.12.0 Deployment to 0 (and suspend any autoscaler), then `helm upgrade --set migrations.run=true`. The migrate Job is off by default and runs as a pre-upgrade hook.
   - **Without the chart:** run `open-model-gateway migrate` and then `open-model-gateway grants apply` as the migrator.
   - The latest migration is **0075**, with **74 migration records**, and the runtime grants change (above).
   - If the migrate Job fails after a migration has committed, fix the cause and re-run `migrate` and `grants apply` with v0.13.0. Do not `helm rollback`, since v0.12.0 cannot serve that schema.
   - **Locks** (from the SQL, not measured): both migrations only create tables, indexes, functions and triggers on new tables. Their foreign keys take `SHARE ROW EXCLUSIVE` briefly on `users` (0074 and 0075) and on `workspaces` (0075). No existing table is rewritten or scanned.
3. **Start and verify.** Deploy v0.13.0 by verified image digest. Restore the replica count and any autoscaler you suspended (`helm upgrade` may leave a manually scaled Deployment at 0). Wait for `/health/ready` to report `schema: ok`, run `open-model-gateway grants verify`, then check sign-in and one bounded inference request.
4. **Do not** reset or recreate an existing database, run a down migration or bootstrap implicitly.
5. **Rollback.** There are no down migrations. Redeploying v0.12.0 is only safe if no migration ran; otherwise restore the pre-upgrade backup into a new database and cut over. Never run old workers against the new schema.
6. **Clients.** Regenerate generated management clients: there are eight new operations, the error envelope has a new optional field, and there are new error reasons.

From an older release, also follow the [v0.12.0 upgrade instructions](v0.12.0.md#upgrade) and their linked requirements. Publication verification and readiness remain separate from production activation and authenticated/provider acceptance.
