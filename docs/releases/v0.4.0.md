# Open Model Gateway v0.4.0

This release is about scale. Every request used to lock one installation-wide row; that lock is gone, so replicas now add capacity. On the laptop load-test stack, one replica serves about **1,000 ok/s** (about 80 before this work) and three replicas about **1,340 ok/s**. History size no longer matters: a database with 10 million past requests serves the same throughput as a small one.

One workspace or one API key still serializes its own requests on its own budget rows (by design, to keep its budgets exact), so it tops out at a few hundred requests per second. A new **Admission ceiling** alert tells Platform Admins when that happens. The Kubernetes [Helm chart](../kubernetes.md) is new and **beta**. There are three breaking changes below; read them before you upgrade.

## Breaking changes

- **Installation-wide budgets and rate limits are removed** (migration 0026). Limits now exist only on personal/team/project workspaces (type defaults, platform overrides, tighten-only local limits) and on API keys — all still hard limits, exactly as before. `GET`/`PUT /api/v1/platform/installation/policy` now return **`410 Gone`** with `error.reason:"installation_limits_removed"`; scripts that read or wrote installation-wide limits must use workspace-type defaults (`/platform/workspace-types/{kind}/policy`), per-workspace overrides, or key limits instead. Any installation budget alert rule you had becomes a non-blocking **Installation spend** rule (`spend_threshold`), keeping its thresholds and recipients; it never denies a request, it only notifies. The migration records your old installation policy and budgets in the audit log first. Workspaces may now use more in total than a former installation ceiling allowed — move any shared ceiling you relied on into type defaults, overrides or keys before upgrading. See [alerts](../alerts.md#upgrade-from-installation-budget-alerts-0026).
- **Reminder: budgeted requests on an unbounded price return `503 price_unbounded`, not `429 budget_exceeded`.** This shipped in v0.3.2 and nothing about it changes here; it's repeated because the admission path it runs through is rewritten in this release (scoped admission, per-replica caches). If you haven't upgraded past v0.3.2 yet, publish a complete v3 price (every meter priced, `not_applicable` or `unknown`) for any model whose budgeted requests report `price_unbounded`.
- **Workspaces, API keys, deployments (routes) and cost centers can no longer be deleted, truncated, or have their id changed, by any role, including the schema owner** (migration 0034). A key's `workspace_id` can't be changed either, and `async_jobs` can't be truncated. (Deployment price versions and `async_jobs` rows already refused deletion and identity changes before this release.) The product has never performed these operations — it disables, revokes and archives instead — so this should change nothing for normal use. It will break **hand-written operator SQL** that deleted or re-keyed these rows directly: that SQL now fails with a named check (for example, `execution key is not a key of its workspace`) instead of succeeding or hitting a generic foreign-key error.

Also worth knowing before you upgrade, not strictly breaking: new ids for requests, attempts, ledger entries and audit events are UUIDv7 (time-ordered) instead of UUIDv4 — `x-request-id` values change shape, not format, and nothing parses them as anything but a UUID. `GET`/`PUT /platform/installation/policy`'s removal also drops `installation_budgets` from `GET /platform/overview` and `GET /platform/usage/overview`, and the installation (`platform`) row from `GET .../access`'s `layers` (reasons may still name the `platform` layer for model-level facts such as a disabled model). Alert rules can no longer watch an `installation` budget layer (`400 reason:"installation_limits_removed"`); use `spend_threshold` instead.

## Upgrade guide

**Migrations 0024 through 0036.** The headline one is history partitioning (0030/0031): `inference_executions`, `governance_reservations`, `monetary_ledger`, `audit_events` and `storage_usage_hours` become monthly range partitions. Existing rows are **attached**, not rewritten — new partition keys are built as indexes first, the legacy boundary is proven with `CHECK ... NOT VALID` then `VALIDATE`, and the swap is metadata-only. Measured on 2 million seeded attempts: the full 0030–0033 run took **27.7 seconds**, the longest exclusive lock on a history table was **0.68 seconds**, and no concurrent reader ever waited more than 5 ms. Every step is resumable: if `migrate` is interrupted, running it again picks up where it left off. On a large installation, run `open-model-gateway partitions prepare` (as the migrator) before your maintenance window to build the partition key indexes online, ahead of the drain.

Steps:

1. **Back up** with `scripts/backup.py` and check the backup. (0033 also fixes a pre-existing bug: `pg_restore` of a database with any reservations used to fail, because its schema-qualifying helper functions assumed a non-empty `search_path`; `pg_restore` runs with an empty one. If you're upgrading from before 0033, your existing backups are unaffected — only the restore path was broken, and only on databases that had reservations.)
2. **Stop every gateway replica.** Mixed-schema replicas are not supported, and 0026, 0030 and 0031 each briefly freeze history writes (0026: 0.9 s on the 2 M-attempt database; 0030/0031: see above).
3. Run `open-model-gateway migrate` as the migrator role.
4. **Reapply `deploy/staging/runtime-grants.sql`** for the runtime role (or let the Helm chart's migration Job do this — see [Kubernetes](../kubernetes.md#migration-job-and-runtime-grants)). This migration range adds several new grants: `EXECUTE` on the scope-lock helpers (0027); `SELECT`/`UPDATE(version,changed_at)` on `config_versions` and `EXECUTE` on `omg_config_bump` (0028); `SELECT`/`UPDATE` of the lease columns on `work_leases` and `EXECUTE` on the lease helpers (0029); `SELECT` on `history_partitions`, the rollup tables and archive records, plus `EXECUTE` on `omg_ensure_partitions(integer)` and the coverage/rollup helpers (0030–0033; partitions themselves get no grants — they're reached only through their parents); `SELECT`/`INSERT`/`DELETE` and `UPDATE(waits)` on `admission_lock_waits` and `UPDATE` of the two ceiling columns on `alert_rules` (0036). 0034 and 0035 add no new grants, but reapplying the whole file after every migration is still required.
5. Run `deploy/staging/verify-privileges.sql` and confirm the runtime role has exactly the expected privileges — no more, no less.
6. Run `open-model-gateway budget verify` and expect `mismatch_count: 0` and `rate_mismatch_count: 0`.
7. Run `open-model-gateway history verify` and expect `finding_count: 0`.
8. Start the new replicas, wait for `/health/ready`, and check sign-in and one bounded inference request.

**New optional environment variables** (none change existing defaults):

| Variable | Default | Purpose |
|---|---|---|
| `GATEWAY_ADMISSION_MODE` | `scoped` | `global` restores the former installation-row admission protocol for one release, as an operational rollback. No schema change either way; an invalid value fails startup. |
| `GATEWAY_CONFIG_CACHE` | `on` | `off` turns off the per-replica caches of pre-admission reads (no LISTEN connection, no version poll); admission always re-checks authorization live either way. |
| `GATEWAY_LISTEN_DATABASE_URL` | `DATABASE_URL` | The one session connection per replica that `LISTEN`s for configuration changes. |
| `GATEWAY_REPORTING_DATABASE_URL` | unset | An optional read-only reporting replica (or reporting pooler) for reports, usage and logs only — never for admission, settlement or write authorization. |
| `GATEWAY_REPORTING_MAX_LAG_SECONDS` | `30` | A reporting replica replaying WAL further behind than this is skipped in favor of the primary. |
| `GATEWAY_PARTITIONS_AHEAD_MONTHS` | `3` (2–12) | Future month partitions `serve` keeps created ahead of time. |
| `GATEWAY_USAGE_ROLLUPS` | `auto` | `off` answers every usage read from raw history instead of the hourly rollups (identical results, slower). |
| `GATEWAY_HISTORY_RETENTION_MONTHS` | `25` (1–1200) | Months `archive partition` keeps hot before an operator can detach them; the CLI's `--retention-months` overrides it per call. |

**PgBouncer in transaction mode:** `LISTEN` does not work through transaction pooling. Point `GATEWAY_LISTEN_DATABASE_URL` at PostgreSQL directly (or a session-mode pooler database) and budget one extra connection per replica in `max_connections`. Without a working listener, the caches still catch up through a 1-second version poll — nothing is unsafe, just a little slower to notice a configuration change. `migrate` must also run directly against PostgreSQL, never through a transaction-mode pool (it takes a session-level advisory lock). See [operations](../operations.md#pgbouncer).

## Highlights

- **Scoped admission: replicas finally help.** Admission and settlement no longer serialize on the installation row (migration 0027). They take a fixed, deadlock-free sequence of scope locks (workspace type, workspace, user and key lineage) instead, so requests from different workspaces run in parallel; a workspace's own requests still serialize on its own totals rows, which is what keeps its budgets exact. On the laptop stack this raised the ceiling from about 240 to **1,050–1,080 ok/s**, and for the first time three replicas beat one (998 vs 814 ok/s at 1,000/s offered). `GATEWAY_ADMISSION_MODE=global` restores the old protocol for one release if you need to roll back.
- **Per-replica caches, with live revocation.** Each replica now caches key metadata, candidate routes, routing configuration and immutable prices, and learns about changes within milliseconds through PostgreSQL `LISTEN`/`NOTIFY` (about a second without it). Admission still re-checks everything live under its locks, so a revoked key or tightened budget is refused on every replica immediately — tested against a deliberately stale replica for eleven kinds of change. One replica now serves about **1,000 ok/s on a 10-connection pool** (was about 810), and three replicas about **1,340 ok/s**.
- **Monthly history partitions, hourly rollups, and archival.** Request history is partitioned by month so old months stop slowing down or bloating current ones; new months are created automatically ahead of time (an alert fires if they aren't). Long usage ranges and the spend-spike alert read exact hourly rollups instead of scanning raw history. Operators can archive a closed month — checksummed CSV export, then detach — once it's past retention with no pending or unknown cost. **Throughput no longer depends on history size:** converting 2 million seeded attempts took 27.7 s, and three replicas serve the same ~998 ok/s at 1,000/s offered whether the database holds 2 million or 10 million attempts of history.
- **History writes no longer lock their parents.** Every history insert used to take a shared lock on its workspace, key, route, price and cost-center rows through foreign keys, which under load created enough PostgreSQL MultiXacts to force constant anti-wraparound vacuums. Those relationships are now checked by triggers that read without locking (migration 0034), and the parent rows can never be deleted, truncated or re-keyed by any role — which is what makes the lock-free check safe. Load tests at 1,000 requests/s against 10 million rows of history created **zero** MultiXacts (versus up to 5.4 members per request before), and one busy workspace or key is back to about 240–255 requests/s.
- **See when one workspace or key nears its ceiling.** Because a workspace (or key) still serializes its own admissions, it caps out at a few hundred requests/s on typical hardware however many replicas you run. New metrics `gateway_scope_lock_wait_seconds` and `gateway_scope_lock_waiting` show these waits without naming anyone, and a new installation-only alert rule, **Admission ceiling**, names the Team or Project (or says "a personal workspace") whose request rate or lock-wait p95 crosses your threshold — visible to Platform Admins only.
- **Helm chart (beta).** `deploy/helm/open-model-gateway/` deploys the gateway to Kubernetes: a hardened Deployment (non-root, read-only root filesystem, no capabilities, seccomp, no mounted service-account token, `httpGet` probes, `preStop` drain), an explicit pre-install/pre-upgrade migration Job that runs `migrate` and then applies `runtime-grants.sql` (never automatic in `serve`, never the runtime role), an optional CloudNativePG `Cluster`/`Pooler` with operator-managed credentials, default-deny `NetworkPolicy`, and a `loadtest` profile. Validated with `helm lint`/`helm template` across four profiles, `kubeconform` against Kubernetes 1.36 schemas, and a real `kubectl apply --dry-run=server` against a live CloudNativePG 1.30.1 operator. **It is marked beta**: a server-side dry run and a kind smoke test passed, but it has not yet been validated end to end on a production-like cluster under real load. See [Kubernetes](../kubernetes.md).
- **No panics when the OS random number generator fails** (rand 0.10). Creating keys, invitations and sign-in sessions, and writing encrypted files, now fail with an error (`503`, `500` or `unavailable`) instead of panicking.
- **Installation spend alert.** A new non-blocking rule type, **Installation spend** (`spend_threshold`), watches total installation spend (settled plus on hold, every workspace, personal ones as totals) against a reference amount you choose, at up to five percentages. It only notifies — it never blocks a request.

## Added

- Metrics: `gateway_admission_seconds`/`gateway_settlement_seconds` histograms by phase and outcome; `gateway_cache_lookups_total`, `gateway_config_changes_total`, `gateway_config_poll_failures_total`, `gateway_config_listener_up`, `gateway_work_leases_held`, `gateway_work_lease_terms_total`, `gateway_background_runs_total`; `gateway_scope_lock_wait_seconds`, `gateway_scope_lock_waiting`; `gateway_history_partition_months_ahead`, `gateway_usage_rollup_hours_total`, `gateway_history_verify_findings`; `gateway_lock_deadlock_retries_total`.
- New CLI commands: `partitions ensure|status|prepare`, `rollups run --once`, `archive partition <history|audit|storage> <YYYY-MM|legacy>`, `archive verify`, `history verify [--since]`.
- New built-in incidents: `partitions_missing` (installation history tables running low on future partitions) and `history_orphans` (a critical incident opened by the hourly `history_verify` job or an operator's `history verify` run; only a clean `history verify` resolves it).
- New alert rule kinds: `spend_threshold` (Installation spend) and `admission_ceiling` (Admission ceiling, installation-only; its incidents carry the workspace name for Platform Admins only — Auditors see the incident without it, and a personal workspace is only ever named as "a personal workspace").
- `tools/mock-upstream`, `tools/loadgen`, and a laptop load-test stack (`deploy/loadtest/compose.yaml`) used to produce every number in this release's notes; see [operations](../operations.md#multi-replica-load-test-harness).

## Changed

- Admission and settlement take scope locks instead of the installation row lock; every management, SCIM, sign-in and lifecycle change that can affect admission takes the matching scope locks up front, enforced by database triggers (site table in [governance](../governance.md#authority-change-sites)).
- Per-replica database connection shares: each replica now admits on up to half of `GATEWAY_DATABASE_MAX_CONNECTIONS` and settles on up to three tenths (previously a quarter each, because the installation lock serialized them anyway regardless of pool size). Size PgBouncer and `max_connections` accordingly.
- Singleton background jobs (account cleanup, compaction, counter pruning, storage usage, alert evaluation, the file sweeper, the installation-wide reservation gauge) run on one replica at a time, under leases with fencing epochs, instead of on every replica.
- Reservation partitions get tighter autovacuum settings (migration 0035: `autovacuum_vacuum_scale_factor=0.01`, `autovacuum_vacuum_threshold=10000`, `vacuum_index_cleanup=on`) so the dead rows every settled reservation leaves behind are cleaned up faster; measured dead-row count on a 2 million-attempt database fell from about 280,000 to 7,700, raising saturation throughput by about 4.3%.
- Routing's seeded weighted choice among equal-priority routes now uses rand 0.10's generator; the same request seed may pick a different route than before an upgrade (same weights and distribution overall; seeds are per-request and never stored).
- Reports, usage, logs, `/me` and `/v1/models` already read from snapshot transactions without the installation or catalog lock (shipped earlier in this cycle); an optional reporting replica is now configurable through `GATEWAY_REPORTING_DATABASE_URL`.
- Configuration changes now reach other replicas' caches within milliseconds rather than instantly; during that short window a revoked, disabled or expired key used on another replica is still refused immediately by admission's live re-check, with the same `401 authentication_error` as before — nothing is ever sent upstream on stale authorization. Files, batches, videos and realtime always authenticate live, uncached.

## Fixed

- `pg_restore` of a database with any reservations used to fail, because the CHECK-constraint validator functions called between schemas assumed a non-empty `search_path`, which `pg_restore` does not provide. The calls are now schema-qualified (migration 0033).
- A request cancelled just after `BEGIN` could return its pooled database connection to the pool while still inside a transaction; transactions now begin in a detached task, and a direct `Pool::begin()` call is a clippy error going forward.
- Expired-lease reconciliation and the reservation index admission reads no longer wait on 20%-of-partition autovacuum thresholds that large partitions rarely crossed in practice (see autovacuum tuning above).

## Known limitations

- The Helm chart is **beta**: validated with `helm lint`/`template`, `kubeconform`, a server-side dry run against a live CloudNativePG webhook, and a `kind` smoke test (install, migration, readiness, an idempotent upgrade, pod deletion under the PodDisruptionBudget, primary-pod-kill recovery). It has not been run against sustained production load or validated on a non-homelab cluster.
- `GATEWAY_ADMISSION_MODE=global` is a one-release rollback. A future release may remove it; don't build permanent automation around it.
- One workspace or one API key still tops out at a few hundred admissions/s on typical hardware (its own totals rows serialize it, by design, to keep budgets exact). Sharding one scope's totals across several rows (decision gate P3b) remains a possible follow-up and is not implemented.
- Development software: not accepted for production. Production load on a non-laptop cluster, live identity provider and SCIM acceptance at this scale, off-host recovery, and an independent security review remain open.

## Verifying the images

The image is `ghcr.io/ncecere/open-model-gateway`, tagged `v0.4.0`, `v0.4` and `latest-release`. Deploy by digest: the digest is in the GitHub Release, its `open-model-gateway-v0.4.0.digest.txt` asset, and the workflow's job summary.

Verify the signature with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer** (keyless, GitHub Actions OIDC). The signature is stored in cosign v3's bundle format, so cosign v2 reports "no signatures found":

```sh
cosign verify ghcr.io/ncecere/open-model-gateway@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/open-model-gateway/.github/workflows/image.yml@refs/tags/v0.4.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The signature covers the multi-arch index, and so every tag that points at it. The SBOM (SPDX) and build provenance are attached to the image as attestations:

```sh
docker buildx imagetools inspect ghcr.io/ncecere/open-model-gateway@sha256:<digest> --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/ncecere/open-model-gateway@sha256:<digest> --format '{{ json .Provenance }}'
```

The Release also carries each platform's SBOM as `open-model-gateway-v0.4.0-linux-<arch>.sbom.spdx.json`, with `checksums.txt` (`sha256sum -c checksums.txt`). The Helm chart (`deploy/helm/open-model-gateway/`, chart version 0.4.0) defaults `image.tag` to `v0.4.0`; its digest is unknown until this image is published, so pin `image.digest` to the verified digest above before a real rollout — the chart's `image.tag` default is for local and development iteration only.
