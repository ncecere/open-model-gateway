# Open Model Gateway v0.3.0

v0.3.0 adds an encrypted file store, a gateway-owned Files API, a batch engine for any model with capacity-aware scheduling for self-hosted servers, and a "Jobs at once" limit. It retires the video provider, which OpenAI shut down. It is also the first release with signed multi-arch images, a security policy and an MIT license. It covers commits `2c0b9f1`, `0e1bde3` and `ba3525e` after [v0.2.0](v0.2.0.md), plus the Portal logo, the uploaded installation logo and the release tooling.

## Highlights

- **Encrypted file store** ([file storage](../file-storage.md)): local disk or S3-compatible storage (AWS S3, MinIO, RustFS, R2) with per-object keys, chunked AES-256-GCM and rotatable master keys. Per-purpose retention, a sweeper, `open-model-gateway files verify` and `files sweep`, and Admin › Settings › Data & privacy › Storage with a health test. CI runs the S3 tests against MinIO and RustFS containers.
- **Files API** ([Files API](../files-api.md)): OpenAI-compatible `/v1/files` on the encrypted store, with streamed uploads and downloads, workspace-scoped file ids, purposes and expiry. A stacked **Storage** quota (type default 1 GiB, platform override, tighten-only local limits) is enforced while uploads stream. Hourly storage usage is shown as GB-days and is **not charged**. New Workspace › Files page.
- **Batches for any model** ([batches](../batches.md)): `/v1/batches` for Chat Completions, Responses, Embeddings and Messages lines, validated up front. A batch runs natively on OpenAI Batch or Anthropic Message Batches when every line routes to one deployment, and otherwise line by line through the normal engine, each line with its own reservation, exactly-once claims, restart resume and no implicit retries. Batch prices are a separate, published price list, never derived. Encrypted output and error files, Logs › Batches with progress and cancel, `batch_failed` and `batch_stalled` alerts, and metrics.
- **Capacity-aware batch scheduling** ([scheduling](../batches.md#scheduling-on-self-hosted-models)): per-route batch settings for gateway-run lines: lines at once (default 2), yield to live traffic, an optional vLLM `/metrics` load signal on an approved local endpoint (fails closed), an optional vLLM `priority` hint, IANA time windows, fair sharing across workspaces and batches, and `completion_window` of 24h, 48h, 72h or 168h with partial results on expiry.
- **Jobs at once:** a stacked concurrent-job limit (default 2 per workspace). Video and batch jobs no longer take request slots or count against requests and tokens per minute, but they stay budgeted. A refusal is `job_limit_exceeded`.
- **SCIM can't remove the last Platform Admin:** such changes are refused whole with `409`, audited and raised as an alert ([operations](../operations.md)).
- **Portal logo and uploaded installation logo:** the app now uses the Portal mark (sidebar, sign-in page, favicon). Admins can upload a PNG, JPEG or WebP logo (at most 512 KiB, stored in the encrypted file store) in Admin › Settings › General; it replaces Portal in the sidebar and on the sign-in page and is served same-origin at `GET /api/v1/branding/logo`.
- **Realtime holds** are sized from the session's reported context plus new client input, capped at the model's ceiling. Responses capped by the hold show as Incomplete.
- **Release engineering:** multi-arch images (linux/amd64, linux/arm64) on `ghcr.io/ncecere/open-model-gateway`, each architecture put through the staging rehearsal before it's tagged, scanned with Trivy, with SBOM and provenance attestations and cosign keyless signatures; [`SECURITY.md`](../../SECURITY.md) and the MIT [`LICENSE`](../../LICENSE).
- The binary (`--version`), the `gateway_build_info` metric and the npm packages report `0.3.0`.

## New environment variables

| Variable | Default | Purpose |
|---|---|---|
| `GATEWAY_FILE_STORE` | `off` | `off`, `local` or `s3` |
| `GATEWAY_FILE_ENCRYPTION_KEYS_ENV` | none | Required when the store is on: the **name** of the variable that holds the master keys |
| `GATEWAY_FILE_STORE_DIR` | none | `local`: an absolute, private directory |
| `GATEWAY_S3_BUCKET`, `GATEWAY_S3_PREFIX`, `GATEWAY_S3_REGION`, `GATEWAY_S3_ENDPOINT`, `GATEWAY_S3_ENDPOINT_ALLOWLIST`, `GATEWAY_S3_FORCE_PATH_STYLE`, `GATEWAY_S3_AUTH`, `GATEWAY_S3_ACCESS_KEY_ID_ENV`, `GATEWAY_S3_SECRET_ACCESS_KEY_ENV`, `GATEWAY_S3_CA_FILE` | see [file storage](../file-storage.md#configuration) | The S3-compatible store; endpoints must be allowlisted |
| `GATEWAY_FILES_MAX_BYTES` | 200 MiB | Largest Files API upload |
| `GATEWAY_BATCH_WORKERS` | `4` | Gateway-run batch lines at once per process; `0` turns the runner off |
| `GATEWAY_BATCH_CONCURRENCY` | `2` | Lines of one batch at once |

`GATEWAY_MAX_BATCH_FILE_BYTES` and `GATEWAY_BATCH_MAX_OUTPUT_SCAN_BYTES` are still validated at startup but no longer used.

## Breaking and behaviour changes

- **Video has no supported provider.** OpenAI shut down the Sora 2 models and the Videos API on 2026-09-24, so `/v1/videos` returns `unsupported_capability`. An OpenRouter video adapter is planned.
- **`/v1/files` and `/v1/batches` need the file store.** Files are now stored by the gateway, encrypted, instead of being passed through to OpenAI. With `GATEWAY_FILE_STORE=off` (the default) the Files API returns `503 file_storage_not_configured`. Configure the store and its master keys before relying on batches. Batches created through v0.2.0's OpenAI passthrough are still polled until they settle.
- **`logo_url` is deprecated.** It is still accepted by the API but no longer shown anywhere, and uploading a logo clears it. Upload a logo instead (it needs the file store).
- **Jobs at once:** workspaces can run at most 2 video or batch jobs at once by default. Review Admin › Settings › Defaults & limits if they routinely run more.
- **Storage quota:** each workspace has a 1 GiB storage quota by default.
- Runtime grants cover the new tables. Reapply `runtime-grants.sql` after migrating.

## Upgrading from v0.2.0

1. Take a backup with `scripts/backup.py` and check it; run a restore drill, since this release has migrations ([operations](../operations.md#upgrade-and-migration-procedure)).
2. Pull the new image by digest and [verify its signature](#verifying-the-images).
3. Stop ingress and the gateway: mixed-schema replicas are not supported.
4. Run `open-model-gateway migrate` as the migrator. Nothing migrates on `serve`.
5. Reapply `deploy/staging/runtime-grants.sql` for the runtime role. `python3 scripts/staging.py migrate` does steps 4 and 5.
6. Run `open-model-gateway budget verify`; it must report no mismatches.
7. If you use files or batches, set `GATEWAY_FILE_STORE` and the encryption keys, then run `open-model-gateway files verify`.
8. Start v0.3.0, wait for `/health/ready`, and check sign-in and one bounded inference request.

To roll back, restore the pre-upgrade backup into a new database and redeploy the v0.2.0 build. There are no down migrations.

## Known limitations

- Development software: not accepted for production. Production load, live identity provider and SCIM acceptance, off-host recovery and an independent security review are still open.
- **Video is retired** until the OpenRouter adapter lands; video remix, edits and references are not implemented.
- **Live verification:** batches had one capped live check (2026-10-09, official `openai` Python SDK): a native Anthropic batch and a gateway-run mixed batch completed and settled exactly; a native OpenAI batch was accepted but hadn't finished after 53 minutes, so its collection wasn't observed. Realtime had one capped live check against `gpt-realtime-mini`. Batch scheduling is mock-tested only, not against a live vLLM server. The Files API was tested with mocks and the official OpenAI Node SDK, without paid calls.
- Chat and Responses requests can't reference a `file_id` yet, and storage has no price.
- Native batches only on OpenAI and Anthropic; image edits, vision input and token-by-token Responses and Messages streaming are not implemented.
- arm64 images are built and rehearsed on GitHub's arm64 runners; no arm64 production deployment has been accepted.

## Verifying the images

The image is `ghcr.io/ncecere/open-model-gateway`, tagged `v0.3.0`, `v0.3` and `latest-release`. Deploy by digest: the digest is in the GitHub Release, its `open-model-gateway-v0.3.0.digest.txt` asset, and the workflow's job summary.

Verify the signature with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer** (keyless, GitHub Actions OIDC). The signature is stored in cosign v3's bundle format, so cosign v2 reports "no signatures found":

```sh
cosign verify ghcr.io/ncecere/open-model-gateway@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/open-model-gateway/.github/workflows/image.yml@refs/tags/v0.3.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The signature covers the multi-arch index, and so every tag that points at it. The SBOM (SPDX) and build provenance are attached to the image as attestations:

```sh
docker buildx imagetools inspect ghcr.io/ncecere/open-model-gateway@sha256:<digest> --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/ncecere/open-model-gateway@sha256:<digest> --format '{{ json .Provenance }}'
```

The Release also carries each platform's SBOM as `open-model-gateway-v0.3.0-linux-<arch>.sbom.spdx.json`, with `checksums.txt` (`sha256sum -c checksums.txt`).

Images from `main` are tagged `sha-<short commit>` and signed the same way, with the identity ending `@refs/heads/main`.
