# Open Model Gateway v0.15.0

A minor release after [v0.14.1](v0.14.1.md). It adds keys to access reviews (#90), which completes access reviews and R18 (#42). A review can now cover the keys of Teams and Projects as well as memberships and platform roles. Each workspace's owners and admins keep or revoke each key. **A reviewer's removal of a key is real, immediate and permanent:** the key is revoked at once (its replacement, if it was rotated after the review started) and a revoked key never returns.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## New features

- **Keys in access reviews** (#90). A review can cover the keys of Teams and Projects (`workspace_keys`), alone or with memberships and platform roles.
  - **What it reviews:** one item per live key lineage of an enabled Team or Project.
    - Human keys and service-account keys are both included; a personal workspace's keys never are.
    - A disabled key is included, since it can be enabled again. A revoked or expired key is not.
    - A rotation keeps the lineage, so rotating a key does not end its review.
    - The workspace filter narrows keys as it narrows memberships.
  - **Who reviews:** the workspace's owners and admins, never the key's own holder. Platform Admins are not key reviewers, because they have no key authority in a workspace they do not administer. Key items are never assigned to a reviewer (`409 access_review_reviewer_ineligible`).
  - **The decisions:** **Keep** or **Remove**. Remove revokes every unrevoked key of the lineage at once, as the revoke route does (the same locks, update and protections), with one `key.revoked` audit event per key. A key rotated after the review started is revoked through its replacement. There is no flag for keys (`409 access_review_flag_requires_group`).
  - **Privacy:** in a review's platform views, Platform Admins and Auditors see key items as Key safety's platform scope shows keys: the key id, workspace, holder kind, expiry and last use.
    - Those views never show the key's name, its holder or its service account. This holds in the item list, the assignment response and the CSV export. It does not change what the audit log already shows them, such as who created a key.
    - A Platform Admin who also owns or administers the workspace reviews its keys as any owner or admin does.
    - Whether a key has a reviewer, and the order of items, never depend on its holder.
    - Reviewers see a key as the workspace key list shows it: its name, the service account, and the holder's name and email only while the holder belongs to the workspace.
- **Dashboard.**
  - **Admin › Access reviews** offers **Team and Project keys** when starting a review.
  - **Review access** shows a key with its name, holder, expiry and last recorded use. A key is kept or revoked. The confirmation names the holder and the start of the key id, since key names are not unique, and says that new requests are refused at once and a revoked key never returns.
  - **A review's page** under Admin shows keys as a member's key or a service account key with the start of the id, never a name or holder. It offers no reviewer assignment for keys; the Reviewer column says **Owners and admins**.

## Behaviour changes

- **Access review items:**
  - `subject_kind` gains `workspace_key`.
  - `user_id`, `role` and `source` may now be null (key items).
  - Every item gains `api_key_id`, `key_name`, `holder_kind`, `service_account_id`, `service_account_name`, `expires_at` and `last_used_at`. They are null for memberships and platform roles.
- **Campaigns:** `subjects` gains `workspace_keys` (up to three subjects), and `counts.by_kind` gains `workspace_key`. `counts.by_source` counts grants only, since keys have no source.
- **Workspace filter:** `workspace_ids` is accepted with `workspace_keys` as well as `workspace_memberships`.
- **Export:** the CSV appends four columns: `api_key_id`, `holder_kind`, `expires_at` and `last_used_at`. Scripts that read columns by position are unaffected; scripts that check the column count need updating.
- **Item order:** items list memberships, then keys, then platform roles.
- **Audit:** a key removed by a review records `key.revoked` for each key of the lineage, in addition to `access_review.decided`.

## Contracts and documentation

- **Management OpenAPI:** still **272 operations**; no operation was added. The access review schemas change as above, and the platform item schema types `key_name`, `service_account_id` and `service_account_name` as `null` (the holder fields stay nullable, since membership items set them). Strict generated clients must be regenerated.
- Both OpenAPI documents' `info.version` is `0.15.0`.
- **Docs:** the management API guide documents keys in reviews (the snapshot, reviewers, removal and privacy), the dashboard guide documents the pages, and the roadmap marks R18 delivered.

## Migrations and runtime grants

- **0080_access_review_keys:**
  - re-adds the campaign subjects CHECK to allow `workspace_keys` (this scans the campaigns table);
  - re-adds the items' subject-kind CHECK to allow `workspace_key` (this scans the items table);
  - adds the item columns `api_key_id`, `key_lineage_id` and `service_account_id`, and makes `user_id`, `role` and `source` nullable for key items only (a shape CHECK, which scans the items table again);
  - adds scoped foreign keys to `api_keys` and `service_accounts`, and `UNIQUE (campaign_id, key_lineage_id)`;
  - replaces the campaign, item and decision guards, the deferred removal check and the three reviewer functions. Person checks in the reviewer functions are NULL-safe. The removal check refuses a remove decision on a key unless the whole lineage is revoked.
  - The database derives a key item's key, lineage, workspace and holder; the runtime supplies only `api_key_id`.
- **Runtime grants** (`deploy/staging/runtime-grants.sql`, applied by the chart's migrate Job): `INSERT (api_key_id)` added on `access_review_items`. `verify-privileges.sql` probes key items under `gateway_runtime`.

## Tests and CI

- **Real PostgreSQL:** 46 access-review tests, 6 of them for keys. The key tests cover:
  - the snapshot and the database guard refusals;
  - masking in every platform view, and an item order, `reviewable` flag and assignment answer that do not depend on the holder;
  - reviewers against the holder, Platform Admins and outsiders;
  - removal through a rotation, its audit, and the key never returning;
  - expiry, last use and a holder who left the workspace.
- **Web and browser:** web tests cover keys in the three pages. A browser spec has a member issue a key that works on `/v1/models`, the Team's owner revoke it from Review access, and the key then refused with 401, while the Platform Admin's page shows no key name or holder.

## Dependencies

No dependency, Rust crate, GitHub Action or base-image change.

## Known limitations

- **A key held by the workspace's only owner or admin** has nobody who may decide it, because nobody reviews their own key and keys are never assigned. It is not marked **No reviewer** (that would reveal the holder to platform readers) and stays undecided; closing the review is the remedy. For a key, **No reviewer** means the workspace has no owner or admin at all.
- **Service accounts themselves** are not review subjects; their keys are.
- **Last use** is the latest recorded request. A key shows no recorded use once its request history has been archived.
- **A rotated key** keeps its review, but the item's key id is the one it had when the review started.
- **Reviews are still started by hand:** there is no recurring schedule, so a periodic review means a Platform Admin starts one each period.
- **Personal workspaces' keys** are never reviewed.
- The other limitations of access reviews are as in [v0.14.0](v0.14.0.md#known-limitations): one-off reviews that snapshot once, due dates that only remind, flags that only record, and records kept indefinitely.

## Upgrade

From **v0.14.1**, replace the image and chart, using the normal drain procedure only after qualification and deployment approval.

1. **Back up.** Take a backup and `verify` it before migrating (`docs/operations.md`, "Upgrade and migration procedure"); the rollback below depends on it.
2. **Drain, then migrate.** A gateway serves only a database whose migrations match its own. v0.15.0 does not start on a v0.14.1 schema. Once 0080 has committed, v0.14.1 does not start and its running replicas report not ready. Drain first.
   - **With the chart:** scale the v0.14.1 Deployment to 0 (and suspend any autoscaler), then `helm upgrade --set migrations.run=true`. The migrate Job is off by default and runs as a pre-upgrade hook.
   - **Without the chart:** run `open-model-gateway migrate` and then `open-model-gateway grants apply` as the migrator.
   - The latest migration is **0080**, with **79 migration records**, and the runtime grants change (above).
   - If the migrate Job fails after the migration has committed, fix the cause and re-run `migrate` and `grants apply` with v0.15.0. Do not `helm rollback`, since v0.14.1 cannot serve that schema.
   - **Locks** (from the SQL, not measured): 0080 alters `access_review_campaigns` and `access_review_items`; its three CHECKs scan those tables (one the campaigns, two the items) and the new UNIQUE builds an index on the items. The new foreign keys briefly take `SHARE ROW EXCLUSIVE` on `api_keys` and `service_accounts`. Those locks queue behind open transactions on those tables and block their writers while they wait, so do not migrate while other writers are active (the drain above covers the gateway).
3. **Start and verify.** Deploy v0.15.0 by verified image digest. Restore the replica count and any autoscaler you suspended (`helm upgrade` may leave a manually scaled Deployment at 0). Wait for `/health/ready` to report `schema: ok`, run `open-model-gateway grants verify`, then check sign-in and one bounded inference request.
4. **Do not** reset or recreate an existing database, run a down migration or bootstrap implicitly.
5. **Rollback.** There are no down migrations. Redeploying v0.14.1 is only safe if no migration ran; otherwise restore the pre-upgrade backup into a new database and cut over. Never run old workers against the new schema.
6. **Clients.** Regenerate generated management clients: access review items, campaigns and counts have new and newly nullable fields.

From an older release, also follow the [v0.14.1 upgrade instructions](v0.14.1.md#upgrade) and their linked requirements. Publication verification and readiness remain separate from production activation and authenticated/provider acceptance.
