# Open Model Gateway v0.16.0

A minor release after [v0.15.1](v0.15.1.md): operators can now see why accounting failed (a new counter and log line, #389), the SCIM documentation says what to set up before the first push (#390), and the gateway's largest source files were split into child modules with no behaviour change. One operator-visible change besides the new metric: some log events now carry a child module as their target, because the code that writes them moved ([below](#behaviour-changes)). No migration, no runtime-grant change. The OpenAPI documents change only in description text (`description`, `x-omg-unobserved-branch` and `x-omg-unobserved-parameter` strings in the management document, which now name the new source files) and in `info.version`; no operation, parameter, schema or response changed, and the inference document changes only in `info.version`. The schema stays at **0080**, so a v0.15.1 database is served as it is.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## New

- **The cause of `503 accounting_unavailable` is recorded** (#389). Until now nothing in production said why accounting failed. Each failed accounting operation increments the new counter `gateway_accounting_failures_total{stage,cause}` and writes one `WARN` log line, `accounting unavailable`, with the same two fields and nothing else.
  - `stage`: `route_lookup`, `pool_acquire_and_begin`, `governance_storage`, `explicit_settlement`, `cancellation_settlement`.
  - `cause`: `pool_timeout`, `pool_closed`, `lock_timeout` (SQLSTATE 55P03), `statement_timeout` (57014), `backend_terminated` (57P01), `deadlock` (40P01 after the re-runs were used up), `read_only_transaction` (25006), `other_database`, `io`, `tls`, `protocol`, `worker_crashed`, `other`; and, for the two settlement stages (the 3 s settlement deadline), what the settlement was waiting on when it elapsed: `deadline_in_queue`, `deadline_acquiring_connection` or `deadline_in_database`.
  - Both labels are fixed lists (5 stages and 16 causes, at most 80 combinations; the code produces at most 45). An unrecognised SQLSTATE counts as `other_database`; no SQL, SQLSTATE, message or identifier is exported or logged. `pool_timeout` also covers a new connection that could not be opened in time (connection refused, the server at its connection limit or still starting), because the driver retries those until the acquire timeout. A starved pool at settlement usually appears as `explicit_settlement`/`deadline_acquiring_connection`, and settlements queued behind it as `deadline_in_queue`.
  - Nothing is recorded when accounting succeeds, and no series exists before the first failure: an alert on this counter must treat a missing series as zero.
  - Background accounting (reconciliation of expired holds, batch and job accounting, realtime session accounting) and an operator's usage reconciliation (`503 Reconciliation unavailable`) are counted too, so the counter can be higher than the number of `accounting_unavailable` responses.
  - The log line carries `request_id` only when the failure happens before the response headers are sent; not for the settlement of a streamed or cancelled response, a realtime session after its upgrade, or background work.
  - The counter is in the System class of the OTLP metrics export, so it is exported wherever that export is enabled.

  See [operations: accounting failures](../operations.md#accounting-failures). Not every path is covered yet ([known limitations](#known-limitations)).

## Behaviour changes

- **Some log events have a new target.** Code that moved into child modules (#512, #515, #518, #525) now logs under that module's target, for example `open_model_gateway::identity::session` instead of `open_model_gateway::identity`. The messages and fields are unchanged, and a prefix filter such as `RUST_LOG=open_model_gateway=info` still matches them; only a filter or query on an exact target needs updating. The events:
  - `open_model_gateway::commands::serve`: `file store configured`, `gateway listening`, `metrics listening`, `metrics listener stopped` (were `open_model_gateway`, from `main.rs`);
  - `open_model_gateway::commands`: `could not update the history_orphans incident` (was `open_model_gateway`);
  - `open_model_gateway::identity::session`: `could not record session activity`;
  - `open_model_gateway::alerts::evaluation`: `alert budget evaluation truncated`; `open_model_gateway::alerts::key_expiry`: the key-expiry reminder cap warning;
  - `open_model_gateway::jobs::runner::line`: `batch line state not recorded`; `open_model_gateway::jobs::runner::segments`: `batch segment not recorded ...` and `batch segment not stored ...`; `open_model_gateway::jobs::runner::repository`: the ungated batch line admission refusal.

  The governance, SCIM and metrics splits moved no log events.

## Internal restructuring

For contributors; no gateway behaviour changes beyond the log targets above.

- **A structure ratchet** (#500): `npm run test:structure` (in CI) fails when a gateway source file passes 800 production lines or a file already over the limit grows; `tests/structure-allowance.json` lists today's exceptions and can only shrink. Clippy checks `too_many_lines` and `cognitive_complexity`, with today's offenders marked `expect(..., reason = "#499")`. See [verification](../verification.md#structure-ratchet).
- **File splits, code moved unchanged**, every public path the same, each file leaving the allowance list: `governance.rs` (#503), `scim.rs` (#505), `identity.rs` (#512), `alerts.rs` (#515), `jobs/runner.rs` (#518), `metrics.rs` (#517; metric names, help text, labels, buckets and exposition order unchanged), `route_policy.rs` (#521: `ROUTES` is now a one-line-per-route `routes! { ... }` table, the same 284 routes in the same order) and `run` in `main.rs` (#525: each subcommand in its own function in `commands.rs`, `serve`'s start-up in named steps in `commands/serve.rs`, in the same order; `serve` still never migrates or bootstraps).
- **Guards that missed code now read all of it**: the randomness source scan reads whole files instead of stopping at the first `#[cfg(test)]`, which had cut 138 of 231 files, and knows more crate and function names (#506; it found nothing new); route authorization is pinned by a committed snapshot, `apps/gateway/src/route_policy.snapshot`, so a weakened declaration fails a test, and a change to the snapshot is an authorization change that needs a security review (#522); the metrics registration inventory reads `metrics.rs` and every file in `metrics/` (#517).
- **Supply-chain test**: refuses Dockerfile constructs that could make it read a stage BuildKit does not build, and `ADD` or an external image in `COPY --from=` or a mount (#485); neither Dockerfile used them. The local supply-chain tests now require Bash 4.4 or newer first on `PATH` and fail, never skip, otherwise (#380; macOS's `/bin/bash` 3.2 is refused). See [verification](../verification.md#supply-chain).

## Dependencies and CI

- **`rustix` 1.1.6** (#491), for RUSTSEC-2026-0486. It reaches the build only through `tempfile`, a test dependency, so it is not in the gateway binary.
- **CI runs on an exact runner image** (#491): `ci.yml` now names `ubuntu-24.04` instead of `ubuntu-latest`, like every other workflow; the supply-chain test refuses a floating, self-hosted or computed runner and a reusable workflow from outside the checkout.
- **CI no longer installs operating-system packages at run time** (#491): `age` for the backup tests is the pinned v1.3.2 release, checked by SHA-256, and Playwright installs its browser without `--with-deps`. Unpinned `apt-get` had failed three jobs on every pull request when the runners could not resolve the Ubuntu mirrors on 2026-11-11. The supply-chain test refuses a package manager in any workflow `run:` step (not in scripts those steps call).

The runtime image, its base and the gateway's runtime dependencies are unchanged.

## Known limitations

- **Accounting failures are not attributed everywhere yet** (#497): realtime accounting deadlines, database errors in the job runner itself (`jobs/*`), `maintenance.rs`, and key authentication with an exhausted pool (the client gets `503 api_error`) still fail with no counted cause, as does an `accounting_unavailable` from an internal consistency check, which has no database cause.
- **`serve` keeps its job leases after a failed start-up** (#527). When start-up fails after the background-job leases are taken (for example a public or metrics port already in use), the process exits without releasing them, and another replica cannot run those jobs until the leases expire, one lease period. This was already true in v0.15.1.

## Upgrade

From v0.15.1 there is no migration and no grant change: deploy v0.16.0 by verified image digest, as a normal rolling update. Update any log filter or query that matches one of the [moved targets](#behaviour-changes) exactly.

From an earlier release, follow the upgrade steps of each release in between, in order; the last migration is 0080 in [v0.15.0](v0.15.0.md#upgrade). v0.16.0 can be the image you finish on: it serves the same schema as v0.15.0 and v0.15.1.

Rollback to v0.15.1 is a redeploy of its image; nothing in the database changes.
