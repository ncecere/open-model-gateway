# Open Model Gateway v0.15.1

A patch release after [v0.15.0](v0.15.0.md): one sign-in fix, a dependency round that removes three security-advisory exceptions, and an image scan on pull requests. No migration, no API or contract change, no runtime-grant change. The schema stays at **0080**, so a v0.15.0 database is served as it is.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## Fixes

- **Sign-in no longer fails when the identity provider closes an idle connection** (#417). The gateway kept its connection to the provider open between requests. A token request sent just as the provider closed that connection was lost, and identity requests are never retried, so the callback answered `400 Login verification failed` and the person had to start again. Each identity request (discovery, token, signing keys) now uses a new connection. A request that fails for another reason (the provider is unreachable or times out) still ends that sign-in, because an attempt is single-use. Measured against the local demo issuer, which closes a connection idle for about six seconds; any provider or load balancer with an idle timeout could cause it.

## Behaviour changes

All three come with the AWS SDK bump (#456) and affect only the Bedrock provider and the S3 file store.

- **AWS requests are signed with the gateway host's clock only.** The new SDK generation corrects for clock skew by default: after any response it takes the difference between the response's `Date` header and its own clock, and signs every later request that far off. In a test, one response dated an hour in the past moved the signing time of the next request by an hour, for Bedrock, S3 and STS alike. That lets a response (or, on an `http://` S3 endpoint, anyone on the path) choose the signing time, so the correction is turned off on the S3 and Bedrock clients and on the gateway's STS client for `aws:role:`. This is how the gateway behaved before the bump; keep the host's clock synchronised. Clients that `aws-config` builds internally for a profile's own role chain keep the SDK default.
- **Credential loading still waits 5 seconds at most.** The new SDK derives the wait from the operation timeouts (20 s for Bedrock, 300 s for S3); the gateway sets 5 s, the previous value, so a stuck credential source fails a request quickly.
- **A Bedrock stream that is broken at its first frame now fails in the stream.** The old SDK read the first raw frame before returning, so a corrupt first frame was an HTTP error. The new one returns once the response headers arrive: the client receives a `200` stream that ends in an error, with no `Done`. It still fails closed and is never retried. #486 tracks whether failures before the first content event should be request failures.

Unchanged, and now pinned so a later bump cannot change them silently: one attempt per request (no retries), the SDK behaviour version (`v2026_01_12`, which is what `latest()` meant before and after the bump), no flexible checksums on S3 requests.

## Dependencies

Every update was reviewed against its changelog and source diff; versions, checksums, publishers and install scripts were checked against the registries.

- **AWS SDK for Rust** (#456): `aws-sdk-s3` 1.122.0 → 1.156.0, `aws-sdk-bedrockruntime` 1.124.0 → 1.152.0, `aws-config` 1.8.13 → 1.13.0, with the smithy runtime crates of the same generation. Removes `lru` 0.16 (RUSTSEC-2026-0253) and `pin-utils` (RUSTSEC-2026-0441). The versions are the release train published by 2026-10-30, not the newest, with one exception: `arc-swap` 1.9.5 (2026-11-09), because 1.9.3 has a memory-safety bug in the call the SDK's new endpoint cache makes on every request.
- **`openidconnect`** 4.0.1 → 4.1.0 (#461): moves the elliptic-curve crates to the generation that fixes RUSTSEC-2026-0387 (`crypto-bigint`). The library's verification code is unchanged; ES256 and ES384 verification now runs on new curve crates, and a test checks both against signatures made by an independent implementation. RSA verification is unchanged (`rsa` 0.9.10, RUSTSEC-2023-0071 still applies and stays the one documented exception).
- **`jiff`** 0.2.38 → 0.2.39 and **`prometheus-client`** 0.25.1 → 0.25.2 (#461). `prometheus-client` now escapes `\`, `"` and newlines in label values in the `/metrics` text, which is what the format requires; a provider or model label containing `"` or `\` was written raw before.
- **`cargo-deny` exceptions**: three removed (RUSTSEC-2026-0387, RUSTSEC-2026-0253, RUSTSEC-2026-0441); one remains (RUSTSEC-2023-0071).
- **Dashboard** (#473): `@tanstack/react-query` 5.105.0 → 5.107.1 and `lucide-react` 1.62.0 → 1.70.0. No visible change is intended.
- **Build and test tools** (#473, #459, #477): Vite 8.3.6, Vitest 5.1.0, `@vitejs/plugin-react` 6.2.1, Playwright 1.65.0, the Anthropic (1.6.0) and OpenAI (7.53.0) SDKs used by the contract tests, `taiki-e/install-action` 2.90.0, `github/codeql-action` 4.39.2, and new digests for the Node 22.23.4 and Rust 1.99.1 build images. The runtime base image is unchanged.
- **Minimum Rust version** for building `apps/gateway` from source is now 1.94.1 (the AWS SDK requires it). The pinned toolchain is still 1.99.1.

## Tests and CI

- **Pull requests scan the candidate image** (#475). v0.14.0 was tagged before its image had been scanned, and the tag run then refused it. The `staging-image` check now runs the tag run's Trivy scan (same pinned binary, same policy: fixable HIGH and CRITICAL fail) on the image built from the pull request and on the arm64 runtime base, in a job with a read-only token. `docs/verification.md` says what to do when it fails on an unrelated pull request: a fix for the runtime base has been published, and the base needs re-pinning.
- The collector-outage test proves by ordering, not by timing, that a request returns while a trace export is still in flight (#290).

## Known limitations

- Outbound clients for providers, S3 and trace export can still lose a request written to an idle connection the upstream is closing; the identity client no longer can (#483).
- No test reaches real AWS endpoints. Bedrock and STS are tested against local mocks that check the request shape and signature headers, S3 against MinIO and RustFS containers, which verify signatures.

## Upgrade

From v0.15.0 there is no migration and no grant change: deploy v0.15.1 by verified image digest, as a normal rolling update.

From an earlier release, follow the upgrade steps of each release in between, in order; the last migration is 0080 in [v0.15.0](v0.15.0.md#upgrade). v0.15.1 can be the image you finish on: it serves the same schema as v0.15.0.

Rollback to v0.15.0 is a redeploy of its image; nothing in the database changes.
