# Open Model Gateway v0.5.0

This release finishes most of the scale work: the dashboard stays fast with tens of thousands of users, workspaces, keys and models; backups can now be encrypted and copied off the host; and the Helm chart installs in one step and survives a database failover with its accounting intact. Responses and Messages now stream text as it is generated.

It is the first release tested on a real multi-node Kubernetes cluster (the homelab, with a CloudNativePG primary and synchronous standby). Those tests are not finished; see [Known limitations](#known-limitations).

## Before you upgrade

These changes can affect clients, scripts or Helm values:

- **Messages streaming usage.** `POST /v1/messages` with `stream: true` now sends `message_start` at once, with `usage: {"input_tokens": 0}` as a placeholder. The observed input, cache and output counts arrive in `message_delta`, which the Anthropic SDKs apply. A client that reads usage only from `message_start` now sees 0 (#23).
- **Responses streaming events.** `POST /v1/responses` with `stream: true` now sends text as `response.output_text.delta` events while the model generates, instead of all at the end. Tool calls still arrive whole, after the text (#22).
- **Slow dashboard lists return 503.** Platform users, user detail and workspace lists, and workspace members, keys and service accounts now read from the same lock-free snapshots as reports. Like reports, a statement running over 10 s is cancelled with 503 "The request took too long; narrow it and try again", instead of holding up other admin requests (#65).
- **Person pickers search instead of listing.** Add member, initial owners, SSO group mappings and cost-center assignment search on the server (first 20 matches). People who are already members are no longer shown as disabled options; they are not candidates (#67, #69).
- **Helm values:**
  - `migrations.grants.image` is removed. The migration Job applies the runtime grants with the gateway image itself (`open-model-gateway grants apply`), so there is no second image to pin (#20).
  - `cnpg.cluster.backup.destinationPath` is removed; it was never rendered. Put `destinationPath` inside `cnpg.cluster.backup.barmanObjectStore` (#134).
  - The loadtest profile's `loadtest.loadgen.requests` and `concurrency` are replaced by `rate`, `duration`, `warmup`, `keys` and `extraArgs` (#25).
  - New default `cnpg.cluster.smartShutdownTimeout: 15` (see Highlights).

## Upgrade guide

**One migration, 0037**, adds two indexes (`workspace_membership_grants(user_id, workspace_id)` and `platform_role_grants(user_id)`). It adds no grants, but reapplying the runtime grants after every migration is still required.

1. Back up with `scripts/backup.py` (now with `--encrypt-to`, see below) and run `verify`.
2. Stop every gateway replica. Mixed-schema replicas are not supported.
3. Run `open-model-gateway migrate` as the migrator.
4. Run `open-model-gateway grants apply` as the migrator (it applies `deploy/staging/runtime-grants.sql`, now embedded in the binary), then `open-model-gateway grants verify` with a role that can `SET ROLE gateway_runtime`.
5. Start the new replicas and wait for `/health/ready`.

**Helm:** a first install with `--set migrations.run=true` is now one command, including the chart-managed CloudNativePG cluster: the migration Job runs as a plain resource on install, waits for the database, and gateway pods wait for the schema instead of crash-looping. Upgrades that ship a migration still use `--set migrations.run=true`; there the Job is a `pre-upgrade` hook (#19).

## Highlights

- **A dashboard that stays fast at scale (#65–#69).** Measured on a cluster with 50,000 users, 20,000 shared workspaces, 107,000 keys and 2,004 models:

  | | Before | After |
  |---|---|---|
  | Platform users list, any page | 1.1 s, deep pages minutes to hours | about 0.19 s |
  | One slow admin list | froze the admin area for 12 minutes | lists never block other requests; 10 s statement limit |
  | Home, for a user in 2,003 workspaces | about 2,000 requests, 116 s, then the tab crashed | 5 requests, 0.64 s (`GET /api/v1/me/models`, `GET /api/v1/me/summary?totals_only=true`) |
  | Audit log, people, workspace, key and model pickers and filters | loaded whole lists | named by the server or searched |
  | Full model list | 11 requests, 23 s | pages built only for the requested rows |

  New and extended endpoints: `GET /api/v1/me/models`; `GET /api/v1/platform/workspaces/{ws}/member-candidates`; `q` on member, key and model lists; `GET /api/v1/platform/models?not_in_catalog=&not_direct_in=`; `actor_name`, `workspace_name`, `target_name` on audit rows; `issued_to_name` on key rows; workspace names and kinds on mapping and cost-report rows.
- **Encrypted, off-host backups (#104).** `scripts/backup.py backup --encrypt-to age1…` streams `pg_dump` through [age](https://age-encryption.org); the plaintext dump never reaches disk. `verify --identity` checks the decrypted plaintext, and `restore --identity` decrypts in two passes without writing plaintext. New `upload`, `list`, `download` and `prune` copy backups to S3-compatible storage (tested against RustFS). Manifests record the file-store key IDs that stored files need, and restore checks them. Key custody is in [operations](../operations.md#encrypted-backups). These are logical dumps, not point-in-time recovery.
- **A timed clean-host restore drill (#105).** On the homelab cluster, the newest encrypted off-host backup was restored onto a fresh environment. The RPO was the 48 s since the last backup; recovery to a serving gateway took 92 s, 73 s of it creating the new environment. The drill found two bugs, both fixed: backups carried extensions from the cluster's `template1` (pgvector), and `restore --create` copied `template1`.
- **Faster, safer database failover on Kubernetes (#25).** With CloudNativePG's default `smartShutdownTimeout` of 180 s, deleting the primary under load kept writes down for about 3 minutes, because pooled and LISTEN connections never close on their own. The chart now sets 15 s, and the standby was promoted in under a minute. Under every fault tested (graceful and hard gateway kills, including streams cut mid-way, and a primary failover under load), interrupted attempts kept their holds and were reconciled as unknown. Across 117,256 attempts no reservation stayed pending, nothing was charged twice, and `budget verify` and `history verify` were clean.
- **A slow commit no longer stalls the connection pool (#132).** Every 30 s, each successful request on every replica used to refresh the same routing-health row; behind a slow commit they all queued on it, each holding a pooled connection. Now one task per replica refreshes it and skips the row while it is busy.
- **New [HA PostgreSQL operations guide](../postgresql-ha.md) (#27):** failover behaviour, synchronous versus asynchronous replication, connection and database sizing, CNPG base backups and WAL next to logical backups, monitoring, and managed PostgreSQL requirements.

## Added

- `open-model-gateway grants apply|verify` (#20) and `open-model-gateway wait-for-database [--schema] [--timeout-seconds]` (#19).
- `scripts/backup.py` `--encrypt-to`/`--encrypt-to-file`/`--identity`, `--file-keys-env`/`--skip-file-key-check`, and `upload`, `list`, `download`, `prune` (#104).
- Helm value `cnpg.cluster.smartShutdownTimeout` (#25).
- `loadtest-image` workflow: builds `ghcr.io/ncecere/open-model-gateway-loadtest:dev-<commit>` on request for cluster load tests (#25).
- Design document for [content guardrails](../guardrails-design.md) (#36): decisions recorded, nothing implemented.

## Changed

- Helm loadtest profile: the loadgen Job passes the flags `loadgen run` accepts, verifies settlement against the database as the runtime role, and the profile's NetworkPolicies admit loadgen and let the gateway reach the mock (#25).
- `scripts/backup.py` dumps only `plpgsql` (`--extension=plpgsql`); the gateway schema uses no extensions (#105).
- `gateway_settlements_total{outcome="held"}`, and the `GatewaySettlementHeld` alert, now also count settlement writes that time out after 3 s, the usual case during a database outage (#136).
- The chart's default `image.tag` follows the release again (it was left at `v0.4.0` in v0.4.1); a test now keeps it equal to `v` plus the chart's `appVersion`.

## Fixed

- Dashboard key dialogs: a cancelled, closed or navigated-away create or rotate dialog, or one whose access was revoked, can no longer submit a request or copy a one-time key from a stale callback (#62).
- `restore --create` copies `template0`, so a cluster whose `template1` has extensions no longer makes the new database look non-empty (#105).
- `prune` never counts an incomplete or truncated archive toward `--keep` (#104).
- Helm: the `preStop` comment named a nonexistent `GATEWAY_DRAIN_SECONDS` (#134).
- `docs/kubernetes.md`: loading the image into kind with `kind load docker-image` can fail with "content digest … not found"; the workaround is documented (#21).

## Known limitations

- **The homelab cluster tests are not finished (#25).** Still to run: a PgBouncer pooler restart under load, dropping the gateway's LISTEN connection, a primary failover under load with the new 15 s setting, and a clean capacity measurement. They were paused after the cluster's Kubernetes API became unreachable during a test, most likely for reasons unrelated to the test.
- **No certified capacity number yet.** Steady load ran cleanly at 100–150 requests/s, but about half the runs hit a 1–5 s lock stall that the queue never recovered from. The routing-health amplifier is fixed (#132), but the fix has not yet been confirmed on the cluster, so #132 stays open.
- **The chart's default database sizing is too small for load.** The default (2 CPU / 2 GiB, `shared_buffers` 256 MB, Pooler limited to 500m CPU) collapsed at 50 requests/s; 6 CPU / 8 GiB with `shared_buffers` 2 GB handled 100–150 requests/s. Size the database for your load ([HA guide](../postgresql-ha.md#database-sizing)).
- The Helm chart is still **beta**.
- One workspace or one API key still tops out at a few hundred admissions per second, by design (unchanged since v0.4.0).
- Development software: not accepted for production. Live SCIM acceptance against a real identity provider (#60) and an independent security review (#61) remain open.

## Verifying the images

The image is `ghcr.io/ncecere/open-model-gateway`, tagged `v0.5.0`, `v0.5` and `latest-release`. Deploy by digest: the digest is in the GitHub Release, its `open-model-gateway-v0.5.0.digest.txt` asset, and the workflow's job summary.

Verify the signature with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) **v3.0 or newer** (keyless, GitHub Actions OIDC). The signature is stored in cosign v3's bundle format, so cosign v2 reports "no signatures found":

```sh
cosign verify ghcr.io/ncecere/open-model-gateway@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/open-model-gateway/.github/workflows/image.yml@refs/tags/v0.5.0 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The signature covers the multi-arch index, and so every tag that points at it. The SBOM (SPDX) and build provenance are attached to the image as attestations:

```sh
docker buildx imagetools inspect ghcr.io/ncecere/open-model-gateway@sha256:<digest> --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/ncecere/open-model-gateway@sha256:<digest> --format '{{ json .Provenance }}'
```

The Release also carries each platform's SBOM as `open-model-gateway-v0.5.0-linux-<arch>.sbom.spdx.json`, with `checksums.txt` (`sha256sum -c checksums.txt`). The Helm chart (`deploy/helm/open-model-gateway/`, chart version 0.5.0) defaults `image.tag` to `v0.5.0`; pin `image.digest` to the verified digest before a real rollout.
