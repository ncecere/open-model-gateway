# Open Model Gateway v0.8.0

Changes since [v0.7.2](v0.7.2.md) (and so since [v0.7.1](v0.7.1.md), which is what production runs today). This is the first feature release since v0.7.0. It adds four migrations, **0049 to 0052**, so unlike the v0.7.x patches it needs an explicit upgrade procedure: read [Upgrade](#upgrade) before you deploy.

## Summary

- **Alerts get more reliable and more useful.** Alert email now goes through a durable per-recipient outbox with bounded retries (#46), and built-in reminders warn key holders and workspace admins 7 days and 1 day before an API key expires (#100).
- **Machine administration.** Platform Admins can create long-lived, scoped, expiring and audited **admin API tokens** for scripts (#37), with a dashboard page to manage them. Token management itself is browser-only.
- **Tracing.** Opt-in OpenTelemetry traces for interactive generation requests (#98), with a `trace_id` in Logs, and Helm chart documentation.
- **Operations.** The Helm chart can back up its CloudNativePG cluster through the Barman Cloud plugin (#261); new Authentik acceptance notes for SCIM (#265); budget headroom reporting (#103); a Refresh action on Logs (#232).
- **Hardening and fixes.** Batch planning no longer reserves budget for lines an adapter will always reject (#238, #243, #245), duplicate key creation is blocked in the dashboard (#272), egress stops over-refusing a range of IPv6 addresses (#244), and advisory coverage and dependencies are updated.
- **Heads-up for v0.9.0.** Local-upstream approvals in some special-use address ranges will be refused at startup in the next minor release (#203). v0.8.0 warns; it does not refuse.

## Upgrade

**Schema:** the enterprise schema goes from **0048** (v0.7.0, v0.7.1 and v0.7.2) to **0052**. Migrations **0049, 0050, 0051 and 0052** are new; nothing beyond 0052 exists in this release. `serve` never migrates or applies grants: both are explicit commands run with migrator credentials.

**Which path you are on.** v0.7.1 and v0.7.2 have the same schema (0048) and the same environment settings, so the procedure below is identical from either. The only difference is behavior: v0.7.2 contains the compatibility fixes #220, #221 and #228 (and the #225 guide fix), which v0.7.1 does not. An upgrade from v0.7.1 picks those up as well; see [v0.7.2](v0.7.2.md#no-argument-tools-and-empty-successful-results-220). Nothing in v0.7.2 needs action on its own. Coming from v0.6.1 or earlier, first follow the [v0.7.0 precautions](v0.7.0.md#before-you-upgrade) (reserved credential names, management denial codes, local approvals); from before v0.6.0, first apply [v0.6.0's eleven migrations, 0038 to 0048](v0.6.0.md#upgrade-guide). Never reset or reinitialize an existing database.

### Before you start

1. **Management requests that carry an `Authorization` header are now refused** (see [Breaking changes](#breaking-changes-and-behavior-changes)). If a reverse proxy, SSO gateway or other layer in front of the dashboard adds an `Authorization` header, remove it for requests to the management API (`/api/v1/...`) first.
2. **Check `GATEWAY_LOCAL_UPSTREAMS`** against the ranges in [Upgrade note: #203](#upgrade-note-special-use-local-approvals-will-be-refused-in-v090-203). Nothing fails in v0.8.0, but you should plan the change.
3. **Do not set a non-default transaction isolation** (`default_transaction_isolation` other than `read committed`) on the gateway's database or roles. Admin-token creation refuses it ([Security notes](#security-notes)).
4. If you use Helm, read [CNPG backups](#helm-cnpg-backups-through-the-barman-cloud-plugin-261) before touching `cnpg.cluster.backup.method`. Leaving it alone changes nothing.

### Operator order

Follow the [standard upgrade and migration procedure](../operations.md#upgrade-and-migration-procedure) with this order:

1. **Record and back up.** Note the running image digest and configuration. Take a backup and `verify` it; run a restore drill, since this release includes migrations.
2. **Stop the old alert email workers, before anything touches the database.** Every `serve` replica of v0.7.x runs the alert/email loop, and so does any scheduled `alerts evaluate --once`. Scale the old gateway pods to **zero** (this also gives you the drain the standard procedure asks for: mixed-schema replicas are not supported) and pause any `alerts evaluate --once` job. If you cannot scale to zero and must keep an old replica running, set `GATEWAY_ALERT_INTERVAL_SECONDS=0` on it and restart it. **Unsetting the variable does not stop the worker**: unset means the default of 60 seconds, which is enabled; `0` disables it.
   Why: old binaries do not understand the recipient outbox that 0050 introduces. The database refuses an old worker's attempt to finalize a delivery whose recipients are still queued (SQLSTATE `55006`), so no outbox state is lost, but an old worker sends mail before it writes the result and retries every interval, so one left running repeatedly **re-sends** that delivery's email to every recipient.
3. **Migrate**, as the migrator: `open-model-gateway migrate` (applies 0049 to 0052). On Helm, `helm upgrade ... --set migrations.run=true --wait` runs the same `migrate` followed by `grants apply` in the pre-upgrade Job; scale the old pods down first, because that Job starts while they still exist.
4. **Apply the runtime grants**, as the migrator: `open-model-gateway grants apply`. The new migrations add tables and columns the runtime role needs privileges on ([runtime grants](#runtime-grants)). Skipping it leaves the new tables and columns without runtime privileges, so the new features fail at runtime.
5. **Verify the grants**: `open-model-gateway grants verify`, with a role that can `SET ROLE gateway_runtime`. The Helm Job applies grants but does not run this check.
6. **Start the new release**, deployed by verified image digest ([verify the signature](v0.3.0.md#verifying-the-images) first). Wait for `/health/ready` to report `schema: ok`.
7. **Check.** Sign-in, one bounded inference request, and the new health field `checks.local_upstream_approvals` (`"ok"`; `"warning"` means an approval needs changing before v0.9.0). Confirm `gateway_alert_email_deliveries` appears on the metrics listener. `open-model-gateway budget verify` is the routine post-upgrade check; this release changes no budget accounting.
8. **Rollback.** There are no down migrations. Redeploying v0.7.x is only safe if no migration ran; otherwise restore the pre-upgrade backup into a new database and cut over. Never run old workers against the new schema.

**Migration timing.** Migration 0049 alters constraints on `alert_events` and `alert_deliveries` and builds indexes on `alert_events` and `api_keys`; on a large installation run it in a quiet period (`lock_timeout` bounds lock waits, not execution time). Migration 0052 adds a column and a partial index to the partitioned `audit_events` table, which builds an index on every partition; allow time in proportion to your audit history. Neither was timed for this release.

## Breaking changes and behavior changes

- **A management request with an `Authorization` header is refused with `401`.** Management routes accept exactly one credential family: a browser session (`omg_session` cookie) or an admin API token (`Authorization: Bearer omg_admin_...`). A duplicate `Authorization` header, or any request carrying both an `Authorization` header and an `omg_session` cookie (even a malformed one), is refused before either is examined, with no fallback. Before this release, the header was ignored on management routes. Inference keys still never authorize management, and admin tokens never authorize inference. This does not affect `/v1/*`. ([management API](../management-api.md))
- **Old alert workers must be stopped before 0050** (see Upgrade). Old and new alert workers are not compatible.
- **Old replicas do not see key-expiry reminders.** A `key_expiring` incident carries neither `rule_id` nor `builtin`, so an older replica's feed, history and recipient queries cannot match it and it never displays or emails them. Its email worker can consume a pending delivery that has no recipients, so best-effort email may be lost during any overlap. Completed deliveries are not replayed.
- **New fields, additive.** Logs request list and detail responses add `trace_id` (`null` for personal workspaces; withheld together with the row for an unauthorized viewer). Business-action audit events, including SIEM exports (`omg.audit.v1`), add a nullable `admin_token_id` (`null` for browser-session actions). Consumers that reject unknown fields need updating.
- **Egress is less strict in one narrow case (#244).** Addresses in `3ff0::/12` outside `3fff::/20` are allowed again. See [Fixes](#fixes-and-smaller-changes).
- **Nothing is refused newly at startup.** The special-use local approvals below keep working in this release.

### Upgrade note: special-use local approvals will be refused in v0.9.0 (#203)

`GATEWAY_LOCAL_UPSTREAMS` approvals for an HTTPS endpoint still accept, in v0.8.0, ranges that the egress policy already refuses for every other client:

- `198.18.0.0/15` and `2001:2::/48` (benchmarking)
- `192.0.0.0/24` (IETF protocol assignments)
- `192.88.99.0/24` (deprecated 6to4 relay)
- `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`, `3fff::/20` (documentation)
- `fd00:ec2::/32` beyond the already-refused `fd00:ec2::254` (AWS IPv6 metadata). Unlike the others, this one is accepted over plain HTTP too, like an ordinary private address.

**The next minor release, v0.9.0, will refuse these ranges too and fail startup** for an installation that approved one, naming the approval and the setting to change. `64:ff9b::/96` (NAT64) stays refused as today.

**Find out now:**

- Inspect your approvals against the list above. An installation with only public or RFC 1918 approvals is not affected.
- v0.8.0 logs a `WARN` at startup for each affected approval, naming its host (never credentials) and the category.
- `GET /health/ready` adds a non-failing `checks.local_upstream_approvals`: `"ok"` normally, `"warning"` when any approval is in one of these ranges. It never changes the `ready`/`not_ready` decision and carries no endpoint names.

**What to change:** replace the approval's address with one in an ordinary public or RFC 1918 range, or remove it. Every address accepted or refused today keeps its current decision in v0.8.0.

## Highlights

### Alert email retries: a durable per-recipient outbox (#46)

Before, each alert email was sent once and a failure was only recorded. Now:

- **Retries.** Each recipient is retried on transient SMTP failures, up to five attempts within 24 hours, with 1 minute, 5 minute, 30 minute and 2 hour backoff. A refusal from the relay is permanent. EOF before the relay accepts the message counts as a retryable connection failure and is never recorded as success; it can duplicate a message the relay had in fact accepted.
- **Replicas.** Claims are leased across replicas and fenced, so a result from an expired claim is ignored. SMTP I/O never holds a database connection, and each tick has a bounded send budget. A single send has a 40 second deadline.
- **Status.** Incident History shows Waiting, Retrying, Sent, Exhausted or Failed per delivery, plus the waiting count and the next attempt time.
- **Monitoring.** New metrics `gateway_alert_email_attempts_total{outcome}` and `gateway_alert_email_deliveries{state}`, and an example Prometheus rule `GatewayAlertEmailPersistentFailure` in `deploy/monitoring/prometheus-rules.yml`.
- **Privacy.** Recipient addresses are not stored in the outbox, only delivery-scoped fingerprints. They are pseudonymous personal data and never appear in the API, metrics or logs. Pending deliveries snapshot their initially eligible recipients once, then recheck live eligibility on every claim.
- **History.** Historical terminal deliveries are not replayed. Outbox rows are append-only and retained like other audit tables.

See [alerts](../alerts.md#recipient-outbox-46).

### Authorized key-expiry reminders (#100)

Two built-in reminders, with fixed thresholds and no new configuration: "An API key expires within 7 days" and "within 1 day", delivered in app and by email for every active, authorized API key that has an expiry.

- **Recipients follow the key**, never a rule or platform role. A personal workspace's key reminds its owner only (never another Platform Admin or Auditor). A shared human key reminds its holder plus that workspace's current owners and admins. A service-account key reminds that workspace's current owners and admins. Every recipient needs live platform entitlement, and a shared recipient also needs effective workspace membership right now. Revoked, disabled, expired and expiry-less keys, disabled workspaces and service accounts, and human keys whose holder lost workspace membership are excluded.
- **Deduplication.** `(credential id, expiry, threshold)` is permanently deduplicated, including resolved history: at most one incident per combination, which is not at-most-once email (a crash after relay acceptance but before the delivery commits can resend). The first evaluation that sees a key already inside one day emits only the urgent reminder. Rotation and expiry changes start a new cycle. The 1-day reminder supersedes an open 7-day one, and nothing sends a "resolved" email for this kind.
- **Bounds.** Each workspace is capped at 100 new `key_expiring` incidents in any rolling 24 hours; excess candidates stay eligible later, possibly at the 1-day threshold. Each evaluation tick creates at most 500 new reminders and retires at most 500 incidents, inside the existing alert loop and `GATEWAY_ALERT_INTERVAL_SECONDS` (default 60, `0` disables).
- **Privacy.** No key names, ids, prefixes, hashes or holder identities appear in the event, the email or the logs. The email links to Notifications and the dashboard's **Open keys** action goes to the workspace's keys list. Live eligibility is rechecked just before each send; a revocation that lands during the send itself can still receive that one reminder. Workspace history stays admin/reader-only; members see their own reminders in the feed and bell. These reminders never appear in platform history.

See [alerts](../alerts.md#authorized-key-expiry-reminders-100).

### Admin API tokens (#37)

Long-lived credentials for scripts and out-of-band tooling, separate from inference keys and browser sessions. Delivered in three parts: storage and lifecycle (0051), authentication, scopes and audit (0052), and the dashboard.

- **Format and storage.** `omg_admin_<32-hex id>.<64-hex secret>`, 256 secret bits from the OS CSPRNG. Only the SHA-256 of the whole token is stored. The plaintext is returned once, with `Cache-Control: no-store`.
- **Limits.** Expiry is required, 1 to 90 days, with no renewal. Optional immutable CIDR allowlist (1 to 32 entries, never `/0`, no duplicates), enforced against the request's resolved client address (same trusted-proxy resolution as sign-in throttling) and failing closed when none can be resolved. Identity, scopes, expiry and allowlist are immutable; only revocation (final) and last-use tracking change.
- **Five scopes**, assigned per exact method and path template: `platform:read`, `catalog:write`, `access:write`, `governance:write`, `settings:write`. Write scopes do not imply read. No wildcard. Workspace-member, key, admin and SCIM routes refuse tokens, and existing workspace, object and personal-privacy checks still apply.
- **Token management is browser-only.** Listing and creating at `/api/v1/platform/admin-tokens` and revoking at `/api/v1/platform/admin-tokens/{token}` need a browser session of a Platform Admin; a token can never create, list or revoke tokens. Creation is only for oneself. Any Admin can revoke any token. Auditors are refused.
- **Live authority.** Every request rechecks the token and its owner against the primary database: unrevoked, unexpired, owner active and currently an effective Platform Admin. There is no positive cache. Losing the last active Admin grant (manual or group-derived), suspension, SCIM deactivation or cleanup revokes the owner's tokens in the same transaction, and regaining Admin does not restore them. Signing out sessions does not revoke tokens. Protected writes serialize with revocation and owner demotion.
- **Bounded and audited.** Per-replica token buckets bound authentication work (per address, per token and in aggregate; excess gets `429`). Every admitted attempt writes a start and a completion record to `admin_token_attempts`; business-action audit carries `admin_token_id`, also exported through webhook, syslog and OTLP (personal events remain excluded). Pre-authentication and over-limit floods are counted, not individually audited. If the completion record cannot be written after an action committed, the response is `503`: inspect the resource before retrying. The attempt table is not exported to a SIEM.
- **Dashboard** (Admin > Settings > **Admin API tokens**, `/admin/settings/admin-tokens`): lists token metadata, creates a token (name, scopes, expiry 1 to 90 days with a default of 30, optional CIDR allowlist) and revokes with confirmation. The plaintext is shown once, kept only in dialog state and copied only on an explicit click; closing, navigating away or an authority refresh retires it, and late responses cannot restore it or mint another token. Users without Admin-portal access are redirected Home; Auditors cannot open the page.
- **Backups.** `scripts/backup.py reapply-revocations` (#146) now also covers `admin_api_tokens`, so restoring an older backup cannot resurrect a revoked token.

Docs: [management API](../management-api.md#admin-api-tokens), [identity](../identity.md), [audit export](../operations.md#audit-export).

### Traces: OpenTelemetry for interactive generation (#98)

Disabled unless `GATEWAY_TRACES_OTLP_URL` is set; `OTEL_*` variables are ignored. Settings: `GATEWAY_TRACES_OTLP_URL` (full `/v1/traces` URL, verified HTTPS, or HTTP on development loopback only), `GATEWAY_TRACES_SAMPLE_RATIO` (0 to 1, default `0.01`) and `GATEWAY_TRACES_OTLP_HEADERS_ENV` (names a dedicated secret variable of headers). The collector destination goes through the gateway's egress protections: a refused destination (for example a private address without `GATEWAY_EGRESS_PRIVATE_ALLOW`, or cloud metadata) fails startup before any database connection, without echoing the URL.

- **Scope.** Chat completions, Responses and Messages through the shared engine only: `inference.request`, `routing`, `admission`, `upstream.attempt` (at most 3, under the existing explicit failover policy) and `settlement`. Async jobs, batches, embeddings, images, audio and realtime are not instrumented.
- **Privacy design.** Nothing exports unless a shared (team or project) workspace admission actually committed. Personal-workspace requests export nothing.
- **Correlation.** Logs request list and detail show a `trace_id` (and a "Trace ID" field on the request detail page) so you can search a collector such as Grafana Tempo by it.
- **Never in the way.** Recording never waits for a collector; a whole export exchange is limited to 2 seconds, no retries. Failures are counted in `gateway_trace_dropped_spans_total{reason}` and `gateway_trace_deliveries_total{outcome}`.
- **Helm.** No chart template changed: `gateway.env` already carries the three settings to the gateway container (never the migrate Job), `gateway.extraEnvFrom` carries the header secret, and `networkPolicy.egress.extraEgress` opens the collector's port (typically TCP 4318). `values.yaml` and `docs/kubernetes.md` now document this.
- **Not supported by design:** `OTEL_*` variables, protobuf or gRPC, inbound `traceparent`/`tracestate`/`baggage` (and nothing is forwarded upstream), automatic resource discovery, and metrics or logs over this exporter.

See [operations](../operations.md#traces-98) and [Kubernetes](../kubernetes.md#traces-98).

### Helm: CNPG backups through the Barman Cloud plugin (#261)

`cnpg.cluster.backup.method` selects `barmanObjectStore` (the default; rendering unchanged from earlier releases) or `plugin`, the Barman Cloud plugin that upstream CloudNativePG now recommends. In `plugin` mode the chart also renders a `barmancloud.cnpg.io/v1` `ObjectStore` (named `<cluster>-backup-store`, or `cnpg.cluster.backup.plugin.objectStoreName`) from `cnpg.cluster.backup.plugin.objectStore`. The `Cluster` gets `spec.plugins` for `barman-cloud.cloudnative-pg.io` as WAL archiver and no in-tree `spec.backup` block, and the `ScheduledBackup` uses `method: plugin`. S3 credentials are Secret references only, and `values.schema.json` validates `method` and refuses an inline credential. Omitting S3 credentials in plugin mode now fails with the required-value message instead of a template error.

**Switching an existing cluster between modes is a one-way cutover, not a migration.** WAL archiving restarts under the new mode and the plugin does not adopt the old backup catalog. Take a fresh base backup immediately, keep the old object-store prefix until its retention passes, point the new mode at a different `destinationPath`, and do not rely on point-in-time recovery across the switch. Restoring from either mode is a CNPG-native recovery into a fresh Cluster, not a chart operation.

The chart's `NetworkPolicy` templates cover only the gateway's own pods and never selected CNPG's instance pods in either mode; under a default-deny namespace policy, add your own egress rule for them to reach the object store. See [Kubernetes > Backups](../kubernetes.md#backups).

### SCIM: Authentik acceptance recorded (#265)

`docs/scim.md` records that Authentik 2025.10 was run against v0.7.1 on 2026-10-23 (matching existing users, one pushed group, deactivate and reactivate), and adds the three non-default Authentik settings the gateway's `userName` and group matching needs: a custom user mapping so `userName` is the email, a custom group mapping using `SkipObject` so only mapped groups are pushed (the provider's `filter_group` filters users only), and omitting `emails` for reserved test domains. Okta and Entra acceptance (#60) has not been run. Docs only.

### Budget headroom (#103)

Workspace and key budget views separate settled estimates, pending holds and retained unknown-cost floors. Remaining budget is shown only when accounting is complete; hidden parent usage stays restricted, and unknown or invalid accounting never becomes available money. Effective headroom is the lowest remaining amount across applicable layers within each independent period, not a sum of overlapping scopes. An older gateway without the new facts shows headroom unavailable. Reporting only: admission, limits, schema and runtime privileges are unchanged. See [governance API](../governance-api.md).

### Logs: Refresh action (#232)

Workspace and Admin Logs have an explicit **Refresh** action that re-fetches the current tab's rows and summary tiles for the current filters; Logs still does not poll. The empty **Sessions** tab now explains that requests without session metadata are listed under **Requests**, with a button that switches there keeping the filters. No backend change; Admin Logs still excludes personal workspaces.

## Fixes and smaller changes

- **Key create and rotate duplicate-submit guard (#272).** Creating an API key refuses a second submit in the same React batch as the first, so one form can no longer create two active keys while showing one secret. After a new or replacement key is shown, both dialogs are sealed: a retained submit callback cannot create another key or rotate again (which would invalidate the key you were shown). A failed request still allows an explicit retry. No API or data change. A residual low-severity gap is tracked in #276.
- **Batch planning (#238, #243, #245).** Creating a gateway-run batch now applies the same pre-admission check an interactive request gets (#228) before the parent budget envelope is sized: lines every candidate route would always reject are excluded from the reservation, and a batch is never submitted to a provider's native batch API while a line is excluded. The runner no longer claims a route that would deterministically reject a line when another capable route would accept it, and a line the scheduler never claimed capacity for can only be refused, never admitted. An explicit-maximum line's exclusion at planning is a read, not a persisted fact: if routing changes before dispatch the line can still run, through its own live admission. A persistent storage or timeout condition while planning a line's route now makes it wait, up to the batch's completion window (24 hours by default), before it is reported `expired`, instead of failing fast. Pinned omitted-maximum lines are validated at dispatch against the same output bound planning used. No schema or grant changes. This resolves the batch-planning limitation carried since v0.7.2.
- **Egress and `3ff0::/12` (#244).** The outbound address policy classified the IPv6 documentation range `3fff::/20` with a mask that matched all of `3ff0::/12`. Addresses in `3ff0::/12` outside `3fff::/20` (for example `3ff0::1`) are now ordinary global unicast and allowed; `3fff::/20` itself is still refused. Availability-only: nothing was ever wrongly allowed.
- **Key Budgets card spacing (#242).** Cosmetic: "Effective headroom" on the key Limits tab has its own spaced section.
- **Vendored upstream-base advisory coverage (#214).** The read-only cargo-deny job runs a separately labelled advisory-only check for explicitly registered vendored dependencies; unknown path dependencies and stale or malformed registrations fail closed. There are no vendored dependencies today, so the check passes and says so. `cargo deny --all-features check` is unchanged. See [verification](../verification.md#supply-chain).
- **Loadgen fix (#273).** Development tooling only, not shipped in the image: `tools/loadgen` readers now wait for the run's common start before their first request, so reader endpoint coverage inside the measured window no longer depends on host speed, and its end-to-end scenarios are serialized. No gateway behavior change.
- **Tests and CI.** Flaky or leaking tests fixed (#257, #258, #262). No runtime effect.

## Security notes

- **RUSTSEC-2026-0387 is a documented exception (#284, tracked by #285).** `crypto-bigint 0.5` (some operations meant to be constant-time may branch on secret values) reaches the gateway only through `openidconnect 4.0.1` and the `p256`/`p384` 0.13 curves, which the gateway uses solely to verify ES256/ES384 ID-token signatures with the issuer's public JWKS keys. It never holds an EC private key or does secret-scalar arithmetic. The fix needs `openidconnect` on the `elliptic-curve` 0.14 generation, which has not shipped; the ignore entry in `deny.toml` is removed when it does (#285). The existing RUSTSEC-2023-0071 (`rsa`) exception is unchanged.
- **`aes-gcm` 0.10.3 to 0.11.1, file format unchanged (#17).** This is the file store's mandatory streaming AES-256-GCM. Format v1 is byte-for-byte identical: the same 106-byte header, 12-byte nonce construction, postfix 16-byte tag, wrap and chunk AAD and 64 KiB chunks. Nothing is rewritten or rotated automatically, and existing stored objects decrypt as before (regression fixtures from earlier releases pass, and a new test confirms rewrapped fixtures decrypt after the old key is dropped). Entropy still comes only from the gateway's OS CSPRNG. The transitive bump (`aead` 0.6, `aes` 0.9, `cipher` 0.5, `ctr` 0.10, `ghash` 0.6, plus `ctutils`, `cmov` and `cpubits`) was reviewed for build scripts and network or process execution; none was found.
- **Other dependencies.** `sha2` 0.10 to 0.11 (gateway and tools; it is still SHA-256, so stored digests are unaffected), `tokio` 1.53.3, `tokio-rustls` 0.26.6, `serde_json` 1.0.154, `libc` 0.2.191 and the `proptest` development dependency 1.12.0. The build images move to Rust 1.99.1 and a refreshed Node 22.23.3 digest, pinned by digest as before.
- **Admin tokens are high-risk credentials.** They are a new way to reach management APIs; treat them like privileged keys. Use short expiries, the narrowest scope and a CIDR allowlist. They cannot reach workspace-member, key, admin or SCIM routes.
- **Transaction isolation.** The admin-token creation and role-loss guards refuse any transaction not at READ COMMITTED (SQLSTATE `OM002`); the gateway's own transactions are READ COMMITTED. An operator who sets a higher `default_transaction_isolation` on the database or role would break token creation and weaken other lock-then-check logic; enforcing READ COMMITTED everywhere is tracked as #281.
- **No independent review.** This release is not an independent security certification (#61), and no new live-provider or capacity acceptance is claimed.

## Known limitations

- **#203, special-use local approvals:** the refusal itself ships in v0.9.0 (see above).
- **Alerts:** alert delivery generation and dispatch are not bounded or scheduled fairly per workspace (#253, #277); the per-workspace cap on key-expiry reminders is the only bound today. Hold-age notifications (#101), signed webhooks (#45) and scheduled cost reports (#102) are not implemented. Email crash recovery can duplicate accepted mail.
- **Traces:** only interactive chat, Responses and Messages; no metrics or logs over OTLP (#99).
- **Admin tokens:** token management is browser-only by design; there is no OpenAPI contract for the management API yet (#81). Token attempt records are not exported to a SIEM. Key dialogs have a low-severity hardening follow-up (#276), and API-key issuance has no per-holder bound yet (#253).
- **Personal workspace existence (#282):** another user's personal workspace id returns `403` where an unknown id returns `404` on some workspace routes; with random UUIDs this is low severity, and is tracked for one consistent response.
- **SCIM:** Authentik is accepted; Okta and Entra acceptance (#60) has not been run.
- **Compatibility:** the broader client conformance program (#222) is incomplete. There is no universal or drop-in SDK or provider claim and no full protocol conformance claim.
- **Carried from v0.6.0 and v0.7.x:** independent security review (#61), steady-load admission and settlement stalls (#132), the second write outage after a two-instance CNPG failover (#149), unimplemented guardrails (#181) and IdP-initiated logout (#162). The Helm chart remains beta. There is no certified capacity number and no production-ready claim, and no new live-provider acceptance is made by this release.
- **The v0.7.2 batch-planning limitation (#238) no longer applies;** #215 to #221, #225, #228 and #238 are fixed.
