# Open Model Gateway v0.7.2

Changes since [v0.7.1](v0.7.1.md): the merged compatibility fixes #220, #221 and #228, plus the #225 Chat Completions guide correction. This patch improves bounded SDK request/response behavior; it does not establish universal or drop-in SDK/provider compatibility or full protocol conformance.

## Upgrade and database compatibility

**No new migrations, runtime grants or environment settings relative to v0.7.1.** The enterprise schema still ends at **0048**. No application dependencies change in this release vehicle.

**Upgrading from v0.7.1** needs nothing special: back up, deploy by verified digest, wait for `/health/ready`, and check sign-in, authorization denials and configured integrations, as the [operations runbook](../operations.md) describes. There is no new schema migration or grant application required by this patch.

**Upgrading from v0.6.1 still inherits all [v0.7.0 upgrade precautions](v0.7.0.md#before-you-upgrade)**, especially the [reserved credential allowlist refusal](v0.7.0.md#reserved-credential-names-now-stop-startup-197-pr-208), management denial-code changes and local-endpoint approval checks. Inspect names, not secret values; use separate dedicated provider/SMTP variables and do not bypass the refusal by copying gateway secrets. Never reset or reinitialize an existing database.

## No-argument tools and empty successful results (#220)

Chat function definitions may omit `parameters`, meaning no arguments. Only omission becomes the closed empty-object schema (`type:object`, `properties:{}`, `additionalProperties:false`); explicit object schemas are unchanged and null/nonobject parameters remain invalid. Omitted `strict` stays absent, with existing per-adapter strict capability rules unchanged.

Native Messages accepts omitted `tool_result.content` as empty text and explicit `is_error:false` as the default success. Call IDs and content bounds remain intact. Error-marked results (`is_error:true`) are explicitly unsupported, not silently downgraded; null content, malformed flags, missing IDs and unknown fields remain invalid. Messages still requires `max_tokens`. No database/runtime-grant changes, hosted/beta/thinking expansion or general nullable-field compatibility is included.

## Nullable OpenAI defaults (#221)

Chat Completions and Responses accept omitted/null `stream` as non-streaming. Responses accepts omitted/null/false `store` as stateless operation under the gateway privacy subset; explicit `store:true` still fails before admission and every native upstream Responses request still sends `store:false`. Existing nullable supported scalar/options keep omission-equivalence and pricing defaults.

This is not blanket null acceptance: OpenAI SDK 7.28 `tools` collections are optional, not nullable; malformed nested values, nonnullable fields and unknown/unsupported options remain rejected. Public Chat assistant `refusal:null` means no refusal and is accepted without forwarding; non-null refusal content, other-role refusal fields, empty messages and unknown fields such as `parsed:null` remain rejected. This does not add typed refusal support. Native Anthropic 0.131 `stream`/`tools` and required `max_tokens` are unchanged. No schema or environment changes.

## Deterministic refusals no longer take a budget hold (#228)

A Chat or Messages request that an Anthropic or Bedrock route would always reject (for example a `strict` function tool, an out-of-range temperature, or a tool result with no matching call) is now refused before durable admission: no execution, reservation, ledger, counter or routing-health row, and no upstream call. Before this, such a request was admitted first and left an unknown-cost hold with nothing dispatched, so a shared-workspace key holder could tie up the workspace's budget by repeating it.

Validation reuses each adapter's own request encoder, runs once per adapter per request, and checks every authorized route: another route that can serve the request still does. When every route refuses, the error kind (400 invalid request or 501 unsupported) comes only from routes the routing policy would use, so residency, disabled routes and cooldown apply first. Existing unknown holds are untouched; credential, endpoint and network failures after admission still retain their holds as before. Gateway-run batch lines get the same check before each line's admission; batch *planning* is not yet covered (see Known limitations). No schema or grant changes.

## Fixes

- **Chat Completions API guide (#225).** The model-page guide now correctly lists `max_tokens` as an accepted alias of `max_completion_tokens`; when both are supplied, values must be equal (otherwise 400). Optional maxima and existing unsupported-capability disclosures are unchanged; no runtime behavior changes.

## Internal: CI conflict-marker guard (#235, PR #236)

A merge on `main` (`df01e7a`) committed raw conflict markers into `docs/releases/unreleased.md` (repaired in #234); every required check still passed because nothing parsed Markdown and the local marker check skipped unmerged paths. CI now runs `npm run test:conflict-markers` (`tests/conflict-markers.test.mjs`) in the existing required `web` job: it scans every tracked text file from `git ls-files` and fails on an unresolved `<<<<<<< `/`>>>>>>> ` marker or a bare `=======` inside an open conflict. This is a CI/process change only; it has no runtime, API, schema or grant effect.

## Known limitations

- The broader compatibility program **#222** remains incomplete: this patch does not claim universal or drop-in SDK/provider compatibility, nor full protocol conformance.
- Batch planning still checks only coarse capability support (**#238**). A batch whose lines an Anthropic or Bedrock route will always reject is refused line by line before any per-line admission, but its parent budget envelope stays reserved until the batch closes (unused envelope is released then).
- No new live-provider, independent security or capacity certification is made by this patch. Mock/SDK contracts do not certify every SDK version or provider.
- The [inherited v0.7.0 limitations](v0.7.0.md#verification-and-known-limitations) continue (#215–#221, #225 and #228 are now fixed), including the carry-forwards (independent security review #61, live SCIM acceptance #60, steady-load stalls #132, the second failover write outage #149, unimplemented guardrails #181, IdP-initiated logout #162) and the beta Helm chart. There is still no universal/drop-in SDK or provider claim, full-conformance claim, certified capacity number or production-ready claim.

Report security problems privately as [SECURITY.md](../../SECURITY.md) describes.
