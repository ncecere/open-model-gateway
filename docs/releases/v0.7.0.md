# Open Model Gateway v0.7.0

Changes since [v0.6.1](v0.6.1.md). No database migrations are added in this release.

This is an assurance-focused update: explicit route authorization, stronger credential/configuration boundaries, inference-steering regression coverage and separation of CI verification from publication. The work was prompted by incidents in other projects; it is not evidence of a compromise of Open Model Gateway. It is also not an independent security certification.

## Before you upgrade

### Reserved credential names now stop startup (#197, PR #208)

Both operator-controlled allowlists, `GATEWAY_SECRET_ENV_ALLOWLIST` (providers) and `GATEWAY_SMTP_SECRET_ENV_ALLOWLIST` (SMTP), now refuse gateway-owned names, even if an operator explicitly lists them:

- `DATABASE_URL`, `DATABASE_URL_FILE`, every `GATEWAY_*` and `AWS_*` name, database-client `PG*` variables, `OTEL_*`, and the proxy names `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` (including their lower-case forms).
- Variables selected by the gateway's secret pointers: `GATEWAY_SCIM_TOKEN_ENV`, `GATEWAY_S3_ACCESS_KEY_ID_ENV`, `GATEWAY_S3_SECRET_ACCESS_KEY_ENV`, `GATEWAY_FILE_ENCRYPTION_KEYS_ENV`, `GATEWAY_AUDIT_WEBHOOK_SECRET_ENV` and `GATEWAY_AUDIT_OTLP_HEADERS_ENV`.
- Other startup-owned secret names; see [credential allowlists](../operations.md#credential-allowlists). The provider and SMTP lists must remain disjoint.

**Action:** inspect names, not secret values, before rollout. Remove reserved entries, give providers and SMTP separate dedicated variables, and update the corresponding connection/password references before restarting. Never copy a gateway secret into a provider variable to bypass the refusal. Startup diagnostics name the failing settings and entries (and selecting pointer settings), never their secret values.

**Intentional provider exceptions:** `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` remain usable on the provider allowlist, but never the SMTP list. Each produces a startup warning: a custom-endpoint connection using that reference receives the credential. Prefer dedicated provider variables and review endpoint approvals. A gateway secret pointer selecting either name still makes it reserved.

### Management denial responses change (#195, PR #206)

Authorization is checked before reading the body. Clients must tolerate these deliberate changes; they do not grant additional access:

- A non-admin workspace member rotating another person's key gets `404` in every state (previously `403` for an active key). Workspace admins still get `403`, now also for a disabled key (previously `key_disabled`).
- Auditors without workspace membership get `403` rather than `404` on its key-policy routes.
- Platform-admin-only workspace actions return `403` to non-admins before looking up the workspace.
- Malformed workspace or key ids in management paths return `404`.

See the [management API](../management-api.md) for the authority contract. The route preflight adds a live authority read before the handler; it is not a new runtime database privilege or a replacement for handler authorization.

### Local endpoints, model names and upstream ids (#196, PR #204)

- **Local-upstream approvals:** HTTPS approvals containing 6to4 or Teredo IPv6 addresses now check their embedded IPv4 address. Embedded metadata/link-local addresses are refused; embedded loopback works only with `GATEWAY_ENV=development`. Private/public embedded addresses remain accepted over HTTPS as their plain forms are. NAT64 and other existing approval rules are unchanged; this is not a blanket refusal of all special-use ranges (follow-up #203). Check `GATEWAY_LOCAL_UPSTREAMS` before rollout: an approval that fails validation stops startup.
- **Model lookup:** control characters (including NUL) and names exceeding the 2,704-byte stored-name bound now return `404 model_not_found` without a database lookup, rather than an accounting `503` or a query that could never match. Other names still use exact equality; SQL-created names containing spaces, `@` or accented letters are not newly rejected.
- **Provider job/file ids:** all-dot ids, including `.` and `..`, are refused rather than used as URL path segments. Valid ids with embedded dots remain supported.

## Upgrade and database compatibility

**No new migrations and no new runtime grants relative to v0.6.1.** The enterprise schema still ends at **0048**, introduced in [v0.6.0](v0.6.0.md#upgrade-guide). The #195 changes to `deploy/staging/runtime-grants.sql` are explanatory comments; `verify-privileges.sql` adds read probes using existing grants. They are not a privilege expansion.

For an installation already on v0.6.0/v0.6.1:

1. Record the current image digest and configuration, and keep a verified backup under the normal [operations runbook](../operations.md).
2. Resolve the allowlist and local-approval incompatibilities above before restarting replicas. Review automation that depends on management denial codes.
3. Once the release is actually published and accepted, deploy its verified image by digest. There is no schema change requiring `migrate` or `grants apply` for this scope; do not reset or reinitialize the database. Standard deployment automation may still verify schema and grants explicitly.
4. Wait for `/health/ready`, then check sign-in, expected authorization denials and configured integrations under the normal acceptance procedure. A successful readiness check is not provider acceptance.

For versions older than v0.6.0, first follow the intervening release guides, including v0.6.0's **eleven migrations, 0038–0048**, runtime grants and changed SMTP/egress/session/object-visibility settings. This release does not waive those requirements or promise mixed-schema compatibility.

## Assurance changes

- **Exact route-policy inventory (#195).** Every served method/template has an explicit policy in `apps/gateway/src/route_policy.rs`, never a prefix match. Undeclared management routes deny even Platform Admins; handlers retain live scoped checks. Source-inventory tests, a 15-caller authorization matrix and tests pinning the seven unauthenticated routes guard the declaration.
- **Configuration/secret boundary (#197).** The management/SCIM write inventory found no setting that can set process environment variables, arbitrary file paths or code. Unknown JSON management fields are rejected; logo uploads remain stored objects, not paths. Source tests pin reviewed unsafe/process-spawning surfaces, and CI checks a denylist of scripting/template/dynamic-loading crates. The concrete fix prevents accidentally allowlisted gateway secrets from resolving as provider/SMTP credentials.
- **Inference boundary (#196).** The audit found no client-controlled upstream destination or credential selection. Tests exercise steering bodies, headers and model strings against approved and attacker mock upstreams. The [threat model](../threat-model.md#provider-credentials-and-egress) records outbound destinations and authority. This coverage is bounded, not a claim that every possible attack was independently tested.
- **Supply-chain isolation (#194, PR #200).** Native amd64/arm64 builds push by digest; read-only verification pulls each exact digest for version, staging/runtime-contract and Trivy checks; publication tags/signs only after verification. Write-token jobs use a short pinned action allowlist, not scanner/installer actions. CodeQL analysis is read-only and SARIF upload is separate. Run-time downloads use `.github/scripts/fetch-verified.sh` with workflow-pinned checksums (Trivy, cosign, Helm, kubeconform and Node); cargo-deny's installer verifies its manifest checksum. Strict workflow tests enforce pins, permissions and download rules. The image/signature/SBOM/provenance and release-asset contract is unchanged. See [image CI](../staging.md#image-ci-and-registry-publication) and [supply-chain checks](../verification.md#supply-chain).
- **Verification process (PR #198).** Real-path refusal checks, two independent security reviews (one adversarial), coordinator diff review and protected-main checks remain requirements; they do not substitute for independent security review or live acceptance. The coordinator controls minor/patch releases; the user retains the v1.0.0 launch decision.

## Separate inference host (#187, PR #210)

Set `GATEWAY_INFERENCE_BASE_URL=https://api.example.com/v1` (Helm: `gateway.inferenceBaseUrl`) when inference is published separately from the dashboard. Startup validates an absolute HTTPS URL ending in `/v1`, without credentials, query or fragment; HTTP is allowed only on development loopback. Unset uses the browser's current origin plus `/v1`.

Key and model pages show separate copyable OpenAI-compatible and Anthropic SDK bases: Anthropic omits only the final `/v1`, because its SDK adds `/v1/messages`. Prefixes and ports are preserved. Realtime endpoint copies use WSS/WS; Files and Batches have separate endpoint copies. Batch payload paths remain literal relative paths.

This is display-only configuration: it does not configure ingress or routing, and dashboard requests remain same-origin relative URLs. Keep `GATEWAY_PUBLIC_URL` on the dashboard origin for OIDC and CSRF. See [separate inference hosts](../kubernetes.md#separate-inference-host).

## Dashboard fix

- Your profile › Your data now spaces the date fields and download button consistently (#189, PR #207). Export authority, format and retention bounds are unchanged.

## Test stability

- The stale-replica cache invalidation test now pins only its test fixture's version-freshness timestamp (#185, PR #209). It preserves a real stale cache under load, keeps the original assertion and adds a direct cache-hit check. Production cache behavior is unchanged.

## Verification and known limitations

Release images are published only after test, staging/runtime-contract and scanning gates pass. Acceptance is recorded in CI and the release PR; a successful earlier `main` pipeline is not acceptance of a later candidate. Use the published release's digest and cosign v3+ verification instructions, checking `image.yml@refs/tags/v0.7.0` as the signing identity before rollout. Readiness and automated checks are not new live-provider acceptance or independent security certification.

The [v0.6.0 limitations](v0.6.0.md#known-limitations) still apply: independent security review (#61), live SCIM acceptance (#60), steady-load stalls (#132) and the second failover write outage (#149) remain open; there is no certified capacity number or production-ready claim. Guardrails are designed (#36) but not implemented (#181); IdP-initiated logout is not implemented (#162); the Helm chart remains beta. This update does not add provider capabilities or establish new live-provider acceptance.

Report security problems privately as [SECURITY.md](../../SECURITY.md) describes.
