# Open Model Gateway v0.12.0

A minor release after [v0.11.0](v0.11.0.md). It completes self-service access requests (#83). A member of a Team or Project can ask for a model from the workspace's catalog, and only that workspace's owners and admins decide. Request events now appear in the in-app notifications. It is a minor release because it adds two migrations (**0072**, **0073**), runtime-grant changes and new fields in existing management responses.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## New features

- **Request a model for your workspace** (#83, slice B).
  - **Who can ask:** a current member of an enabled Team or Project asks for an enabled model in that workspace's catalogs that the workspace cannot use yet: `POST /api/v1/me/access-requests` with `model_id` and an optional plain-text reason. In the dashboard, members who cannot add models see **Request** on each model that is available to add on the workspace's **Models** page, then **Requested** while it is pending.
  - **Refusals:** a non-member (including a Platform Admin without membership), a personal, unknown or disabled workspace, and an unknown, disabled or out-of-catalog model all get the same `404`. A model the workspace can already use is `409`. A request that would be refused is refused before any authority lock is taken.
  - **Who decides:** only a live owner or admin of that workspace, on the workspace path (Workspace Settings › **Access requests**), and never the requester. Platform authority never substitutes: the platform decision routes refuse model requests with `403`, and Admin › **Access requests** lists them without actions.
  - **Approval:**
    - It rechecks, under the workspace's authority locks, that the requester is still entitled and a member, and that the model is still enabled, in the workspace's catalogs and not yet usable. If any check fails the answer is `409` and the request stays pending.
    - It then selects the model from the catalog exactly as a workspace admin's **Add** does (`source: catalog`, audited `model.granted`), and records an immutable application. The dialog says which model it adds.
    - Approving again returns the recorded outcome and never selects the model again, even after it was removed.
  - **Limits:** expiry (7 days), withdrawal, idempotency and the existing per-requester caps are shared with membership requests. In addition, at most 5 model requests can be pending per requester and workspace and 100 per workspace; beyond that the answer is `409 model_request_queue_full`. That is not a rate limit: a slot frees when an owner/admin decides or a request expires.
- **Access requests in your notifications** (#83, slice B3).
  - **Approvers:** owners and admins of a Team or Project see pending requests to join it or for a model in **Notifications**. Platform Admins see pending membership requests, which they can decide.
  - **Requesters:** they see their own requests approved, denied or expired in the last 30 days.
  - **Behaviour:** events follow your current access (they disappear when you lose it), count towards the unread badge, and **Open requests** opens the queue that can decide them, or My requests. Marking read works per state, so a decision is unread again for the requester.
  - **In-app only:** request events are never emailed or sent to webhooks, and never carry the reason or the requester's identity.

## Behaviour changes

- **Access-request objects** gain `model_id` and `model_name_at_request` (the model's public name when requested, frozen). `target_kind` can be `model_selection`, `requested_role` is `null` for it, and `membership_grant_id` is `null` on an approved model request. Clients with closed schemas need the new contract.
- **`GET /api/v1/me/notifications`** items can be access-request events (`source: "access_request"`, a fourth item shape), merged newest first with alert incidents. The summary's `unread` includes up to 100 of them (the bell shows 99+); `firing` is unchanged. `POST /me/notifications/read` marks them too. Clients that assumed every item is an alert incident need the new contract.
- **`GET /api/v1/me/access-requests`** accepts optional `workspace_id` and `status=pending` filters. The pending filter reads a snapshot and expires nothing.
- **Platform decision routes** (`POST /platform/access-requests/{id}/approve|deny`) refuse model requests with `403`; membership requests are unchanged.
- **A new error reason**, `model_request_queue_full` (409).
- **Submission forms:** the positional submission form `[workspace_id, reason, idempotency_key]` still works, and a fourth element carries the model. Membership request digests are unchanged, so a replay across the upgrade still matches.
- **Workspace Settings › Access requests** now also lists model requests (a **Request** column shows what was asked for), and **My requests** shows "Use <model>" or "Join as member".

## Contracts and documentation

- **Management OpenAPI:** still **255 operations**.
  - Request objects gain the model fields.
  - The platform decision responses stay membership-only schemas.
  - The notification feed gains `IdentityRequestNotification`.
  - `GET /me/access-requests` gains the two filters, and the reason enum gains `model_request_queue_full`.
- **Docs:** the management API guide documents model requests and request notifications, with the migrations, the caps and the visibility rules. The dashboard, identity and roadmap docs are updated (#83 is complete; reviewed onboarding templates, #84, remain planned).

## Migrations and runtime grants

- **0072_model_access_requests:**
  - Adds `access_requests.model_id` (a foreign key to models) and `model_name_at_request` (a constant default, so no table rewrite).
  - Replaces 0066's insert guard. The kind, role and frozen names derive from the target, so the runtime cannot set them. A model request needs a current member, an enabled shared workspace and an enabled model, and the model-request caps apply.
  - Splits the one-pending-request uniqueness per target.
  - Replaces 0066's application check: an application names exactly one of the membership grant or the model, and an approved model request needs the workspace's catalog selection at application.
  - Existing requests are all membership requests and satisfy the new CHECKs.
- **0073_access_request_notifications:**
  - Adds the insert-only `access_request_notification_reads` (per user, request and state; the server sets the read time; no update, delete or truncate).
  - Adds two partial indexes on `access_requests` (pending by workspace, decided by requester).
- **Runtime grants** (`deploy/staging/runtime-grants.sql`, applied by the chart's migrate Job):
  - `INSERT(model_id)` on `access_requests` and `access_request_applications`;
  - `SELECT` and `INSERT(user_id,request_id,state)` on `access_request_notification_reads`.
  - The schema preflight (startup and `/health/ready`) inventories the new table.

## Tests and CI

- Real-PostgreSQL tests for model requests cover:
  - request, approval and replay;
  - refusals and privacy;
  - authority (platform path, a non-member or demoted admin, self-approval);
  - rechecks that leave requests pending;
  - database bindings and forgeries;
  - concurrent decisions, and approval racing membership removal in both orders;
  - expiry by the worker and by reads;
  - the caps (including 100 across 20 members);
  - a replay after catalog retirement.
- Tests for request notifications cover:
  - who is notified;
  - read state;
  - merging with incidents, with paging;
  - lost authority, expiry and disabled workspaces;
  - withdrawn requests;
  - the 30-day window.
- `verify-privileges.sql` probes the new rules and grants under `gateway_runtime`. The management contract fixtures observe every new response shape and walk the new request forms and query parameters.

No dependency, Rust crate or base-image change.

## Upgrade

From **v0.11.0**, replace the image and chart, using the normal drain procedure only after qualification and deployment approval.

1. **Back up.** Take a backup and `verify` it before migrating (`docs/operations.md`, "Upgrade and migration procedure"); the rollback below depends on it.
2. **Drain, then migrate.** A gateway serves only a database whose migrations match its own: v0.12.0 does not start on a v0.11.0 schema, and v0.11.0 does not start, and its running replicas report not ready, once 0072 has committed. Drain first.
   - **With the chart:** scale the v0.11.0 Deployment to 0 (and suspend any autoscaler), then `helm upgrade --set migrations.run=true`. The migrate Job is off by default and runs as a pre-upgrade hook.
   - **Without the chart:** run `open-model-gateway migrate` and then `open-model-gateway grants apply` as the migrator.
   - The latest migration is **0073**, with **72 migration records**, and the runtime grants change (above).
   - If the migrate Job fails after a migration has committed, fix the cause and re-run `migrate` and `grants apply` with v0.12.0; do not `helm rollback`, since v0.11.0 cannot serve that schema.
   - **Locks** (from the SQL, not measured): 0072 alters `access_requests` and `access_request_applications` (new nullable or constant-default columns, no rewrite; the new CHECKs scan those small tables under `ACCESS EXCLUSIVE`) and rebuilds two partial unique indexes. 0073 creates one table and two partial indexes on `access_requests`.
3. **Start and verify.** Deploy v0.12.0 by verified image digest. Restore the replica count and any autoscaler you suspended (`helm upgrade` may leave a manually scaled Deployment at 0). Wait for `/health/ready` to report `schema: ok`, run `open-model-gateway grants verify`, then check sign-in and one bounded inference request.
4. **Do not** reset or recreate an existing database, run a down migration or bootstrap implicitly.
5. **Rollback.** There are no down migrations. Redeploying v0.11.0 is only safe if no migration ran; otherwise restore the pre-upgrade backup into a new database and cut over. Never run old workers against the new schema.
6. **Clients.** Regenerate generated management clients: access-request objects have new required fields, the notification feed has a new item shape, and there is a new error reason.

From an older release, also follow the [v0.11.0 upgrade instructions](v0.11.0.md#upgrade) and their linked requirements. Publication verification and readiness remain separate from production activation and authenticated/provider acceptance.
