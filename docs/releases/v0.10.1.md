# Open Model Gateway v0.10.1

A patch release after [v0.10.0](v0.10.0.md). `/v1/messages` accepts the Anthropic API version current SDKs send (`2026-10-21`), two error responses now use the status or code their sibling routes use, and the full local gates run in about half the time. It is a patch because no request that succeeded on v0.10.0 is refused now: the version change only accepts requests that were refused, and the other changes affect error responses.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## Fixes

- **`/v1/messages` accepts `anthropic-version: 2026-10-21`** (#430). The gateway accepted only `2023-06-01`, so clients on the current SDK majors, which send `2026-10-21` by default (TypeScript `@anthropic-ai/sdk` 1.x, Python `anthropic` 2.x and the others listed in Anthropic's [migration guide](https://platform.claude.com/docs/en/api/migration-2026-10-21)), were refused with 400. Both versions are now accepted; any other value, a repeated header or a missing one is still 400. Verified with the official TypeScript SDK 1.4.0; the other SDKs were not tested.
  - Under `2026-10-21` the gateway applies that version's request rules: `temperature`, `top_p` and `top_k` are refused with 400 naming the field and the version (`temperature: not supported with anthropic-version 2026-10-21`), even at a default value or `null`, instead of being dropped (Anthropic's guide states the same refusal). An ill-typed value gets the generic 400.
  - The version's other two rules (a `document` block in an assistant message, a user `text` block with `citations`) are already met: documents, search results and citations are outside the supported grammar under both versions. A `system`-role message (a stable Messages API feature that the current SDKs' message types include) is refused with 400 `messages.role` under both versions, as on v0.10.0; use top-level `system`.
  - Native Anthropic routes keep sending `2023-06-01` upstream, since an accepted request means the same under either version. `/v1/batches` lines for `/v1/messages` carry no version header and keep the `2023-06-01` rules.
- **Chat Completions and Responses** answer an oversized streamed request body (no `Content-Length`) with the shared OpenAI 413 envelope, code `payload_too_large`, like the embeddings, rerank, image, System One, audio, video and batch routes; they used code `invalid_request_error` with the generic invalid-request message (#438). A declared `Content-Length` over the cap is still the plain-text `length limit exceeded` 413.
- **Authentication storage failures are 503, not 500** (#439). When the database fails while a management request is authenticated (browser session or admin token), while signing in or while signing out, the gateway answers `503`, the status every other management storage failure answers, with `{"error":"Authentication service unavailable"}` (private headers, no cookie set or cleared; a failed sign-out has not revoked the session, so retry it). It logs the sanitized `management storage error` warning: error kind, SQLSTATE, constraint/table/column/routine names and, for classes whose messages never contain values, the PostgreSQL message; never row data or bound parameters. A failed OS random-number generator during sign-in stays `500`. A storage failure during the sign-in callback, after the one-use login attempt was consumed, needs a fresh sign-in (reloading the callback answers 400).

## Behaviour changes to note

- Monitoring or clients that treated a management `500 Authentication service unavailable` as the database-outage signal now see `503` with the same body (#439).
- An admin-token authentication storage failure no longer logs the ERROR line `admin token authentication database lookup failed` with the full error; it logs the sanitized `management storage error` WARN line like every other storage failure. Session, sign-in and sign-out storage failures now log the same WARN line (they logged nothing before). Alerts keyed on the old line, and request metrics keyed on status `500`, need updating; the same body with status `500` now means only a failed OS random-number generator during sign-in (#439).
- Clients that upgrade to a current Anthropic SDK and send mid-conversation `system`-role messages get 400 `messages.role` (#430).
- A streamed oversized body to Chat Completions or Responses now answers `code: payload_too_large` with the message `Request body too large` instead of `invalid_request_error` with the generic message (#438).
- `anthropic-version: 2026-10-21` requests that send `temperature`, `top_p` or `top_k` are refused; keep such requests on `2023-06-01` (#430).
- Generated clients and contract tests see the management contract's authentication `500` replaced by `503`, and the inference `anthropic-version` header schema change from a `const` to an `enum` of both versions.

## Contracts and documentation

- Inference OpenAPI: the `anthropic-version` header is an enum of both versions and the sampling fields state the version rule; the shared streamed-413 description covers Chat Completions and Responses (#430, #438).
- Management OpenAPI: every authenticated route and logout document the authentication storage `503` (`ManagementAuth503`) instead of a `500` (#439).
- Workspace-wide object visibility also shows ordinary members the key names on other members' batch rows; the keys list stays filtered. This is the intended behaviour, now documented in the management API, batches guide and contract (#403).
- Protocol matrix, Claude Code guide and the model-setup Messages card list both Anthropic versions (#430).

## Tests and CI

- The management contract harness derives the validator cache key of an artifact node once instead of re-serializing it on every validation (about 40 million times in the slice 3 fixture, counted with temporary instrumentation). Maintainer measurements, not CI figures: on an idle 4-core machine the slice 3 fixture went from 60.7 to 18.6 minutes, and a full local gate run from 3 h 43 min to 1 h 54 min (#444).
- The metrics acceptance tests respawn the gateway on fresh ports when another process took a reserved port before the binary bound it (#396).
- The telemetry acceptance tests run one at a time, removing the suspected cause of an outage-timing flake; the bounds are unchanged and #290 stays open for a structural assertion.
- The official Anthropic SDK contract tests (create, stream, retries, wire replay) run against `@anthropic-ai/sdk` 1.4.0 and assert the SDK sends `2026-10-21`.

## Dependencies

- Development only: `@anthropic-ai/sdk` 0.131.0 → 1.4.0 (licence MIT → Apache-2.0 at 1.0.0), with its new dependency `@opentelemetry/api` 1.10.0 (Apache-2.0) (supersedes #422). They are installed only in the image's build stage, never shipped in the runtime image. No runtime dependency, Rust crate or base-image change. The root lockfile's `apps/web` entry now spells `@tanstack/react-query` as the exact `5.105.0` that `apps/web/package.json` already pins (resolved version unchanged).

## Upgrade

From **v0.10.0**, replace the image and chart, using the normal drain procedure only after qualification and deployment approval. The schema is unchanged: the latest migration remains **0068**, with **67 migration records**. There are **no new migrations or runtime-grant changes**. Do not reset or recreate an existing database, run a down migration or bootstrap implicitly.

From an older release, also follow the [v0.10.0 upgrade instructions](v0.10.0.md#upgrade) and their linked requirements. Publication verification and readiness remain separate from production activation and authenticated/provider acceptance.
