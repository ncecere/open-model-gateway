# Open Model Gateway v0.11.0

A minor release after [v0.10.1](v0.10.1.md). Platform Admins can apply a route change only at the revision they reviewed, restore a route's earlier configuration, and disable up to 50 explicitly chosen routes in one operation that reports each route's outcome (#87, #88). With the previews and history of v0.9.0 (#85, #86) this completes the approved first scope of change safety (#41, roadmap R15): route enablement. Other kinds of configuration change remain deferred. Management text limits now count characters, not bytes (#405). It is a minor release because it adds three migrations (**0069**–**0071**), runtime-grant changes and new management routes.

These notes do not establish completed release qualification, authenticated/provider acceptance or authorization for production activation or v1.0.0.

## New features

- **Apply at a reviewed revision, and restore** (#87). The preview has reported each route's enablement revision since v0.9.0 (#86); now it is enforced.
  - `POST /api/v1/platform/deployments/{id}/configuration/apply` `{enabled, expected_revision, restore_of?}` writes only at that revision. If the route changed since the preview, including a change away and back, nothing is written and the answer is `409 revision_conflict`. Applying the current value answers `outcome: "unchanged"` and records nothing. The dashboard's route review dialog now applies through this route. **Retire** still uses the unguarded `DELETE`, as before.
  - The route's **History** tab offers Platform Admins **Restore this configuration** on each change whose values were recorded. `POST .../configuration/restore-preview` `{change_id}` previews re-applying that change's value. An unknown or another route's change is `404`; a legacy entry without values is `409 restore_values_unavailable`. Applying the restore records a new change, authored by you and linked to its source (`restored_from`); history is never edited. Restoring to enabled is checked like any enable, so it can be refused (for example `400 route_unsupported_capability`). A value that does not match the source is `409 restore_source_mismatch`.
  - Platform Admin, browser session only (Origin and CSRF). Admin tokens are refused. The existing `PATCH` and `DELETE` routes, and admin tokens on them, are unchanged.
- **Bulk disable routes** (#88). On a model's **Routes** tab, select up to 50 routes and choose **Disable selected**.
  - The review dialog previews each route at its current revision. It also warns when several routes of one model are selected, since each preview counts its route alone.
  - `POST /api/v1/platform/deployment-bulk-operations` `{action: "disable", idempotency_key, items: [{id, expected_revision}]}` takes 1 to 50 explicit, distinct route ids (any routes, not only one model's) and a key of 1 to 128 characters from `A-Z a-z 0-9 . _ : -` (otherwise 400); there is no filter and no "all matching". Each target is disabled in its own transaction, in request order, with live Platform Admin authority and its reviewed revision. Its outcome commits with the change:
    - `committed`: disabled now.
    - `unchanged`: already disabled.
    - `conflict`: the revision changed.
    - `refused`: not found, or authority lost mid-operation.
    - `unattempted`: never applied.
  - **Idempotency is per user and key.** The same request again returns the recorded outcomes and applies nothing. The same key with different targets, revisions or order is `409 idempotency_key_reused`. A retry while the first request is still running is `409 bulk_incomplete`.
  - **Failures.** A target that fails, including one that waits more than 10 seconds for another catalog change, stops the operation: the response is still 200 (`completed: true`), with that target and the rest recorded `unattempted`.
  - **Interrupted requests.** If the request is interrupted, committed targets stay committed. The request holds a 30-second lease, renewed before each target; once it has lapsed, reading `GET /api/v1/platform/deployment-bulk-operations/{idempotency_key}` or retrying completes the operation, recording the targets it never reached as `unattempted`. Until then a retry is `409 bulk_incomplete` and is never replayed blindly. The dashboard offers only **Check outcome** after an unknown result.
  - **Keys and status.** Keys never expire: reusing one with the same targets and revisions replays its recorded outcomes. A status read of an operation whose request still holds its lease answers 200 with `completed: false` and null outcomes for undecided targets; a status read of a lapsed one completes it (and writes its audit event). Another user's key is 404.
  - **Load.** Each target takes the exclusive catalog lock for its own transaction, as `PATCH` does, so new admissions can wait briefly behind each of up to 50 targets. Prefer small batches under load.
  - **Records.** One `configuration.bulk_disabled` audit event lists each target's outcome. Each change also appears in the route's history, naming the operation (`bulk_operation_id`).
  - Platform Admin, browser session only; admin tokens are refused.

## Behaviour changes

- **Management text limits count characters, not bytes** (#405). Every management text limit now counts Unicode characters (code points), matching the contract's `maxLength` and the dashboard forms. Text that was refused for its byte length but fits in characters (for example a 61-character name of two-byte letters) is now accepted; nothing that was accepted before is refused.
  - **Affected limits:**
    - names: 120;
    - descriptions: 2000;
    - emails: 320;
    - OIDC group-mapping issuers: 2048, and group values: 512;
    - upstream model IDs: 512;
    - the SMTP username: 256;
    - time zones: 64;
    - log and cost-report filters: 200;
    - compare ids: 148;
    - the sign-in callback code: 8192;
    - provider-cost reconciliation text:
      - account IDs: 200;
      - evidence references: 256;
      - model names: 512;
      - dimensions and cursors: 4096.
  - **Sign-in, SCIM and bootstrap** count characters as well: the asserted email (320) and group values (1024) at sign-in, SCIM emails and `bootstrap` emails. So every account and group mapping the management API accepts can sign in and match.
  - **Cost-report raw query:** its bound is now 16,384 bytes, so both filters fit at their limit in any script.
  - **Contract:** the management contract drops its `x-omg-max-bytes` annotations, so `maxLength` is exact. The exception is the settings support/logo URLs, whose limit applies to the stored, percent-encoded form (#419).
- **The dashboard's route Enable/Disable review applies at the previewed revision** (#87). A route changed by someone else after you opened the review is no longer overwritten: the dialog says it changed and asks you to review it again. A review that shows no change can no longer be confirmed.
- **Route history entries carry two new required, nullable fields** (#87, #88): `restored_from` and `bulk_operation_id`. The history schema is closed, so generated clients need the new contract.
- **Audit:** a new action `configuration.bulk_disabled` (resource type `deployment_bulk_operations`) lists each bulk target's outcome; `configuration.updated` metadata can now carry `restored_from` and `bulk_operation_id` (#87, #88).
- **Error reasons:** management errors can carry five new `reason` values: `revision_conflict`, `restore_source_mismatch`, `restore_values_unavailable`, `idempotency_key_reused` and `bulk_incomplete`. The route preview's last `warnings` entry now says the apply route refuses a stale revision and PATCH/DELETE do not enforce it.

## Contracts and documentation

- **Management OpenAPI:** **255 operations** (251 in v0.10.0).
  - New: apply, restore preview, the bulk operation and its status.
  - History gains `restored_from` and `bulk_operation_id`.
  - `maxLength` counts characters, with no `x-omg-max-bytes` (#405).
- **Docs:** the management API guide documents the revision rule, restore, bulk semantics (the lease, outcomes, idempotency) and the new database rules. The roadmap's phase 5 row and R15 entry list #87 and #88 as shipped.

## Migrations and runtime grants

- **0069_provider_cost_text_characters:** the provider-cost reconciliation text CHECKs count characters. No data change.
- **0070_configuration_restore:**
  - Adds `configuration_changes.restored_from`; existing rows keep NULL.
  - The history capture trigger records the link from a transaction-local setting, consumed by one change. The history validator checks that the link names an earlier change of the same route with the same value.
- **0071_configuration_bulk:**
  - Adds `configuration_bulk_operations` and `configuration_bulk_items` (no deletes; outcomes written once) and `configuration_changes.bulk_operation_id`.
  - Triggers enforce these rules:
    - Operations are created incomplete, and items undecided, within the declared count.
    - An outcome is decided once, before completion, on the server's clock.
    - A committed outcome names this operation's change at the next revision.
    - Completion happens once, after every declared item.
    - Leases are short (at most a minute ahead).
    - No row is deleted; on an operation, only the lease changes before completion.
  - A bulk-linked change must be an undecided item of that incomplete operation, made by the operation's user with no admin token. At commit it must be that item's committed outcome.
  - These rules are database triggers that bind the runtime role. They are consistency checks, not protection against the migrator or owner role, or against a runtime role that sets its own actor.
- **Runtime grants** (`deploy/staging/runtime-grants.sql`, applied by the chart's migrate Job):
  - SELECT on both new tables.
  - INSERT of their creation columns only.
  - UPDATE of the lease, completion and outcome columns only.
  - No DELETE.
- The schema preflight (startup and `/health/ready`) inventories both new tables.

## Tests and CI

- Real-PostgreSQL tests for the revision guard, concurrent applies and restore linking. Bulk tests cover:
  - concurrent same-key requests;
  - interrupted and lapsed operations;
  - a slow request keeping its committed outcome while its operation is completed;
  - the lock timeout;
  - refusals;
  - database-level forgery attempts.
- `verify-privileges.sql` probes the restore and bulk rules and the column privileges under `gateway_runtime`.
- The management contract fixtures cover each new operation in object and positional form, every outcome arm and the revision bounds.

## Dependencies

No dependency, Rust crate or base-image change.

## Upgrade

From **v0.10.1**, replace the image and chart, using the normal drain procedure only after qualification and deployment approval.

1. **Back up.** Take a backup and `verify` it before migrating (`docs/operations.md`, "Upgrade and migration procedure"); the rollback below depends on it.
2. **Drain, then migrate.** A gateway serves only a database whose migrations match its own: v0.11.0 does not start on a v0.10.1 schema, and v0.10.1 does not start, and its running replicas report not ready, once 0069 has committed. Mixed-schema replicas are not supported, so drain first: with the chart, scale the v0.10.1 Deployment to 0 (and suspend any autoscaler), then `helm upgrade --set migrations.run=true` (the migrate Job is off by default and runs as a pre-upgrade hook); without it, run `open-model-gateway migrate` and then `open-model-gateway grants apply` as the migrator. The latest migration is **0071**, with **70 migration records**, and the runtime grants change (above). If the migrate Job fails after a migration has committed, fix the cause and re-run `migrate` and `grants apply` with v0.11.0; do not `helm rollback`, since v0.10.1 cannot serve that schema.
   - Locks (from the SQL, not measured): 0069 drops and re-adds CHECKs on the three `provider_cost_*` tables (each add scans its table under `ACCESS EXCLUSIVE`; they hold provider-cost imports and mappings). 0070 adds a nullable column to `configuration_changes`; 0071 adds a nullable column and a deferred constraint trigger there, and creates two new tables. No table is rewritten, and `audit_events` is untouched.
3. **Start and verify.** Deploy v0.11.0 by verified image digest. Restore the replica count and any autoscaler you suspended (`helm upgrade` may leave a manually scaled Deployment at 0). Wait for `/health/ready` to report `schema: ok`, run `open-model-gateway grants verify`, then check sign-in and one bounded inference request.
4. **Do not** reset or recreate an existing database, run a down migration or bootstrap implicitly.
5. **Rollback.** There are no down migrations. Redeploying v0.10.1 is only safe if no migration ran; otherwise restore the pre-upgrade backup into a new database and cut over. Never run old workers against the new schema.
6. **Clients.** Regenerate generated management clients: history entries have two new required nullable fields (`restored_from`, `bulk_operation_id`), the error `reason` enum has five new values, and four operations are new.

From an older release, also follow the [v0.10.1 upgrade instructions](v0.10.1.md#upgrade) and their linked requirements. Publication verification and readiness remain separate from production activation and authenticated/provider acceptance.
