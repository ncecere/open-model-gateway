# Open Model Gateway v0.9.0

Changes since [v0.8.0](v0.8.0.md). It adds fifteen migrations, **0053 to 0067** (schema 0052 → 0067), so like v0.8.0 it needs an explicit upgrade procedure: read [Upgrade](#upgrade) before you deploy.

## Summary

- **Breaking: local-upstream approvals in special-use address ranges are now refused at startup** instead of only warning (#203). Check `GATEWAY_LOCAL_UPSTREAMS` before you upgrade.
- **Scheduled cost reports.** Weekly/monthly schedules for installation, cost-center, Team/Project and personal scopes, bounded aggregate generation, link-only email delivery, authorized report reads and aggregate CSV downloads (#102).
- **Signed alert webhooks.** Saved, HMAC-signed platform webhook receivers with bounded retried delivery, a fixed test send and an Admin dashboard tab (#45).
- **Fairer, bounded alerts.** Bounded API-key issuance (#253 slice A), fair per-workspace alert email dispatch (#253 slice B) and a 100-deliveries-per-workspace-per-day email generation cap (#277).
- **Aged unknown-hold alerts.** Built-in 24-hour warning / 168-hour critical incidents with Platform-Admin-only email (#101).
- **Observability.** Opt-in OTLP metrics (#99) and OTLP operational logs (#294); telemetry egress refusals no longer repeat or name the collector (#321).
- **Claude Code.** The Claude Code field grammar now works on native Anthropic routes within the documented subset, including cache controls, thinking, effort, signed assistant history, deferred tools and task budgets (#70, deliveries 1–2).
- **Admin visibility.** Deployment configuration history and change-impact previews (#86, #85); an OIDC group-mapping preview (#89); self-service Team/Project membership requests (#83, slice A); a first, API-only slice of provider-reported cost reconciliation against uploaded Anthropic Cost Report JSON (#48); a drift-checked, still-incomplete management OpenAPI contract skeleton (#81, PR1).
- **Hardening and fixes.** Development-only plain-HTTP telemetry/audit exports are now loopback-only after DNS resolution (#313); `grants apply` now revokes `TEMPORARY` from `PUBLIC` and the runtime role (#295); fresh chart-managed CNPG installs restrict database ACLs (#315); another owner's personal workspace now returns a consistent `404` (#282); a bounded dashboard access refresh replaces indefinite retry (#291); key dialogs get a lifetime-hardening follow-up (#276); the Rust toolchain is pinned to 1.99.1 (#354).

## Upgrade

**Schema:** the enterprise schema goes from **0052** (v0.8.0) to **0067**. Migrations **0053 through 0067** are new. `serve` never migrates or applies grants: both are explicit commands run with migrator credentials.

### Before you start

1. **Check `GATEWAY_LOCAL_UPSTREAMS`** against the ranges in [Local-upstream approvals in special-use ranges are now refused](#local-upstream-approvals-in-special-use-ranges-are-now-refused-203). Unlike v0.8.0's warning, this release **fails `serve` at startup** for an affected approval.
2. **Stop every v0.8.x (or older) alert evaluator and any scheduled `alerts evaluate --once` job before running migration `0059`.** Older evaluators do not prelock delivery buckets in canonical order; under 0059 an inverted acquisition fails with `40001` instead of waiting, which rolls back that evaluation and can permanently miss a transient incident.
3. **Stop every older replica before running migration `0067`.** An older replica that changes a deployment after 0067 is applied still has its change captured, but attributed to System, with its own audit event shown as a second history entry.
4. If you run chart-managed CNPG and inherited an older cluster, review [existing CNPG cluster ACL remediation](../postgresql-ha.md#existing-cnpg-cluster-acl-remediation-315) (#315); fresh installs need no action.
5. After `grants apply`, `grants verify` now also attempts `CREATE TEMP TABLE` under the runtime role and requires its refusal (#295); reapply grants as the owner/migrator before verifying.

### Operator order

Follow the [standard upgrade and migration procedure](../operations.md#upgrade-and-migration-procedure):

1. **Record and back up.** Note the running image digest and configuration. Take a backup and `verify` it; run a restore drill, since this release includes migrations.
2. **Drain and stop every old replica** (step 2 above covers the evaluator specifically; this release's full migration set needs every replica stopped, as migration 0067 also requires).
3. **Migrate**, as the migrator: `open-model-gateway migrate` (applies 0053 to 0067). On Helm, `helm upgrade ... --set migrations.run=true --wait` runs `migrate` followed by `grants apply` in the pre-upgrade Job.
4. **Apply the runtime grants**, as the migrator: `open-model-gateway grants apply`.
5. **Verify the grants**: `open-model-gateway grants verify`, with a role that can `SET ROLE gateway_runtime`. This now also checks that the runtime role cannot `CREATE TEMP TABLE` (#295).
6. **Start the new release**, deployed by verified image digest. Wait for `/health/ready` to report `schema: ok` and `checks.local_upstream_approvals: "ok"`.
7. **Check.** Sign-in, one bounded inference request, and `open-model-gateway budget verify`.
8. **Rollback.** There are no down migrations. Redeploying v0.8.x is only safe if no migration ran; otherwise restore the pre-upgrade backup into a new database and cut over. Never run old workers against the new schema.

**Migration timing.** `0055_alert_delivery_buckets` holds an **ACCESS EXCLUSIVE** lock on `alert_deliveries` through its pending-row backfill until commit; the locked interval grows with the pending backlog, so plan a maintenance window for a large queue. `0065_report_delivery` alters the same table and builds shared partial indexes transactionally; plan similarly. `0054`, `0056`, `0060` and `0062` are `CREATE INDEX CONCURRENTLY` builds outside a transaction; an interrupted build leaves an invalid index that the next `migrate` drops and rebuilds automatically.

## Breaking changes and behavior changes

### Local-upstream approvals in special-use ranges are now refused (#203)

**Breaking change for affected installations.** `GATEWAY_LOCAL_UPSTREAMS` approvals that pin an address in one of the ranges below are refused at startup. v0.8.0 only warned. An installation whose approvals are all public or RFC 1918 (private) addresses is not affected and needs no action.

| Range | Category |
|---|---|
| `198.18.0.0/15`, `2001:2::/48` | benchmarking |
| `192.0.0.0/24` | IETF protocol assignments |
| `192.88.99.0/24` | deprecated 6to4 relay |
| `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`, `3fff::/20` | documentation |
| `fd00:ec2::/32` (all of it, not only the previously refused `fd00:ec2::254`) | AWS IPv6 metadata range |

These are exactly the ranges the outbound egress policy already refused for every other client; approvals now follow the same shared table (`special_use.rs`). The rule applies over both schemes: `fd00:ec2::/32` was also accepted over plain HTTP like a private address, and is refused there too. An address carrying an IPv4 address (IPv4-mapped, compatible, 6to4, Teredo) is judged by that IPv4 address, so a 6to4 address of a refused IPv4 range is refused as well. NAT64 (`64:ff9b::/96`) stays refused, as before. Every other decision is unchanged: public over HTTPS, RFC 1918/unique-local over HTTP or HTTPS, loopback only with `GATEWAY_ENV=development`.

`open-model-gateway serve` stops before connecting to the database, naming every affected approval's host, pinned address and category, and `GATEWAY_LOCAL_UPSTREAMS` — never a credential. Only `serve` loads approvals; `migrate`, `grants` and other commands are unaffected. A replica that fails this way never answers `/health/ready`, so a rolling deployment keeps the old replicas until you fix the setting.

**What to change:** replace the approval's address with the real address of the model server, an ordinary public or RFC 1918 address, or remove the approval. `GET /health/ready`'s `checks.local_upstream_approvals` now always reports `"ok"` when a replica is answering — the warning phase has ended, because an affected approval stops startup instead of being reported.

See [provider adapters](../provider-adapters.md#approve-local-endpoints-out-of-band), [operations](../operations.md#health-endpoints) and the threat model (EGR-3).

### Runtime TEMP privilege revoked (#295)

`grants apply` now revokes `TEMPORARY` from `PUBLIC` and `gateway_runtime` on the connected gateway database, removing PostgreSQL's default PUBLIC grant and any old explicit runtime grant. Runtime code does not need TEMP; migrations that use temporary objects still run as the database/schema owner. Reapply the matching binary's grants as the owner/migrator, then run `grants verify` with a role that can `SET ROLE gateway_runtime`: verification now attempts `CREATE TEMP TABLE` and requires its refusal. Use a dedicated gateway database — every role relying on PUBLIC TEMP loses it there, not just runtime.

### Fresh CNPG installs restrict database ACLs (#315)

Fresh, explicitly installed chart-managed CNPG clusters now revoke PUBLIC/runtime `CONNECT` on `postgres` and `template1`, and PUBLIC/runtime `TEMPORARY` on the application database, from one-time initdb hooks. Application `CONNECT` is retained; CNPG's own replication, monitoring and PgBouncer authentication privileges are preserved. This changes only fresh installs, not `grants apply`, migrations, external databases or existing clusters. **Existing installations** need the explicitly reviewed [manual remediation](../postgresql-ha.md#existing-cnpg-cluster-acl-remediation-315), including operational-role preconditions and strict tagged verification before restarting gateways.

### Development HTTP telemetry exports are loopback-only after DNS (#313)

**Behavior change for development installations only.** Plain-HTTP OTLP traces, OTLP metrics, OTLP operational logs, audit OTLP logs and audit webhooks (allowed only with `GATEWAY_ENV=development`) now connect only to canonical loopback addresses after name resolution, including IPv4-mapped loopback. If any resolved address is not loopback, the whole answer is refused, even when other answers are loopback or the address is covered by `GATEWAY_EGRESS_PRIVATE_ALLOW`. Literal non-loopback HTTP endpoints are refused before any connection. HTTPS exports keep the general egress policy, and production (non-development) installations are unaffected: they never allowed plain HTTP. Every OTLP signal shares one export transport, so OTLP metrics (#99) and operational logs (#294) get the same tightening. To export to another host, use HTTPS.

### Personal workspace existence privacy (#282)

Workspace-scoped management routes now return the same `404` for another owner's personal workspace as for an unknown UUID, including for Platform Admins/Auditors (previously `403`). Non-admin platform writes retain their role-first `403` for both. Personal-owner access, Team/Project authorization and platform aggregate reporting are unchanged.

### Stop older replicas before migrating `0067` (#86)

`0067_configuration_history.sql` captures every deployment state change in a database trigger. Stop every older replica before migrating: an older replica that changes a deployment after 0067 is applied still has its change captured, but attributed to System, with its own audit event shown as a second history entry.

### Other additive changes

- Logs `trace_id`, business-audit `admin_token_id` and the other additive fields from v0.8.0 are unchanged. New additive fields in this release: `alert_deliveries` progress/report metadata, `workspaces.discoverable`, `deployments.revision`. Consumers that reject unknown fields need updating.
- Egress and address classification are otherwise unchanged from v0.8.0's #244 fix.

## Highlights

### Scheduled cost reports (#102)

Platform Admins (installation and cost-center scopes), shared-workspace owners/admins (Team/Project, optionally cost-center-narrowed) and personal owners can schedule **weekly or monthly** reports. Creation starts **paused**; a validated IANA time zone and local `HH:MM` control only *when* email goes out — accounting periods are strict UTC Monday-to-Monday weeks or calendar months, `[start,end)`. Recipients are 1–50 explicitly selected internal user IDs with live scope-specific entitlement revalidation, never email addresses or directory expansion. Capacity is capped at **10 schedules per personal owner, 50 per shared workspace, 100 combined installation/cost-center schedules**; over-cap resumption and creation are refused with `409 reason:"report_schedule_limit_reached"`.

A leased `ReportScheduler` generates bounded aggregate snapshots (10-second deadline, 1 MiB payload cap, 100 entries/dimension with explicit truncation and full untruncated totals) from the existing rollup/raw fallback. Snapshots are additive estimates — exact settled configured-rate amounts, retained held floors and unresolved counts — never a frozen request export; root-request counts and detailed health/pricing/billing measures are explicitly unavailable rather than fabricated. Platform snapshots combine every personal workspace into one identity-free allocation. Payloads expire after **90 elapsed UTC days** and are pruned in bounded batches; occurrence and deduplication metadata is retained independently.

Active schedules **email links only** — a generic availability notice, the UTC period and an authenticated link, never amounts, names, a recipient list or an attachment — through the existing SMTP relay, recipient outbox, bounded retries/leases/fencing and the same fair per-workspace dispatch buckets as alert email (`quota_charged:false`: reports share dispatch fairness, not the #277 alert-generation allowance). Active configuration requires the operator's HTTPS `GATEWAY_PUBLIC_URL`, validated at OIDC startup; `GATEWAY_ALERT_INTERVAL_SECONDS=0` stops report *delivery* (as it does alert email) but not report *generation*. Every read, including CSV, independently reauthorizes; **aggregate CSV** downloads are capped at **1,000 data rows** (422 beyond that) with the same escaping as usage exports.

Browser-only routes (`/platform/report-schedules`, `/workspaces/{ws}/report-schedules`, and their `/runs` and `/runs/{run}/csv` children) refuse all admin API tokens, including a Platform Admin's token with every scope. See [scheduled reports](../cost-reporting.md#scheduled-reports), [API contract](../governance-api.md#scheduled-cost-reports-102-slices-ad) and [rollout rehearsal](../operations.md#scheduled-report-rollout-and-rehearsal-102).

### Signed alert webhooks (#45)

Platform Admins manage up to **10** saved, disabled-by-default webhook destinations (`Admin › Settings › Alerts › Webhooks`). Destination URLs must be in `GATEWAY_ALERT_WEBHOOK_URL_ALLOWLIST` and signing references in `GATEWAY_ALERT_WEBHOOK_SECRET_ENV_ALLOWLIST` (`env:NAME`, 32–4096 bytes, never the secret value in management). Enabling queues only future eligible transitions — no historical backfill. Final deletion scrubs the URL and signing references while keeping the destination's identity and history.

Delivery sends `omg.alert.v1` JSON envelopes, HMAC-SHA256 signed over `<timestamp>.<raw body>` (`X-OMG-Signature: t=...,v1=...`, optional dual signatures during a saved ≤24-hour key-rotation overlap), to only the installation incidents that notify Platform Admins and the built-ins `scim_last_admin`, `partitions_missing` and `history_orphans` — never workspace rules, personal incidents, `key_expiring` or `admission_ceiling` events. Any 2xx succeeds; connection failures, timeouts, 408/429 and 5xx retry at **1 minute, 5 minutes, 30 minutes, 2 hours**, up to **5 attempts in 24 hours**; other statuses, invalid signing material, TLS failures and policy refusals are terminal. Dispatch is bounded to 25 steps and a 70-second hard timeout per invocation. `POST .../webhooks/{id}/test` queues one fixed single attempt (2/person/minute, 2/destination/minute, 20/installation/hour); `GET .../webhooks/{id}/deliveries` returns bounded status. Receivers must verify the signature in constant time, enforce a **±300-second** timestamp window and deduplicate by `X-OMG-Delivery`.

See [alerts](../alerts.md#saved-platform-webhooks-45-slice-1) (storage, slice 1), [signed delivery](../alerts.md#signed-delivery-slice-2) (slice 2) and [dashboard administration](../alerts.md#dashboard-administration-slice-3) (slice 3).

### Bounded key issuance and fair alert dispatch (#253)

**Slice A: bounded API-key issuance.** Creating or rotating a key now counts in a rolling 24 hours against the holder's and the workspace's budgets — defaults **50 per holder, 500 per workspace**, editable 1 to 10,000 on the type default, platform override and tighten-only workspace layers. A spent budget refuses with `429 reason:"key_issuance_limit_exceeded"` and `Retry-After`. `GET /workspaces/{ws}/key-issuance` reports the caller's (and, for admins, the workspace's) remaining budget; the API keys page shows "X of Y issued in the last 24 h".

**Slice B: fair alert dispatch.** Alert email slots are now shared fairly across per-workspace delivery buckets (plus one nil-UUID bucket for installation-scope events), rather than FIFO: each tick prefers the due bucket served least so far, then least-recently-served, then oldest due head. A quiet workspace no longer waits behind another workspace's entire backlog. New gauges `gateway_alert_delivery_pending_buckets` and `gateway_alert_delivery_oldest_pending_age_seconds`.

See [governance](../governance.md#key-issuance), [governance API](../governance-api.md) and [alerts](../alerts.md#recipient-outbox-46).

### Workspace alert email generation limit (#277)

Each workspace (and the nil installation bucket) can now generate at most **100 email deliveries per rolling 24 hours**, across every rule and built-in, counting firing and clearing separately. Each admitted delivery conservatively reserves **50 recipient slots**, capped at **5,000 reserved slots per bucket/window**, with no refunds for failed, ineligible or unconfigured deliveries. **There is no priority exemption** — critical alerts and urgent 1-day key-expiry reminders use the same allowance. Excess deliveries are immediately terminal `suppressed` with `suppression_reason:"workspace_generation_limit"`; History shows "Not emailed — workspace notification limit". In-app incidents, history and eligible webhook enqueue are unaffected. See [alerts](../alerts.md#workspace-email-generation-limit-277).

### Aged unknown-hold alerts (#101)

Built-in, never a configurable rule: `aged_unknown_hold` fires at **24 hours** (warning) and **168 hours** (critical), using database time against the reservation's `unknown` ledger entry. One open incident per enabled Team/Project, and one anonymous installation-wide incident for all enabled personal workspaces combined. In-app visibility follows live authority (Platform Admins/Auditors see all; shared-workspace owners/admins see their own); members and personal owners get no role-only alert but keep their authorized Holds queue. **Email goes to Platform Admins only**, at most 50 addresses per incident, through the existing recipient outbox — Auditors, shared-workspace owners/admins, members and personal owners are not email recipients solely for those roles. Only the anonymous installation aggregate is webhook-eligible. New metric `gateway_aged_hold_alerts_total{result="fired|escalated|cleared|deferred|suppressed"}`. See [aged unknown-hold review alerts](../alerts.md#aged-unknown-hold-review-alerts-101) and the [review queue/Holds tab](../governance-api.md#aged-unknown-hold-review-queue).

### Opt-in OTLP metrics and operational logs (#99, #294)

**OTLP metrics (#99)** is now fully wired: each configured `serve` replica runs one optional OTLP/HTTP JSON metrics worker, independent of traces and the Prometheus listener, exporting the same scrape-derived metrics on a 10–300-second interval (default 60). Set `GATEWAY_METRICS_OTLP_URL` (full `/v1/metrics` URL); optional `GATEWAY_METRICS_OTLP_HEADERS_ENV` and `GATEWAY_METRICS_OTLP_TRAFFIC` (`off` by default; includes identity-free personal-workspace aggregates when `on`). Caps: 300 series/family, 2,000 points, 1 MiB body. No retries or spool; a collector outage never gates readiness or HTTP. Development plain-HTTP export is loopback-only after DNS (#313), through the transport shared with traces and logs.

**OTLP operational logs (#294)** adds one optional worker emitting seven fixed, closed infrastructure events only (`exporter_degraded`/`exporter_recovered`, `egress_refused`, `lease_lost`, `config_listener_down`, `finalization_needs_reconciliation`, `background_job_failed`) — there is no tracing-subscriber bridge, and prompts, responses, request/execution ids and collector error text never leave the process through this transport. Set `GATEWAY_LOGS_OTLP_URL` (full `/v1/logs` URL); optional `GATEWAY_LOGS_OTLP_HEADERS_ENV` and `GATEWAY_LOGS_OTLP_MIN_SEVERITY` (default `warn`). Development plain-HTTP export is loopback-only after DNS (#313).

See [OTLP metrics](../operations.md#otlp-metrics-99) and [OTLP operational logs](../operations.md#otlp-operational-logs-294).

### Telemetry export egress refusals no longer repeat or name the collector (#321)

Telemetry/OTLP export (traces, metrics, operational logs) now logs a fixed, destination-free warning only when a purpose's connectivity actually changes — into refusal or back to allowed — never on every export attempt. Provider, OIDC, storage, catalog, SMTP, audit webhook/syslog and alert-webhook refusals are unchanged and still name the host, resolved address and reason on every refusal. The audit exporter's own OTLP collector destination gets the same transition-only, host-free treatment without quieting the audit webhook/syslog destination's diagnostics. See [operations](../operations.md#outbound-connections).

### Claude Code Messages: native Anthropic fidelity (#70, deliveries 1–2)

`/v1/messages` (including `?beta=true`) parses Claude Code's field grammar through the ordinary workspace/key, admission and per-attempt accounting path. **Claude Code now works on native Anthropic routes within the documented subset**: native routes preserve block-form system prompts, cache controls (including 1-hour TTL), thinking controls, effort, signed/redacted assistant history, context management, deferred tools, task budgets and `tool_result.is_error`. A reviewed beta-header denylist blocks only `context-1m-`, `code-execution-`, `web-search-`, `web-fetch-`, `files-api-`, `mcp-client-` and `computer-use-` prefixes; refusals use Anthropic's exact `Unexpected value(s)` message so Claude Code can retry without the rejected beta. Operators can disable experimental features with `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`.

Native Anthropic also accepts bounded base64 PNG/JPEG/GIF/WebP images (5 MiB decoded per image, 20 images, within the 2 MiB HTTP body cap); remote URL sources are refused. Native cache-enabled requests now require a pinned v2/v3 price that explicitly prices cache reads and every requested write TTL. Structured output and strict tools remain refused (OpenAI-style reasoning/structured-output mapping is deferred to a future delivery); server tools remain refused because their charges are unpriced. The Messages output cap rises to 16 MiB. See [Claude Code field rules](../protocol-matrix.md#claude-code-field-rules) and [setup](../claude-code.md).

### Deployment configuration history and change-impact previews (#86, #85)

Admin route pages gain a browser-only **History** tab (`GET /api/v1/platform/deployments/{id}/configuration/history` and `/history/{change}`) with enabled-state before/after diffs, actor/token attribution, immutable IDs and cursor pagination; all admin tokens and ordinary users are refused. Every deployment write atomically captures actual before/after values with audit identity; existing rows start at revision `0`, new rows at `1`. `POST /api/v1/platform/deployments/{id}/configuration/preview` lets Platform Admins review an enable/disable change — the state diff, routes gained/lost, last-serving-route warnings and bounded affected Team/Project metadata — before confirming, without writing anything. Revision-precondition enforcement and bulk actions remain future work.

### OIDC group-mapping preview (#89)

`POST /platform/oidc/group-mappings/preview` (new/edited proposal) and `.../{id}/preview` (edit or delete) are a read-only dry-run using the exact matching predicates the real reconciliation runs, so the preview can never disagree with the write it previews. It reports `immediate` (what the real PATCH/DELETE revokes synchronously the instant it commits) separately from `diff` (the net effective-role change once a later sign-in/SCIM reconciliation catches up). An optional `If-Match` digest header refuses a stale review with `412`. See [identity](../identity.md#group-mapping-previews).

### Self-service membership requests (#83, slice A)

An active, entitled user can request to join an explicitly discoverable Team/Project as `member` from the new workspace-portal **Request access** page; owners/admins and Platform Admins approve or deny from matching queues. Discoverability defaults off and only Platform Admins can change it. Approval atomically applies a linked manual `member` grant; self-approval is always refused. Requests are capped at **20 pending / 5 per minute / 50 per rolling day** per requester and expire after **7 days**. Model-selection requests, notifications and onboarding templates are not implemented in this slice. See [identity](../identity.md#self-service-membership-requests), [management API](../management-api.md#self-service-membership-requests-83-slice-a) and [dashboard](../dashboard.md#access-requests-83-slice-a).

### Provider-reported cost reconciliation (#48, first slice)

Platform Admins can upload complete closed **Anthropic Cost Report** JSON periods, attest effective-dated immutable mappings, and freeze aggregate comparisons against bounded raw historical configured-rate estimates (`/api/v1/platform/provider-cost-imports`, `.../provider-cost-mappings`, `.../provider-reconciliations`; browser session only, all admin tokens refused). **This is provider-reported cost reconciliation, not a verified invoice or a complete payable balance.** There is no UI, automated pull, credential resolution or new egress; uploads are capped at 5 MiB / 50,000 lines. See [provider-reported cost reconciliation](../provider-cost-reconciliation.md).

### Drift-checked management OpenAPI contract skeleton (#81, PR1)

A checked-in OpenAPI 3.1.0 artifact, generated by test-only tooling from every declared `/api/v1/*` method/template, including access/token policies, session/CSRF/Origin requirements, exact admin-token scopes and the shared error vocabulary. **Request/response schemas remain explicitly incomplete and counted** — DTO/handler coverage follows in later slices. No API, authorization, database or runtime behavior change. See [contract maintenance](../openapi/management/README.md).

## Fixes and smaller changes

- **Bounded dashboard access refresh (#291).** A refused management GET now triggers at most one automatic session refresh per navigation; a repeated refusal retires cached data and shows a stable permission notice instead of retrying indefinitely.
- **Key dialog lifetime hardening (#276).** Each key-creation/rotation dialog gets a fresh lifetime; successful non-secret actions cannot be repeated through a retained submit callback, and an admitted create stays uncancelled on local retirement so a newly created key can still be found and revoked.
- **Webhook metrics plan gate (#310).** The alert-webhook metrics collector counts waiting, leased and recent-terminal rows in separate branches of one statement and one statement-start clock, bounding work to active/recent rows plus index traversal rather than a scan of retained terminal history.

## Security notes

- **Rust toolchain pinned to 1.99.1 (#354).** `rust-toolchain.toml` pins the exact compiler (with `rustfmt`/`clippy`) that CI, both image builds and local gates now all use, matching the digest-pinned `rust:1.99.1-bookworm` stage in both Dockerfiles. `tests/supply-chain.test.mjs` fails the build on any mismatch or run-time override.
- **Runtime TEMP privilege revoked (#295)** and **fresh CNPG ACL restriction (#315)** both narrow what a compromised or misconfigured runtime connection, or a shared cluster's PUBLIC grants, can reach. See [Breaking changes](#breaking-changes-and-behavior-changes).
- **Local-upstream approvals (#203)** close the gap flagged in v0.8.0: an approval can no longer pin an address in a range the egress policy refuses for every other client.
- **Admin tokens remain high-risk credentials** (carried from v0.8.0): use short expiries, the narrowest scope and a CIDR allowlist.
- **No independent review.** This release is not an independent security certification (#61), and no new live-provider or capacity acceptance is claimed.

## Known limitations

- **Admin tokens / OpenAPI:** the contract artifact (#81, PR1) has request/response schemas explicitly incomplete; DTO/handler coverage is future work. Token attempt records are still not exported to a SIEM (carried from v0.8.0).
- **Self-service access (#83):** only Team/Project membership requests are implemented; model-selection requests, notifications and onboarding templates remain planned.
- **Provider-reported cost reconciliation (#48):** API-only, Anthropic Cost Report JSON only; no UI, automated pull or other provider.
- **Scheduled cost reports (#102) and signed webhooks (#45):** implemented end to end, but coordinator release-gate acceptance (staging rehearsal, candidate `dev-env` run) is a separate step from implemented scope, as for every feature in this release.
- **SCIM:** Authentik is accepted; Okta and Entra acceptance (#60) has not been run (carried).
- **Compatibility:** the broader client conformance program (#222) is incomplete; OpenAI-style reasoning/structured-output mapping for Claude Code (#70) is deferred to a future delivery, and server tools, structured output and strict tools remain refused on every adapter.
- **Carried from v0.6.0–v0.8.0:** independent security review (#61), steady-load admission/settlement stalls (#132), the second write outage after a two-instance CNPG failover (#149), unimplemented guardrails (#181) and IdP-initiated logout (#162). The Helm chart remains beta. There is no certified capacity number and no production-ready claim, and no new live-provider acceptance is made by this release.
