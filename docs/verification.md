### Database tests

A database test is `#[dbtest::test] async fn name(pool: PgPool)` (`crates/dbtest`, a dev-dependency proc macro; the runtime is `apps/gateway/src/dbtest_runtime`, test builds only). It replaces `#[sqlx::test(migrations = "./enterprise_migrations")]`: same test name and module path, same per-test database (named by sqlx's rule from the test path and recorded in `_sqlx_test.databases`), same single-threaded runtime, same `DATABASE_URL`. Only the way the schema gets there differs: the database is `CREATE DATABASE ... TEMPLATE` of a database the real migrator (`sqlx::migrate!("./enterprise_migrations")`) built once, about 60 ms instead of an empty database plus every migration (about 1.8 s). `#[sqlx::test(migrations = false)]`, the plain `#[sqlx::test]` and the legacy `./migrations` test stay on sqlx: they need an empty database or another schema, and the integration targets under `apps/gateway/tests` are separate crates that cannot reach the test-only runtime.

- **Template name.** `_omg_tpl_`, 8 hex characters of a SHA-256 of the maintenance database name (the family: collection only lists its own, because the leases of another maintenance database are invisible to it), then 24 hex characters of a SHA-256 over the format version, the maintenance database name, the server's UTC hour and every migration's version, description, kind, transaction mode and checksum. A changed or added migration is another template, so a stale one is never cloned. The hour is in the name because migrations seed state relative to when they run (the history partitions cover the following months with no default partition, and the rollup and storage-usage watermarks start at the current hour), so a template is at most an hour older than the database the test would have migrated itself; a test process that outlives the hour asks for the new hour's template, and the old ones are collected once no process leases them. A rebuild takes about a second.
- **Building.** The first process takes a session advisory lock, builds under `<name>_b`, runs the migrator, checks it recorded every migration, marks the database `IS_TEMPLATE` with connections refused, and renames it last. Other test threads of that process and other processes (worktrees, CI shards sharing a server) wait on the lock and then find the finished template. A template is complete only as a marked template that refuses connections: a process killed mid-build leaves a scratch name or an unmarked database, which the next builder drops and rebuilds; it is never cloned. Nothing stays connected to a template, so cloning is not refused with "being accessed by other users"; the clone retries that error briefly anyway.
- **Cleanup.** A test that returns normally and succeeds drops its database (`DROP DATABASE ... WITH (FORCE)`) and its `_sqlx_test.databases` record. A failing test (an `Err`, an assertion or a panic) keeps its database and prints `test database <name> kept for inspection`; the same test replaces it on the next run, as under sqlx. When the leftover is still in use (another process on the same server is running the same test), the test takes a database named from its path and its process id instead of dropping one that is in use. Each process holds a shared advisory lock on the template it uses for as long as it lives, so building another template collects only templates no live process uses (the exclusive try-lock fails while any process holds one). During that same setup, recorded test databases older than a day that nobody is connected to are dropped (a database with a connection refuses the drop), which clears what killed runs left.
- **Connections.** Each test's pool holds at most 5 connections, and creating or dropping a database takes one more for a moment. Unlike `sqlx::test`, the pools of one process share no cap, so a process can hold about 5 connections per test thread; keep test threads times 5, summed over the processes sharing a server, under its `max_connections`. The leases are session advisory locks on a direct connection: a transaction-mode pooler in front of the test server would break them.
- **Force a rebuild.** Set `OMG_DBTEST_REBUILD=1` for a run: the template is dropped and rebuilt unless another process is using it. Or drop the databases by hand (`ALTER DATABASE x WITH is_template false allow_connections true; DROP DATABASE x;`).
- **Proof.** `dbtest_runtime::tests::cloned_database_equals_a_freshly_migrated_one` compares a clone with a database the migrator ran on: relations, columns, constraints, indexes, triggers, function bodies, views, sequences, types, policies, extensions, schemas, default privileges, comments, ACLs, every table's rows and the `_sqlx_migrations` records. The only differences are values a migration stamps with the moment it ran, which are excluded in `installation`, `installation_settings`, `history_partitions`, `storage_usage_progress` and `usage_rollup_progress` (the snapshot reads `_sqlx_migrations` without its `installed_on` and `execution_time`, which record when and how fast the one build ran). The other tests of the module cover one build under contention, a changed migration set, half-built templates and the three cleanup outcomes.
- **Differences to know.** Every test database now has the same installation id and migration timestamps, where each used to have its own. The source checks that bind a fixture to its area group (`inference_openapi` wiring and `management_openapi` hardening) recognise `#[dbtest::test]` as well as `#[sqlx::test]`.

### Shared configuration source inventory

`configuration_source_tests::production_sources` supplies the configuration,
unsafe-site and entropy guards, as well as the management JSON write matrix.
It follows `lib.rs`, `main.rs`, both conventional Cargo binary layouts
(`bin/name.rs` and `bin/name/main.rs`), ordinary file and inline modules, and
unconditional literal `#[path]` attributes. A file reached
by production and test declarations stays production; filenames alone never
exclude it. Unreferenced `.rs` files are conservatively scanned too. The existing
test-gate predicate and the consumers' policy exceptions are unchanged.

The inventory fails closed on conditional module paths (`cfg_attr`, including
nested and raw-identifier forms), missing or ambiguous modules, and resolved file
modules outside `src` or without an exact `.rs` extension (#510). Inline module
directory overrides remain supported. Child resolution distinguishes ordinary
file modules from explicit paths, including when both reach the same file.
Symlinks are refused to avoid aliases, escapes and recursive directory walks.

A production `include!` must have a literal path to an `.rs` file in the final
scanned production set and parse as a Rust item file. A test-only target, missing
file, computed path or file outside the source tree fails. Included files with
external module declarations are unsupported because their resolution depends on
the inclusion context.
Imports/aliases of `include!`, module or `include` tokens inside opaque macros,
and macro calls with metavariable names also fail rather than assume coverage.
Ordinary item macros, strings, comments and test-gated helper includes remain
supported. Benign fixtures in `configuration_source_tests::coverage` exercise
these refusals and the supported layouts through `sources_at`.

Run the source guards and the management matrix with the commands below.
The matrix requires a disposable PostgreSQL test instance with database creation privileges.

```sh
cargo test -p open-model-gateway --lib configuration_
cargo test -p open-model-gateway --lib entropy::tests::only_this_module_draws_randomness
cargo test -p open-model-gateway --all-features --lib every_json_management_write_rejects_unknown_fields_after_valid_control
```

This is source-inventory coverage, not Rust macro expansion or a sandbox:
generated code from external procedural macros/derives, `build.rs` and other
crates still require review.

### CI scheduling and Rust shards

CI runs on every pull request, and pushes only to `main` or `v*` tags. New PR runs cancel superseded runs for that PR; each main/tag run has a unique concurrency group and is never cancelled by this policy. CodeQL, branch images and release-image workflows are unchanged.

The protected `gateway` check aggregates `gateway-lint` (fmt/Clippy), all four mandatory `gateway-tests` matrix legs, and `gateway-special`; any failed, skipped, cancelled or missing dependency refuses success. Each test leg has its own PostgreSQL service and SDK dependencies. `.github/scripts/rust-shards.mjs` builds each workspace package's tests (`cargo test -p <package> --all-features --no-run`, the same selection as its later runs, so nothing is compiled twice) and discovers the test targets from structured Cargo output, reconciles metadata per package, lists each target through Cargo, then distributes sorted gateway-library names round-robin using multiple exact libtest filters in one invocation per shard. Other targets stay whole with deterministic assignment. Terse listings have no footer in libtest, so a pretty listing cross-check supplies the count footer. Selected execution counts and default-ignored counts must match the inventory; ignored/live-opt-in tests keep their previous default behavior. New tests/targets join automatically; unsupported harness/listing formats fail closed. Doctests run once, on shard 0, per package that has a documented library. The test jobs build without debug information, and the shards' PostgreSQL data directory is memory.

`gateway-special` exclusively owns `filestore_s3` (Docker required) and both ordinary and ignored `runtime_privileges` runs, followed sequentially by the exact ignored Anthropic terminal probe and backup drill (with an explicit binary build). The terminal test stays ignored in ordinary shards; there is no broad workspace ignored-test sweep. Read-only `staging-image` builds/verifies its own image independently; publishing still needs `gateway`, `web` and `browser`. No test executable artifact crosses into a write job.

The shard runner reports inventories, selected/passed/ignored counts, per-target execution durations and total build/discovery duration. Round-robin balances test counts, not measured runtimes: compare actual CI wall time, slowest shard and runner-minutes after warm and cold runs before claiming a speedup. Parallel jobs still compile independently and can contend for runner capacity.

### Supply chain

CI's `cargo-deny` job runs `cargo deny --all-features check` (cargo-deny 0.20.2's release binary, installed and checksum-verified by the SHA-pinned `taiki-e/install-action`), and the `npm-audit` job gates on `npm audit --omit=dev --audit-level=high` and writes the full, non-blocking `npm audit` (dev tooling included) to the job summary. `.github/workflows/codeql.yml` runs CodeQL for `javascript-typescript` and `rust` (build mode `none`) on pushes to `main`, pull requests and weekly; results appear on the Security tab. `.github/dependabot.yml` opens weekly grouped updates for Cargo, npm (root workspace), GitHub Actions (SHA pins) and the `Dockerfile` base images. The release image is additionally scanned by Trivy in `image.yml`.

**Vendored upstream-base advisories (#214).** The normal `cargo deny --all-features check` stays unchanged on the real graph. Cargo marks path packages with `source: null`, which cargo-deny 0.20.2 omits from advisory matching. A separately labelled step in that same read-only job runs `node .github/scripts/vendored-advisories.mjs`: it reads `cargo metadata --locked --all-features --format-version 1`, validates registrations and graph references, copies the metadata into a private temporary directory, and invokes the same pinned tool with `--all-features --metadata-path <temporary-file> check advisories`. It removes the temporary input afterwards. The OAuth2 5.0.0 and OpenID Connect 4.1.0 ports are registered at their crates.io upstream identities; the helper verifies actual scanner coverage for both. Maintenance instructions and provenance are in `vendor/oauth2/MAINTENANCE.md` and `vendor/openidconnect/MAINTENANCE.md`.

Register a reviewed crates.io upstream base in the **root** `Cargo.toml` only when adding a vendored dependency, for example:

```toml
[workspace.metadata.vendored.example]
name = "example"
version = "1.2.3"
manifest = "vendor/example/Cargo.toml"
```

Only those three fields are accepted; crates.io is the fixed registry identity. The name/version must exactly match the actual path package, and the manifest must be a canonical, existing `vendor/.../Cargo.toml` within the repository (no traversal or symlinks). Registered packages must be explicitly excluded from workspace membership. Cargo's automatic workspace membership does not establish first-party ownership: only canonical manifest directories explicitly listed in the root `[workspace] members` array are exempt, and never packages under `vendor/`. To avoid ambiguous TOML interpretation without a second general-purpose parser, the root manifest must begin with `[workspace]` followed by `members = [...]` (blank lines/comments allowed); entries must be literal single- or double-quoted paths without escapes, globs, traversal, symlinks or duplicates. Unsupported layouts fail closed. All other path packages require registration, including implicit workspace members and explicitly listed vendor packages. Unknown path packages, stale/duplicate registrations, name/version mismatches, unexpected metadata shapes, missing/inconsistent graph references and projected ID collisions fail closed. First-party workspace packages are never projected. Before accepting a successful scan with registrations, the helper requires exactly one strictly parsed `[INFO] gathered N crates in Nms` diagnostic and strictly parsed `[DEBUG] filtered <name> <version>` lines. Each filtered identity must uniquely match one projected metadata package and appear only once; the gathered count plus filtered package count must equal the total projected metadata package count. Missing/altered filter diagnostics that leave a package unaccounted for, malformed/duplicate graph diagnostics, unknown/ambiguous filtered identities, count mismatches, or any filtered registered package refuse coverage even if cargo-deny itself exits green. This guards the pinned diagnostic/count contract; it does not independently attest the scanner's advisory-matching internals. It does not invent roots/edges or override the real policy to force inclusion. Only the registered package source/ID and corresponding graph references change in the copy; actual dependency declarations, `Cargo.lock`, the build graph, normal license/ban/source checks, SBOMs and provenance are untouched. No blanket mapping or advisory ignores are added. This means **upstream-base advisory coverage**, not proof that patched code is unmodified or independently certified.

The job also runs `node --test tests/vendored-advisories.test.mjs` with the installed pinned scanner. A temporary fixture named/versioned `smallvec 1.10.0` and an isolated local Git advisory database with a **synthetic**, non-production `RUSTSEC-2026-9999` demonstrate the unprojected miss and projected detection, plus unchanged-registry/no-vendor and refusal controls, including registered packages filtered by `cfg(any())` or `[graph].exclude`. Its `db-path` is temporary and `db-urls` selects only that cached database; cargo-deny's `--offline` disables fetching (0.20.2 has no `--disable-fetch` flag), and `disable-yank-checking = true` prevents index access. The fixture uses no network or credentials and does not build Rust. `--offline` is also accepted by the helper for local runs with a previously cached real advisory database.

**Third-party code never shares a job with a write token (#194).** A job whose `GITHUB_TOKEN` has any `write` permission may use only these actions, all pinned by SHA: `actions/checkout`, `actions/download-artifact`, `docker/setup-buildx-action`, `docker/login-action`, `docker/build-push-action` and `github/codeql-action/upload-sarif`. "Has a write permission" means any scope set to anything but `read` or `none`, set in the job or at the workflow level, inherited from the caller of a reusable workflow (`ci.yml`'s `image` job grants `contents`, `packages` and `id-token` write to `image.yml`), or implied by declaring nothing, because the repository's default token may write. Scanners, linters and setup steps run in jobs with a read-only token.

- **Image pipeline.** In `image.yml`, `build` pushes the per-architecture images by digest and nothing else. `verify` (`contents: read`, `packages: read`) pulls the digest, drops its registry login and runs the version check, the staging rehearsal, the runtime contract test and the Trivy scan. `publish` (which holds `id-token: write` for cosign) starts only after every `verify` leg passes. Tags and annotations come from a read-only `meta` job. The digests move between jobs as job outputs.
- **Pull-request scan (#475).** `ci.yml`'s `staging-image` job (read-only token, no persisted checkout credentials) runs the tag run's scan before any tag exists: the same pinned Trivy and the same policy (fixable HIGH and CRITICAL fail), straight after the build and before any script from the pull request runs on the runner. It scans the amd64 image built from the pull request (from the Docker daemon only) and the arm64 child of the approved runtime base (from the registry only). Trivy runs from an empty directory, and the repository may not contain a `.trivyignore` or `trivy.yaml`. It is not a boundary against a malicious pull request, which controls the workflow, the Dockerfile and the test; the required check name and the review of the diff are. **When it fails on a pull request that did not touch the image:** a fix for a HIGH or CRITICAL finding in the runtime base has been published. Every open pull request fails `staging-image` until the base is re-pinned: update the digest in `Dockerfile`, `deploy/loadtest/Dockerfile`, `APPROVED_RUNTIME` in `tests/supply-chain/lib.mjs` and `ci.yml` in one pull request (#474 is the example), then update the other branches. A failed download of the vulnerability database fails the job too; re-run it.
- **Dockerfile rules (#377, #485).** `tests/supply-chain.test.mjs` checks every Dockerfile in the repository on its `FROM` lines (a file named `Dockerfile*`, `*.dockerfile` or `Containerfile*`, in any case, but not `*.dockerignore`; a file with such a name that is not one of the two known Dockerfiles fails the test by name, with what to do; discovery uses `git ls-files -z --cached --others --exclude-standard` with the sanitized test Git environment, so force-added tracked and new untracked source files are checked while ignored artifacts such as `.local/` are excluded (#609). Undecodable UTF-8 paths fail inventory. An untracked embedded repository or a tracked submodule stops discovery because its contents are outside the parent Git inventory. Discovery also skips `.git`, `node_modules`, `target*`, `dist` and `.turbo`, which hold Git objects, installed packages and build output rather than source, and nothing may build from them, see the next rule): every `FROM` image is pinned by digest; every `FROM` of an image named `rust` carries the exact version in `rust-toolchain.toml`, and all of them the same digest, and is the whole approved reference `APPROVED_RUST` (registry, repository, tag and digest; #488); and in the production and load-test Dockerfiles the last `FROM` is the one approved distroless base, the only `gcr.io/distroless/` image in the file. No other image can enter a stage through `COPY --from=` or a mount (the rule on images below); what a `RUN` command downloads is not checked. All three checks read the file through one reader (`dockerfileStages`), which must see what BuildKit builds, not lines that only look like `FROM`. It does this by refusing what the Dockerfiles do not use instead of parsing it; the test fails naming the file, the line and the rule. Not allowed in any Dockerfile:
  - `<<` anywhere in an instruction, also when a `\` continuation splits it (`<\` then `<EOF`). A heredoc body is content and could carry the approved `FROM` line while the image is built from another base. Shell here-strings (`<<<`) and shifts (`$((1<<4))`) are refused with it, because they cannot be told apart safely; put such a script in a file and `COPY` it.
  - Any instruction other than `ARG`, `CMD`, `COPY`, `ENTRYPOINT`, `ENV`, `EXPOSE`, `FROM`, `HEALTHCHECK`, `LABEL`, `RUN`, `SHELL`, `STOPSIGNAL`, `USER`, `VOLUME` and `WORKDIR` (in any case). So no `ADD` (it fetches URLs and git repositories; use `COPY`), no `ONBUILD` or `MAINTAINER`, and no `//syntax=` line, which BuildKit also reads as the instruction to load another build frontend. A line of JSON is refused the same way, as an unknown instruction.
  - A `#!` line, and a comment whose text starts with one word (a letter, then letters or digits) followed by `=`, with or without spaces around either (`# escape=...`, `#syntax=...`, `# check = ...`), anywhere in the file, because BuildKit reads such a comment at the top as a parser directive. Reword the comment, for example `# Set word to ...`.
  - Any character other than printable ASCII, tab and LF (no CRLF, no byte order mark, no Unicode spaces or control characters).
  - A blank line, a comment or a line starting with `FROM` inside a continued (`\`) instruction, and a line ending in two backslashes.
  - A `FROM` that spans lines or is not `FROM [--platform=<p>] <image> [AS <name>]` with a literal image (no `ARG`/`$` variable, quotes or escapes).
  - An image that enters a stage other than as its `FROM`: `COPY --from=<x>` and every `from=<x>` of every `RUN --mount=` (any mount type) must be the name of an earlier stage of the same file, in any case, and nothing else. No stage index (`--from=0`; BuildKit resolves an index only for `COPY`, and reads a mount's `from=0` as the image `0`) and no external image, pinned by digest or not: an image that is needed gets its own `FROM ... AS <name>` stage, where the checks above see it.
  - A `COPY` or `RUN` flag that is not `--name` or `--name=value`, with lower-case letters and `-` in the name and only letters, digits and `. _ / : @ , = -` in the value. So no `$` variable, quotes or backslash, and also no `*`, `+` or `~` (`--exclude=**/*.md` and `--chmod=u+x` are refused; write `--chmod=0755`).

  Continued `RUN`, `ENV` and `HEALTHCHECK` lines, comments between instructions, and instructions in any case or indentation are read normally. If a Dockerfile needs one of the refused forms, change the reader and its fixtures in the same pull request; do not work around the test.
- **What these checks are, and are not.** The supply-chain suite makes a change to what CI builds, and to every job that builds, publishes or tests an image, a visible change in review, and it catches accidental drift. It is not a boundary against a deliberately malicious pull request, which controls the workflows and these tests alike: mandatory review of workflow diffs and of `tests/supply-chain/pinned-jobs.yaml` is. What it does not read: the contents of the repository files that the jobs run. For the pinned image jobs, those files are the list `PINNED_JOB_INPUTS` in `tests/supply-chain/policy.mjs`, derived from the pinned jobs and their local actions (every path a `run:` line names, also under a checkout directory such as `control/`, each local action, and each npm script with the files its command names) and required to equal the list:

  `.github/actions/setup-node/action.yml`, `.github/scripts/build-oras.sh`, `.github/scripts/fetch-verified.sh`, `.github/scripts/oci-index.py`, `.github/scripts/oci-layout.py`, `.github/scripts/oci-stage.py`, `.github/scripts/publication-tags.py`, `.github/tools/oras.json`, `.github/workflows/image.yml` (the cosign certificate identity), `apps/gateway/Cargo.toml` (the version check), `package.json: test:container`, `scripts/github-release.sh`, `scripts/staging.py`, `tests/container-image.test.mjs`.

  **A change to one of these files is a change to the image jobs and must be reviewed as one.** The remaining routes to change what a pinned job tests that a verification pass found all need an edit to a pinned or listed file, and so show in review: the contents of `scripts/staging.py` (or another listed script), a pinned step's `env`, a pinned run line that runs a script directly through its shebang, through `bash -c` or through a variable command word, and a pinned run line using `uv run` or another runner. A new or renamed file that a pinned job runs fails the test until it is listed (here and in the policy). Their contents are not hashed or copied (AGENTS.md). ### Secret scanning

No secret gets committed (#596). Before this, the protection was `.gitignore` and review. Two layers now, plus the ignore files.

**CI (`ci.yml`, job `secret-scan`).** gitleaks 8.30.1 (MIT licence; [project](https://github.com/gitleaks/gitleaks)), fetched by `.github/scripts/fetch-verified.sh` against the SHA-256 in the workflow: the `linux_x64` line of the release's `gitleaks_8.30.1_checksums.txt`, equal to the digest GitHub records for the asset and to a fresh download. No third-party action: the only action is `actions/checkout` (pinned), the token is `contents: read`, and the only project code that runs in the job is `fetch-verified.sh`. The checkout takes the whole history (`fetch-depth: 0`, no persisted credentials, no `ref`, sparse checkout or filter). The scan step runs with `--config .gitleaks.toml --redact --ignore-gitleaks-allow` and these ranges:

- on a pull request, `gitleaks git --log-opts="-m --text <base>..<head>"`: every commit the pull request adds, so a secret added in one commit and removed in the next is still found. Merges of `main` into the branch are excluded by the base. `-m` shows a merge commit's changes (plain `git log -p` shows none, so a secret added in a merge was invisible), and `--text` scans files that a `.gitattributes` `-diff` entry or a NUL byte would turn into "Binary files differ";
- on a push (to `main`, and `v*` tags), `<before>..<after>`; when the old tip is the all-zero id or is no longer in the checkout (a new ref, a force push) the whole history reachable from the pushed commit;
- on both, `gitleaks dir .` over the checked-out tree, the final state of every file.

**The step does not fail open.** gitleaks exits 0 with "0 commits scanned" when its `git log` fails, so before scanning the step requires every SHA it uses to be 40 lower-case hex digits that exist in the checkout (an empty, malformed or unknown id fails the job; a push `before` that is well formed but missing means a force push and scans the whole history), runs `git rev-list --count` on the range under `set -e`, and requires gitleaks to report how many commits it scanned. It does not compare that number with `rev-list`: gitleaks counts only commits that add or remove lines, so renames, empty commits and merges without a patch are not in it (two of four in a test repository). An **empty range** (base equal to head, no commits) scans no history, says so in the log, and still scans the tree. Before the real scans, two canaries run with the same config and the same options: a directory and a throwaway git repository (one commit, a `.gitattributes` `-diff` entry, so `--text` is exercised) holding made-up values built from pieces: an AWS key, a gateway key, a session cookie, a file-store key, a URL password, a PEM private key and a generic `API_KEY` assignment. Each rule has to fire in both, or the job fails: a scanner, config or default rule that stops working cannot pass quietly.

**What the log shows.** The matched text is redacted (`--redact`), but gitleaks' verbose output also prints the matched line, up to about 50 characters before the keyword, unredacted, so a secret fused to an identifier would appear. The step therefore prints a report template instead: one line per finding with the rule, the file, the line number and the commit (`finding rule=... file=... line=... commit=...`), never the text. File names are shown, so a secret in a file name would be too. gitleaks' own log lines (counts, timings) remain.

**Required check, and releases.** `secret-scan` is a new job, and branch protection does not require it until the owner adds it. It is not a dependency of the `image` job (that would change a pinned job and the graph tests), so a failing `secret-scan` does not stop a tag: **before tagging, check that `secret-scan` is green on the commit**.

**Config (`.gitleaks.toml`).** The scanner's default rules, unchanged (`[extend]` has `useDefault = true` and nothing else; the test refuses disabled rules and any local rule whose id is not this repository's own, so a local rule cannot shadow a default id), plus:

- `omg-gateway-key`: inference keys `omg_<32 hex>.<64 hex>` and admin tokens `omg_admin_...` (`auth.rs`, `admin_tokens.rs`), also when fused to other text;
- `omg-session-cookie`: `omg_session=` or `omg_csrf=` followed by 64 hex characters (`identity.rs`);
- `omg-file-encryption-key`: `<key id>:<43 base64 characters>=` after a variable name that contains FILE and KEY, such as `GATEWAY_FILE_KEYS` (`filestore/crypto.rs`; the variable's name is the operator's choice, so a differently named variable is not found);
- `omg-url-credentials`: `scheme://user:password@host` with a password of 12 or more characters and entropy of at least 3.0, without `$`, `{`, `<`, `*` or brackets, so `postgres:postgres@`, `user:pass@`, `$VAR`, `${VAR}` and `<placeholder>` forms are not matched. A low-entropy real password is not found. It finds ten marker passwords in test fixtures, covered by three allowlist entries.

The allowlist has one entry per known fixture, each with its reason: one exact file, a regex anchored `^...$` to the whole text the scanner matched (so a different key that merely contains a fixture's text is not excused; a test plants one), the one rule it silences, and `condition = "AND"` (the default OR would let the path alone allow the whole file). The three private-key fixtures are matched in full. The `bitop-lock.json` entry (`regexTarget = "match"`) excuses exactly the text `tokens.css": "<64 hex>"` in that file, which is the SHA-256 of a copied UI file whose name contains "tokens"; it excuses nothing else there. Directories, globs, stopwords, commit scopes, baselines and `.gitleaksignore` files are refused by `tests/supply-chain/secret-scan.test.mjs`, and inline `gitleaks:allow` comments are ignored by the scan, so the config is the only place a finding is accepted. The config comes from the checkout under test, like the workflow: a pull request that widens it is a change to review. Test fixtures in the repository that need a key-shaped string build it from pieces, as the tests do.

**Local scan and the optional pre-commit hook.** `scripts/secret-scan.py` runs the same scanner version, config and options, printing findings the same way. Nothing installs it; it fails closed (exit 2, nothing scanned) when `gitleaks` is missing or is not the pinned version. From the repository root, install the pinned release (this can be repeated; other platforms: take the matching asset and its line from `gitleaks_8.30.1_checksums.txt`) and tell the script where it is:

```sh
d="$HOME/.local/bin/gitleaks-8.30.1"
mkdir -p "$d" && rm -f "$d/gitleaks.tar.gz"
bash .github/scripts/fetch-verified.sh https://github.com/gitleaks/gitleaks/releases/download/v8.30.1/gitleaks_8.30.1_linux_x64.tar.gz 551f6fc83ea457d62a0d98237cbad105af8d557003051f41f3e7ca7b3f2470eb "$d/gitleaks.tar.gz"
tar -xzf "$d/gitleaks.tar.gz" -C "$d" gitleaks
export GITLEAKS_BIN="$d/gitleaks"   # or put "$d" on PATH; GITLEAKS_BIN may also be a bare name found on PATH
```

- `python3 -I scripts/secret-scan.py staged` scans the **staged content itself**: the staged files are written from the index to a temporary directory (removed on every exit path) and scanned there, so a `-diff` attribute or a NUL byte cannot hide a secret in a patch, and unstaged edits are not read.
- To use it as a hook, create `.git/hooks/pre-commit` yourself (mode 755) with `exec python3 -I scripts/secret-scan.py staged`.
- `python3 -I scripts/secret-scan.py history` scans `-m --text HEAD`: what CI scans for a push of the checked-out commit.

**What the local scan leaves out.** Other tools keep private refs in the same repository (editors, agents and checkpointing tools, for example under `refs/t3/`), and those can hold snapshots of untracked files; that is how a local environment file once ended up in a scan of `--all` without ever being tracked. Those refs are not this project's history and CI never has them, so `history` reads only `HEAD`'s history. To check your own clone completely: `gitleaks git --config .gitleaks.toml --redact --no-banner --log-opts="-m --text --all" .` (every ref; add `-v` to see where, which prints the matched line). Scanning `--branches --remotes --tags` instead is expected to report one finding, prose in `docs/live-acceptance.md` at commit `64d442dc12` on the remote branch `origin/issue/60-isolated-scim-staging`, which is not in `main`; the allowlist has no entry for it, and it would be flagged in CI if that branch is merged.

**When the scan flags something.**

1. Treat it as real until shown otherwise. **Rotate or revoke the credential first**, then remove it from the change. Deleting it in a later commit, or rewriting the branch, does not make it safe: it is in the history and in clones. The log shows rule, file, line and commit only.
2. Only a test fixture or a false positive (a documented placeholder, a hash, prose) goes into `.gitleaks.toml`, as the narrowest entry (exact file, whole-text regex, rule, reason). Never allowlist a real secret, and never add a path pattern to make a failure go away.
3. A file that holds secrets and is not tracked belongs in `.gitignore` and `.dockerignore`. Both ignore `*.env`, `*.env.*` (the tracked `*.example` files stay tracked), `.env`, `.env.*`, `ai.env`, `.envrc`, `.netrc`, `.pgpass`, `.git-credentials` and `.local/` at any depth (staging, load test and demo state); `.dockerignore` also excludes `*.pem`, `*.key`, `*.p12`, `*.pfx`, `secrets/`, `backups/` and `*.bak`. A file such as `boat.env` is matched by neither `.env` nor `.env.*`, which is how one was once missed. `tests/supply-chain/secret-scan.test.mjs` checks, with `git check-ignore` and a `.dockerignore` matcher, that those places stay out of git and out of the image build context, and that dropping or re-including any of them fails the test.

**Limits.**

- *What the ignore files cannot do.* The image build context is deny-by-default, but `apps/gateway/src`, `apps/gateway/migrations`, `apps/web/src`, `apps/web/public` and `tools/*/src` are re-included as whole directories. Any file in them that no exclusion names (a credential with another name) enters the build context; the scanner, not the ignore file, is the control there.
- *Formats.* Pattern and entropy scanners miss unusual formats: a credential with no recognisable prefix or shape, a short or low-entropy password, a variable named unlike FILE...KEY. The project's own rules cover only the gateway's own shapes (the unknown `boat_` format has none).
- *Where it does not look.* Paths gitleaks skips by default (lock files, images and other binary extensions, `node_modules`, any file named `gitleaks.toml` including the repository's own config); archives (`--max-archive-depth` is not set); UTF-16 and values split across lines or strings; commit and tag messages, notes and file names; submodules and LFS content; branches without a pull request and tags not named `v*`, which CI does not run on; a commit whose message skips CI.
- *When.* It runs in CI after the push: the commit is on the remote when it fails, so rotation is the remedy, and the local hook is the earlier check. The scan cannot prevent a history rewrite or a force push. `secret-scan` is not a required check until the owner adds it.
- *Who controls it.* The config and the tests come from the same pull request as the change they check. Widening them is visible in the diff and is a review item; a scan of the base branch's config is not done (planned).
- *Not replaced.* GitHub's own secret scanning and push protection are repository settings the owner turns on; they complement this scan (they know many vendors' token formats and can block the push) and are not replaced by it.

### Bash for the shell fixtures

`npm run test:supply-chain` and `tests/oci-tool.test.mjs` run the real workflow `run:` scripts and `.github/scripts/*.sh` under Bash and check that their guards refuse. **The minimum supported Bash is 4.4** (#380); CI's Ubuntu runners have 5.2. With an older, missing or non-Bash `bash` first on `PATH`, both suites fail at once, before any test or fixture runs, with a message naming the required version, the file found and its version. It is a failure, never a skip, and there is no variable or flag that turns the check off: install a newer Bash and put it first on `PATH`. macOS ships `/bin/bash` 3.2, which is refused; Homebrew's `bash` is supported. The suites run every fixture with the `bash` that was checked, not `/bin/bash`, and a `bash` that a fixture looks up itself (`#!/usr/bin/env bash` in a stand-in tool, `bash file` in a helper script) is that same file: the fixture's `PATH` starts with a private temporary directory that holds only a link to it. Relative and empty `PATH` entries (the current directory) are not passed on to fixtures.

The no-direct-shell check in `tests/bash-preflight.test.mjs` parses all committable JS/TS files under `tests/` with the installed TypeScript parser (#597). It refuses imports/re-exports of `child_process` and `node:child_process`, `module`/`node:module` (including `createRequire` aliases), CommonJS `require`, nonliteral dynamic imports, and literal native process loading APIs. Call spacing, aliases, optional calls, comments and computed child-process member names do not matter: tests have no raw process import to call. Strings, regexes, comments and TypeScript type syntax are data, so shell words and workflow `shell` fields need no line exceptions. Syntax errors fail closed. The existing Git inventory still refuses unknown extensions, submodules and committed `node_modules`; ignored generated files are excluded.

Tests import only `spawn`, `spawnSync`, `execFile` or `execFileSync` from `tests/process.mjs`. This wrapper validates actual runtime arguments, rejects shell names (case-insensitively, including rbash/mksh/pwsh/elvish), shell script extensions, every `shell` option (including inherited options), and indirect launchers such as env, busybox, npx, yarn and pnpm. It always passes `shell: false`. Node entry points must be JavaScript files, preventing Node from treating `.py`/`.yaml` data as CommonJS or accepting inline evaluation/loader flags. npm is limited to the browser stack's existing web build argument form; its script remains an explicitly reviewed entry point. Bash fixtures use the checked `bashPath()`/`runBash()` preflight. `runBash()` rejects caller-supplied shell options before setup and explicitly disables the outer shell. Only `process.mjs`, `bash-preflight.mjs` and `bash-preflight.test.mjs` have raw process authority, by exact path.

Supported scope is accidental or casual direct process use in JS/TS tests, not hostile code containment. Python tests, JSON/YAML data, dependencies, external scripts, transitive program behaviour (including git hooks, tool configuration, executable stand-ins and interpreter input), dynamic evaluation and fabricated loader/native API access are not sandboxed. Adding a new trusted API, launcher or executable script requires review. Inert source and argument fixtures exercise refusals without executing them; the suite also scans the actual repository and exercises benign wrapper execution.

Why 4.4, measured with the official Bash builds of each release:

- **Before 4.1 a failing `[[ ... ]]` does not end a `set -e` script.** The workflow guards are bare `[[ ... ]]` lines under `set -euo pipefail`. Under 3.2 and 4.0 a script whose first guard fails carries on and returns the status of its last line, so the `workflow_call` probe guard and the empty `ARTIFACT_ID` importer guard returned 0 in the tests where they must refuse. From 4.1 on both refuse.
- **Under 4.1 to 4.3 `.github/scripts/build-oras.sh` exits 1 after a failed build, not the build's own status,** and one `tests/oci-tool.test.mjs` test (exit 71 after a compiler failure with a read-only module cache) fails.
- Under 4.4, 5.0, 5.1, 5.2 and 5.3 both suites pass.

The check (`tests/bash-preflight.mjs`) asks the `bash` it found for `BASH_VERSINFO` and also runs the first behaviour above directly. The workflows themselves run only on GitHub's Ubuntu runners (Bash 5.2), so nothing changes there; the guards are not weaker under a newer Bash, and no assertion was changed.

### Rust toolchain

`rust-toolchain.toml` pins an exact channel version (currently 1.100.0) with the `rustfmt` and `clippy` components. `rustup` reads it automatically, so a plain `cargo fmt`/`cargo clippy`/`cargo build`/`cargo test` on a machine with `rustup` installs and uses that exact compiler without any extra flag — **local gates must run on the pinned version, not whatever toolchain happened to be default or active before**. All `ci.yml` jobs that install Rust (`gateway-lint`, `sdk-compat`, `gateway-tests`, `gateway-special`, `browser`) pass the same version explicitly to the SHA-pinned `dtolnay/rust-toolchain` action's `toolchain:` input, and every Rust build stage in every Dockerfile in the repository — the root `Dockerfile` and `deploy/loadtest/Dockerfile` — uses `rust:1.100.0-bookworm` at the identical digest, pinned by digest. `tests/supply-chain.test.mjs` parses `rust-toolchain.toml` with a small strict TOML-subset parser, finds every Dockerfile through that Git source inventory (not a fixed list) and checks every `FROM rust:...` stage in each, and fails if any of them disagree; if the channel is not an exact `x.y.z` version; if two Dockerfiles pin the same version at different digests; if any `dtolnay/rust-toolchain` step omits `toolchain:`, sets a floating channel (`stable`, `beta`, `nightly`, with or without a date), or names a different exact version; or if any workflow or local composite action overrides the pin at run time (`RUSTUP_TOOLCHAIN`, `rustup default`/`override set`/`toolchain install`, or `cargo +<toolchain>`).

`rust-version` fields in `Cargo.toml` (`apps/gateway` and `tools/loadgen`: `1.94.1`, which the AWS SDK crates require; `tools/mock-upstream`: `1.88`) are each crate's **minimum supported Rust version** for crates.io consumers, not the build pin: they are allowed to sit well below 1.100.0 and are not checked against `rust-toolchain.toml`.

This exists because CI and local development can otherwise drift onto different compilers: PR #348 passed every local gate on rustc 1.98.1, then failed CI's `-D warnings` build because the newer floating `stable` channel had deprecated an API the code used (#354).

**Bumping the pinned version is a single reviewed PR, never a side effect of another change:**

1. Read the new version's release notes for behavior changes, new lints and deprecations.
2. Change the version in `rust-toolchain.toml`, every `ci.yml` Rust setup step's `toolchain:` input, the `rust:<version>-bookworm` tag and digest in both Dockerfiles and `deploy/spark/test-job.yaml`, and `APPROVED_RUST` in `tests/supply-chain/lib.mjs` together, in the same commit. Dependabot's `docker` entry reads `directory: /` only, so a Dependabot refresh of the Rust digest changes the root `Dockerfile` but not `deploy/loadtest/Dockerfile`: update the load-test Dockerfile, the Spark test image, and `APPROVED_RUST` in the same pull request.
3. Fix any lint or warning the new compiler introduces (CI turns warnings into errors).
4. Run the full local gates in [Test commands](#test-commands) above on the newly pinned version before opening the PR; `tests/supply-chain.test.mjs` also runs as part of `npm run test:supply-chain`.

An optional non-blocking scheduled job on the floating `stable` channel would give early warning of an upcoming deprecation, but it would need its own job with a read-only token and no secrets, distinct from the pinned jobs above; none exists yet (#354 leaves it for a follow-up rather than adding a job that is not yet verified to run safely).

### Structure ratchet

The gateway crate has files and functions that are too large (#499). Two checks stop them growing while they are being split. Neither changes what the gateway does.

**File size** (`npm run test:structure`; `tests/structure.mjs`, `tests/structure.test.mjs`). The test counts the production lines of every `.rs` file under `apps/gateway/src` and compares them with `tests/structure-allowance.json`.

- Test files are not counted. A test file is `tests.rs`, a file ending in `_tests.rs`, any file under a `tests` directory, or a module that its parent declares under `#[cfg(test)]` or `#[cfg(all(test, ...))]` (with everything in that module's directory, for example `management_openapi/`).
- In other files every line counts, blank lines and comments included, except top-level test modules: a `#[cfg(test)]` or `#[cfg(all(test, ...))]` attribute at the start of a line followed by a `mod` item. An inline `mod x { ... }` is left out up to its closing brace. Code after it still counts. A `#[cfg(test)]` on a function, an `impl` or a `use` is counted.

Three checks stop a file leaving the count by accident:

- A file that is skipped as a test file may not also be declared by production code. `pub mod adv_tests;` without `#[cfg(test)]`, or a production `#[path = "..."]` into a test-only directory, fails: rename or move the file. Test names and test-only directories are not measured.
- A measured file may not contain `rustfmt::skip`. The counting relies on rustfmt's layout.
- Nothing under `apps/gateway/src` may be a symbolic link. Links are not followed.

The rules:

1. A file with more than 800 production lines must be in `files`, and may not exceed its ceiling there.
2. A ceiling may be at most 50 lines above the file's real size.
3. A listed file that is at or under 800 lines, or that no longer exists, must be removed.
4. The list only shrinks. Every entry in `files` must also be in `baseline`, with a ceiling no higher than the baseline value. An entry in `baseline` with no entry in `files` must be deleted, so a file taken off the list stays off.

To lower an allowance after shrinking a file, set its number in `files` to the new size that the failure message prints. Leave `baseline` alone. When the file reaches 800 lines or fewer, delete its entry from both `files` and `baseline`. Never add an entry and never raise a number: split the file instead.

**Splitting a listed file.** A listed file cannot be renamed while it is still over 800 lines: rule 3 refuses the old path and rule 1 refuses the new one. Keep the file at its path and move code out into child modules (`x.rs` plus `x/part.rs`). Lower its ceiling as it shrinks.

**Why the remaining files are still listed.** None of these has a reason to be large beyond not having been split yet (#499 goes file by file, and each move is a pure move of whole items into child modules, with no caller changed). This is what each holds and where the cut would go:

- `audit_export.rs`: the SIEM exporter (webhook, syslog over TLS and OTLP transports, the delivery loop and the nested `pki` module) in one file. Not yet done; one module per transport is the obvious cut.
- `filestore/files.rs`: file metadata, the storage-quota SQL and the `FileStorage` upload/read/delete path (about 400 lines of one `impl`). Not yet done; the quota and policy SQL and the upload path are separable.
- `jobs/schedule.rs`: the batch-line scheduler (route settings and time windows, the metrics gate and the `Scheduler` claim logic). Already split once (`schedule/visibility.rs`); the settings types and the metrics parser are the next cut, not yet done.
- `management/alerts.rs`: alert rule and notification handlers; the webhook part is already in `alerts/webhooks.rs`. Not yet done.
- `management/catalogs.rs`: catalogs, workspace-type defaults, overrides and per-workspace model selection handlers. Not yet done.
- `management/directory.rs`: workspace, user, group-mapping and cost-centre handlers. Not yet done; one module per resource is the cut.
- `management/governance/policies.rs`: limit and budget types, layered policy storage and the policy handlers. Not yet done.
- `management/resources.rs`: the transaction helpers every management module calls (`platform_write`, `platform_read_tx`, workspace access) together with provider, deployment and model handlers. Not yet done; the shared helpers have the most callers, so that cut touches the most paths.
- `providers/openai.rs`: the OpenAI adapter with the chat wire decoder and the SSE stream decoder, 66 lines over the limit. Not yet done.
- `telemetry.rs`: the OTLP trace recorder, alias registry, exporter and worker, 90 lines over. Not yet done.

The test also reads the raw text of the list and fails when a key is written twice in one section. `JSON.parse` would keep the last one and say nothing.

The limit of rule 4: `baseline` is a second copy in the same file, not git history. Someone can edit both copies in one commit and the test will pass. The test does not prevent that. It makes it visible: any added line or raised number in `baseline` shows in the diff, and a reviewer must refuse it. The same holds for the `800` and `50` constants in `tests/structure.mjs`.

**Function length and complexity** (Clippy). `apps/gateway/src/lib.rs` and `apps/gateway/src/main.rs` turn on `clippy::too_many_lines` and `clippy::cognitive_complexity` for the non-test build, at Clippy's default thresholds (there is no threshold setting in `clippy.toml`, and none may be added). CI runs Clippy with `-D warnings`, so a new offender fails the build. Test code is not checked.

Each function that offended when this landed carries a marker directly above it:

```rust
#[cfg_attr(not(test), expect(clippy::too_many_lines, reason = "#499"))]
```

`expect` works in both directions. A new long function fails because it has no marker. A marked function that no longer offends also fails (`this lint expectation is unfulfilled`), so the marker has to be deleted in the commit that fixes the function. To find the remaining work, search for `reason = "#499"`.

Do not add a marker to new code, and do not use `allow`. Clippy does the checking. `npm run test:structure` checks that its switches are still on:

- `lib.rs` and `main.rs` each contain the crate line `#![cfg_attr(not(test), warn(clippy::too_many_lines, clippy::cognitive_complexity))]`.
- `apps/gateway/clippy.toml` sets neither `too-many-lines-threshold` nor `cognitive-complexity-threshold`. A `clippy.toml` or `.clippy.toml` at the repository root is checked too if one appears.
- Under `apps/gateway/src`, `clippy::too_many_lines` and `clippy::cognitive_complexity` are named only on the two crate lines and in markers. A marker is the attribute above, for one lint or both, on one line or in the four-line form rustfmt writes. An `allow`, another level, another reason or a comment that names a lint fails. So does `reason = "#499"` on anything else.
- The number of markers equals `markers` in `tests/structure-allowance.json` (58 when this landed), and `markers` may not exceed `markersBaseline`.

When you remove a marker, lower `markers` by one in the same commit. Leave `markersBaseline` alone. Never add a marker and never raise either number. As with `baseline`, someone can raise both numbers in one commit; the diff shows it and a reviewer must refuse it.

The thresholds are Clippy's, so a toolchain bump may change which functions offend; handle that in the bump's own PR ([Rust toolchain](#rust-toolchain)).

**Known limits.** The ratchet stops accidental growth. It does not resist someone who sets out to get around it. Nothing enforces the following; review must catch them:

- Code pulled in with `include!`, or with a `#[path]` to a file that does not end in `.rs`, is not counted.
- A `#[cfg(test)]` line inside a block comment, a string literal or a macro body can confuse the line counter. Every such case found so far had to be constructed on purpose.
- A `mod x;` declared inside an inline module (not at the start of a line) is not followed when deciding which files are test-only or declared by production code.
- Clippy does not see a long body moved into a `macro_rules!`, or a long closure or block in a `static` or `const` initialiser.
- Clippy lints the all-feature build with tests and the default-feature library and binary. Test code compiled only without `integration-tests` is not linted.
- An `allow` of a whole Clippy group (`clippy::pedantic`, `clippy::nursery`, `clippy::all`) placed after the crate line could switch the lints off without naming them.
- Only `apps/gateway/src` is covered. Other crates and `build.rs` are not.

### Egress client rule

Every outbound reqwest client starts from `crate::egress::client_builder` (or `pinned_client_builder` for an approved local endpoint; it takes an `ApprovedDestinations` that only `providers/local/endpoints.rs` can construct, after its approval checks), which turns off redirects, implicit retries (reqwest's retry policy: the connection pool beneath it may re-dispatch a request it never wrote, see [Lost connections](operations.md#lost-connections-483)) and ambient proxies (`HTTP(S)_PROXY`, `ALL_PROXY`) and sets the egress resolver; callers add only their own timeouts, pool and TLS-mode settings (#509). Clippy enforces this with `disallowed-methods` in `apps/gateway/clippy.toml`: `reqwest::Client::new`/`builder`, `reqwest::ClientBuilder::new`, `reqwest::get`, and every builder method that changes destination, proxy, redirect, retry, DNS or TLS trust (`redirect`, `retry`, `proxy`, `no_proxy`, `dns_resolver`, `dns_resolver2`, `resolve`, `resolve_to_addrs`, `connector_layer`, `unix_socket`, `windows_named_pipe`, the `danger_*` methods, `use_preconfigured_tls`, the `tls_built_in_*` switches, `add_root_certificate`, `hickory_dns`). Clippy matches by name resolution, so aliases, braced or renamed imports and re-exports such as `openidconnect::reqwest::Client` are caught. Only the egress client module (`egress_http.rs`, the private `egress::client` module) uses them, under `#[expect(clippy::disallowed_methods, reason = "the egress-guarded constructor (#509)")]`; `S3` trust anchors go through `egress::add_root_certificates`.

Clippy cannot name a `Default` impl for one type, so the `Default` routes are closed by type (#569). The builders return `egress::HttpClientBuilder` and its `build` returns `egress::HttpClient`; production code holds a client only as that type. Neither implements `Default` (a compile-time assertion in `egress_http.rs`), neither has a `Deref`, `AsRef` or `From` to or from a reqwest value, and the builder (crate-private) exposes only timeouts, the idle pool, HTTPS-only and `build`. So `HttpClient::default()`, `Default::default()`, `mem::take`, `unwrap_or_default()`, `or_default()` and `#[derive(Default)]` on a struct with a client field do not compile. `disallowed-types` refuses `reqwest::Client` and `reqwest::ClientBuilder` by name everywhere else in the non-test build: as a field, parameter, return or annotation type, in `reqwest::Client::default()` and in `<reqwest::ClientBuilder as Default>::default()`, through aliases and re-exports. `RequestBuilder::build_split` and `RequestBuilder::from_parts`, the reqwest methods that hand out or accept a raw client, are `disallowed-methods`. `egress_http.rs` is the one sanctioned site, under a file-level `#![expect(clippy::disallowed_types, …)]`.

Test code may build its own clients: `lib.rs` allows the lint for the test build, and integration tests under `tests/` opt out per file. `egress_source_scan_tests.rs` keeps the rule switched on. It parses every file under `src/` with `syn` and compares lint paths token by token (comments inside an attribute and raw identifiers such as `clippy::r#style` read as the plain form), including outer and inner attributes, `cfg_attr` nested to any depth and attributes inside macro bodies. An `allow`, `expect` or `warn` of `clippy::disallowed_methods` or `clippy::disallowed_types` (or their old names `disallowed_method`/`disallowed_type`), `clippy::style`, `clippy::all` or `warnings` is allowed only at the sanctioned sites, each on its own item: the file-level `expect` of `disallowed_types` in `egress_http.rs` and the `expect`s on its functions `client_builder`, `pinned_client_builder` and `add_root_certificates`, the `allow` on the `let` in `db.rs`'s `start`, the `expect` on `handshake_request` in `providers/openai/realtime.rs` (#511), and the test-build line at the crate root of `lib.rs` (both lints). The same attribute on a module, an `impl`, another function or a nested item is refused. `warn` is still an error under CI's `-D warnings` but is refused too. A `#[path]` that leaves `src/` or is not a string literal, any `include!`, any `use` that names `include` (a rename or re-export), and `include` anywhere in a macro body are refused, so no unscanned file is compiled as code. The scan fails closed on what it cannot read: an attribute built from a macro metavariable (`#[$m]`, `#[$l(..)]`, `#[path = $p]`), an attribute in a macro body that `syn` cannot parse, and a macro call whose name is a metavariable (`$i!`) are findings. Outside Rust sources it refuses a Cargo `lints` table in the root or gateway `Cargo.toml`, any `.cargo/config(.toml)` in the repository, a second `clippy.toml`/`.clippy.toml`, and, in `.github/`, `scripts/` and every `package.json` (CI and the local gates), `CLIPPY_CONF_DIR`, `rustflags` (which also catches `--config build.rustflags=…`), `cap-lints`, the lint names, and `-A`/`--allow`/`-W`/`--warn` of `warnings`, in any case and with `-` and `_` read alike. It also checks that `clippy.toml` still lists every reqwest entry with a reason naming its `crate::egress` alternative, including the two types and the two `RequestBuilder` methods.

Neither lint constrains `egress_http.rs` itself, so the scan holds that file to an exact list (`CLIENT_MODULE` in `egress_source_scan_tests.rs`), not to a set of bad shapes. The list has one entry per top-level item and per method of the two inherent impls, each compared as its full token text without doc comments: the file-level `expect`, the `use` lines, both structs with their derives and single private field, the no-`Default` proof (the trait, both blanket impls with the `T: Default` bound, and the `const _` assertion for the client and for the builder), every method with its attributes, visibility, signature and body (`get`, `post`, `delete`, `execute`, `request` and the `#[cfg(test)]` `from_test_client`; `timeout`, `connect_timeout`, `read_timeout`, `pool_max_idle_per_host`, `https_only`, `build`), and the three constructors with their bodies, so their builder chains (`no_proxy`, `dns_resolver` or `resolve_to_addrs`, `redirect(Policy::none())`, `retry(never())`) cannot gain a `proxy` or `danger_*` call. Anything else in the file (a type alias, static, constant, trait impl of any name, module, macro call, extern block, extra method, changed signature or body) fails, and so does a missing entry. Independently of the list, the file may not contain `Default` beyond the proof's one bound, any identifier containing `default`, `take`, `transmute`, `unsafe`, an item nested in a body, or a macro call. Planted variants of each kind are tests. A `#[path]` whose target is not a `*.rs` file is refused everywhere, because the scan reads only `*.rs` files. `egress_client_tests.rs` checks both constructors over real HTTP on loopback: no redirect is followed, ambient proxy variables are ignored (in a child process), a failed request is sent once, a refused address is never connected to, and an approved local endpoint reaches only its pinned address (an unpinned client cannot resolve it).

`local_address` and `interface` are not disallowed: they choose the source address or device, not the destination, and the egress policy is enforced on the destination address the resolver returns.

**Known limits.** Review must catch these:

- A raw reqwest client whose type is never written is not caught (#569 closed every named route): `disallowed-types` sees written types, not inferred ones. Gateway code no longer has a source of one (the `HttpClient` field is private and the reqwest methods that return or take a client are disallowed), so this needs a dependency that returns or accepts a `reqwest::Client`/`ClientBuilder` by value, used without naming the type (for example `dependency::takes_client(Default::default())`). No dependency API in use does.
- Test builds may name the raw types and wrap a test client with `HttpClient::from_test_client` (`#[cfg(test)]`); integration tests under `tests/` opt out per file.
- Code inside `egress_http.rs` is trusted: no lint constrains it. The allowlist test pins it, so a change there is a reviewed change to the list.
- Other workspace crates (`tools/mock-upstream`, `tools/loadgen`: not in the image, no `clippy.toml`), any new path-dependency crate, and `build.rs` are outside the rule.
- `hyper`'s own client is enabled through feature unification and is not covered; production code does not use it.
- Code that is not compiled in a Clippy run is not checked. CI runs Clippy twice: on every target with `--all-features`, and on the gateway library and binary with default features (#502). Test code built only without `integration-tests` is not linted.
- Code expanded from an external macro or a derive may not be linted.
- Clients built inside dependencies (the AWS SDK's credential providers, `openidconnect` internals) and non-reqwest transports (SMTP, syslog, raw sockets) are outside the rule.
- With the `http2` feature off in this build, reqwest's default retry policy has nothing to retry, so the retry test cannot tell `retry::never()` from the default today; it guards a future feature change.
- A lint level produced by a procedural macro is not seen by the source scan (macro_rules fragments fail closed).
- Configuration outside the repository is not checked: `~/.cargo/config.toml` or a parent directory's Cargo configuration, and `RUSTFLAGS`, `CLIPPY_CONF_DIR` or `--cap-lints` set in a developer's environment. CI's own workflow files are checked.
- `egress::add_root_certificates` accepts any certificate from any module; the caller chooses the trust anchors.
- Only `apps/gateway` has this `clippy.toml`; `tools/` crates are not covered.

### Property tests of untrusted-input parsers

Five parsers and encoders that read or build untrusted data are checked by `proptest` properties (#593), not by golden outputs. They replace the throwaway differential tests that proved the #499 splits behaviour-preserving and were then deleted. Each is a `*_property_tests.rs` child module next to its target, runs in the library suite (so CI's shards pick it up), writes no regression file to the source tree (`failure_persistence: None`; a failing case prints its shrunk input), and has an explicit case count. The shared generators (hostile JSON values, random JSON, events with real `type`s and field names, and the drop/duplicate/swap/truncate/retype/unknown-field and nested-unknown-field mutations of an event sequence) and the single-mutation sweep are in `proptest_support_tests.rs`. Failure seeds are not persisted, so a failing generated case must be pasted from the test output into a named regression test before it is fixed or ignored. The stream modules also run deterministic sweeps over one rich valid stream: an unknown non-empty field injected into every object node of every event, refused except at a pinned table of nodes that tolerate extras (stated from the code in each module), and every single mutation (each event and each node of each event replaced by each hostile value, each event dropped, duplicated and truncated at, each pair swapped) through the same invariants; they report how many mutated streams still reach `Done` (OpenAI Responses 10 066 swept, 1 780 reach `Done`; Anthropic 5 173 and 478 without, 6 653 and 544 with, the Messages mode), so the reconciliation checks and the independent usage read run. The Bedrock stream is built from the SDK's typed events, which cannot carry an unknown field, so the unknown-field sweep does not apply to it.

- **OpenRouter price mapper** (`governance/suggestion/mapping_property_tests.rs`). `microusd` equals an independent decimal-digit reference (no `u128`, no `pow`) on generated price strings: same amount, rounded up, same exactness, `None` exactly for what the grammar refuses (negative, `NaN`/`inf`, `+1`, hex, separators, fullwidth digits, a bare `.`, an exponent outside -40..=40, over 64 bytes) or an amount past `i64`/`u128`; it never rounds a nonzero price down to zero. `map` never panics for any catalog entry (including non-objects), workload or image body; is deterministic; every amount is a canonical non-negative integer micro-USD string in an allowed batch; a missing, unparseable, negative, over-range or non-string rate is a `null` amount with `needs_review` and an `unknown` draft line, never `0`; every `"0"` traces to an explicit zero rate (the only deliberate zero is a missing per-request fee); generation token rates equal the reference and are flagged when rounded up; image prices are the highest parsed per-image price per size and a truncated or non-JSON body prices nothing; the draft validates or says it did not; ceilings stay below the model's own limits. `map_with_endpoints` is checked against an oracle: the endpoint list in six wrappers (including ones holding no usable list and an empty `data` list that shadows a usable one), non-object elements and prices, several `status` values, and evidence built from the generated endpoints (an attempt whose cost is an endpoint's list cost for small token counts, off by -3 to +3 micro-USD) mixed with random attempts; the named provider must be the cheapest endpoint reported up, or the one the most attempts match within 2 micro-USD (the dearest of equals), with `matched_attempts` equal to the oracle's, and the draft passes the full output check against the model it was priced from. Every priced line of every workload equals the reference for its source rate (the audio meters' first exact batch of 60 000, 1 000, 3 600 000 ms, else rounded up at the largest; the request line; tiers) and every priced draft line is exactly its annotated line (meter, variant, threshold, batch, amount, labels). `microusd` is also checked at `i64::MAX` plus or minus two micro-USD for units 1, 1 000 and 10^6 and for zero units. It is total over every database-legal evidence cost and every catalog entry, including a `top_provider` that is not an object (#634, fixed; a named regression test asserts the resulting ceiling). One defect remains pinned by ignored tests: a prompt-size tier on a meter with an unusable base rate gets no explicit `unknown` base line (#635, in its strict form over any catalog entry as well as the single example).

- **Bedrock Converse request encoder** (`providers/bedrock/encode_property_tests.rs`). For a generated valid request (leading system messages, user and assistant turns with tool calls and their results in any order, tools, tool choice, temperature, token limit, `top_p`, stop sequences) `encode` accepts it, carries every system message, message, tool call (id, name, JSON arguments), tool result, tool (name, description, schema) and the tool choice whole and in order (the one documented merge: the tool results of one turn become one user message), has temperature, limits and options present exactly when set, and is deterministic. For a mangled request (messages dropped, duplicated, swapped, truncated; roles, content, ids and arguments changed; tools, choice and limits edited) it never panics, refuses only with `InvalidRequest`, `Unsupported` or `InvalidField`, and carries whole whatever it accepts. Each of 34 single faults (a strict tool, `tool_choice: none`, the developer role, error-marked results, a late or empty system message, an orphan, duplicate or missing tool result, a duplicate or invalid call id, bad arguments, an oversize body, too many messages or tools, a non-finite temperature, an image, `strict`, `top_k`, an output format, a denied beta header) is refused with its own class, not a catch-all. The limits (128 tools, 1024 messages, 128 calls in one message, the 4 MiB output limit) are inclusive and refuse the next unit instead of truncating; the output limit is checked to the byte over message text, tool-call arguments and each tool's name, description and schema; a tool name, call id and call name are identifiers of 1 to 64 letters, digits, `_` or `-` in all three places. Messages options other than `top_p` and `stop_sequences` (thinking, cache controls, context management, native tools, a system value, a task budget, history thinking, beta headers) are not forwarded to Bedrock (`providers/messages.rs` calls it deliberate for translated providers): the tests pin that omission as it is, adding them to a valid request changes nothing in the encoded input (#637 tracks whether they should be refused instead; change that property if it does).

- **OpenAI Responses stream parser** (`providers/openai_responses/stream_property_tests.rs`). For a generated valid stream (message, function-call and reasoning items with their parts, deltas and done events, with or without usage, completed or incomplete) `State::push`, driven the way `execute` drives it, reproduces exactly the text deltas, tool starts (ids, names, contiguous indices) and argument fragments the stream carried, then one `Finish`, one `Usage` equal to the reported counts (absent usage stays unknown, never `0`; cache and reasoning fields round-trip) and one `Done`. A stream cut anywhere before its terminal ends at end-of-frames (the `InvalidUpstream` of `framing::frames`), emits no `Finish`, `Usage` or `Done`, and what it emitted is a prefix of the full stream's events. For a stream mutated by dropping, duplicating, swapping and truncating events, wrong types, huge, negative and oversized values, unknown fields and event types, or for arbitrary JSON events, it never panics and the only error is `InvalidUpstream`. At most one terminal is emitted and nothing follows it for a driver that returns at the first `Done`, as `execute` does; that is true by construction of the driver loop, not a property of `State`, whose lack of a terminated flag is the ignored #636 test. `Done` comes only from a terminal frame whose snapshot equals the streamed text and tool calls, and the emitted usage equals the terminal frame's `usage` field by field, read independently (absent or null is unknown, never `0`). An unknown non-empty field in any object the parser guards with `fields(..)` (items, parts, a terminal's output items) is refused at any depth. A snapshot that fails reconciliation still reports its valid usage as evidence, exactly. Only directly reported usage fields are compared (input, output, cache read, cache write, reasoning, and total at least input); the derived ones belong to `metering`'s tests. 129 output items, 128 tool calls and 4 MiB of streamed bytes are accepted whole and the next unit is refused, not truncated. `State` has no terminated flag (the Anthropic parser does); a second terminal would re-emit, which `execute` never reaches. An ignored test pins that finding (#636).

- **Anthropic Messages stream parser** (`providers/anthropic/stream_property_tests.rs`). For a generated valid stream (text, tool-use and, in Messages mode, thinking blocks; pings anywhere; any stop reason; usage with cache counters present or absent) `State::push` reproduces exactly the text, tool starts and argument fragments (an empty tool input is delivered as `{}`), preserves every native `content_block_*` frame in Messages mode, and ends with one `Finish`, one `Usage` equal to the merged reported counts and one `Done`; the start event's output count is never used (absent output stays unknown, not `0`); a counter that goes down, or any count past `i64::MAX`, is refused before any `Finish`; nothing is accepted after `Done` (the parser has a `done` flag, so this is a property of `State`); the emitted usage equals the merge of `message_start.usage` and every `message_delta.usage` read independently from the frames. An unknown non-empty field in `message`, `content_block` or `delta` (and in Messages mode in the `content_block_*` frames) is refused. A reported cache-write total of 0 with no allocation detail reports each allocation as a known zero, which `metering::checked` documents and is right; an absent total or a positive total with no detail leaves them unknown (named test). A stream cut before `message_stop` emits no `Usage` or `Done`, and what it emitted is a prefix of the full stream. For mutated and arbitrary JSON streams it never panics, errors are `InvalidUpstream` (or, only for an upstream `error` frame on a Messages stream, `ContextLength`, `Overloaded` or `Busy`, with no upstream text reflected), at most one `Finish`/`Usage`/`Done` is emitted in order, `Done` only after a stop reason and `message_stop`, and no text, tool call or count the upstream did not send appears. 256 blocks, 128 tools and the response limit on tool arguments are accepted whole and the next unit is refused, not truncated.

- **Bedrock ConverseStream parser** (`providers/bedrock/stream_property_tests.rs`, a child of `stream.rs` for its private state). For a generated valid stream (text blocks started explicitly or by their first delta, tool blocks with id, name and JSON input, a stop reason that agrees with the tool calls, metadata with or without usage) `State::push` reproduces exactly the text and argument fragments with contiguous tool indices, then one `Finish`, one `Usage` equal to the reported counts (cache details round-trip; absent usage emits none, never zero) and `end()` accepts. Bedrock has no in-band `Done`: `decode` yields it only when `end()` accepts, which the tests model; a stream cut anywhere, including just before the metadata, is not accepted and emits a prefix of the full stream. For mutated and arbitrary streams it never panics, the only error is `InvalidUpstream`, one `Finish` and one `Usage` in order, nothing is accepted after the stop or twice, and nothing is invented; negative counts are refused; a tool block that closes without a JSON-object input (including an empty one) is refused; 256 blocks, 128 tools and the byte limit are accepted whole and the next unit is refused, with a refused push returning none of its events; the byte limit is exact at the boundary (accepted at the counted size, refused one byte below). Only directly reported usage fields are compared.

### AGENTS.md rules and their checks

Every rule in AGENTS.md's Invariants and Deployment lists is either enforced by a deterministic check, enforced in part (the gap is stated), or left to review (the reason and the review that covers it are stated). A correction to an agent becomes a check where one can be written (#591); text and keyword scans kept losing to code the compiler resolves (#509, #488), so the new source checks parse the production build with `syn`, and each has planted-violation tests proving it fails. The Rust checks share one module-tree reader (`source_rules/tree.rs`): it follows `mod x;` and `#[path]`, keeps every item whose `cfg` could be true in a production build (`cfg` is three-valued: only a definitely false predicate such as `test` or `all(test, ..)` drops an item, so `not(feature = "x")` and `not(debug_assertions)` stay), and fails closed (the test panics) on a `mod` it cannot find, `include!`, a `mod` declared inside a macro, and `cfg_attr(.., path = ..)` on a module. "Review" is the code review every change gets, and for security-relevant changes the two independent reviews AGENTS.md requires.

The shared rule reader refuses a file module declared inside a production block,
including one nested in a block-local inline module. Declare file modules at
module scope so the reader can resolve them. Inline modules with self-contained
bodies are supported inside blocks. An inner file cfg that is definitely false
excludes the file from the inventory. When checking for unreadable modules, the
loader skips definitely disabled local items, impl and trait members, enum
variants, and fields. Downstream rules can still see block-local syntax in a
retained file. Unknown predicates and expression-level conditions are conservative.

#### Governance lock SQL

The helper exemption is tied to the canonical `governance/locks.rs` source file and module. The check flags explicit renames of the SQLx namespace and its direct query imports, including imports prefixed by `self`, `super` or `crate`. The check follows the spelling of these paths: a local module named `sqlx` can also trigger the inspection diagnostic. Imports through named re-export modules require review because the syntax check does not resolve those modules. The governance gate also flags block-local file modules whose contents the shared reader would otherwise omit.

## Tests on the Spark platform (#653)

`scripts/spark-test.py` runs the Rust and web suites for a **pushed** commit as a job on the Spark test platform (AGENTS.md, "Running the test suites on the cluster"). It provides additional branch verification, extra concurrency and targeted reruns without queueing behind the local build slot; the commit must be pushed before the job can fetch it. By default it is an arm64 run on 1.8 CPUs: it finds failures early and proves the suites on a second architecture. For a branch that is already pushed, GitHub CI gives the full library result fastest (four parallel shards, about 7 to 13 minutes) and is the merge gate; a Spark run never replaces green CI.

```sh
python3 -I scripts/spark-test.py run <name> --ref <branch|commit|tag> --suite lib|integration|web|checks|all [--test-args "<filter>"] [--fresh] [--fast] [--summary PATH] [--log PATH] [--timeout MINUTES] [--keep] [--detach]
python3 -I scripts/spark-test.py status [name] | logs <name> [-f] | result <name> [--summary PATH] [--log PATH] | down <name> | purge
```

### Trust model

The job runs the ref's build scripts, proc-macros, npm commands and tests, with internet egress, in a pod whose cache volume persists between runs. Pods cannot reach the LAN, other tenants or the production cluster, and the pod holds no Kubernetes credentials, but a hostile ref could read the run's database password (a file in the pod), use the internet, and leave files in the slot's cache for the next ref. So: **only test refs you would run on your own machine**; dependency updates are tested only after their review (AGENTS.md, Supply chain); after any ref you would not run locally, `purge`. The cache is trusted only as far as the refs that ran in the slot (below), and `--fresh` starts with an empty `target/`.

### Results and exit status

`run` and `result` print `RESULT: <label>`, the `test result:` lines, the failing tests, the failed steps, notes, what was not covered, and one line of compact JSON (also written, mode 0600, to `--summary`, which is opened before the run starts). Test counts are parsed with anchored regular expressions. Test names are restricted to printable ASCII and 200 characters, with terminal escape sequences removed (CSI, OSC, DCS and the rest); setup failures and test output blocks are also sanitised and bounded before display. Marker lines (`::omg-test::<nonce>:: ...`) are accepted only when well formed and carrying the run's random nonce, which is not exported to child steps. This separates ordinary test output from progress markers; it is not authentication against hostile code running in the same pod, which can inspect the pod's initial environment. The exit status of cargo and npm is authoritative: output lines cannot turn a failing step into a pass.

| Label | Exit | Meaning |
| --- | --- | --- |
| `passed` | 0 | every suite of the run passed in full |
| `failed` | 1 | a test, a check or a step failed; or the run executed no tests; or a step of the suite did not run; or the library shards do not account for every test listed |
| `killed` | 2 | the platform stopped the pod: out of memory, deadline, eviction, deletion (`pod_reason` says which) |
| `setup failed` | 2 | the run could not start its tests (for example the commit is not pushed); the last lines of the log are shown |
| `passed (partial)` | 3 | `--test-args` narrowed the run; the summary has `partial: true` and the narrowing in `test_args`. Never a pass of the suite |
| (tool or platform error) | 2 | refused third run, quota, `Forbidden`, a bad `--summary` path, an unexpected error of the tool |
| `run --detach` | 4 | started; nothing is known about the outcome |

A run that did not fully pass saves its sanitised, redacted log to `--log PATH`, or without that option to `.local/spark-test/<name>-<sha12>.log` (0600; `.local/` is ignored), before the run is removed, and shows the failing tests' output blocks (bounded to 10 blocks of 40 lines), so a 40-minute failure needs no rerun to see why. Every summary lists what the suite does not cover (`not_covered`), from `deploy/spark/test-coverage.json`. Any other exit of `run` than a result (an error while waiting, an interrupt) prints ``run kept: `down <name>` `` and leaves the run; `down` of an unknown run is not an error.

### Design

- **Safety.** The Spark kubeconfig only (`SPARK_KUBECONFIG`, else `~/.kube/spark-k3s.yaml`), refused unless it names the Spark server; every `kubectl` gets `--kubeconfig` explicitly and a scrubbed environment (the helpers of `scripts/spark-env.py`, which the tool loads). It touches only `<base>-omg-test-s1` and `<base>-omg-test-s2`, and only when they carry `app.kubernetes.io/managed-by=omg-spark-test`, which the tool sets when it creates them: an existing namespace of that name without the label is refused for use, `down` and `purge`; one being deleted gives a retry message. The namespaces are created one at a time with the two network policies awaited. `spark-env.py` reserves names beginning `test-` and never lists or touches these namespaces; this tool never touches `<base>-omg-<name>` environments. A `Forbidden` or a quota refusal is a boundary, not something to work around. Creation retries the documented `QuantityLedger ... is not initialized` condition after a namespace delete; waiting also tolerates transient kubectl errors as described below.
- **Toolchain.** No custom image (publishing one needs a workflow with a write token, which this change does not add). The test container is the Dockerfile's build image, `mirror.gcr.io/library/rust:1.100.0-bookworm@sha256:ade39a71...`, the multi-arch index (linux/arm64 and amd64) pinned by digest, which already carries git, a C toolchain, pkg-config and Python 3.11. Node comes from the Dockerfile's Node image (`node:22.23.4-bookworm-slim@sha256:5ec23b7c...`): an init container copies its `node` and `npm` into a volume, so there is no download. `rustup` adds `rustfmt` and `clippy` for the exact channel `rust-toolchain.toml` names (rustup verifies its downloads against the channel manifest, as `dtolnay/rust-toolchain` does in CI), Cargo downloads crates checked against `Cargo.lock` checksums and npm packages against `package-lock.json` integrity hashes. `npm ci` runs with `--ignore-scripts`: CI runs it plain, but the only package of `package-lock.json` with an install script is the macOS-only `fsevents`, and the web, integration and library suites pass with the flag (measured). The script downloads and installs nothing else (no `curl`, `apt`, `pip`, `cargo install`, no piped installer); `tests/supply-chain/spark-test-manifests.test.mjs` fails if an image is not pinned by digest or differs from the Dockerfile's, if the pod is not locked down (non-root, no capabilities, read-only root file system, seccomp `RuntimeDefault`, no service account token, no ports, no host access, no secret in the environment), or if the script gains a download.
- **Fidelity to CI.** `deploy/spark/test-coverage.json` lists the run commands of CI's `gateway-lint`, `gateway-tests`, `gateway-special` and `web` jobs as covered (and then present in `deploy/spark/test-run.sh`) or as not covered with the reason; `tests/supply-chain/spark-test-coverage.test.mjs` compares the list with `ci.yml`, so a step added to CI fails the test until the list and the script follow. The library is split exactly as CI splits it (sorted names in C order, element i to shard i modulo 4).
- **Source.** The job runs `git fetch --depth 1` of `https://github.com/bitop-dev/open-model-gateway.git` at the exact commit the ref resolves to locally (no credentials), makes the index that commit and rewrites only the files whose content differs (so files that did not change keep their mtime and Cargo does not recompile them), runs `git clean -ffdx`, and fails unless `git rev-parse HEAD` equals the commit and the tree is clean; the tool compares the commit the job reports with the one it asked for. A commit that is not pushed cannot be fetched and fails in the first seconds as `setup failed: cannot fetch ...: push the branch first`. Pods reach the public internet (GitHub, crates.io, static.rust-lang.org, the npm registry, mirror.gcr.io, ghcr.io) but not the LAN, which is all this relies on.
- **Cache.** Two slots, each a namespace holding one 20 GiB `local-path` volume `omg-test-cache` (cargo registry and git, target directory, rustup home, npm cache, the source checkout). A pod can only mount a volume of its own namespace, so the cache cannot live in a separate namespace and `down` cannot delete the namespace: `down` removes the run (job, database, secrets, lease) and keeps the slot and its cache; `purge` deletes idle slots and with them the volumes. A slot is reserved by atomically creating the fixed-name `omg-test` Job **suspended**. Its UID, namespace UID and nonce identify the generation; setup returns that handle to waiting, result collection and auto-down instead of finding the name again. The Job is also the launch fence: an API-server JSON Patch tests its UID and setup phase while unsuspending it. Two processes starting the same name at once still give way by lease order; losing admission removes only its own generation. Secrets, script ConfigMap and database names include the nonce and carry the Job owner UID. Setup only creates the shared cache PVC; it never applies or patches an existing cache.
- **Fenced cleanup and recovery.** `down` atomically changes the expected Job to `cleaning` and suspends it before requesting foreground deletion. A cleanup finalizer retains the slot reservation while that generation's pods, database, volumes and configuration disappear. All object DELETE requests carry Kubernetes UID preconditions; finalizer release tests the Job UID, cleaning phase and resource version. Concurrent/stale manual down, auto-down, failed setup, duplicate admission and timeout cleanup cannot remove a replacement reservation. Interrupted or timed-out cleanup retains a visible `cleaning` Job: retry `down <name>` with this version; there is no expiring client lock to steal. A setup request already in flight may still create a uniquely named resource with the extinct Job owner UID, but it cannot activate a Job, alter the replacement's resources, or overwrite the cache; Kubernetes garbage collection removes such orphans.
- **Atomic purge.** Purge creates a suspended `purging` Job in the same reservation name before deleting an idle namespace; admission and purge cannot both reserve the slot. This sentinel has no cleanup finalizer and stays until namespace deletion. An interrupted purge is resumed by `purge`, and the namespace DELETE is conditional on its original UID. If a delayed sentinel CREATE lands in a new namespace incarnation, purge removes only that obsolete sentinel by UID and asks for a retry, leaving the replacement namespace intact.
- **Runner upgrade.** Do not run old and fenced clients concurrently: old clients do not honor the Job reservation. Stop prior clients and finish/down active pre-upgrade runs using the prior script **before** starting the upgraded runner. The upgraded runner refuses a legacy lease ConfigMap or unannotated Job rather than adopting/deleting it. Idle labelled slots and their existing caches can be reused directly (or purged); no schema conversion or cache reset is needed. `setup`, `cleaning` and `purging` are visible in status; recover abandoned setup with `down`, cleanup with `down`, and purge with `purge`.
- **What a run resets.** At the start of every run everything cargo, rustup, git and npm do not verify against a lockfile or a hash is reset: `rustup` is copied again from the image, `CARGO_HOME`'s configuration, credentials, `bin`, unpacked sources (`registry/src`), registry index and git checkouts are removed, the home directory is emptied (npm and git configuration), `/cache/.cargo` is removed, and the source checkout's `.git` is recreated (a fresh `git init` and fetch of the exact commit: no hook, configuration or lock survives), with untracked and ignored files cleaned. Kept: `registry/cache` and `git/db` (Cargo checks crates against `Cargo.lock`), the npm cache (npm checks integrity values) and **`target/`, which cannot be verified**: it is kept for speed unless `--fresh`. So a ref's build scripts can leave artifacts that a later ref's build reuses: the cache is trusted only as far as the refs that ran in the slot, and `purge` after one you would not run locally. The reset costs about 4 seconds (below).
- **Disk.** The local-path volume does not enforce its size. At the start and end of a run the script measures the cache and prunes: the npm cache over 3 GiB, the crate cache over 4 GiB and git databases over 2 GiB are removed, the target directory over 12 GiB loses its incremental data and then everything, and a cache over 17 GiB loses its target directory; a marker records the sizes (`cache` in the summary). Measured after all suites: 3.0 to 5.6 GiB in total (below). An idle slot costs the shared quota one namespace (of 10), one volume (of 12) and 20 GiB (of 100): 40 GiB for two slots, standing until `purge`.
- **Database.** A CloudNativePG `Cluster` per run (`ghcr.io/cloudnative-pg/postgresql:17.6`, the digest of `deploy/spark/values.yaml`, `local-path`, one instance, 8 GiB, defaults as CI's service container: `max_connections` 100), database `gateway`, superuser `postgres` with a password generated per run into a Secret over stdin and mounted as a file `/secrets/password`: the pod has no password environment entry. `with_db` and `with_loopback_db` inject a credential-bearing `DATABASE_URL` into database commands and their child processes; the redaction filter also reads the file to remove its value from logs. Standalone dependency installation, build and source/toolchain setup steps receive no `DATABASE_URL`. This does not isolate the file from other code in the pod: only run trusted refs, as described above. The tests create and drop databases and roles, as CI's superuser `gateway`. After the database is ready a marker records `version`, `lc_collate` and `max_connections` (in the summary as `database`). All output passes a filter that redacts the password and any `postgres://user:password@`; the load generator's end-to-end tests and datetime crate's PostgreSQL tests insist on a loopback host, so that one step reaches the database through the pod-local relay `deploy/spark/pg-forward.mjs`, as the demo does.
- **Resources, concurrency and `--fast`.** Test pod: requests 1.5 CPU / 6 GiB, limits 1.8 CPU / 10 GiB; database: requests 250m / 512 MiB, limits 1 CPU / 1 GiB. One run therefore adds 1.75 CPU and 6.5 GiB to the requests (2.8 CPU and 11 GiB to the limits) of the shared quota (4 CPU and 16 GiB requested, 8 CPU and 24 GiB limits, 12 volumes, 100 GiB), so **two runs fit next to one demo environment** (the arithmetic is a test). The tool refuses a third run and checks the quota's remaining room (from the base namespace's `ResourceQuota`, the smallest when several define a key) before creating run workloads; an idle slot namespace may already have been created. `--fast` raises only the CPU limit, never the request, by all the free limits quota beyond one normal run (up to 6 CPU), with cargo jobs, libtest threads and Vitest workers following it; it is refused when less than 500m extra is free. Vitest sizes its workers from `os.availableParallelism()`, which rounds the 1.8 CPU limit down to 1 (measured), so `--maxWorkers` is explicit: 1 at 1.8 CPU. The runner invokes the workspace test script directly (`npm run test --workspace @omg/web -- ...`), because the root nested npm wrapper consumes option flags before they reach Vitest; an executable real-npm regression checks the received arguments. Bulk workspace test compilation for integration discovery always uses `--jobs 1`, including with `--fast`, to avoid overlapping large compiler/linker processes within the 10 GiB pod limit; other Cargo commands retain the slot job count. Default deadlines: web 30, checks 45, integration 60, lib 120, all 180 minutes (`--timeout`).
- **Waiting.** `run` polls every 20 s, fails with the reason and the Warning events when the pod cannot start for ten minutes (`ImagePullBackOff`, `Unschedulable`, `CreateContainerConfigError`, an unbound volume), when the job vanishes, or when the slot's lease no longer belongs to this name, commit and nonce; it tolerates three consecutive kubectl errors. The script traps `SIGTERM` (bash is PID 1) so `down` and the deadline stop it at once.
- **Shards.** The gateway library is one test binary (2,491 tests at the measured commit) whose memory grows to more than 10 GiB in one process (OOM-killed after 1,789 tests), so `lib` runs four processes one after another, split as CI's shards are (`.github/scripts/rust-shards.mjs`), and the run fails unless the passed, failed and ignored counts of each shard equal the tests selected and the shards together account for every test listed. Parallel pods would not help: each needs its own target directory and the quota's CPU is the limit.
- **Suites.** `lib`: `cargo test -p open-model-gateway --all-features --lib`. `integration`: every gateway test target except `filestore_s3` and `runtime_privileges` plus the gateway binary's tests (an empty selection is an error), each reconciled against CI's Cargo artifact discovery and complete/ignored libtest inventories; missing executables or mismatched execution counts fail, while legitimate zero-test targets must report zero; `runtime_privileges` ordinary and `--ignored --test-threads=1`; the two ignored library probes CI runs after it (key issuance contention, Anthropic terminal fidelity); the non-gateway workspace tests (including the datetime crate's PostgreSQL tests and all non-gateway doctests); the gateway's doctests. `web`: `npm ci`, `npm run typecheck:web`, `npm run test:web`. `checks`: `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo clippy -p open-model-gateway --bins --lib --locked -- -D warnings`. The workspace step sets both `DATABASE_URL` and `DATETIME_PG_URL` to the run's disposable database through the pod-local loopback relay; the datetime credential is scoped to that command. `all` runs web, checks, lib and integration in one pod. A suite that must run tests (`lib`, `integration`, `web`) and executes none is `failed`. `--test-args` passes extra libtest arguments (`lib`) or Vitest arguments (`web`) restricted to letters, digits and `_ : . , = / @ -`, never one that would not run tests (`--list`, `--help`, `--format`, `--shuffle`, `--watch`, `-u`, ...); a narrowed run is partial. A failed Vitest file is not retried automatically; rerun it alone with `--test-args <file>`.

## Release candidate: Spark environment and journeys (#592)

Before tagging a minor or patch release, run the candidate on the Spark test platform (never the production cluster) and run the journey suite against it. The suite signs in as the five demo personas through the real OIDC flow and exercises sign-in and sign-out, `/me`, workspaces, keys (create, rotate, disable, revoke, and that a revoked key stops authenticating), inference authentication and the documented refusals per protocol, members and invitations, platform administration, the auditor's read-only boundary, access requests and reviews, reports and usage, health and the SPA fallback, each with its refusal cases. [Journeys](journeys.md) has the feature map (every flow with the journey and checks that cover it, or why it is not covered), the guarantees and what each journey leaves behind.

1. `python3 -I scripts/spark-env.py up rc --ref <tag or candidate commit>`
2. `python3 -I scripts/spark-env.py forward rc &`, recording `$!` and its `kubectl` child (`pgrep -P`) so both can be stopped; wait for `/health/ready` on `http://127.0.0.1:3000`. The suite needs Python 3.12 or newer and runs against one environment at a time.
3. `mkdir -p .local/journeys && python3 -I scripts/journeys run --base http://127.0.0.1:3000 --label <tag> --summary .local/journeys/summary.json`. Run it twice in a row on the same environment (re-runnability: the access-request allowance per person is about fifty runs a day, see [journeys](journeys.md#what-the-suite-promises)), and once with `--shuffle` (the seed is printed and recorded) or `--only <a> <b>`. Exit code 0 is the bar: any failed check, or a journey that errored, blocks the release until understood. A failure caused by the gateway is kept as a failing check and filed as an issue; do not weaken the journey. The suite refuses a non-loopback base and any gateway whose sign-in is not the passwordless demo issuer.
4. Attach `summary.json` to the release PR. It holds only the label, time, run id, journey order and seed, and per journey the check names, expected and actual HTTP statuses and timings, never a body, cookie, key or token.
5. Stop the forward (the recorded process and its child; confirm nothing listens on 3000 and 18084), then `python3 -I scripts/spark-env.py down rc` and confirm `status` lists no environment.

The demo has no model server or provider, so no generation completes here: a candidate that changes inference behaviour also needs the provider-backed checks the release process already requires. The suite is not a substitute for `npm run test:browser`, which covers the UI.
