# Alerts

Alerts tell people when budgets fill up, spend jumps, requests fail or a connection keeps failing. They notify; they never block a request. Admission enforces budgets on its own. Schema: `enterprise_migrations/0011_alerts.sql`. API: [management API](management-api.md#alerts).

## Where

- **Admin › Settings › Alerts** (`/admin/settings/alerts`): installation-wide rules (Rules tab) and their incidents (History tab). Platform Admins edit; Auditors read. Rules open on their own page (`/admin/alerts/{id}`, `/admin/alerts/new`) with Cancel and Save in the header.
- **Workspace › Settings › Alerts**: Team/Project rules, for that workspace's admins (actual membership). Platform readers may read them through the API; members don't see the tab.
- **Personal workspaces** have built-in budget alerts for their owner only (80% and 100%). Nothing is configurable and nobody else sees them, Platform Admins included.
- **SCIM safeguard:** a built-in installation alert, "SCIM tried to remove the last Platform Admin", fires when SCIM is refused for that reason ([SCIM](scim.md#the-last-platform-admin-is-protected)). It appears in Admin › Settings › Alerts › History and in Notifications for Platform Admins and Auditors, is emailed to Platform Admins, and clears once a second active Platform Admin exists. At most one is open at a time.
- **Authorized key-expiry reminders** (see the dedicated section below).
- **Notifications** (`/notifications`, the bell in the top bar with the unread count): each person's alerts, with per-user read state.

## Rule kinds

All money is exact integer micro-USD. Spend is never estimated from floats, and unknown cost is never counted as zero.

| Kind | Fires when | Scopes |
|---|---|---|
| `budget_threshold` | Spend in a budget's current window reaches one of up to five percentages (default 50/80/100) of an applicable stacked budget. Layers: `type` (type default, only while no platform override exists), `override`, `local` (workspace) and `key` (each key lineage with an active key). There is no `installation` layer (installation-wide limits were removed; `400 reason:"installation_limits_removed"`). | Installation (Team/Project workspaces, never personal ones); workspace |
| `spend_threshold` | **Installation spend.** Installation-wide spend in the current UTC window of `spend_period` (`day`, `week`, `month` or `lifetime`) reaches one of up to five percentages of `spend_amount_microusd`, a reference amount you choose. It is a notification only: nothing is ever denied (there is no installation budget). Spend is the sum over every workspace, personal ones included, as totals. | Installation only |
| `spend_spike` | Settled spend admitted in the last hour ≥ factor × the trailing 7-day hourly average (the 168 hours before the last hour), and ≥ a minimum amount. The factor is an integer percent (`300` = 3×, 110–100000). | Installation (all workspaces, as totals); workspace |
| `error_rate` | Attempts started in the window (5–1440 min): `failed / finished ≥ rate%`, with at least `min_requests` finished. | Installation; workspace |
| `provider_failing` | For each enabled connection (or one chosen connection): the last N relevant attempts in the window all failed upstream, or the upstream error rate over the window crosses its threshold with enough volume. Upstream failures are `upstream_unavailable`, `timeout_error`, `invalid_upstream_response` and `provider_configuration_error`. Successes count; request-specific rejections and cancellations neither count nor reset. | Installation only |
| `batch_failed` | One incident per batch that ended `failed` or `expired` in the last 24 hours (summary names a budget stop or expiry; details carry the batch id, mode and counts). It resolves 24 hours after the batch ended. See [batches](batches.md#monitoring). | Installation (Team/Project batches, never personal ones); workspace |
| `admission_ceiling` | **One workspace or key near its admission ceiling** (scoped admission serializes one workspace's, and one key's, admissions on that scope's totals rows, so a single scope tops out at a few hundred requests/s however many replicas run; see [operations](operations.md#per-scope-admission-ceiling)). Per workspace and per key lineage over the last `window_minutes` (5–10) complete UTC minutes: admissions stayed at or above `ceiling_requests_per_second` in **every** minute, or at least 100 admissions were made and 5 % or more of them waited at least `ceiling_lock_wait_ms` (10, 25, 50, 100, 250, 500, 1000 or 2500) for their scope locks, that is a lock-wait p95 at or above the threshold. Set either threshold or both. One incident per scope; it resolves when the condition clears. Admissions are the interactive ones the minute rate counters count (async jobs excluded); waits come from each replica's counts, flushed every 5 s (`admission_lock_waits`, kept an hour), so the last minute can miss a few seconds. | Installation only |
| `batch_stalled` | One incident per unfinished batch whose last progress (a finished line, or new provider counts) is older than `window_minutes` (5–1440). It resolves on progress or when the batch ends. A gateway-run batch legitimately waiting for its routes (time window, live traffic, server load, concurrency, its turn) is not stalled; the clock starts when the wait ends ([scheduling](batches.md#scheduling-on-self-hosted-models)). Unreadable server metrics do not count as a wait. | Installation (Team/Project batches); workspace |

## Authorized key-expiry reminders (#100)

Built in (migration 0049), fixed thresholds, never a configurable rule: "An API key expires within 7 days" and "...within 1 day" for every active, authorized API key with an expiry.

**Recipients follow the key, never a rule or a platform role:**

| Key | Recipients |
|---|---|
| Personal workspace | The owner only, never another Platform Admin or Auditor. |
| Shared human key (a Team/Project member's own key) | The holder plus that workspace's current owners and admins. Only the holder can rotate their own credential; admins can inspect or revoke it. |
| Service-account key (no human owner; never in a personal workspace) | That workspace's current owners and admins only. Creating the service account grants its creator no lasting recipient entitlement. |

Every recipient needs live platform entitlement; a shared recipient also needs effective workspace membership right now. Revoked, disabled, expired and expiry-less keys, disabled workspaces and disabled service accounts are excluded entirely (not just from recipients), as are human keys whose holder lost workspace membership. A reminder goes through the same [recipient outbox](#recipient-outbox-46) as every other alert kind, keyed by the same `(delivery, recipient fingerprint)` idempotency: eligibility is rechecked, by the same live predicate, in the outbox's own short claim transaction immediately before leasing a recipient and strictly before any SMTP I/O (never a locked, held-open transaction spanning the handoff). A removal committed before that claim prevents the email; a removal committed after a recipient is already claimed and sending may still let that one send (the outbox's general, documented race). There is no listed-address or platform-role-only fallback.

**Schedule and permanent deduplication.** Two bands, using database time: `1 day < expires_at − now ≤ 7 days` and `0 < expires_at − now ≤ 1 day`. `(credential id, expiry, threshold)` is permanently deduplicated, including resolved history: at most one incident is recorded per credential/expiry/threshold combination, ever. This does not guarantee at-most-once email: a crash after relay acceptance but before the delivery transaction commits can cause another SMTP handoff. The first evaluation that sees a key already inside one day emits only the urgent reminder, never a missed 7-day one too. Rotation issues a new credential id, so starts a new cycle; a different expiry starts another cycle; restoring an identical expiry does not replay it; re-enabling a key never creates another incident for an already-recorded tuple. The 1-day reminder silently supersedes an open 7-day one (no "resolved" email, ever, for this kind); a key that becomes ineligible resolves its open reminder the same way, also silently. Each workspace is capped at 100 new `key_expiring` incidents in any rolling 24 hours, using database time and counting even resolved incidents by workspace and firing time. Excess candidates are not recorded or permanently deduplicated: they remain eligible later (a skipped 7-day reminder may be followed by a 1-day reminder). A warning logs the workspace id and counts, never key names. Each tick creates at most 500 new reminders globally and silently resolves at most 500 obsolete ones, in short transactions, inside the same bounded evaluation loop and fence as every other alert. Workspace allowances are applied before the global cap, preserving expiry ordering without letting a capped workspace's backlog block other workspaces.

**Visibility and privacy.** Notifications and the bell show reminders only to their live recipients. Workspace history remains admin/reader-only: members receive `403` there and see their own reminders through Notifications/the bell instead. Owners/admins and permitted readers see reminders in workspace history only when the same live recipient predicate allows them; platform-reader authority alone does not qualify. Platform Admins/Auditors never see another owner's personal-workspace reminders, and these reminders never appear in platform history. Loss of membership, entitlement or key eligibility removes access immediately, including read-marking and history; an old read mark grants no authority. Resolved incidents remain stored for deduplication, even when no longer visible. No key names, ids, prefixes, hashes or holder identities anywhere this reminder appears: events, email or logs. The email links to Notifications; the UI offers **Open keys**, linking to the workspace's keys list, never a key identifier.

**Rolling-upgrade safety.** A `key_expiring` incident carries neither `rule_id` nor `builtin` (every other kind always carries exactly one); that is deliberate. The released gateway's feed, summary and read-marking predicate, its platform/workspace history predicates and the outbox's other recipient-resolution branches key off those two columns. An old replica therefore cannot display or email these events to anyone. Explicit `kind=key_expiring` history filters on that binary are rejected as unknown. An old email worker (pre-outbox) can still consume a pending delivery, recording `no_recipients` (or `not_configured` without SMTP); best-effort email may be lost during overlap; completed deliveries are not replayed after upgrade. See 0049's migration header, the PostgreSQL upgrade-oracle regression and `apps/gateway/src/alerts.rs`/`apps/gateway/src/alerts/outbox.rs` for the mechanism.

Budget and installation spend is settled actual cost plus in-flight pending holds, as admission counts them. Reservations in state `unknown`, and pending holds with no bounded amount, are not added to spend: they are reported as `unknown_cost_requests`, and the UI says the spend may be higher. Spend spikes use settled cost only and flag unknown cost the same way. Zero (deny-all) budgets never alert.

A budget or installation spend alert fires at the highest threshold reached. When spend later reaches a higher one, the open incident is marked `superseded` and a new one fires (one email). When the window rolls over, the budget (or reference amount) is raised or the key is revoked, the incident resolves (`cleared`).

## Evaluation

`serve` runs a background evaluator every `GATEWAY_ALERT_INTERVAL_SECONDS` (default `60`; `0` disables it; at most `86400`; anything else fails startup). One-shot: `open-model-gateway alerts evaluate --once` evaluates every rule, sends pending email and prints counts.

- **Idempotent.** At most one open incident per rule (or built-in alert) and subject, enforced by a partial unique index. Repeated evaluation never fires twice; an incident resolves once (a trigger refuses re-resolution, edits and deletion).
- **Bounded.** One replica evaluates at a time: a short claim transaction takes a transaction advisory lock with `try` (others skip that tick), then each rule is evaluated and reconciled in its own short transaction that waits for the same lock, so no snapshot spans the whole pass and vacuum is not held back. Statements time out after 10 seconds. A failing rule neither resolves its incidents nor affects other rules. At most 2000 rules and 5000 budget conditions per rule are considered.
- **Budget rules read maintained totals** (`budget_totals`, migrations 0015/0025), so their cost does not grow with history, including `lifetime` windows. Installation spend rules sum the workspace rows of one window (one indexed range per rule; no installation-scope row exists since 0026). Spend is settled cost plus pending holds; unknown-cost requests are counted separately, exactly as the former scans reported. Spike and error-rate rules still read their own (bounded) windows.
- **Admission ceiling rules read** the minute rate counters (`rate_minute_counters`, the window's rows; a few hundred thousand at most) and the flushed lock waits; at most 100 scopes per evaluation, busiest first.
- **No admission impact.** The evaluator reads with the runtime role and never takes the installation lock.
- Turning a rule off, deleting it (soft delete; its history stays) or disabling its workspace closes its open incidents as `rule_disabled`, without email.
- **Key-expiry reminders** run once per tick (not per rule: there is no rule), in their own fenced, bounded transaction, immediately after the rule loop.

## Delivery

- **In-app.** Visibility follows live authority, not a stored recipient list: installation incidents for Platform Admins and Auditors; workspace incidents for that workspace's current owners and admins (and for platform readers when the rule notifies Platform Admins); built-in incidents for the personal owner. Losing a role removes the incidents from that person's feed. The feed covers the last 90 days.
- **Email** through the [Admin › Settings › Email](settings.md#email) relay when one is set up, when an incident fires and when it clears: to the rule's recipients (workspace admins, Platform Admins and up to 10 validated addresses) or, for built-in budget alerts, the owner (the SCIM safeguard goes to Platform Admins). Disabled users get nothing. Messages contain the summary, a scope label (Installation, the Team/Project or connection name, "Your personal workspace"), the rule name and time, and a link to Notifications when `GATEWAY_PUBLIC_URL` is set.
### Recipient outbox (#46)

- Outcomes retain the existing transition statuses: `pending`, `sent`, `partial`, `failed`, `not_configured`, `no_recipients`, and sanitized error categories. Additive incident metadata reports total recipient `attempt_count`, `retrying`, `waiting`, `next_attempt_at` and `exhausted` counts. No recipient identifiers appear in the API. The incident History table shows Waiting, Retrying or Exhausted and the next due time/count. A host-policy refusal is terminal and retains the public `connection` category; SMTP 4xx/5xx both retain `rejected`, distinguished by retry scheduling. Unsupported client/relay capabilities (such as missing required STARTTLS or compatible AUTH) and malformed SMTP replies also use terminal `rejected`, never a connection retry.
- A durable per-recipient outbox snapshots the initially eligible addresses **once**, as delivery-scoped SHA-256 fingerprints, not stored addresses. The normalized address and optional internal-user link are captured atomically by the eligibility query; the immutable link keeps disablement effective even if account cleanup or an email change erases the old address before the snapshot is persisted. Before each claim it intersects that snapshot with live rule/recipient eligibility; newly added recipients are not included. Successful recipients are recorded immediately and never deliberately resent when another recipient fails. Revoked workspace admins and disabled/unentitled internal users lose future eligibility, including when a disabled internal user's address was explicitly listed. Explicit external addresses remain admin-chosen. Personal built-in alerts remain owner-only. A send already authorized and claimed may finish while authority changes.
- **Key-expiry reminders (#100) use this same outbox,** with the same `(delivery, recipient fingerprint)` idempotency: a reminder's recipients (the key's own live-authority recipients, never a rule) are snapshotted once and rechecked live on every claim exactly like any other alert kind. A reminder that becomes obsolete before its claim is leased (key revoked/disabled/expired, workspace disabled, holder lost membership, band changed, incident resolved) is excluded by that recheck and is never sent; it is recorded in the snapshot (so `recipients` still counts it) but never counted `sent` or `failed`. There is no separate authority-locking mechanism for this kind: the outbox's existing before-the-claim recheck, not a lock held across the SMTP handoff, is what makes an obsolete reminder unsendable.
- Each replica commits a short `SKIP LOCKED` claim **before SMTP**, recording the attempt and a 90-second lease with owner and unique token. No database connection, installation lock or admission lock spans mail I/O. Whole sends have a 40-second ceiling (and cannot extend beyond their lease); stale completions cannot overwrite a successor. Each invocation/tick processes at most 25 recipient attempts. Due times and expiry use the database clock.
- **Fair dispatch (#253):** each workspace has a delivery bucket; installation-scope events share the nil-UUID bucket. Within each tick the worker gives the next slot to a due bucket with the fewest slots served, breaking ties by least recently served across ticks (never-served first), then its oldest due delivery and bucket id. Initialization-only, revoked-recipient and missing-SMTP steps also consume a slot. A lone bucket can use all 25 slots; a busy workspace cannot monopolize the tick while quieter buckets are due. Selection first walks distinct buckets on the partial pending index without locks, then tries up to 32 candidates with `SKIP LOCKED`. Fairness across replicas is approximate; recipient leases and live authorization are unchanged. The evaluator process remembers at most 4,096 buckets' last-served instants, evicting the oldest when full. This in-memory history may reset on restart or lease failover; multi-replica fairness remains approximate. Each claim captures one database timestamp for its due checks and indexed creation-time range, skipping expired rows even before cleanup catches up. A claim statement timeout ends dispatch for this tick with a warning (other errors still follow the outbox failure path); bounded cleanup runs before claims. The 60-second evaluator send budget and 24-hour delivery cutoff still apply; fair scheduling does not guarantee delivery before expiry.
- Connection/timeouts and explicit non-authentication SMTP 4xx failures retry after **1 minute, 5 minutes, 30 minutes, 2 hours**. At most **five attempts per recipient within 24 hours of delivery creation**; a retry that would fall beyond that window exhausts immediately. Credentials, invalid addresses, host/egress policy, authentication (including 454), TLS configuration and SMTP 5xx are terminal. Missing/disabled SMTP records `not_configured`, never a retry loop. This retries email only, never inference or user HTTP requests.
- SMTP success requires the relay's positive completion response to DATA. The connection then closes without waiting for QUIT; a hanging cleanup cannot turn accepted mail into a scheduled retry. EOF or an incomplete response before acceptance is never recorded as success and may duplicate a message the relay already accepted (it is retried as a Connection failure, bounded by 5 attempts/24h). Message stages have 10-second deadlines within the SMTP send ceiling; no address failover occurs after a message attempt starts.
- **SMTP is not exactly once.** A crash after relay acceptance but before fenced completion can cause a duplicate after lease expiry. Durable queue identity and fencing prevent concurrent ownership and stale database writes; they cannot make an external relay transaction atomic with PostgreSQL. Transient retry/recovery is at-least-once with possible crash duplicates, bounded by the attempt/window limits (not guaranteed eventual delivery).
- The existing 24-hour interrupted cleanup exhausts unfinished recipients/leases without rewriting successes; a partially successful delivery becomes `partial`. Legacy uninitialized pending deliveries older than 24 hours remain `failed`/`interrupted`. Email failures never stop incident evaluation.

### Upgrade

Apply explicit migration `0050_alert_recipient_outbox.sql` (after 0049's key-expiry reminders), then reapply/verify runtime grants. `serve` never migrates. **Historical terminal deliveries are not replayed**; only pending deliveries initialize an outbox. Stop every older delivery worker before applying the migration (scale to zero, or set `GATEWAY_ALERT_INTERVAL_SECONDS=0`; unset means enabled): old workers don't understand the recipient queue. The guard refuses an old worker's finalize while recipients are queued (SQLSTATE 55006), but an old worker sends before that write and retries every interval, so one left running re-sends the delivery's mail. No operator action should reset a terminal delivery to pending; guards refuse reopening terminal deliveries or recipient outcomes.

## Saved platform webhooks (#45, slice 1)

Migration **0057** adds saved destinations and a separate retained outbox. Slice 2 adds signed HTTP delivery, test-send and delivery-status reads; the Webhooks UI follows in slice 3. Enabling a destination queues future eligible transitions only, with no historical backfill.

Platform Admins manage up to ten nondeleted destinations through the [management API](management-api.md#saved-alert-webhooks). Auditors and `platform:read`-only tokens read redacted status without URLs or secret references. Configuration details require a browser-session Platform Admin or an admin token also holding `settings:write`. Destinations start disabled; live URLs are immutable (create another destination to change receivers). Final soft deletion scrubs the URL and signing references while retaining the destination identity and history. Disable and delete make committed `waiting` rows terminal `ineligible`. Re-enabling does the same for every `waiting` row of an older enable generation (see below); a label edit changes nothing. A terminal row never reopens, so re-enabling does not replay. An already-authorized leased send may finish.

Enqueue takes no explicit destination locks (plain READ COMMITTED reads). The outbox `INSERT` still takes `FOR KEY SHARE` on the destination row through its foreign key; management locks destinations `FOR NO KEY UPDATE` (the PATCH `SELECT`, and the `UPDATE`s), which does not conflict with it, so destination edits neither stall alert evaluation nor wait for it. Keep it that way: a `FOR UPDATE` would block the enqueue, and a blocked enqueue hits the evaluator's `statement_timeout` (SQLSTATE 57014), which the isolating exception block does not catch. A concurrent enqueue can still commit after a disable/delete. **The worker rechecks live destination/rule/workspace/URL/reference eligibility before every attempt**, making an ineligible row terminal before sending. That recheck must also refuse rows whose destination is deleted or whose `url` is NULL (a scrubbed tombstone), and **the claim, holding the destination lock, must require the row's `destination_generation` to equal the destination's `enable_generation`** (plus enabled and not deleted). The lock is `FOR SHARE OF` the destination: `FOR KEY SHARE` does not conflict with management's `FOR NO KEY UPDATE` (nothing would serialize with a concurrent disable), and `FOR UPDATE` would block alert enqueue's foreign-key `FOR KEY SHARE`. Slice 2's status counts must count `waiting` rows only where the row generation equals the destination's: a late-committed stale row stays `waiting` until a claim terminalizes it, and must not inflate the count. If a claim locks both resources, it must lock **destination before outbox row**, matching management order. No lock or database connection may span HTTP.

Approval requires exact canonical URL equality with `GATEWAY_ALERT_WEBHOOK_URL_ALLOWLIST`, separately from egress policy. Signing references are `env:NAME` from a dedicated `GATEWAY_ALERT_WEBHOOK_SECRET_ENV_ALLOWLIST`, disjoint from provider and SMTP secrets. Management validates references without reading secret values or contacting receivers. Optional previous-reference overlap is explicit, at most 24 hours; deploy both variables to every worker before rotating, and clear both previous fields to end overlap. Delivery requires 32–4096-byte secrets, zeroized after use; management never resolves them. Arbitrary `file:` references are unsupported.

The `AFTER INSERT` trigger on `alert_deliveries` snapshots enabled, nondeleted destinations with plain READ COMMITTED reads, with no historical backfill. With no enabled destination it returns before reading the event projection. **Enable generations** close the disable-then-re-enable window. `enable_generation` on each destination starts at 0 and a trigger increments it on every change of `enabled`, in both directions (nobody can set or rewind it). The enqueue reads it in the same `SELECT` that filters on `enabled` and stores it in the immutable `destination_generation` of each outbox row. The outbox guard refuses an insert whose generation differs from the destination's current one, so a snapshot whose enqueue read generation N cannot be queued after a disable and re-enable. The re-enable trigger ends visible `waiting` rows of older generations. A row inserted under N whose transaction is still uncommitted across both changes is invisible to the trigger and commits `waiting`, but its generation no longer matches, so the claim's equality check keeps it from ever being sent.

Webhook enqueue is exception-isolated, and each destination has its own nested block: a failure (including missing grants during an explicit upgrade) or a destination that races a disable skips only that destination's snapshot, never the others' and never email or built-in alert evaluation. The fixed sanitized warning names the event id (a UUID) and nothing else: no URL, reference, payload or error text. There is no backfill for a skipped snapshot. Only installation rules notifying Platform Admins and the built-ins `scim_last_admin`, `partitions_missing`, `history_orphans` qualify. Workspace rules, personal incidents, every `key_expiring` and every `admission_ceiling` are excluded. Installation aggregate incidents may reflect personal activity only as totals. One SQL function, `alert_webhook_payload(delivery, event, transition)`, builds every envelope (the enqueue trigger and slice 2's test-send) and decides eligibility. The outbox guard requires `convert_from(payload,'UTF8')` to equal its output exactly, for test and event rows alike: text equality of the signed bytes, not jsonb equality, so duplicate keys, whitespace or key order differ and are refused. The delivery id in the body is the row id, and an event row is recomputed from the event's live state, so even a direct runtime `INSERT` cannot queue an excluded event, a forged transition or an arbitrary payload. The frozen UTF-8 `omg.alert.v1` envelope carries installation/delivery ids, `test:false` and an event projection containing id, transition, kind, severity, occurrence time and a fixed server-generated kind summary—never raw event summary/details/subject, workspace/key identifiers, identities, batch/request details or content. Only `cleared` resolutions notify; disabling and superseding are silent. The resolve decision uses the rule's current state, so a rule edited between fire and clear (for example no longer notifying Platform Admins, or disabled) can drop the `resolved` webhook although `fired` was queued; receivers must tolerate a `fired` without a `resolved`.

Outbox identity/payload are immutable, bytes are capped at 64 KiB (an exact-bytes envelope is far smaller; the cap is a second bound), attempts at five (one for future tests), and terminal states cannot reopen. There is no deletion or replay path. Runtime column grants and rollback-only privilege probes protect both tables. Run explicit `migrate`, `grants apply` and `grants verify`; `serve` never migrates. Exact schema-lineage readiness still applies: this does not promise healthy mixed-version readiness.

For fair dispatch, apply **0055_alert_delivery_buckets** and **0056_alert_delivery_bucket_index** explicitly before starting the new binary. The first migration sets a bucket with a `BEFORE INSERT` trigger, including inserts from older replicas, and backfills **pending rows only**; terminal history is untouched. Its `ALTER TABLE` holds an **ACCESS EXCLUSIVE** lock through the pending-row backfill until the migration transaction commits: the locked interval grows with the pending backlog and event-join work, so plan a maintenance window for large queues. Its 60-second lock-acquisition timeout is reset before the next migration. The second builds the partial `(bucket_id, created_at, id)` pending index **CONCURRENTLY**, outside a transaction. An interrupted invalid build is dropped concurrently and rebuilt on the next `migrate`, using the same recovery machinery as 0054. Old outbox-aware workers remain FIFO during rolling overlap; the existing outbox guard is unchanged. No additional runtime grant is needed: the role can insert and read buckets but cannot update `bucket_id`.

Two label-free gauges, `gateway_alert_delivery_pending_buckets` and `gateway_alert_delivery_oldest_pending_age_seconds`, refresh with the existing delivery counts. They cover all pending deliveries (including overdue work awaiting cleanup), report zero for an empty queue, and are exported only by the metrics lease holder when background leases are enabled. They contain no workspace identifiers.

### Signed delivery (slice 2)

The alert background loop (and `alerts evaluate --once`) dispatches at most 25 webhook steps per invocation, with a 60-second wall-clock budget. Short `SKIP LOCKED` claims lock destination `FOR SHARE` before the outbox row, serialize with management's `FOR NO KEY UPDATE`, require the current enable generation, and commit before HTTP. Each claim counts an attempt and grants an owner/token lease for 90 seconds (bounded by the row's 24-hour lifetime); completion requires that same unexpired lease. Claims leave at least 15 seconds before the lifetime cutoff. No connection, installation lock or admission lock spans HTTP. A destination disabled/deleted or an incident no longer eligible becomes terminal `ineligible`. URL/reference approval is rechecked before I/O; loss of approval is terminal `destination_policy`.

Any 2xx succeeds. Connection failures, timeouts, 408, 429 and 5xx retry after **1 minute, 5 minutes, 30 minutes and 2 hours**. `Retry-After` is ignored. There are at most five attempts within 24 hours; a retry scheduled at or beyond the lifetime cutoff exhausts immediately. Other statuses (including redirects), invalid signing material, TLS verification failures and egress-policy refusals are terminal. States are `waiting`, `leased`, `sent`, `failed`, `exhausted`, `ineligible`; dead letters remain inspectable, never replayable. Terminal worker audits are committed with their fenced update (`alert_webhook.failed` / `.exhausted`). A crash after receiver acceptance can duplicate a delivery; this is bounded at-least-once, not guaranteed eventual delivery.

Every request uses checked egress resolution (`purpose=alert_webhook`), including IP literals. HTTPS is required except development-only loopback HTTP (including a loopback-only post-DNS address filter for `localhost`). Private destinations still require `GATEWAY_EGRESS_PRIVATE_ALLOW`; URL approval never overrides it. Connect deadline is 5 seconds, whole request 10 seconds; redirects, ambient proxies and implicit retries are disabled. Response bodies are never consumed.

Payload bytes are frozen at enqueue. Headers are `Content-Type: application/json`, `X-OMG-Delivery: <stable delivery UUID>` and `X-OMG-Signature: t=<unix seconds>,v1=<lowercase hex>`. HMAC-SHA256 input is exactly `<t>.<raw body>`; timestamps/signatures are fresh per attempt. While the saved previous-reference overlap is active, another `,v1=<hex>` is appended. Receivers must verify either signature in constant time, require timestamps within **±300 seconds**, check the header delivery UUID equals the signed body's `delivery_id`, and durably deduplicate by that id. Timestamp checks alone do not stop replay inside the window. There are no sequence numbers, heartbeats or ordering guarantees.

`POST /api/v1/platform/alerts/webhooks/{id}/test` accepts no body or `{}` only and queues a single attempt to an enabled saved destination. The fixed envelope is `test:true,event:null`, built by the same SQL constructor. It returns `{id,state:"waiting"}`; poll the delivery-status route. Transactional audit-log limits shared across replicas are 2/user/minute, 2/destination/minute, 20/installation/hour; failed deliveries count too, including token callers. No URL, headers, templates or event id can be submitted. `GET /api/v1/platform/alerts/webhooks/{id}/deliveries` returns state counts and at most 50 newest metadata rows, without payloads or incident ids; waiting counts exclude stale enable generations. Read authority and URL/reference redaction match saved destination reads.

Fixed-label metrics are `gateway_alert_webhook_attempts_total{outcome}`, `gateway_alert_webhook_deliveries{state}` (active rows and terminal outcomes completed in the last 24 hours), and label-free `gateway_alert_webhook_oldest_waiting_seconds`. The waiting gauge is the queued count. Only the metrics lease holder exports installation gauges. Operational failure notifications must use an independent channel, never webhook-about-webhook recursion. No new migration or privilege is needed beyond 0057.

## Privacy

Incidents store a server-generated summary and typed facts (layer, period, amounts as strings, counts, window). They never contain prompt or response data, key names or ids, owner identities or request details. Platform rules never evaluate personal workspaces one by one (installation totals include them, as reports already do), with one exception: an **admission ceiling** incident is about one scope's load, not its spending or content. It names a Team or Project (its workspace reference and name) and says whether the hot scope is the workspace or one of its API keys (never which key). A personal workspace is only ever "a personal workspace" (no id, name or owner, no key). The workspace reference is shown to **Platform Admins only**: Auditors see the same incident without it, and these rules cannot email listed addresses or workspace admins (Platform Admins only). Email bodies, recipients and relay replies are never logged. Outbox fingerprints are **pseudonymous personal data, not anonymous data**: they are delivery-scoped but guessable for known addresses. They must never be exposed in HTTP, metrics, logs or Debug output; apply the same access/retention protections as alert history.

## Upgrade from installation budget alerts (0026)

Migration `0026_remove_installation_limits.sql` removed the installation budget, so rules that watched the `installation` budget layer were converted, idempotently and with an audit event (`alert_rule.installation_layer_removed`) per rule:

- A rule that watched only the installation layer became an installation spend rule in place (same id, name, thresholds, recipients and history) for its shortest former budget period, with that budget's amount as the reference. Each further period became a new spend rule named "<rule> (installation <period> spend)".
- A rule that also watched other layers keeps them; its installation part became new spend rules as above.
- A rule that watched only the installation layer while no installation budget existed could never fire; it was soft-deleted (history kept).
- Open installation-budget incidents continue when the same rule keeps watching the same period; others were resolved as `superseded`, without a "resolved" email.

## Storage and grants

`alert_rules` (soft-deleted; scope, workspace and kind fixed at creation; `spend_period`/`spend_amount_microusd` for installation spend rules, 0026; `ceiling_requests_per_second`/`ceiling_lock_wait_ms` for admission ceiling rules, 0036), `alert_events` (incidents; resolve once; `api_key_id`/`key_expires_at`/`threshold_days`, 0049, for key-expiry reminders only, immutable and permanently deduplicated by that triple, never granted an UPDATE), `alert_deliveries` (counts, retry aggregates and a category per transition; the outcome CHECK gained `host_not_allowed`, 0049, closing a pre-existing gap where recording that failure rolled back), `alert_recipient_outbox` (0050; immutable delivery/fingerprint key, recipient outcome, bounded attempts, due time and fenced lease; no plaintext addresses; used by both rule-based alerts and key-expiry reminders) and `alert_reads` (insert-only read marks). `admission_lock_waits` (0036) holds per-minute, per-scope lock-wait counts: the runtime adds to them and maintenance deletes rows older than an hour. The runtime role has no DELETE or TRUNCATE on any of them; see `deploy/staging/runtime-grants.sql` and the probes in `verify-privileges.sql`. Outbox INSERT grants cover only the immutable key and optional internal-user eligibility link; UPDATE grants cover only attempt/outcome/lease fields. No outbox DELETE/TRUNCATE is granted. Low-cardinality metrics `gateway_alert_email_attempts_total{outcome}` and `gateway_alert_email_deliveries{state}` report attempts and recent retrying/failed/exhausted deliveries without recipient labels. Pending deliveries use a 24-hour creation window; terminal failures/exhaustion use a 24-hour completion window, including expired-delivery cleanup. Cleanup that never sent mail does not increment attempt counters. The example `GatewayAlertEmailPersistentFailure` Prometheus rule uses an independent operational channel: do not route it into a new gateway email-about-email incident. Migration 0011 also adds the `governance_reservations(workspace_id, admitted_at)` index used by budget alerts.
