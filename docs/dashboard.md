# Workspace dashboard

The React application in `apps/web` uses the browser-session management API described in [management-api.md](management-api.md). It makes relative, same-origin requests; the Vite proxy is for local development only. No API key, provider secret, or development-login fallback authorizes the dashboard.

## Sign in and choose a scope

For passwordless local exploration with fixed Platform Admin/Organization Admin/Team Admin/Member personas, use the isolated [local demo](local-demo.md). It still exercises normal OIDC/session authentication; it is not a production fallback.

The dashboard checks `/api/v1/me`. A 401 displays the OIDC sign-in page; when OIDC is disabled, it explains that an operator must configure authentication. Signing out posts to the logout endpoint with the readable `omg_csrf` cookie in `X-CSRF-Token`. The browser supplies Origin and session cookies.

The dashboard uses locally vendored Bitop UI components and its neutral theme. Its collapsible sidebar, Workspace/Admin mode switch, permission-scoped navigation, breadcrumbs, header jump search, and sidebar account menu follow the Open RAG System layout design, without its API or business logic. See [Bitop provenance and refresh instructions](bitop-ui.md).

The top-right **Search or jump to…** button (⌘K / Ctrl+K) searches accessible pages, organizations, teams, and the user's own personal workspaces. Arrow keys and Enter select results; Escape closes it. Search is local to the current session inventory, not a search of users, secrets, prompts, or activity. **Refresh access** is available in search and the sidebar account menu. There is no full-width bottom footer.

For platform admins, the **Platform** sidebar contains **Organizations**, **Teams**, **Projects**, and **Users**, plus platform-level model access and global Models/Oversight configuration. There is no separate Organization section for that role; organization membership/invitation management opens from organization details. Global Teams/Projects directories have organization filters, and creation explicitly selects the parent organization. Org admins see assigned models and local governance, not provider/deployment/routing setup. Team/project admins retain scoped navigation. See [platform administration](platform-administration.md).

The sidebar context selector **only switches existing scopes**. Platform admins always have a **Platform** entry that clears organization/workspace selections. In **Admin** mode, organizations appear only for their administrators and teams/projects only for their shared administrators; personal workspaces are not admin contexts. In **Workspace** mode, ordinary accessible organizations and the signed-in user's personal/shared workspaces remain available. There are no creation actions inside the selector. Create organizations from **Admin → Organizations**, teams from **Admin → Teams**, and add people through the scoped **Members** pages. When no organization exists, platform operators can still open Organizations from Admin or the welcome page. Personal-workspace creation, when needed, lives on the workspace overview/empty state.

The hierarchy is **Platform → Organizations → Teams/Projects → Members**. A platform is this gateway installation, not a new selectable multi-platform tenant entity. Teams and projects are sibling shared workspace kinds (`team|project`); personal workspaces are a separate private branch. Users are global identities and memberships connect them to organizations/teams. Upward navigation drops stale lower-level URL selections.

Choose an organization and workspace in the sidebar workspace switcher. The sidebar account menu opens Profile, Accept invitation, Refresh access, and Sign out, and shows the current access level. Admin mode groups links by permission; platform admins use the flat Platform directory navigation above. Team/project administrators enter their managed workspace directly, with a Shared workspace sidebar rather than an Organization section. Their admin selector supports managed workspaces across organizations without offering organization administration. Ordinary members do not receive an Admin portal. Admin mode exposes scoped administration; Workspace mode exposes activity, keys, costs, and governance. Collapse state remains in memory across navigation; account or permission changes still destroy scoped dialogs and partition query caches; logout clears the client cache. Personal workspaces are private and have no team-member or service-account controls. Team workspaces expose administration according to the effective role returned by the gateway. Platform operators can create organizations. Organization administrators with actual organization membership can create team workspaces.

An operator’s `operator` role does not prove organization membership. The UI uses the authorized organization-members endpoint to establish whether that operator can create a workspace or issue a user-bound key. All permission checks in the UI are presentation only; the gateway remains authoritative.

## Available screens

- **Organizations:** paginated accessible organizations, platform-operator creation, admin renaming, and direct Teams/Members entry points.
- **Teams / Projects:** platform admins have cross-organization directories and organization filters; scoped administrators see their authorized shared workspaces. Supports organization-admin creation, team-admin renaming and member management. No personal workspace enumeration. Operators still need active organization membership to create a team they will own.
- **Users:** platform-operator-only read-only global identity directory. No personal workspace, key, or usage metadata. Identity provisioning remains with SSO/trusted operators; invitations and scoped Members pages handle memberships/roles. No global user deletion, privilege-grant, or impersonation controls are introduced.

- **Overview:** last-30-day usage and paginated execution history. Members see their own-key activity; workspace administrators see workspace activity. Unknown token usage is shown as unknown, not estimated usage or cost. No prompts or generated responses are displayed.
- **API keys:** create with 1–365-day expiry, reveal once, copy, revoke, and rotate. Administrators may revoke another person’s key but cannot rotate it. Service-account keys are available to team-workspace administrators. Human-bound team keys require explicit active team membership even for inherited organization administrators; the UI resolves membership before offering creation or rotation.
- **Service accounts:** create, disable, and re-enable team identities. Disabling revokes their keys; re-enabling does not restore revoked keys.
- **Team members:** add an existing active organization member, change roles, or disable membership. A team admin who cannot browse organization membership can supply an existing member’s UUID. Owner-only role operations are not offered to admins.
- **Model access:** list workspace grants; organization administrators can add and remove grants.
- **Organization members and invitations:** manage roles/status; create, list, and revoke invitations. Disabling membership revokes user keys in the affected scope. Owner protections are enforced by the gateway.
- **Platform models, provider connections, deployments:** platform-operator-only setup, available without organization selection. Org admins instead see assigned models and delegate only those entitlements. An organization-wide personal-access toggle grants/revokes assigned models across existing/future personal workspaces without revealing private metadata. OpenAI and Anthropic forms accept allowlisted environment variable *names*, never secret values; Bedrock uses `aws:default` workload identity and a region. Custom provider endpoints are not supported by the current handlers.
- **Organization limits:** pill tabs separate **Effective**, **Additional**, and **Platform** values instead of stacking them. Effective organization caps show the lower value for each field; platform maximums stay read-only. The edit dialog changes only additional limits. Blank never removes a platform maximum. This organization-only screen does not ask the user to select a workspace.
- **Governance:** pill tabs switch between **Workspace**, **Organization** (organization administrators only), and **API keys**. Workspace opens by default; its **Effective**, **Local limits**, and **Inherited** detail tabs show one panel at a time. Platform-assigned organization ceilings are read-only to org admins and separate from editable local organization/workspace/key policies. Shared workspace admins may tighten their own scoped policies. Unset child fields share the parent's remaining allowance; explicit child caps are additional restrictions, never reserved allocations. Members can read workspace and their visible key policies, not organization policies. Blank fields remove that scope’s limit only; inherited limits still apply. Enter budgets in US dollars, such as `50.00`. Up to six decimal places are supported and preserved using exact integer conversion; micro-USD remains an internal API/storage unit, never a required user calculation. Limits count upstream attempts, including fallbacks, and use fixed UTC minutes and UTC calendar months. Pricing bounds and explicit output limits are required; the full hard upstream input ceiling is reserved rather than a guessed prompt-token estimate. Unknown charges retain reservations; older unpriced usage cannot be retroactively priced and can prevent budget onboarding until the accounting window rolls over. Rotated keys share policy and usage lineage with their predecessors; separately created keys remain separate scopes. Organization policy can govern private workspaces without listing them.
- **Costs:** current-UTC-month known configured-rate estimates, held reservations, unknown-cost attempts, and total upstream attempts (not unique client requests). Known and held figures are separate; unknown is never zero. Members see only activity from their own human keys. History is paginated. CSV export downloads one explicit page (1–1,000 rows, offsets 0–100,000, client cap 10 MiB), never an automatic full-history export or stable snapshot. Download subsequent offsets manually. A platform operator can reconcile visible unresolved terminal records with pinned prices using authoritative token counts and a short evidence reference; this never bypasses personal-workspace privacy. No prompt, secret, or invoice uploads.
- **Routing:** platform-admin model policy controls (priority/weighted strategy, 1–3 attempts, ambiguous-failover opt-in, passive-failure threshold, cooldown, required residency) and deployment priority/weight. Required residency restricts the primary as well as fallbacks; fallback labels must still be identical and explicit. Only operators can change deployment residency assertions. Organization administrators do not configure routes. Labels are not verified provider geography. Missing health observations show **Unknown**, not healthy. Ambiguous failover can duplicate provider charges; no failover occurs after a stream is returned.
- **Pricing:** paginated immutable deployment price versions; platform operators read and publish; organizations consume assigned models rather than managing price versions. Enter rates in US dollars per million tokens (up to six decimal places); the full input-token ceiling is a hard provider bound, not an input estimate. Existing executions keep their pinned version. Neither costs nor prices claim invoice accuracy.
- **Audit history:** paginated administrative events, without credentials or arbitrary metadata. Personal-workspace events retain the gateway’s owner-only privacy boundary.
- **Profile:** signed-in identity and effective organization/workspace access. Identity edits belong to the identity provider.

## One-time tokens and invitations

Key and invitation creation responses bypass TanStack Query’s query and mutation caches. Tokens exist only in temporary dialog state. Closing the dialog, changing context, or signing out clears that state. Tokens are not written to local storage, session storage, URLs, or application logs. Read caches are partitioned by signed-in identity and effective access so cached administrator rows are not reused after an identity or role change. Copying a token deliberately places it on the system clipboard; clear the clipboard after saving it securely.

Invitation delivery is out of band; there is no email sender. The recipient signs in with the matching verified email, opens **Accept invitation**, and pastes the token into the form. There is no invitation-token query-string flow. Acceptance does not implicitly promote or reactivate existing memberships.

## Checks and limits

From the repository root:

```sh
npm run typecheck:web
npm run test:web
npm run build:web
```

Tests cover request/CSRF handling, bounded CSV reads, exact BigInt monetary formatting, policy/price validation, routing payload preservation, permission rules, and server-rendered Bitop/governance output. These are not browser end-to-end tests. Before the Bitop/governance refresh, a separate manual browser smoke used a signed loopback OIDC issuer and an isolated real backend/database to exercise login, organization/team creation, model/personal-access policy, key creation/rotation/revocation, service-account creation, CSRF rejection, and logout. Desktop/mobile screenshots and axe checks passed on the sampled pages. Clipboard fallback, every form permutation and a real enterprise IdP remain separate acceptance checks. That earlier smoke does not verify the new shell, forms, or governance APIs; those require a fresh browser acceptance run. See [verification](verification.md).

Collection tables paginate. Selection controls load at most 20,000 records before reporting a limit error rather than silently presenting incomplete choices. The application provides configured budget enforcement controls and estimated costs, not invoicing, payment collection, profile editing, automatic invitation delivery, unsupported resource-deletion endpoints, or plaintext provider credential entry. API/backend contracts and authorization remain authoritative; unavailable endpoints or denied operations show errors rather than synthesized metrics. Production remains static Vite assets served by Rust, without Next.js or a production Node.js server.
